#### A consumer's SPEC grows forever with nothing to evict or measure it — ship SPEC-maintenance rules derived from the self-authoring gate [shipped-spec-maintenance-rules]
Captured by you 2026-08-12 at /plan. Your question, and you drew the host/target line yourself: might SPEC benefit from some of our self-authoring rules — not for this project, but shipped, so that when the method is deployed against a real external project it carries built-in SPEC-maintenance rules derived from them. The analysis below is Claude's.
**The structural analogy is real and holds.** `resources/self-authoring-rules.md` exists because the always-loaded rule corpus grew monotonically — every session could add, nothing ever removed, and nobody counted until it was at ~218 instructions. SPEC has the identical growth shape: every user-facing change adds a paragraph under the sync gate, nothing evicts, and no measure exists. It is read at every planning session today and, once [spec-is-write-only-during-builds] ships, at every build run too — so its cost is paid more often than the rule corpus's, not less. And a consumer is worse off than this project: their SPEC grows as their app grows, and nothing will ever tell them.
**Three of the gate's four parts transfer; one does not, and the difference matters.**
- **Admission transfers.** "Does this sentence belong in SPEC, or downstream?" is precisely the question [spec-carries-implementation-detail] found unanswered.
- **The rationale split transfers.** The gate's rule that reasoning leaves the operative statement and lives in the record that decided it applies directly: SPEC carries a lot of why-we-chose-this prose that is LOG material.
- **Staleness transfers.** A SPEC sentence describing a retired mechanism is the same defect as a live rule naming a retired term, which the board's REPEALED signal already detects in shape.
- **The ceiling does NOT transfer, and shipping it would be a mistake.** The 150–200 figure exists because a model follows only so many *instructions* reliably. More decisively, **SPEC has a floor the rule corpus does not have**: it must describe the product as it actually is, so it cannot be compressed past that without becoming false. A rule can always be evicted; a true sentence about a live feature cannot.
**To settle at processing.** Where the shipped rules live — most likely `docs-b/plan.md`'s SPEC ground rule rather than a new always-loaded section, since that is where a SPEC edit is decided and it is fetched rather than always-loaded. **Weigh against the admission gate itself** — this proposes adding rules, so it must pass the gate it is derived from, and the cheapest shape is plausibly one clause on the existing SPEC ground rule rather than a new document.

#### A session can span two calendar days, and nothing says whether its records carry the start date, the end date, or both [session-date-start-end-or-both]

**What the method says today, and where it stops.** `done.md` states that a LOG entry's filename date prefix is "the **session** date, not the commit date — write it from the current date at close", and that its only job is the name sort. That settles the filename for a one-day session and says nothing about a session that spans two, which is not an exotic case: it is what happens whenever someone stops for the night, or hits a usage limit, and resumes.
**The datestamps inside the records are the larger half, and they are unaddressed entirely.** Queue items and LOG prose carry dates written into the text — "processed 2026-08-12", "cleared 2026-08-12", "captured by you 2026-08-12". Those are read later to judge staleness and to reconstruct when a decision was made. In this session Claude first stamped everything with the start date, then, on discovering the calendar had moved, restamped this session's writes to the close date for consistency — a defensible choice made on the spot with no rule behind it, and the next session facing it may choose differently.
**Three candidate conventions, none obviously right.**
```
start date only  simple; matches how a person names the session in their head;
                 goes stale the moment a session runs long
end date only    what the shipped filename rule already implies; consistent with
                 the commit landing at the close; loses when the work began
both             honest and self-documenting ("2026-08-11 → 2026-08-12"); costs a
                 longer filename and a wordier stamp, and most sessions gain
                 nothing from it
```
**To settle at processing.** Whether one convention covers the filename and the in-text stamps, or whether they can differ — the filename's stated job is only the name sort, so the end date suffices there, while an in-text stamp is read for meaning and may want both. And whether the close should simply *say* when it spans days, so the LOG entry records the span in prose without any format change, which is the cheapest option and may be the whole answer.

#### The wind-down's best-effort caveat names something Claude cannot check, so a session substitutes a proxy [wind-down-caveat-uses-an-unverifiable-limit]
Captured by you 2026-08-12 at the /done wind-down. Your correction, in your own words: session length is not relevant — whether compaction occurred is; and you asked whether that is visible to Claude. The answer and the diagnosis below are Claude's.
**The instance.** Claude introduced the wind-down with "this has been a long session, so I can only re-read what's still in view". Session length is a proxy Claude *can* observe, standing in for the variable that actually determines the result. `plan.md` and `done.md` both word the caveat correctly — the step re-reads "whatever discussion is still in view", and a surfaced-nothing result is not a guarantee — so the document was right and the session degraded it into something measurable-sounding and wrong.
**The answer to your question: no, not reliably.** There is no signal announcing that compaction happened. It is sometimes *inferable* from oddities — a summary block sitting where the earlier exchange used to be, or a session-start block arriving mid-conversation, which did occur in this session — but those are inferences from anomalies, not a flag, and a compaction that lands cleanly leaves nothing to notice. The failure is silent in exactly the way a truncated file read is: what remains looks complete from the inside, which is the same reasoning behind the page-the-whole-queue rule.
**Why the substitution is worth catching rather than shrugging at.** A caveat's job is to tell the user how much to trust the result. "This session was long" invites them to discount the result by a factor they can reason about, and the factor is fictional. "I cannot tell whether anything has dropped out of view" is less satisfying and is the truth. The shipped wording already says the honest thing; the defect is that nothing stops a session improving on it.
**To settle at processing, and the second half may have no answer.** First, whether the step should carry the caveat's *wording* rather than its intent — a sentence to say, not a thing to convey — since paraphrase is where this went wrong. Second, whether compaction is detectable at all from inside a session by any reliable means; if it is, the caveat could become conditional and honest at the same time, and if it is not, that should be written down so the question stops being reopened. That second half is an external fact and needs checking rather than reasoning.

So the fix is probably to lead with the relevance argument and drop the count as the binding limit, not to restate a bigger number — but that rewrites the opening of the document that governs every rule this project writes, which is not a mid-build edit.
**This is the second-order case [no-link-from-research-to-items-scoped-on-it] predicted**, and it is worth noting as its first confirmation: the superseded figure had propagated further than the four queue items that pass found, into the gate document itself, and nothing connected them.

#### CONTRADICTED reads a multi-item run's mixed dispositions as a contradiction, and every large run will trip it [contradicted-flags-mixed-disposition-runs]
Filed 2026-08-12 by Claude, immediately after repairing the disposition format made the signal readable enough to expose this. The flaw is the detector's; the format error that hid it was Claude's.
**What it does now.** `_log_dispositions` maps a commit hash to a *set* of disposition kinds found across all LOG entries naming that hash. CONTRADICTED fires where that set contains `not needed` and the always-loaded count rose. On a sixteen-item run every entry carries the same commit hash, so one item legitimately recording `not needed` — a script fix, a test-fixture repair, a hook change — puts `not needed` in the set for the whole commit, while a *different* item in the same commit authored a rule and correctly recorded `run` with the count rising because of it. The signal reports a contradiction between two artifacts that do not in fact disagree.
**Why it surfaced only now.** Every disposition in the recent entries was written as `**Rule gate:**` in bold, and the detector matches `^Rule gate:` at line start, so none of them was visible at all. Unbolding them made BORN correct and simultaneously gave CONTRADICTED enough input to misfire: it went from one commit flagged to three (`e5d169b` +5, `0ae69d6` +1, `b51d205` +2). All three are multi-item runs.
**This is not an argument that the check is worthless.** Its stated job — catching a commit whose LOG claims the gate was not needed while the corpus grew — is real, and on a single-item commit it does exactly that with no judgment required. The defect is that a commit is the wrong unit once a run ships sixteen items under one hash.
**To settle at processing.** The obvious route is to key the check on the LOG *entry* rather than the commit: flag an entry that says `not needed` where that entry's own item added rule statements. That needs a per-entry attribution of the count delta, which the current `git show <rev>:<path>` diff cannot give — the delta is per commit by construction. Weigh against that a cheaper reading: a commit is flagged only when **every** disposition naming it says `not needed`, which is checkable today with the data already collected and which would silence all three of these while still catching the single-item case the check was built for. Weigh also doing nothing and documenting the limit, since the signal's own message already says it is "a contradiction between two artifacts, not proof of a bad rule".
**One thing to preserve whichever way it goes.** The existing text is careful to say the check cannot tell whether a gate recorded as *run* ran honestly. Any rework must keep that limit stated rather than quietly implying broader coverage — a check that over-claims is the failure this project fights hardest.
**Files (rough):** `resources/rule_signals.py` (`signal_contradicted`, and possibly `_log_dispositions`'s return shape). Host-only. Relates to [rule-gate-runs-at-close-not-at-authoring] (which moved the disposition to authoring time) and [board-header-counts-inert-signals] (the other board-reporting item filed this session).
