**Design progress banked (user + Claude, 2026-08-01) — continue next session, still undesigned:**
- **Drop staleness entirely (user).** A session should always be *closed* properly, never left to go "stale" — so detecting staleness by mtime is the wrong model. Design so an abandoned-live session doesn't happen, rather than detecting it after the fact. (Kills proposal #1.)
- **The session_start awareness note (#2) stays** — fine as-is.
- **New core direction — live/canonical queue, merge-at-close (user's idea, better than detect-and-warn).** Each session edits its own *live* copy of the queue; at close, its changes merge into the *canonical* version. **Use git if that makes it easier to build (user approved).** The merge is automatic and clean when two sessions touched *different* items/sections; a conflict arises only when both touched the *same* region. Claude resolves the merge **silently**, surfacing to the user **only** when a conflict genuinely can't be resolved safely — the user never sees raw conflict markers. Reframes the problem from *preventing* concurrent writes to *letting them diverge and merging at the end*. Real design work: (a) structure the queue so sessions rarely collide; (b) make Claude's silent conflict-resolution trustworthy.
- **`.git/index.lock` retry/backoff (#4) — minor robustness only.** Two simultaneous commits make git's brief lock file error one of them; retry-after-a-moment avoids it. A small nicety, not core.

Desktop shares the one main tree, so matching that isolation means deliberately branching each desktop session, or a separate-file fallback. Fork to resolve: branch *every* session, or isolate only where sessions overlap?
- **Scope distinction to resolve, not conflate (user, 2026-08-01):** full-project branching vs queue-only branching. The contention is fundamentally about QUEUE.md, so branching *just the queue* may suffice; full-project branching (what the remote worktree already does) is the heavier hammer. **The reframe: isolation is the fix; merging is the price paid for it.** The live corruption happened in **one folder**, with two sessions sharing a single working tree. **Fork 1 — RESOLVED: branch every session.** "Isolate only where sessions overlap" requires knowing another session is live. #### Build the project glossary: GLOSSARY.md scaffolded at /setup, define-and-record vocabulary discipline, and the mirroring-correction rule [project-glossary-and-term-discipline]
Captured by you 2026-08-08; processed the same session. Three threads, one design — the glossary is the mechanism the other two need.
**The core mechanism — the glossary is Claude's check for what the user already knows.** When a general term is used, it gets **defined at the point of use** and then **added to the glossary**. Claude decides *whether* a term needs explaining by checking whether it's in the glossary: membership = "already explained, use freely"; absence = "define it now, then record it." **The two-sided guarantee, in the words from the launch announcement — kept as the feature's plainest statement: Claude never re-explains what you know, and never assumes you know what it hasn't told you.** Both halves matter: the first is the anti-nag direction, the second the anti-stranding direction, and the glossary is the one record that delivers both. The user's framing of why this matters: before, Claude had no way of knowing what the user might know; now it at least knows what has been explained to them before. This extends the vocabulary rule's existing test ("would the user have met this word in something they actually read?") rather than replacing it — an explained term is one they've met, and the glossary is the record that makes that checkable across sessions instead of held in session memory.
**The two-axis distinction the rule gains:** **project-specific terms** (the project's own naming set — canonical, always usable, and the glossary is the authority on which name is canonical) versus **general terms** (jargon from the wider world, governed by define-and-record above). Named this way at the user's correction: "in-project / out-of-project" was the first cut, and it's wrong because general terms are still technically *in* the project once used — the axis is where a term comes from, not where it appears. Term drift happens in both the AI and the human, and words don't get caught at their many statement sites — so the glossary is both the place to check what's canonical and the place a rename lands, giving the ripple-grep discipline a known index of names.
**How entries work (the user's design):** an entry carries the explanation **as it was last given to the user** — mirroring what they might actually remember, not a textbook definition. Each re-explanation may be worded however fits the moment, but **after explaining a term, Claude updates its glossary entry**, developing the definition rather than necessarily replacing it. Entries stay terse, as in a normal glossary. Update-after-explaining is also the staleness answer: the glossary stays current because explaining is the trigger.
**The mirroring-correction rule.** Models mirror the human, so a not-quite-right technical term gets absorbed and repeated. Two cases: where the user *chooses* a nonstandard term — especially with reasoning — it goes in the glossary with that reasoning as a deliberate project-specific term, and is then simply correct. Where they've used the wrong word for a real technical thing, silently adopting it leaves them exposed in professional settings — so Claude names the standard term **once, plainly, then just uses it**: no correction ritual, no repeats. The glossary entry is what stops re-correction.
**The four design calls, settled at processing (user approved all four):**
1. **Home:** its own file, `GLOSSARY.md`, beside SPEC.md and QUEUE.md — and **committed**, because unlike the FAQ it is the user's own record (what has been explained to *them*), not a copy of the plugin's help.
2. **Ships to consumers now**, scaffolded by /setup. The mechanic stands alone without [learning-mode-fork-at-setup]; consumers are its point. Existing projects get it via the migration path when [setup-as-migration-home] lands; until then a missing GLOSSARY.md simply means the check treats every term as unexplained, which is safe.
3. **GLOSSARY.md joins the always-editable set** (queue, log, session working file) in `pre_tool_use.py`, and the planning-session quiet-list in `plan.md`'s ground rules — define-and-record fires unpredictably in any session type, and a build's agreed file list can't anticipate it. **This is a hook-enforced-set change, so the build greps every statement site of the always-editable set** (plugin-behaviour.md's Scope section, plan.md's quiet-list, SPEC.md's scope-lock description, FAQ entries describing the lock) and every hit joins the file list or carries a leave-alone reason.

**Tension carried from the record, so the build doesn't rebuild a retired thing:** the vocabulary rule deliberately retired an enumerated banned-word list because a list is only complete for the past. The glossary is not that list reborn — it is positive content (canonical names and explained terms), never an enumeration of forbidden words. The test stays the rule; the glossary is its memory.

#### A test that builds its own fixture can assert the assumption instead of the world — and it looks exactly like coverage [self-built-fixtures-assert-the-assumption]
