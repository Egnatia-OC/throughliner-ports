**Retire the spec-edit batch type — SPEC becomes a normal file, edited in /plan or via a /next ask** **[retire-spec-edit-batch-type]**

Spec-edit batches have become a time sink across all projects — often a whole batch to change one line. The original decision ([spec-edit-batch-type], f4fba84) made SPEC a normal doc but routed every SPEC change through its own /next-executed batch, to kill a confusing "read-only during builds" special case and a redundant lock. That reasoning held, but it never weighed the ceremony cost, which is now the dominant pain.

This retires the spec-edit batch type entirely. SPEC becomes a normal file any batch can list. Three paths replace the batch: a small SPEC change decided in /plan is edited in that same /plan session; a build that discovers it needs a SPEC change asks the user at /next, adds SPEC.md to its file list, and edits it inline; a large SPEC rework is just a normal build batch that lists SPEC.md. The Spec-edit subheading, its routing, and the guard against a combined Build+Spec batch ([spec-edit-build-guard]) all go, along with the lint that backed the guard.

The load-bearing piece is drift prevention, because last time SPEC was editable in /plan it got left behind. Two spec-sync checks at the session close points carry it. A new check at the /plan close (done-plan.md): if a decision this session changed what SPEC says and SPEC wasn't updated, the close stops and SPEC is updated before committing. The existing /done-build spec-drift check is hardened from "file a capture for later" to a stop-the-close gate: on drift, SPEC is updated in the same session and same commit, not deferred. Both sit at commit boundaries, so a session can never *close* with SPEC behind — which is what "left behind" means.

This complies with spec-driven development, and aligns better with it than the batch did (research: resources/research/spec-driven-development-edit-workflow.md). SDD's core contract is "any change that alters behaviour cites or updates the spec in the same commit" — exactly what the two close-out checks implement. SDD does not require a spec change to be its own gated step; flexible SDD edits the spec inline during work. The one-line-batch friction is itself a recognised weakness in SDD tooling.

Enforcement constraint, governing every rule authored here: both checks are behavioural, not mechanical — "did this change make a SPEC sentence wrong?" is a semantic judgment no hook can make, and no lint backstop is possible. Their sole enforcement is Opus 4.8 actually running them, which on 4.8 holds only when the rule carries its rationale (resources/research/opus-4-8-verbosity-steering.md, model-instruction-compliance.md; resources/4-8-authoring-heuristic.md). So every rule and check authored in this batch ships with its why — why it exists, what drift it prevents, the SDD atomicity it protects. The rationale is the enforcement.

SPEC changes stay user-approved throughout: in /plan the user is present; at /next the scope-lock forces the ask before the build proceeds. Two adjacent questions are handed off, not solved here: SPEC's structure ([spec-sot-rethink]) and how an unattended build handles a needed SPEC change (recorded as a design concern on [cruise-control] — it halts the run, like an open red flag).

**Cruise control skill — design session (the consumer-facing end-goal)** **[cruise-control]**
Status: Unparked 2026-06-23 — blocker met. The /goal-formalization arc ([close-shipped-slug-crosscheck] + [formalize-goal-session]) shipped, and goal sessions have been run for over a week, proving the multi-batch close mechanics before the human comes out of the loop. Deployment prerequisite: [plan-dependency-tracing-gap] — dependency tracing must be solid before the human comes out of the loop (this is concern #2's foundation; the design session can proceed now, the unattended run waits on it).

Cruise control is the consumer-facing end-goal: a skill that runs build→commit→build→commit through a batch (or multiple batches) unattended, stopping only when it hits something requiring user input. The /goal-formalization arc was step 1 — it built the multi-batch close mechanics (shipped-slug cross-check, multi-thread LOG) that cruise control inherits, while a human still bookends the run; cruise control then adds the autonomy, the gate, and the unskippable judgment on top. Key design concerns: (1) wording that doesn't pressure Claude to push through uncertainty — Resolved 2026-06-25: a blocking uncertainty is one whose resolution is a decision the user owns (a design choice, a materially-ambiguous requirement, a product-truth question) → halt-and-record; technical "how" uncertainty Claude resolves as normal building → proceed. The test is categorical (whose call is this?), not a confidence threshold (how sure am I?), because LLMs calibrate confidence poorly but identify decision-ownership reliably — so the gate keys on the category, which sidesteps the field's poor-calibration caveat. Ambiguous category (mine or theirs?) defaults to the user's, the safe side, mirroring capture routing's ambiguous→park default. Reuses the existing plugin-behaviour rule "uncertain about a choice the user owns → ask", with "ask" → "halt-and-record" under autonomy. (2) dependency management when Claude decides when to wrap a batch, (3) /done judgment steps can't get skipped for speed; (4) the red-flags gate — an open red flag in the active scope blocks the unattended run, only resolved or accepted flags let it proceed, and a user who leaves a flag open stays on hand to approve each step (the gate is a hook reading the three flag states defined by [red-flags-screen-rule]); (5) the handoff-claim-marking format — whether a handoff / context prompt marks which claims are user-vouched versus Claude-authored, or whether the standing "Claude-authored handoff content is unverified until the user confirms it" rule (already in CLAUDE.md) suffices (folded in from the /goal fork, item 9, 2026-06-16); (6) a build that discovers it needs a SPEC change is an owner decision under autonomy — it halts the unattended run, like an open red flag, since a product-truth change can't be self-approved (folded in from [retire-spec-edit-batch-type], 2026-06-25); (7) batch granularity under autonomy — how small a change still earns its own batch and its own LOG entry. The reframe from the 2026-06-25 /plan: the costly part of a tiny build is the full cycle (plan → /next → /done → commit), not the LOG entry, which is cheap; goal sessions already prove several granular per-batch LOG entries can share one session and one commit. Cruise control removes the per-cycle attention cost (Claude runs them unattended) but hands Claude the wrap-decision — when to close one batch and open the next, and how small a change still gets its own LOG entry. The principle to preserve: keep each change's why granular (cheap, and the multi-year / two-minds retrieval value the user flagged) without forcing a tiny unrelated change to wait to be bundled, and without blurring several unrelated whys into one entry. Same judgment as concern (2), on the granularity axis. Folded in from the 2026-06-25 /plan granularity discussion; (8) the run's response taxonomy — what cruise control does when it hits something it can't just build (prior-art research filed: resources/research/autonomous-build-loop-design.md). Three categories. **Route-and-continue**, the common case: anything an attended session would surface that does not block progress — captures, ideas, observations, and any user-run / point-and-click test — gets written down (captures to Captures, user-run tests to Deferred tests) and the run continues. No one is sitting there to hand it to, so filing replaces handing-over; the deferred-test machinery already has a user-run lane, so this is a routing rule, not new plumbing. **Halt-for-the-user**, the rare case: only genuine proceed-blockers — an open red flag in scope (concern 4), a needed SPEC/product-truth change (concern 6), or a blocking uncertainty it can't resolve (concern 1). **Hard-stop**, the mechanical safety net the field treats as mandatory: an iteration ceiling, no-progress detection (same error / empty diff / failing test repeats N times), and a per-run budget ceiling — fires regardless of category, the guard against the runaway-cost failure the subagent incident already hit once; steal the "write BLOCKED to a file and exit" mechanism for the stuck case rather than thrashing. Resolved 2026-06-25: when a batch's only verification is a user-run test, that is a deferral case — cruise control ships the batch and defers the test like any user-run line, it does not halt. Open sub-question it raises: deferring verification under autonomy compounds — if a later batch builds on an unverified one and that verification later fails, several committed batches rest on a broken foundation, which attended mode would catch before stacking; whether cruise control may build a batch depending on an unverified one is a dependency-management sub-decision (ties to concern 2 and [plan-dependency-tracing-gap]); (9) the loop driver — cruise control has no human bookends, so the skill itself picks work from the queue unprompted, loops build→close→build→close, and triggers its own end. This skeleton is what goal sessions get from the human who starts, steers, and closes the run; cruise control must supply it, and the gates and the response spine all hang off this loop. Surfaced 2026-06-25 mapping goal-session mechanics against cruise control. Resolved 2026-06-25 — the loop shape, steps (a)–(h): (a) pick the top batch; (b) gate-check before building — open red flag in scope or unsatisfied dependency → halt and wait; (c) build, scope-locked to its files; (d) verify — run every Claude-runnable check, route user-run tests to Deferred tests without waiting; (e) close-and-commit the batch (LOG entry, shipped-slug cross-check, commit — durable); (f) check the limits (iteration / budget / no-progress → stop the run); (g) next batch until the queue is exhausted, a halt fires, or a limit stops it; (h) run-end pass — the single staleness sweep plus a summary of what ran and what awaits the user. Two halt-triggers live inside the build (step c), not only at the gate: a needed SPEC/product-truth change and a blocking uncertainty it can't resolve, each stopping the same way (write BLOCKED and exit), losing nothing because prior batches are already committed; (10) commit cadence — goal sessions land one commit at the end of the whole run (safe only because a human bookends a single sitting), but [cruise-control] is specified build→commit→build→commit, a commit per batch. The fork: close-and-commit each batch as it finishes, or one goal-style close at run-end. It changes how the inherited close machine wires up — the shipped-slug cross-check and the deferred/staleness sweeps run once at a single close today, but would run per batch (or split) under per-batch commits. The why: an unattended run with no one watching must durably commit each finished batch so a crash, a budget stop, or a halt loses nothing and leaves a clean resume point; goal's single-commit model is safe only because a human bookends one sitting. The per-batch close runs the per-batch parts (LOG entry, shipped-slug cross-check, commit, defer this batch's user-run tests); the staleness sweep runs once at run-end. - **[dont-assume-user-environment]** Don't assume the user's environment — a plugin-level communication guard. Split from [user-run-assumes-user-can-run] on 2026-06-23: that batch fixed the narrow test-routing case (classify user-run tests by requirement); this is the broader default underneath it.
  The pattern: Claude defaults to assuming the user is working in the CLI/terminal, and often doesn't account for the desktop app existing at all. That's a poor default for a non-coder plugin, whose users may well be on the desktop app. The only reason Claude reliably treats Alex as desktop-only is that she forced it into her global config after repeated frustration — the plugin can't lean on every consumer doing that.
  The guard (decide shape at /plan): at the plugin level, don't assume the user's environment.
