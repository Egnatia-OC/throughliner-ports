Two sections. **Processed** — work discussed and agreed, ordered top-to-bottom; /next builds from above the `--- Cleared to run above this line ---` marker. **Unprocessed** — captured, not yet fully processed; the next /plan weighs each item. A work item is a `#### ` heading (its description) with a `[slug]` at the end of that line and its rationale in the block beneath. A leading `[audit]` / `[user]` tag names how it's executed; no tag means a build. A work item carrying a security or privacy risk gets a `Red flag · State: …` marker — the flag rides the work.

#### Improve SI for concurrent session running [concurrent-session-support]
By Claude at the user's request. The user wants SI made safer for running concurrent sessions — e.g. a /plan and a build at the same time.
**Premise correction (2026-07-29):** /next "only appends" is not quite right — its *close* removes shipped items from Processed and repositions the cleared-to-run marker, so a /next close and a /plan session can both rewrite QUEUE.md structure at once. The contention is real.
**Reframe reached (2026-07-31):** Drive-sync is *Alex's personal environment*, not a method-general blocker. SI's users are mostly not on Google Drive, so for them there is no sync floor and in-repo concurrency is solvable in-method — a structural safeguard is worth building for the majority; Alex covers her own case by pausing Drive during sessions. The old "the hard half is outside SI's control (Drive conflict copies)" framing is Alex-specific and should be corrected — it is NOT a method-general truth.
**Detect-and-warn design (2026-07-31) — rejected, superseded by the merge direction below.** The earlier proposal was detect-and-warn: (1) liveness by working-file mtime; (2) a session_start awareness note; (3) a pre-write stop-and-ask recheck; (4) `.git/index.lock` retry/backoff. Recorded so it isn't re-proposed; replaced by the 2026-08-01 direction.
**Design progress banked (user + Claude, 2026-08-01) — continue next session, still undesigned:**
- **Drop staleness entirely (user).** A session should always be *closed* properly, never left to go "stale" — so detecting staleness by mtime is the wrong model. Design so an abandoned-live session doesn't happen, rather than detecting it after the fact. (Kills proposal #1.)
- **The session_start awareness note (#2) stays** — fine as-is.
- **New core direction — live/canonical queue, merge-at-close (user's idea, better than detect-and-warn).** Each session edits its own *live* copy of the queue; at close, its changes merge into the *canonical* version. **Use git if that makes it easier to build (user approved).** The merge is automatic and clean when two sessions touched *different* items/sections; a conflict arises only when both touched the *same* region. Claude resolves the merge **silently**, surfacing to the user **only** when a conflict genuinely can't be resolved safely — the user never sees raw conflict markers. Reframes the problem from *preventing* concurrent writes to *letting them diverge and merging at the end*. Real design work: (a) structure the queue so sessions rarely collide; (b) make Claude's silent conflict-resolution trustworthy.
- **`.git/index.lock` retry/backoff (#4) — minor robustness only.** Two simultaneous commits make git's brief lock file error one of them; retry-after-a-moment avoids it. A small nicety, not core.
- **Cloud-sync detection (user).** Google Drive / OneDrive / Dropbox syncing the folder is a *separate* failure mode from in-repo concurrency — these make their own duplicate "conflict copies" and file locks. Add a startup check for whether the project folder is being synced, and surface it. (Correctly re-homes the old Drive-specific worry as one instance of a general cloud-sync issue.)
- **Remote-control convergence.** Remote sessions *already* auto-branch (a git worktree); the manual pain has been merging them back. The merge-at-close machinery here removes that pain, which is why the separate worktree-override hook was deleted rather than built (2026-08-05) — its mechanism facts are carried below.
- **Desktop vs remote asymmetry — the open crux for next session.** Remote already forks (branch-per-session free; only auto-merge missing). Desktop shares the one main tree, so matching that isolation means deliberately branching each desktop session, or a separate-file fallback. Fork to resolve: branch *every* session, or isolate only where sessions overlap?
- **Scope distinction to resolve, not conflate (user, 2026-08-01):** full-project branching vs queue-only branching. The contention is fundamentally about QUEUE.md, so branching *just the queue* may suffice; full-project branching (what the remote worktree already does) is the heavier hammer. Fine to scale up to full-project *if* it solves both concurrency and remote-merge neatly — but name the two scopes so a future pass chooses deliberately rather than sliding between them unnoticed.
**Unnamed cost, added 2026-08-04 from the scope-lock audit (`resources/research/scope-lock-audit.md` §8.6):** the merge-at-close direction has Claude silently resolving conflicts in QUEUE.md. QUEUE.md is the artifact that *defines* scope — the cleared-to-run marker sets how much autonomous work is authorised, and the Files list of every item derives from it. So a silent automatic merge is an expansion of agent authority over the boundary itself, not just over a document, and the design above doesn't frame it that way. Weigh at design whether the queue's *structural* lines (the readiness marker, section headers, red-flag states) should be excluded from silent resolution and always surfaced, even when the merge is technically clean.
**A live instance, 2026-08-05 — and it is worse than this item's design discussion anticipates.** Two sessions ran concurrently **in the same folder**: an overnight-blitz session left open, and a planning session. The blitz filed a new capture and its write landed on the *heading line* of an existing item, destroying that item's heading and slug outright and leaving its rationale orphaned under the item above. It reached a commit. The planning session found it only by trying to move the item by slug and getting "not in section Unprocessed".
**Why it changes the design input.** The discussion above frames concurrency as *conflicting edits* to be merged — two sessions touching the same region, resolved cleanly or surfaced. This was not a conflict at all: one session's write simply consumed a structural line of another item, and every layer passed. Git saw a valid diff. The lint saw a valid queue. The commit succeeded. **So "merge cleanly when different regions were touched" is not sufficient protection, because the damage here was to a region nobody was editing.** It strengthens the note already in this item that the queue's *structural* lines should be excluded from silent resolution — and extends that set from the readiness marker and section headers to **item headings**, which are equally structural and were not previously named.
**Two mitigations that are not this item's to build,** noted so they aren't lost: the queue lint gains an orphaned-prose check (folded into [lint-blind-to-readiness-marker], and it earns its place independently of concurrency); and the Edit tool's "file modified on disk since you last read it" warning fired twice during the incident and was dismissed both times as the queue mover's doing — a session-behaviour lesson rather than a mechanism, that the first such warning should stop work rather than be reasoned past.
**Designed 2026-08-05. Both forks are resolved, and one reframe is what resolved them.**
**The reframe: isolation is the fix; merging is the price paid for it.** The live corruption happened in **one folder**, with two sessions sharing a single working tree. Git was never involved and there was no merge conflict, because there was nothing to merge — just two processes writing one file from stale reads. The design above framed the problem as *conflicting edits to be merged*, which put the emphasis on the wrong half and is why the fork stayed open so long. Branching is what prevents the damage; merge-at-close is the cost of having branched, not the mechanism that saves you.
**Fork 1 — RESOLVED: branch every session.** "Isolate only where sessions overlap" requires knowing another session is live. That requires liveness detection, which the user killed on the grounds that a session should always be *closed* properly rather than left to go stale. So the overlap option depends on the one mechanism already ruled out, and cannot be built without reversing that decision. Branch-per-session doesn't: it costs almost nothing when uncontended, because a merge with no divergence is a fast-forward and effectively invisible. **It is free when you are working alone and pays exactly when you are not** — which is the property you want, since concurrency is unpredictable and the protection has to already be in place when it happens.
**Fork 2 — RESOLVED: full-project branching, not queue-only.** Git gives whole-tree branching for free; isolating a single file would need bespoke machinery built for one document. And the premise that "the contention is fundamentally about QUEUE.md" is too narrow: a build session touches hooks, procedure docs, templates and SPEC, and two concurrent builds collide on source files, not just the queue. The planning session of 2026-08-05 alone touched QUEUE.md, its own working file, and would have touched CLAUDE.md. Queue-only branching would leave all of that unprotected while costing an invention.
**A property worth naming, because it is what makes abandoned sessions tolerable without liveness detection: branching converts an invisible failure into a visible one.** Today an abandoned or colliding session corrupts a file silently and every layer passes. Under branch-per-session, the worst residue is an unmerged branch sitting in `git branch` where anyone can see it. A leftover branch is a housekeeping chore; silent corruption reached a commit and was found only by accident. This is the honest answer to "what about sessions that are never closed" — they leave litter rather than damage.
**Consequence, acted on the same session: [worktree-override-hook] was DELETED rather than built.** That hook existed to *stop* remote sessions forking, because merging them back by hand hurt. With the merge automated and forking the design, it solved a problem this removes — and shipping it would have actively defeated the isolation, pointing every session back at the one shared tree, which is precisely how the queue got corrupted. Its mechanism facts were relocated here before it went (see below). The accepted risk, recorded so it is not a surprise: if this design stalls, the original remote-forking pain returns with nothing queued for it — acceptable because the hook was never built, so nothing working was lost, and unmet pain re-captures itself in use.
**The desktop/remote asymmetry dissolves.** Remote already forks a worktree per session; desktop shares one tree. With desktop branching too, both surfaces behave identically and the asymmetry that made this hard stops existing.
**The remaining build question, and it is the one that carries the risk: what happens on a GENUINE conflict.** Most merges will have no conflict at all, so this narrows to real concurrent edits to the same region. The scope-lock audit's warning stands and is sharpened by the live incident: QUEUE.md is the artifact that *defines* scope — the readiness marker sets how much autonomous work is authorised — so silently resolving it is an expansion of agent authority over the boundary itself, not merely over a document.

    the readiness marker          # sets what /next may run unattended

#### The `captured by you` credit is unreliable in two ways: it only resolves for one reader, and it gets applied wrongly with nothing to catch it [provenance-credit-second-person-ambiguous]
Captured by you 2026-08-03 — you asked who "you" refers to in a provenance line, then challenged a credit that turned out to be wrong.
The credit means the project's user, and the convention is deliberate: [provenance-labelling-reconsideration] shipped at `ea272f6`, dropping mandatory provenance for an asymmetric default-AI scheme where an unmarked item is Claude's and only a user-raised item carries a credit. **That decision is not in question** — the asymmetry is sound and cheap. Both problems below sit inside it.
**Problem 1 — it resolves only for one reader.** The credit is direct address, so it works only if the reader is the person it was written for. That always holds in a solo project. It stops holding for a repo that goes public ([scrub-gate-before-approval], [setup-repo-privacy-and-publishing]), for a project handed on, or for any second reader — where "captured by you" points at nobody identifiable.
**Problem 2 — and this one is worse — the credit gets applied wrongly, and nothing catches it.** Live instance the same day: [reorder-mover-marker-at-top-blind] carried a `captured by you` credit from filing. It records a script throwing an internal error during a /done close — something only Claude could have seen. The user had no way to observe it. The credit was then *inherited unchecked* through a full processing pass, and only caught because the user happened to say it didn't feel like theirs.
**Why that's the more serious half.** An ambiguous credit is a reading problem; a wrong credit corrupts the record. The queue's purpose is preserving who decided what, and a mis-credit silently attributes thinking to the wrong party — in the direction that flatters the user's involvement, which is exactly the direction nobody will question. It also survives processing, because a rewrite preserves the provenance line as given rather than re-deriving it.
**Measured at processing, 2026-08-05: 40 of the queue's 55 items carry a `captured by you` credit.** Framed carefully, because the number is suggestive rather than diagnostic — it is entirely consistent with being true, since there is one user and they are the developer, so they do raise most things. What it does establish is that the credit discriminates almost nothing in practice: a marker on three-quarters of items tells a reader little, and a single wrong credit is well camouflaged among them. That is the condition under which the known mis-credit survived a full processing pass unnoticed.
**Problem 1 is resolved by the user's decision, 2026-08-05: record a real first name, an alias, or another identifier at /setup, and credit captures to it.** Claude had recommended a one-line queue-header explanation instead, on the grounds that a name writes a person into a repo that may be public. **The user's framing already answers that** — offering an *alias* gives multi-user disambiguation with none of the exposure, so the objection applies to a name-only design and not to this one. The user's reason: "you" breaks down as soon as a project has more than one user, and the header line only ever worked because this project has exactly one.
```
rejected: "captured by the user"  -> unambiguous but colder, and the second
                                     person is part of how the queue reads as
                                     the user's own document
rejected: name-only, no alias     -> writes a real person into every item of a
                                     possibly-public repo
kept:     an identity recorded at /setup — real name, alias, or other, the
          user's choice, with the alias route offered plainly
```
**Three things the build must settle rather than assume.**
1. **The multi-user case the field exists for.** A single stored field records *one* identity, so where two people genuinely share a project, the second person's captures would be credited to the first — the exact failure this is meant to fix, reintroduced. Decide between a per-session confirmation, a field explicitly scoped to "the project's primary user", or something else. Do not leave this to inference.
2. **The ask is a solicited identifier, so it is governed by the private-information rules.** /setup must say plainly, at the moment of asking, that the answer is written into committed project docs — and offer the alias in the same breath. /setup already detects repo visibility, so a public repo should lead with the alias option rather than mentioning it as an afterthought.
3. **What happens to the 40 existing credits.** A new field protects new items and does nothing about those already written. Migration is [provenance-credit-audit]'s territory; this item must not silently assume it happens.
**Problem 2 — a filing-time test, plus re-derivation at the keep-step.** State the test in words: *could the user have observed this unaided?* And require the keep-step to re-derive the credit from the discussion rather than inherit the filed one, because inheritance is precisely how the known bad credit survived processing. No lint — this is a judgment a hook cannot make, so it is a wording fix.
**Files:** `plugin/si-plugin/docs-b/setup.md` (the new question and its privacy framing), `templates/CLAUDE-TEMPLATE.md` (the stored field), `docs-b/plugin-behaviour.md` (the Captures provenance convention and the filing-time test), `docs-b/plan.md` (the keep-step re-derivation), the QUEUE.md header prose in setup.md, SPEC.md (a new user-visible setup question), README feature-list sync, and a FAQ entry. #### Design proactive rationale-nudging: Claude asks for the *why* without nagging [throughline-feature-elevation]
Captured by you (2026-07-30); reframed 2026-08-01. Earlier threads are gone: thread (a) — the why-pipeline → "throughline" rename — folded into [rename-to-throughliner]; thread (b) — user-provenance on rationale — folded into [provenance-labelling-reconsideration] (2026-08-01) for one consistent provenance scheme. What remains is the genuinely-undesigned thread: **proactive rationale-nudging.** At certain moments (a decision made, a route chosen, an item kept), Claude could proactively ask the user for the *why* — actively extracting human intention rather than only recording rationale when it surfaces on its own. Because this is the titular feature — durable rationale that survives a forgetful session — it should be genuinely excellent. **Designed 2026-08-05 from that session's own evidence, which resolved the crux and changed the mechanism.**
**The finding: the productive nudge is a proposal, not a question.** Almost none of that session's rationale came from anyone asking "why". It came from Claude stating a recommendation *with its reasoning* and the user disagreeing. The clearest case is this queue's own [provenance-credit-second-person-ambiguous]: Claude recommended a queue-header line and gave its grounds; the user overrode it with "'you' breaks down when there are multiple users", and that sentence is now the item's rationale. The same shape produced the rationale on [lint-blind-to-readiness-marker], [docset-a-completion-ask-inconsistency] and [merge-and-fold-without-asking].
**Why that reframing dissolves the nagging problem rather than managing it.** A "why do you want that?" question arrives empty and makes the user do the work, which is exactly what nags. A proposal costs the user nothing when they agree — one word — and when they disagree, the reason arrives attached, because people justify corrections for free and resent interrogation. So "when can the nudge fire without nagging" is hard to answer for a question and easy for a proposal: wherever a decision is being made.
**The moments, now nameable:**
```
/plan keep-step    ->  a recommendation carries its reasoning explicitly.
                       Mostly making existing practice a rule, not a new beat.
the close          ->  where a decision's rationale is written down.
a user OVERRIDE    ->  the highest-yield moment of the three, and the one with
   of a proposal        no rule at all today. An override is rationale arriving
                        unbidden; nothing currently says to capture it as such.
```
**One suppression limb, non-negotiable:** don't propose where the answer is predictable. [merge-and-fold-without-asking] is the user saying plainly that a whole class of Claude's asks was redundant, filed the same day. A nudge design that ignores that reinvents the behaviour the user asked to stop.
**Rejected: sharpen-and-skip for a dedicated design pass.** Legitimate and offered; the user chose to keep it, because the crux is settled and the remaining questions are build-sized rather than design-sized. Recorded so the option isn't re-proposed as though it had been overlooked.
**Cost to weigh at build:** a proposal-with-reasoning spends tokens every time, and the same session established that approval-time token cost lands hardest on Pro users ([approval-flow-token-doubling-simplification]). The suppression limb is what keeps this affordable, so it is part of the feature rather than a refinement.
**Files:** `docs-b/plugin-behaviour.md` (the throughline section — the nudge's proposal form and its suppression rule), `docs-b/plan.md` (the keep-step: a recommendation carries its reasoning), `docs-b/done.md` (capturing rationale at a user override), SPEC.md if its description of the throughline changes, README feature-list sync, and a FAQ entry. Relates to [rename-to-throughliner] (which renames this concept), [provenance-labelling-reconsideration], [merge-and-fold-without-asking], [throughline-value-articulation].

#### Test explicit structural delimiting on plugin-behaviour.md as a second harness experiment — the better-evidenced lever we hadn't considered [structural-delimiting-experiment]

That may be the wrong axis. The better-evidenced intervention for a document of this exact shape — long, multi-section, always loaded, carrying many independent rules — is explicit structural delimiting: XML-style section boundaries whose purpose is to stop an instruction in one section being read as applying to another.
**Why it's a distinct experiment rather than a variant of the register question.** It changes the document's boundaries, not its voice. That suggests the rules which keep slipping here do so for structural reasons rather than poor wording, and also that a format change alone may not fix them. #### Shell commands bypass the file scope-lock entirely — `pre_tool_use.py` only guards Edit/Write/MultiEdit [shell-writes-bypass-file-scope-lock]
By Claude, from this session's scope-lock audit; filed at your request.
**The finding.** `pre_tool_use.py:391` reads `if tool_name not in ("Edit", "Write", "MultiEdit"): return 0`, so the file-scope enforcement below it never runs for Bash or PowerShell. Those tools route to the git-safety checks only (`:348–386`), which match four git patterns and consult `build_files` not at all. During a fully scope-locked build, `sed -i`, a `>` redirect, `cp`, `mv`, or `Set-Content` writes any file on disk with nothing noticing.
**Why it matters more than the other known holes.** [plan-scope-lock-gap-and-emergency-path] and [post-close-tail-state] both record the lock being *off* in a named state — planning, and the post-close tail. This is different: the lock is *on*, the session believes it is contained, and one tool class walks around it. It is the only hole in the one layer that can't be skipped by instruction, so every doc-level scope rule rests on a floor with a gap in it.
**What has masked it.** The user's global instructions forbid shell redirection for writes on stale-mount grounds, and the procedure docs never reach for shell writes, so no session has exercised the path. That is convention, not enforcement, and it doesn't ship to consumers.
**What to weigh at design.** Whether to parse shell commands for write intent (fragile — the same pattern-as-data limit the git checks already acknowledge at `:63–68`), or to deny the small set of obvious file-writing forms during an active build and name the Edit/Write alternative in the denial, or to accept it and say so plainly in SPEC rather than describing a containment the hooks don't provide. Note the third option interacts with SPEC's already-overstated scope-lock description, which [plan-scope-lock-gap-and-emergency-path] flags for the same reason.
**Independent corroboration, 2026-08-04.** The user shared a scope-lock tool built separately for someone else, on a different agent platform (Codex, alongside a memory tool called Hermes). It solves the same problem and hit the same gap, which makes its reasoning a second data point rather than an opinion.
**It reached option three deliberately.** Its documentation lists shell-side writes as a known, accepted gap in v1, with the reason stated: blocking them reliably means parsing arbitrary shell, which produces false denials — and **false denials train workarounds**, so the false-denial failure is the worse one. That phrasing is worth keeping; this project has the underlying idea in its anti-invention rule but has never said it this compactly about enforcement specifically. It also names its own honest consequence: the gap is closed behaviourally, by an instruction not to route around denials, and not mechanically.
**But it does not accept the whole gap, and this is the part that changes the options above.** It catches one case — a structured patch envelope invoked through the shell — by matching the command name and extracting the target paths from the envelope. So there is a **fourth option** this item did not list: don't attempt shell parsing in general, but do catch the specific *structured* write forms that have a parseable shape and a known target. That is narrower than "deny a small set of obvious file-writing forms" and it carries no false-denial risk, because a structured envelope either parses or it doesn't. Weigh it as the leading candidate.
**Two convergences worth recording, because they confirm existing directions rather than opening new ones.** The tool fails open on any error, which is the direction [unscoped-advisory-fires-once-ever] already establishes as the safe one here. And every denial it issues names the alternative — this project's rule that a prohibition without a stated escape route produces an invented one, arrived at independently by someone not reading these docs.
**The source is kept** at `resources/research/scopelock-independent-implementation/` — its README, the hook implementation, and its agent-instruction fragment. Read the implementation directly rather than this summary when building; the hook payloads are another platform's, but the structure of the checks transfers. The always-editable scope-file question it raises is filed separately as [scope-file-editable-vs-locked].
**Files (rough):** `plugin/si-plugin/hooks/pre_tool_use.py` (the tool-name gate and any shell write-intent check), `SPEC.md` (correct the scope-lock description), FAQ entry if consumer-visible. Relates to [plan-scope-lock-gap-and-emergency-path], [post-close-tail-state].

#### Should the file that defines a build's scope be editable during the build, or locked? [scope-file-editable-vs-locked]
Captured by you 2026-08-04, from comparing this method's scope-lock against an independently-built one (source at `resources/research/scopelock-independent-implementation/`).
**The fork.** That tool makes its scope file **always editable**, deliberately. **Why it is a real question and not just a different taste.** Both designs are trying to stop the same thing — a build quietly growing past what was agreed. And note this touches the same surface as [build-scope-vs-described-work-unenforced], which observes that staying inside the `Files:` list was never the real boundary anyway.
**Files (rough):** `plugin/si-plugin/hooks/pre_tool_use.py` (whether `_build.md` is writable during a build), `docs-b/next-build.md` (the halt-and-ask path), `SPEC.md` (the scope-lock's described behaviour).
