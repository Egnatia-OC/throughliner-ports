# QUEUE

Two sections. **Processed** — work discussed and agreed, ordered top-to-bottom; /next builds from above the `--- Cleared to run above this line ---` marker. **Unprocessed** — captured, not yet fully processed; the next /plan weighs each item. A work line is a `#### ` heading (its description) with a `[slug]` at the end of that line and its rationale in the block beneath. A leading `[audit]` / `[user]` tag names how it's executed; no tag means a build. A work line carrying a security or privacy risk gets a `Red flag · State: …` marker — the flag rides the work.

#### A /quickplan skill that bundles queue processing into one bulk-approval pass [quickplan-skill]
By Claude at the user's request. This session, at the user's ask, Claude powered through the whole Unprocessed queue in one pass and produced a single list of per-item recommendations for bulk approval, instead of the one-item-at-a-time capture loop — the user found this efficient. The idea: systematise that into a new skill, tentatively /quickplan, that does the same bundling where applicable — process the queue in a batch and present recommendations as one set the user bulk-approves (contesting by exception) — and reverts to normal /plan behaviour when there are no bundle-able items in the queue. Design questions: what makes an item bundle-able versus needing the full one-at-a-time loop (items needing a full design pass clearly aren't bundle-able); how it relates to the [SEQUENCE] bulk-approval inversion already in the rules; whether it's a separate skill or a mode of /plan; and how it hands off to a normal /plan pass for the items it can't bundle.

Refinement (user, 2026-07-14): reconsider whether /quickplan should be a skill at all. Candidate reframe — drop the standalone skill and make it a triage step /plan runs at the start of processing, before the close-out reorder: "are there items that can be skimmed and quickly bulk-dropped? If so, do that pass first; otherwise order by unblock-potential and go deep on the unblockers." Key nuance that keeps it safe: the bundle-able case is bulk-dropping (deleting low-value items), not bulk-keeping. Bulk-keep is the risky direction — it moves undesigned work into Processed as if ready, the [defer-for-design-process] failure — whereas bulk-drop is low-stakes (git keeps a deleted line). So the triage is "quick deletes first, then deep on the rest," which resolves the old "separate skill or a mode of /plan" question toward a /plan step. Mirrors how this very session chose to proceed.

Companion narration (user, 2026-07-14): right before processing begins, /plan briefly narrates that the queue has been reordered to maximise effectiveness, and states how many items are recommended to be processed this session at minimum before /next is next run. Gives the user the session's shape up front and a floor — "process at least N unblockers before building" — tied to unblock-potential and the cleared-to-run line.

#### A /migrate capability for bringing old-format projects onto the current queue model [migrate-skill]
Captured by you. The plugin is global, so reinstalling the new SI already updates the hooks and skills for every project — what's "on the old version" is a project's docs, not the code. On inspection of a real old project (`.si-version` 1.13.0-test1, pre-two-section model), the only real conversion is QUEUE.md: its old `## Red flags` / `## Batches` / `### Parked` / `## Deferred tests` / `## Captures` shape has to become the `## Processed` / `## Unprocessed` two-section model with `####` work lines, slugs, provenance, and per-line red-flag markers. The other docs need little or nothing: LOG/ is already per-entry files + index.md (matches the new model), CLAUDE.md settings are auto-topped-up by session_start, and SPEC.md is format-agnostic.

The conversion needs judgment, not a script. Example from the real project: its red flags are "accepted" and "resolved" with no remaining work, and the new model forbids a bare red-flag line with no work attached — so each must be judged (becomes a work line, or is done-history that moves to LOG). A find-and-replace can't make that call. So the capability is a guided conversion pass — a `/migrate` skill, or a documented checklist Claude follows.

Facets to design:
- Detection is mechanical, early (Claude-surfaced). session_start gains an "adopted-but-stale-format" state alongside its existing unadopted / adopted / active-build detection. When it sees an old format it stops the normal load and tells the user to run /migrate first — before a full /plan or /next spends context on the old scaffolding. Extends the `.si-version` comparison session_start already runs.
- /migrate is its own session, closed by /done (which writes a LOG entry recording the migration), so the user then clears or starts fresh for the next skill, per the README's one-skill-per-session advice.
- Version-delta knowledge needs a maintenance trigger (Claude-surfaced). /migrate needs a running record of what structurally changed between which versions, keyed to version. A notes doc that isn't kept current is worse than none — it silently misses the newest breaking change — so it needs a self-hosting rule: whenever a build changes the queue/doc format, it records a migration note keyed to the version. Same shape as the existing README-sync and SPEC-sync triggers.
- Version pickup already half-exists. `.si-version` records which plugin version scaffolded the project and session_start already reads it; /migrate reads it to know which version to migrate from. Build on it, don't reinvent it.

Interim reality: until /migrate ships, every old project is migrated by heavier manual judgment in a session opened on that project (the user is doing the `Stephanie abuse` project this way first). So there's mild priority — each old project stays a heavy manual job until the skill exists.

Open design questions: skill vs. documented checklist (hinges on how many projects — a handful, spread over time); how the format-era check distinguishes "needs migration" from an ordinary version bump that broke no format; whether /migrate closes via /done or its own close; and the exact shape and home of the migration-notes doc.
