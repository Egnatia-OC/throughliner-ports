**The narrower defensible form of the discarded third reason,** kept rather than dropped: a branch structure *invites* scoping a rule to a branch, because branches are what the notation offers, whereas prose has no branch for a global rule to fall into. It was one instance generalised to a class when the call was made, but it has a second instance now — the capture line-format block that shipped in docset B asserted structure its own prose contradicted (point 1 of the fidelity restores, `f37e332`).

#### Write approval-time text straight to its doc and link it, instead of pasting in chat — remote the only exception [write-first-link-dont-paste]
Captured by you (2026-08-02), processed the same day. Approval-time text whose destination is a Throughliner doc — a capture, a work item, a LOG entry, a SPEC or CLAUDE.md edit — is written to that doc first and surfaced as a link, and the user approves against the file rather than against a chat paste. **Remote mode is the only exception:** on a phone, opening the file is impractical, so the text is surfaced inline there as it is today. Two supporting parts from the capture: any draft that *is* shown in chat carries a link to the line it concerns; and pointer-style asks ("shall I go to it?") are hollow without either a working link or, in remote, the surfaced text — so they go where the link does.
**The strongest argument, which the capture didn't state: this deletes a branch rather than adding one.** The render rule today has two cases — doc-resident text gets a pointer, text not yet written is always inline "since there's nothing to point at." Write-first removes the second case entirely: write it, and it's resident. One rule instead of two. Lead the build with this.
**Boundary — doc-destined text only (settled at processing).** Not every approval-time output is headed for a file. A commit message isn't (Claude runs the commit), and neither is a recommendation or an option set. Those keep today's behaviour, because there is nothing to write them to and no link to give. Without this clause the rule would try to write a commit message somewhere in order to link it.
**The reject path must be specified, not assumed (settled at processing).** "Revert on reject" is load-bearing and isn't free: nothing is committed mid-session, so reverting means editing the text back out, and getting it wrong leaves rejected content in the file. The build states plainly what happens on a no — remove exactly what was written, confirm by re-read, say so. This buys back explicitly the safety that showing-first currently gives for free.
**What is genuinely lost.** A transient window in which a tracked file holds unapproved text. If a concurrent session or a crash lands in that window, unapproved content persists. Small but real, and it interacts with [concurrent-session-support].
**This inverts a load-bearing rule deliberately.** plan.md's "never write to QUEUE.md without showing the exact text first" exists so approval attaches to shown text. Approval still attaches to exact text here — arguably more so, since the user reads it in final rendered position — but it moves to *after* the write.
**Lift-condition (below the line):** link reliability must be settled first. [line-anchored-link-dead-in-desktop-app] recorded a link opening nothing on the current host; [desktop-native-md-open-vs-editor-field] recorded links opening natively at the right line on that same host. Until that contradiction resolves, write-first-then-link can leave the user with neither the text nor a way to reach it — strictly worse than pasting. Lift once link behaviour is understood and dependable.
**Convergence:** this is the ordering flip [approval-flow-token-doubling-simplification] identified, reached independently from the user's side and *not* gated on the harness feature that item waits for — it is a pure method ordering change. Design the two together; they may collapse into one build.
**Files:** docs-b/plugin-behaviour.md (Working mode and view-in-doc rendering — the two-branch rule collapses to one; the approval-time blockquote rule; write-then-verify-then-point), docs-b/plan.md (the show-before-write rule, the capture and keep steps), docs-b/next-build.md, docs-b/done.md (LOG-entry approval), SPEC.md (working-mode description), README feature-list sync if user-facing, plus a FAQ entry. #### Test explicit structural delimiting on plugin-behaviour.md as a second harness experiment — the better-evidenced lever we hadn't considered [structural-delimiting-experiment]

#### Test that hooks actually work, in a way Claude's own compensation can't mask [hook-liveness-and-schema-testing]
Captured by you 2026-08-03 — filed after `d682117`. The `session_start` hook emitted a malformed output shape and had its entire payload silently discarded, probably for a long time. Nothing caught it. Sessions kept working, because Claude read CLAUDE.md and the queue directly and reconstructed roughly what the hook would have said. That compensation is the problem: it makes a dead hook invisible, and the user's own words are that this has happened before.
**Two distinct gaps, and they need different tests.**
The first is **schema conformance** — is the hook emitting the shape Claude Code documents? This one is mechanically checkable and cheap. A script drives each hook with a sample payload and asserts the output matches the documented contract, including that `SessionStart` nests its context under `hookSpecificOutput` with `hookEventName`. It would have caught this bug at authoring time, years of sessions ago. The tell that it's a real defect rather than a convention: `pre_tool_use.py` and `post_tool_use.py` already use the correct nested form, so the codebase disagreed with itself and nothing noticed.
The second is **liveness** — did the output actually reach a session? Schema conformance can't answer this, because a correctly-shaped hook can still be dropped by the harness, and that is exactly the failure being fixed. The only proof is a session reporting what arrived in its context. So the Rezip and Push rituals gain a verification step: after the restart they already require, the first fresh session is asked what orientation text it received, and the answer is recorded.
**Why the liveness half can't be automated away.** It needs a real session start, which nothing inside a session can trigger. That makes it irreducibly a `[user]` step, which is an argument for attaching it to the restart the rituals already demand rather than making it a separate chore someone must remember.
**The deeper pattern worth naming in the build:** Claude compensating for missing infrastructure is a general hazard, not a hook-specific one. Any mechanism whose output Claude could plausibly reconstruct from other context will fail silently the same way. The test has to ask "what did you actually receive?", never "does this seem right?"
**Files (rough):** a schema-conformance script under `resources/testing/`, CLAUDE.md (the verification step in the Rezip and Push rituals). Relates to [session-start-output-not-reaching-sessions], and the research at `resources/research/session-start-hook-output-schema.md`.

#### When the tooling misbehaves, check our own contract conformance before theorising — and search the issue tracker early [harness-misbehaviour-diagnosis-order]
Captured by you 2026-08-03 — filed after `d682117`. This session spent most of its length diagnosing a dead `session_start` hook. Two hypotheses were built and argued in detail: that the desktop app silently drops oversized injected context, and that it doesn't run `SessionStart` hooks at all. Both were wrong. The actual cause was that our hook emitted an output shape Claude Code doesn't accept. One web search found the documented contract and three matching issues in about a minute. That search should have been the first move, not the fourth.
**The ordering rule to build.** When something in the harness misbehaves — a hook, a skill not loading, a setting apparently ignored — check our own conformance to the documented contract first, then search the tool's issue tracker, and only then theorise about a bug in the tool. The default assumption should be that we are wrong, because our code is unverified against the contract while the harness is used by very many people. This session inverted that default and nearly filed a bug report on someone else's tracker for our own defect.
**The issue tracker is a diagnostic resource, not just a place to report things.** `anthropics/claude-code` had our exact symptom already catalogued — valid JSON, exit code 0, output silently discarded. Reading it cost one search and would have saved the whole session.
**A second, sharper learning about evidence.** Running the hook through the CLI with `--include-hook-events` showed its full output in the event stream, and that was read as proof the injection worked. It was not: that flag echoes a hook's raw stdout whether or not the harness accepts it, and the run failed authentication before any model call. The general form is worth stating as its own rule — *the thing ran* and *the thing had its effect* are different claims, and evidence for the first is routinely mistaken for the second. This is the same error twice in one session, since a single missing symptom was earlier matched to an expected cause without checking the others.
**Where it lands.** The diagnosis-order rule is method-general and helps consumers too, who hit harness misbehaviour without knowing an issue tracker exists — so it belongs in the shipped behaviour rules, near the existing research-offer rule it extends. The never-file-outward-before-ruling-out-our-own-code half also touches the existing consumer feedback channel, which handles the mirror case of routing *method* problems out.
**Files (rough):** `docs-b/plugin-behaviour.md` — the Research and evidence filing section, or a short new rule beside it. Docset A is frozen, so shipped changes land in `docs-b` only. Relates to [session-start-output-not-reaching-sessions], [hook-liveness-and-schema-testing], and the research at `resources/research/session-start-hook-output-schema.md`.
