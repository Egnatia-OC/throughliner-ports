**Fix the inline `Files:` line that shadows the scope-lock** **[inline-files-shadow-fix]**

When `/next` builds a working file (`_build.md`), it copies in the batch's own entry text — and that text can carry a stray `Files:` line. The scope-lock parser (`_parse_build_files`) binds to the first line starting with `Files:`, so it latches onto the stray inline line, finds no bare-path bullets under it, breaks at the next non-bullet line, and returns an empty list. The hook then reports "method docs only" and denies every source edit — the build is locked out of its own files even though the real, structured `Files:` section lists them correctly. Confirmed by tracing the parser against the 2026-06-20 `/next` build of [plan-close-dep-check], where this fired. Fixed in two layers, matching the spec-edit guard's shape — a mechanical guard that can't be skipped plus an authoring tidy-up at the source: the hook is hardened so a content-bearing `Files: a, b, c` line can never be mistaken for the section header (the load-bearing fix, robust to every future recurrence), and next.md's working-file template stops copying the inline line in. Same hook and adjacent parse gap as [scope-lock-drop-dash-stripping] (a related fix, already shipped to target); this is additive to that same function.

Build:
- `plugin/si-plugin/hooks/pre_tool_use.py` — harden `_parse_build_files` so an inline content-bearing `Files: a, b, c` line cannot shadow the structured `Files:` section. Bind the section to a bare `Files:` header (nothing after the colon), or scan all `Files:` sections and accumulate — settle on the fail-safe approach at build, so a malformed file never silently turns the lock off.
- `plugin/si-plugin/docs/next.md` — in Step 2's `_build.md` template, instruct that when copying the batch's entry text into the `Entry:` field, omit any inline `Files:` line, since the structured `Files:` section below is the canonical list the lock reads. Add a one-line caution at the `Files:` template noting it's the only list the lock reads.

Test:
- Run-now (Claude, in-session): import `_parse_build_files`, feed it a `_build.md` string with an inline `Files: a, b, c` line above the structured `Files:` section, and assert it returns the structured paths, not an empty list. Mirrors the dash-stripping fixture test.
- Deferred (host-side, observed): the first `/next` build after push + reinstall whose working file carries an inline `Files:` line edits its own listed files successfully instead of being denied.

**Surface readable edits in chat and allow small mid-build tweaks** **[surface-readable-edits]**

Today `/next` treats every edit like a code change: it lists the upcoming changes as bullet points, makes them silently, and never shows the actual new wording. For readable content — a doc, copy, a spec section, anything that isn't code — that's the wrong shape. The bullet preview is often pointless: the edit lands almost instantly, so a "here's what I'm about to change" beat right before it is just noise. And the user never sees the real wording in chat; they have to open the file. The exact wording of a readable edit is produced in `/next` and was never shown in `/plan` (which agreed only the intent), so surfacing it is the first time the user can react to the actual words. The change: for readable edits, drop the pre-edit preview and show the actual new text in chat after the edit, as an informational reveal — not an approval ask, since the change was already agreed in `/plan`. Once the text is visible, a small "just change this one bit" tweak that refines the build's agreed work product is allowed inside the same `/next` session — it's refining the work, not new planning — and folds into the build's existing LOG entry rather than a separate logged object (which would bloat the index line); a tweak that's actually new scope still routes out via existing scope management. For code edits the surface-the-text half doesn't apply (a non-coder can't review code text the same way), but the other half does: drop the redundant pre-edit preview, since the work was already approved in `/plan` — the success path stays quiet-until-done, just without the preview. Sibling in spirit to [review-vs-test-framing] — both about how the method handles human-readable generated output rather than code.

Build:
- `plugin/si-plugin/docs/next-build.md` — in the Execute [SILENT] success-path framing and the build-entries loop, add the carve-out: when an edit changes readable (non-code) content, after making it, surface the actual new text in chat as an informational reveal (readable/wrapped), with no approval ask appended. Drop the point-form pre-edit summary for all edits, readable and code; the success path stays [SILENT] for code apart from removing that preview. Add the mid-build-tweak allowance: a small wording tweak to a just-surfaced readable edit that refines the build's agreed work product is in-scope — make it, record it in the build's changes so it folds into the single LOG entry /done writes, no new logged object and no /plan round-trip; a tweak that is actually new scope routes out via the existing scope-management path.
- `plugin/si-plugin/templates/faq-template.md` + `plugin/si-plugin/templates/faq-index-template.md` — add an entry explaining that readable edits now show their new text in chat and you can ask for a small tweak on the spot, plus its index line.

Test:
- Deferred (host-side, observed): the first `/next` build after push + reinstall that edits readable content surfaces the new text with no bullet preview and no re-approval ask, and a first code edit drops the preview while staying quiet-until-done. Also naturally observable in the Taskflow E2E project. No pass/fail fixture — this is observed narration behaviour, not a code test.
