#### Stop inlining the behaviour rules in the session_start payload — the harness truncates it and no session receives them [session-start-payload-oversized-and-misordered]
Captured by you 2026-08-03; premise corrected and re-scoped 2026-08-04 after live measurement. The ordering half was split out to [session-start-state-lines-first] and shipped. What remains is the size question, and it is now confirmed rather than suspected.
**Measured, in a real session (2026-08-04, host 1.16.0-test5, docset B live).** `session_start.py` reads `<docset>/plugin-behaviour.md` and appends it whole; that file is **50,685 bytes** in docs-b and 89,411 in docs. The payload delivered to this session was **54,886 bytes**. The harness truncated it to a ~2KB preview and persisted the remainder to a file, leaving a path in its place. So the behaviour rules did not govern that session at all — only the docset directive and the state lines survived, because [session-start-state-lines-first] had moved them to the front.
**The original premise was wrong, and in the worse direction.** This item predicted docset B's payload at 3,524 characters on the assumption that B replaces the inlined rules with a pointer. It does not — B inlines its own full rules file. The docset fix cut the payload by roughly 40% (92,112 → 54,886) against a cap that appears to sit near 2KB. Fixing docset selection did not dissolve this item; it barely moved it. **Every session in this project is currently running without its behaviour rules.**
**The build, in three parts, and the first two are not optional.**
1. **Establish the threshold rather than inferring it.** Two data points exist (~53KB and ~90KB), both truncated, none below. Check the documented hook contract and the Claude Code issue tracker before designing against an observed number — this is exactly the trap [harness-misbehaviour-diagnosis-order] names, and this item has already been wrong once by assuming rather than measuring.
2. **Replace the inlined rules with an unconditional read instruction** naming `docs-b/plugin-behaviour.md`, so the payload drops to the state lines, the docset directive and a short directive to read the rules file first.
3. **Carry detection with it.** A redirect that is skimmed leaves a session governed by rules it never read, with nothing noticing — the identical complaint [docset-routing-mechanism] makes about the docset directive. The two edit the same injected text and must be built together or adjacently, not apart.
4. **Replace the injected FAQ index with a one-line pointer** (folded in from [faq-index-injected-as-session-start-bulk], 2026-08-04 — that item is now retired into this one). `session_start.py` reads `FAQ/index.md` and appends its full contents — **2,336 bytes**, small against the total but larger than the entire surviving preview, and sitting immediately before the rules block so it is the last thing competing for the truncation boundary. It is a list of question titles and anchors: no state, nothing time-sensitive, and unlike the behaviour rules it *does* have a trigger — a session that needs an answer can read `FAQ/faq.md`. The one thing it genuinely does is make a session aware the FAQ exists so it can point the user there, and that needs a single sentence, not an index. So: replace the append with a one-line pointer, and place whatever remains **below** the rules block so the documented truncation ordering actually holds — the comment at that block already says the bulk goes last deliberately, and the FAQ index sits above it only because [session-start-state-lines-first] didn't move it. **Leave `has_faq_index` alone:** it also feeds the scaffold-drift check further up the file, so the *check* stays and only the content read and append go.
**Why this does not contradict the no-split decision, and the distinction is load-bearing.** CLAUDE.md rejects splitting `plugin-behaviour.md` because progressive disclosure fails for standing behavioural rules — a session has no trigger that would make it fetch "lead with the decision," so moving those rules behind an index deletes their effect rather than deferring their cost. That argument is about **triggered** fetching. An unconditional read-this-first instruction is a **redirect**, and the redirect mechanism is proven in exactly this payload: the docset directive is the one part that reached the session, and it was followed. The file is not being split and no rule moves behind an index. Recorded here so the no-split decision is not read as forbidding this.
**What is genuinely traded.** Today's failure is loud in effect but silent in appearance — the rules simply aren't there and nothing says so. After the change, the failure mode becomes a skimmed redirect, which is quieter still unless part 3 ships. That is why detection is inside this item rather than deferred to its sibling.
**Docset A is frozen, and this is a hook change rather than a doc change, so it applies to both docsets' payloads without editing A's prose.**
**Files:** `plugin/si-plugin/hooks/session_start.py` (the `plugin-behaviour.md` read and append, the injected directive), `SPEC.md` if the hook's user-visible behaviour description changes, plus a FAQ entry if what a session loads becomes user-visible. #### Give /plan an ask-never-deny file gate, and dissolve the emergency path into a record duty plus a red-flag triage rule [plan-scope-lock-gap-and-emergency-path]
Captured by you 2026-08-03 — you asked whether a hook stops writes outside SPEC and QUEUE during /plan, and how a red-flag fix should be protected. Processed 2026-08-04; both halves resolved, and the resolution is smaller than the capture expected.

A planning session has no `_build.md`, so **any file in the repo is editable** — shipped hooks, procedure docs, templates, anything — with nothing noticing. Only git safety and the subagent ask still fire. [post-close-tail-state] records the same gap one door along; [shell-writes-bypass-file-scope-lock] records a third.
**SPEC overstates this.** It describes `pre_tool_use` as enforcing "the scope-lock (which governs SPEC.md like any other file)" with no hint that it is build-only. A reader would reasonably conclude planning sessions are contained. They are not. Correct it here — and note [build-scope-vs-described-work-unenforced] wants the same sentence corrected for a different reason, so make it one edit.
**Finding 2 — there is no sanctioned move for "this must be fixed now."** The 2026-08-03 session found a named third party's abuse case publicly readable in committed LOG entries and a consumer project name shipping inside the installed plugin. Claude edited seven files inline to scrub them, with no work item, no scope and no /next — breaking plan.md's first ground rule. **The call was right and would be made again**; deferring an actively-spreading exposure so the paperwork is tidy is the wrong trade. But nothing permitted it and nothing recorded it.
**The decision (2026-08-04): the gate ASKS, it never denies.** Modelled on the existing subagent gate, which returns `ask` rather than `deny` and is the method's precedent for expensive-but-legitimate. Reasoning, and it is the load-bearing part: denial is right during a **build**, where the file list was agreed in advance so a surprise means drift. In **/plan** there is no agreed list to drift from — the session is a conversation, the user is present, and a legitimate write can be authorised in one word. A denial there would block work the user is actively asking for.
**Evidence from the processing session itself.** That /plan wrote QUEUE.md and `_plan.md` — and moved a document into `resources/research/` at the user's request. That third action would not have been on any sensible whitelist and was entirely ordinary. A deny-list would have blocked it; an ask surfaces it and costs one word.
**So the whitelist is a quiet-list, not a boundary.** QUEUE.md, `_plan.md`, SPEC.md and `LOG/` pass silently, because /plan writes them by design and prompting for each would be unusable. Everything else asks. Note this makes the gate *weaker* than a scope-lock and that is deliberate — its job is visibility, not containment. A planning session that edits a shipped hook should not be stopped; it should be unable to do it *unremarked*.
**The emergency path dissolves rather than getting built — a mechanism removed, not added.** With ask-never-deny, the user's explicit go-ahead is structural: the scrub would have surfaced an ask, the user would have said yes, and the record would exist. What the capture called an emergency path is therefore just the gate working. Two smaller things remain, and neither is an override:
1. **The record duty.** A write approved through the gate that departs from the session's normal shape is named in the LOG entry — what was changed and why. Cheap, and it is what makes the departure auditable rather than invisible. Handed here from [sanctioned-override-mechanism], which found this the one part of its original framing that survived.
2. **Actively spreading vs sitting still — a red-flag triage rule, not an override.** A risk *sitting still* in the queue can wait for /next; a risk *actively spreading* — published, installed, being served — cannot. The method has no word for that difference, and it is what made the 2026-08-03 call obvious. It belongs with the red-flag rules as a triage question ("does this wait?"), not with any exception machinery.
**What was rejected and why, recorded so it isn't re-proposed.** A deny-list plus a named emergency exception. It fails twice: it blocks ordinary planning work (the `resources/research/` move), and an exception convenient enough to cover a real emergency is convenient enough to be reached for when it isn't one — the bound problem the capture itself named. Ask-never-deny has no exception to abuse because it forbids nothing.
**Files:** `plugin/si-plugin/hooks/pre_tool_use.py` (a planning-session ask gate — reuse the subagent gate's `ask` shape and its "declining is a normal, safe choice" framing), `SPEC.md` (correct the scope-lock description — one edit shared with [build-scope-vs-described-work-unenforced]), `docs-b/plugin-behaviour.md` (the spreading-vs-sitting-still triage with the red-flag rules), `docs-b/done.md` (the LOG record duty at close), `docs-b/plan.md` (the never-build ground rule now has an honest account of what the gate does), plus a FAQ entry — a new prompt appears in planning sessions, which is user-visible. #### State the missing-rule-vs-sanctioned-override distinction once — four captures were misread as one override mechanism [sanctioned-override-mechanism]
By Claude, from the scope-lock audit at `resources/research/scope-lock-audit.md` (§8.3); filed and re-scoped at processing 2026-08-04. **The original framing — build a general override mechanism because four captures circle one — was tested at processing and does not hold.** It is recorded here rather than dropped, because the reasoning that killed it is what makes the remaining work worth doing.
**The four cases, and what each session actually lacked.**
- **[plan-scope-lock-gap-and-emergency-path]** — Claude scrubbed seven files inline during /plan to stop an active exposure. A rule existed ("never build during /plan"), was **right**, and had to be broken anyway.
- **[skill-docset-override-unsanctioned]** — the skill named docset A, Claude read docset B. **No rule existed** for the host's routing disagreeing with the project's model target.
- **[plan-skill-did-not-engage]** — a /plan procedure followed with no skill around it. **Nothing detected it**; no departure was chosen at all.
- **[drive-testing-signals-skill-routing]** — `[user]` verification driven informally in a post-close tail. **No routing rule** for "I want to verify something."
**Only the first is a departure.** In the other three there was no rule to break — and you cannot depart from something never written. Calling them departures makes the remedy look like *permission* when what was actually missing is *authorship*. The docset case wants a precedence rule, not an override path: state what happens when host routing and project config disagree, and following it stops being a departure at all.
**So the general mechanism would be built for a population of one**, and that one is already designed further elsewhere — [plan-scope-lock-gap-and-emergency-path] specifies its trigger, its mandatory record and its bound. Building a general form here would re-derive that item's work at lower resolution and settle its shape by accident.
**What this item becomes.** State the distinction once, in plain terms, where a session will meet it: when you hit a moment the rules don't cover, decide which of two things is true — **a missing rule** (write it, capture it, don't act on it now) or **a right rule that must be broken in this instance** (the narrow override, which is not yours to invent and carries a mandatory record). That is a short passage, not a mechanism.
**Why it earns its keep rather than being bookkeeping.** Four separate sessions hit this fork and none had the distinction available; each improvised, and each improvisation was captured separately as its own problem. Without it stated, the next novel case re-derives it a fifth time. It also has an active job — it is the thing that stops a session reaching for an override when what it should do is capture a missing rule, which is the more tempting and more damaging of the two errors. That active-recurrence-prevention test is the one [decided-no-has-no-home-rule] proposes for deciding what needs a loaded home versus a LOG entry, and this passes it.
**What is handed off rather than solved here.**
- The single genuine override -> [plan-scope-lock-gap-and-emergency-path], which owns its trigger/record/bound.
- The two undetected cases -> detection, not sanction. [docset-routing-mechanism] is the relevant build; a sanctioned path helps only where the session knows it is departing.
- The precedence rule for host-vs-project disagreement -> [skill-docset-override-unsanctioned], which should now be processed as "write the missing rule," not "sanction the override."
**The record duty is the one part that survives from the original framing unchanged:** a departure that is not recorded is indistinguishable from a violation. Whatever else, the LOG carries it.

No SPEC change; nothing user-facing changes. Docset A is frozen. #### Verify an item's load-bearing factual claims at the moment it is processed — captures rot and nothing re-reads them [unprocessed-blocker-claims-go-stale]
Captured by you 2026-08-02 when [migration-recipe-freshness] was processed; widened at processing 2026-08-04 after the same failure recurred twice in one session.
**The original catch.** [migration-recipe-freshness] said it was "gated on [migration-checklist] existing first — the recipe this keeps fresh isn't built yet." That recipe had shipped the previous day, 130 lines, present in both docsets. The item had been sitting unbuildable on a premise that stopped being true.
**The hole is specific.** /plan's below-line revisit re-checks lift-conditions every session — but only for items *below the readiness line in Processed*. A claim stated as prose inside an Unprocessed capture is re-read by nothing. Those claims are written at filing time, when they are true, and then quietly rot.
**Widened 2026-08-04, because the two fresh instances were not blockers at all.**
- **[next-over-warns-run-length]** rested on "/next warns a run is too long," implying a rule telling it to. Grepping both docsets found no such rule and three statements of the opposite. The whole item's fix direction reversed.
- **[session-start-payload-oversized-and-misordered]** rested on "under docset B the payload is 3,524 characters." Measured live: 54,886. The item's stated reason for not being ready — that the docset fix might dissolve it — was false.
Neither was a stated blocker. Both were **factual premises**: what the docs say, what a number is. So the check is not "verify the blocker," it is **verify the item's load-bearing factual claims before discussing it on its own terms** — a stated blocker being one kind of load-bearing claim, not the category.
**What makes a claim load-bearing, since the check must not become a fact-audit of every sentence:** it is one the item's *disposition* rests on. If the claim were false, would the item change shape, priority, or readiness? Both of today's would have, and did. Background colour would not.
**The fix stays where the capture put it: at the moment of processing.** That is exactly where all three catches happened — read the claim, verify it still holds, before the discussion. One item, one check, only when the item makes such a claim, so cost scales with work being done rather than with queue size.
**Rejected, and worth keeping recorded: a staleness sweep at the /plan close.** Unprocessed holds around thirty items; re-checking every claim in all of them each close is the diff-everything-every-session cost the method fights, the same trap the SPEC-seeding trigger was narrowed to avoid. It would near-always find nothing, and a check that near-always no-ops is one that gets skipped.
**Why it needs writing down at all:** all three catches happened because Claude happened to check, not because any step asked. That is precisely what stops happening in a fresh short session, which is the design target — and two of the three were caught only after the item had already been half-discussed on a false premise.

#### Write approval-time text straight to its doc and link it, instead of pasting in chat — remote the only exception [write-first-link-dont-paste]
Captured by you (2026-08-02), processed the same day. Approval-time text whose destination is a Throughliner doc — a capture, a work item, a LOG entry, a SPEC or CLAUDE.md edit — is written to that doc first and surfaced as a link, and the user approves against the file rather than against a chat paste. **Remote mode is the only exception:** on a phone, opening the file is impractical, so the text is surfaced inline there as it is today. Two supporting parts from the capture: any draft that *is* shown in chat carries a link to the line it concerns; and pointer-style asks ("shall I go to it?") are hollow without either a working link or, in remote, the surfaced text — so they go where the link does.
**The strongest argument, which the capture didn't state: this deletes a branch rather than adding one.** The render rule today has two cases — doc-resident text gets a pointer, text not yet written is always inline "since there's nothing to point at." Write-first removes the second case entirely: write it, and it's resident. One rule instead of two. Lead the build with this.
**Boundary — doc-destined text only (settled at processing).** Not every approval-time output is headed for a file. A commit message isn't (Claude runs the commit), and neither is a recommendation or an option set. Those keep today's behaviour, because there is nothing to write them to and no link to give. Without this clause the rule would try to write a commit message somewhere in order to link it.
**The reject path must be specified, not assumed (settled at processing).** "Revert on reject" is load-bearing and isn't free: nothing is committed mid-session, so reverting means editing the text back out, and getting it wrong leaves rejected content in the file. The build states plainly what happens on a no — remove exactly what was written, confirm by re-read, say so. This buys back explicitly the safety that showing-first currently gives for free.
**What is genuinely lost.** A transient window in which a tracked file holds unapproved text. If a concurrent session or a crash lands in that window, unapproved content persists. Small but real, and it interacts with [concurrent-session-support].
**This inverts a load-bearing rule deliberately.** plan.md's "never write to QUEUE.md without showing the exact text first" exists so approval attaches to shown text. Approval still attaches to exact text here — arguably more so, since the user reads it in final rendered position — but it moves to *after* the write.
**Link behaviour is settled (2026-08-03), and the constraint is load-bearing.** Tested live on the desktop app (2.1.219): a plain relative `.md` link opens the file, always at the top; a `.md` link with a `:N` line suffix is **dead** — the click does nothing; a `#heading` anchor is ignored but harmless; a code-file link with `:N` opens at the exact line. Filed as anthropics/claude-code#83475.
**So the build must never emit a line-anchored link to a `.md` file** — that is the one form that fails, and it fails silently while still looking clickable. Code files keep their line anchors.
**And because a markdown link can only reach a file, never a position, every pointer carries the target's exact heading text** so the user can search straight to it rather than scanning. This is not decoration: landing at the top of a 480-line queue and being told "it's in there" is the failure mode the pointer has to avoid, and searchable heading text is what converts a scan into a copy-paste. The user chose this over the alternative of pasting fresh drafts inline, on the grounds that the heading text makes the search cheap and it is the version that actually cuts the token cost.
**Lift-condition: cleared 2026-08-03.** Link reliability was the only thing holding this below the line, and it is now understood and dependable within the constraint above. Ready to build.

A pasted draft cannot be claimed without being produced; a pointer can. So the build should carry the write-verify-point order explicitly rather than assuming the existing plugin-behaviour.md rule covers it — that rule exists and did not prevent this.
**Convergence:** this is the ordering flip [approval-flow-token-doubling-simplification] identified, reached independently from the user's side and *not* gated on the harness feature that item waits for — it is a pure method ordering change. Design the two together; they may collapse into one build.

#### The `captured by you` credit is unreliable in two ways: it only resolves for one reader, and it gets applied wrongly with nothing to catch it [provenance-credit-second-person-ambiguous]
Captured by you 2026-08-03 — you asked who "you" refers to in a provenance line, then challenged a credit that turned out to be wrong.
The credit means the project's user, and the convention is deliberate: [provenance-labelling-reconsideration] shipped at `ea272f6`, dropping mandatory provenance for an asymmetric default-AI scheme where an unmarked item is Claude's and only a user-raised item carries a credit. **That decision is not in question** — the asymmetry is sound and cheap. Both problems below sit inside it.
**Problem 1 — it resolves only for one reader.** The credit is direct address, so it works only if the reader is the person it was written for. That always holds in a solo project. It stops holding for a repo that goes public ([scrub-gate-before-approval], [setup-repo-privacy-and-publishing]), for a project handed on, or for any second reader — where "captured by you" points at nobody identifiable.
**Problem 2 — and this one is worse — the credit gets applied wrongly, and nothing catches it.** Live instance the same day: [reorder-mover-marker-at-top-blind] carried a `captured by you` credit from filing. **Why that's the more serious half.** An ambiguous credit is a reading problem; a wrong credit corrupts the record. #### Test explicit structural delimiting on plugin-behaviour.md as a second harness experiment — the better-evidenced lever we hadn't considered [structural-delimiting-experiment]
