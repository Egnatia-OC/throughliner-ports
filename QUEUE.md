#### The queue lint flags the section preambles /setup itself scaffolds [lint-flags-scaffold-preamble]
Reported by another project running this plugin (INBOX message, 2026-08-14; host 1.20.0-test5, build stamp 0e82374374d9). The QUEUE.md structure lint fires two advisory flags on every PostToolUse invocation — every Bash call, every Edit — saying the prose under `## Processed` and under `## Unprocessed` "belongs to no work item" and "has no `####` heading above it in this section".

**Checked against the mechanism rather than taken on the report's word, and the report is right.** `_check_orphaned_prose` in `plugin/throughliner/hooks/post_tool_use.py` exempts a line beginning `>`, and its own docstring says why: /setup scaffolds each work section's description paragraph as a blockquote, positionally identical to a destroyed first item's stranded rationale, so form discriminates where position cannot. But `docs-b/setup.md`'s QUEUE.md scaffold writes both preambles as plain paragraphs, not blockquotes. The exemption and the scaffold disagree, so every project set up by the shipped /setup trips the check forever.

**Why it matters past the noise, in the reporter's own framing:** the flag's text warns that a destroyed or missing heading leaves rationale orphaned exactly like this — which is the corruption the hand-move fallback exists to catch. Firing it on every tool call in every session trains sessions to skim past it, so a genuine overwritten heading arrives looking identical to the two that are always there.

**The fix, settled at processing: scaffold the preambles as blockquotes.** The wider alternative — exempting all prose between a `##` section heading and that section's first `####` — was weighed and refused. It repairs every existing project at once with no migration, which is its real advantage, but it widens the hole the check exists to guard: a first item whose heading is destroyed leaves its rationale in exactly that position, and the wider exemption stops catching it. The narrow fix keeps the check's teeth against the expensive case. The user chose the narrow fix.

**Files, and what changes inside them.** `plugin/throughliner/docs-b/setup.md` only: in the QUEUE.md scaffold, prefix each of the two section preamble paragraphs — the one under `## Processed` beginning "Vetted work, ready to build" and the one under `## Unprocessed` beginning "Captured ideas and tasks not yet fully processed" — with `> `, making them blockquotes. Nothing else moves. `post_tool_use.py` is already correct and is not edited; its docstring already describes the blockquote form as the scaffold's shape, so this build makes the scaffold match the hook rather than the reverse.

**Migration for already-adopted projects: nothing new is built, and that is checked rather than assumed.** `migrate-checklist.md` rule 3 names the QUEUE.md header prose as method-shipped boilerplate refreshed by re-copying the current shipped template, so any project that migrates for any reason picks the blockquote form up for free. No step is added there.

**No `FORMAT_EPOCH` bump, deliberately.** The epoch's bar is that an existing project's files become structurally *wrong*; these files are not wrong, they are noisy. Bumping would halt every consumer project on a migration prompt over two advisory warnings, which is the crying-wolf failure the epoch rule exists to prevent.

**The accepted residual, stated rather than left to be discovered.** A project already adopted, which never migrates again, keeps emitting both flags until someone edits its QUEUE.md by hand. That is a real cost of choosing the narrow fix and it is being accepted, not solved. The one-line repair is available to any session that cares to make it.

#### `py -c` escapes the script-write guard, and it is the invocation this project's own rules recommend [py-dash-c-escapes-the-script-write-guard]
Filed 2026-08-13 by Claude from a live instance in its own post-close tail. Filed after the last committed close, so it belongs to no committed session record.
**What happened.** During a rezip, the version in `plugin/throughliner/.claude-plugin/plugin.json` was bumped by running `py -c "..."` with a `open(p,'w')` inside it, rather than by using the editing tools. `pre_tool_use` is supposed to block exactly that and did not. The file was read back and was correct, so no damage was done — the finding is the silence, not the outcome.
**The cause, read off the hook rather than guessed.** `PY_INVOCATION` is `\bpython[0-9.]*\b|\bpy\s+-[0-9]`. That catches `python`, `python3`, `python3.13` and `py -3.13`, and misses `py -c`. The write-call detection downstream never ran, because the invocation half of the test failed first.
**Why this is worse than an ordinary pattern gap.** This project's own scripting constraints, in `CLAUDE.md`, tell sessions to use `py` rather than `python` on this machine, because `python` resolves to Inkscape's bundled interpreter. So the guard covers the invocation the rules steer sessions *away* from and misses the one they steer sessions *towards*. #### Design the standing audit set that maintains the rule corpus once the cleanup is finished [standing-audit-programme]
**Captured by you 2026-08-14, in your own words: design the routine audits that you will run in the future and maintain the full corpus once we're done.** The reasoning below came out of that discussion — your strategy is yours, the argument about what it can and cannot retire is Claude's, and you asked for it to be captured.

**Your strategy, recorded first because the design serves it.** Dedupe and de-contradict the corpus first, to cut the word count and therefore how much there is to process; then design the audits and edits that put the final finish on the method rules, converting them into the law-prose style; and then, once the always-loaded self-authoring rules are doing their job, stop needing to run these audits at all.

**The sequencing is right and is not what is being questioned.** Deduping before restyling is correct for a concrete reason: a restyle pass over a corpus holding four copies of one rule restyles it four times and creates four chances for the copies to diverge. Cutting first means each rule is rewritten once. The `done-plan.md` merge processed the same day is that shape in miniature — four items, one file, one judgment applied consistently, where deciding them apart would have answered the same question four times inconsistently.

**Where the strategy overreaches: the self-authoring rules govern ADMISSION, and audits catch DRIFT. They are different jobs.** Admission asks whether a rule should exist, worded this way, in this file — it fires when someone is writing a rule. Drift is what happens to a correctly-admitted rule *afterwards*, when something else changes around it and the rule is left describing a mechanism that no longer exists. **No admission gate can prevent drift, because the cause arrives after admission.** Three items in the queue at the time of writing are pure drift and every one passed admission cleanly: [done-md-names-a-repealed-clear-step], [adopted-claude-md-describes-retired-structure], [docs-b-name-outlives-the-two-docset-model]. A perfect gate produces all three anyway.

**The harder evidence, which is that correct wording does not make a rule fire.** The corpus documents at least four instances of an always-loaded, correctly-worded rule failing: the provenance rule, shipped and deliberately sharpened, still not holding ([invented-rationale-compounds-past-the-shipped-rule]); the file-the-blocker rule, unambiguous and explained by the user five to ten times in a month ([nothing-blocks-it-read-as-a-dead-end]); the INBOX-opening step skipped in the very session that authors it ([inbox-open-step-not-enforced]); and the subagent-cost rule broken hours after being read. The provenance item already draws the conclusion in terms: "state the rule again, or state it harder" is no longer a candidate direction.

**The rule board is this experiment already run.** It was built on the theory that the rules could watch themselves, and it reported clean while five real rule defects shipped in the same session — see [rule-board-measures-paperwork-not-health], settled the same day as keep-and-rename for exactly that reason.

**What the strategy genuinely buys, which is substantial and is not being dismissed.** Fewer rules and no duplicates means fewer sites where drift can occur, and each future retirement ripples to fewer places. An audit over a deduped corpus costs a fraction of one over the corpus as it stands. The win is real; it is a change in cost, not in necessity.

**So the goal is reframed rather than abandoned: not eliminate the audits, but make them cheap enough to run routinely without dreading them.**

**The design test this item applies, and it is the actionable part.** What retires an audit class is a **mechanical check, never a prose rule.** The queue lint and the digest genuinely removed the need to eyeball queue structure, because code reads the whole file and cannot skim. So for each drift class the standing set would cover, ask first whether it is mechanically detectable: if yes, build the check and retire the audit; if no, the audit stays and gets a trigger. The board's retired-terms check is an existing instance of the first kind.

**What this item must produce.** The standing set itself — which audits, what each reads, what triggers each one, and how the user runs it without needing to remember it exists. A siteless audit is the failure this project has now recorded five times.

**One risk to design around.** The law-prose restyle is itself a large authoring pass over the whole corpus, and every rewrite is a chance to reintroduce what was just cut. It should be the last big pass and should be audited *after* rather than trusted to verify itself — the party doing the restyling is the party that would certify it, which is [rule-admission-has-no-independent-approver].

**The finish line this set takes over from is already assembled**, in the same session that captured this item: twenty-two remaining items in five groups plus [law-prose-restyle], with five stated finish conditions. It lives in this session's LOG entry rather than in a queue item, because it is a record to be read rather than work to be done — the item that was going to produce it was resolved in-session and deleted, since its only output would have been queue items and planning work belongs in planning.

**Two of the five finish conditions are already mechanically checkable** by `resources/rule_signals.py` as it stands — no live rule naming a retired term, and no near-duplicate rule pairs. That is this item's own design test paying off before the design starts: the standing set inherits two conditions it never has to audit by hand, and should look for more of the same before proposing any audit that a script could do instead.

**Files (rough):** not yet derivable — the output is a designed programme, and its file list depends on which checks turn out to be mechanical. Likely `resources/method-compliance-audit-checklist.md` (which already holds the criteria for the periodic three-lens sweep and is the obvious home), `resources/rule_signals.py`, and `CLAUDE.md` for whatever trigger the set gets. Host-only — consumers do not maintain the method's rules. Relates to [law-prose-restyle], which is the last piece of cleanup this set follows.

#### Convert the method's rules to the law-prose style — the terminal pass of the cleanup [law-prose-restyle]
**Filed 2026-08-14 while assembling the remaining-cleanup inventory (recorded in that session's LOG entry), from finding it absent.** The restyle is the final step of the user's stated strategy — dedupe, then "put the final finish on all the method rules, putting them all into the new law-prose style format" — and it existed only in conversation. **What it is.** A pass over the method's rule text converting it to the wording style the rule gate already specifies — state the action the rule requires rather than the prohibition; express a qualification as structure rather than explanation; main clause first, conditions after; one idea per provision; every exception at the same level as the rule it qualifies. **Why it runs last, and this is a hard ordering rather than a preference.** A restyle over a corpus still holding duplicates restyles each copy separately and gives every copy its own chance to diverge — so it must follow the deduplication work (inventory group A) and the drift work (group C), not run alongside them. **Not designed here, and the scoping question is real.** Whether it runs whole-corpus in one pass or file by file, and whether `skill-nonspecific-rules.md` alone captures most of the value — it is the only file loaded in every session — are the same trade-offs [rationale-audit-second-pass] weighs, and the two should be scoped together since both are per-paragraph passes over the same thirteen files.
