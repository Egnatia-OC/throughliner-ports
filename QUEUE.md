- **[deferred-roll-testzip-blind]** The deferred-test roll's host-side freshness check is blind to test zips, so it can give false "live" readings. The roll resolves "is the host carrying the latest target changes?" by comparing release base versions — host base ≥ target base ⇒ all host-side changes live — and it ignores the `-testN` suffix. But in this self-hosting project the host catches up to the target when a test zip is rezipped and reinstalled, and a rezip moves only the `-testN` suffix, never the base. So the check literally cannot see that a test build was installed, even though that is the real freshness event.
  Why this is wrong, not just imprecise: between releases the target base version is static — it bumps only at push. Build batches add changes to the target without moving the base. A host installed from the last release then compares as equal to the target base, so the rule announces "all host-side changes are live" when none of the unreleased changes have been reinstalled. The `-testN` suffix is the only signal a private rebuild happened, and the rule discards it. The check is only sound right after a push+reinstall or a rezip+reinstall; in the ordinary dev window (unreleased build changes piled up under a static base) it reports false "live."
  Surfaced 2026-06-22 in a /plan session: the roll was resolved as "host 1.14.0 == target 1.14.0, so host-side lines are live."
