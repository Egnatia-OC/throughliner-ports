#### Emit the resolved blocker graph from the session-start hook, and read a mechanical digest at /plan Step 1 instead of the whole queue [hook-emits-counts-not-the-graph]

**The build.**
1. `_queue_dependency_facts()` gains a fourth bucket: held items whose blocker slug sits in **neither** section. That bucket is the lift signal, and it is one intersection away from the two the function already computes. The emitter names those items and their dead blocker slugs, carrying the queue lint's caveat that of the three causes — shipped and removed, in flight in a build, or a wrong reference — only one is a fault, so LOG is still checked before anything is lifted.

3. `plan.md` Step 1's read-state runs the digest in place of reading QUEUE.md whole. Full prose is read per item at the moment that item is presented, which Step 2 already does at its checkpoint re-read — so Step 2 barely changes. **The digest is a script /plan can re-run on demand, not only a one-shot read at Step 1.** Added 2026-08-11 from the user's question about whether the hook could show the graph again mid-session: it cannot — `session_start` fires once, so its facts describe the queue as it stood *before* the session touched it, and a /plan that has processed a dozen items is reasoning against a stale picture from then on. **Why the digest strengthens the safety rule rather than trading it away, and this is the reason the wider option was chosen.** The page-to-the-end rule exists because a truncated read is indistinguishable from a complete one to whatever reasons over it. A digest generated from the whole file by code cannot be silently truncated. So the guarantee is better than paging gives, not weaker.
**The cost and the failure mode, stated rather than discovered.** This is a new script plus a change to a read-state, where the narrow option was a few lines in a function that already computes everything it needs. **What is not at fault, so the build does not chase it.** This step is none of the four reorders [processed-reorder-mostly-unnecessary] repeals. Nor is the mechanical mover the cost: it ran three commands byte-for-byte and its em-dash echo came back clean, which is incidentally a second observation bearing on [mover-encoding-fix-verification]. The cost is entirely the re-derivation upstream of it.

**DESIGN PROGRESS — 2026-08-11. Decision 1 of the design: Constraint A wins over Constraint B, and "cycle" is retired as the organising word.** Proposed by Claude, agreed by you.
**The contradiction that forced it.** Constraint A says no stage may be downstream of another completing — each fires on its own trigger whether or not anything else ran. Constraint B says every session must know where the cycle currently stands, read as state at session start. These cannot both hold. If every stage fires independently there is no current stage: all five are always live, each waiting on its own trigger, and B's "where the cycle stands" has nothing to point at. If there is a real position in a cycle, A is already broken, because a position only means anything when stages follow one another.
**The resolution: five independent mechanisms, and a status board rather than a position.** Three reasons, in the order they carried.
1. "Cycle" is inherited vocabulary from the merge cycle, which is the thing that failed. That was positional — branch → blitz → soak → differential audit → reconcile → merge — and the user's recorded words are that it "is still a total mess that looks different every single time." Cause 4 was compression sitting permanently downstream of machinery that never ran. A positional cycle reproduces cause 4 by construction.
2. Constraint D wants inaction to produce a signal. Five mechanisms each emitting their own signal *is* a status board, and a board is readable at session start — which satisfies B properly, just not as a position.
3. It makes the thing buildable. Five independent triggers can be designed and shipped one at a time, in any order. A cycle has to land whole, which is what has defeated every previous attempt.
**Constraint B is therefore reinterpreted, not dropped.** The state a session reads at start is *which stages are currently signalling*, not where the project sits in a loop. B's requirement — that this is state the project holds rather than knowledge carried in the user's head — is fully preserved and is arguably better served, because a board cannot be misremembered.
**What is given up, stated so it is not rediscovered as a loss.** The project no longer has a rhythm in which a release closes something and a new pass begins. That was the user's own placement — the cycle may end on a release, or begin after one — and it goes away under this reading. A release becomes just another moment, with no phase attached to it.

**Decision 2 of the design: the board is computed from the artifacts each session, never stored.** Claude's call, taken rather than put to the user, on the user's instruction to keep going.
A stored state file must be maintained, and cause 2 of the merge cycle's failure was that nothing enforced any phase. A state file inherits that failure exactly: the first session that forgets to update it makes the board lie, and a lying board is worse than no board. Computed state cannot go stale. It also matches Constraint B's own wording more closely than a file does — the queue is *read* at session start, not maintained as a separate state record — and it follows the principle established twice elsewhere this session, that anything a hook computes costs no model attention.
**The known unevenness, recorded because it will shape the stage designs and must not be mistaken for a defect in Decision 2.** The five stages are not equally computable. Measured is exact and cheap (count instructions across the always-loaded files). Audited is clean (date of the last sweep, read off LOG). Born is approximate at best. Maintained and Repealed have no computable signal at all, because neither has a mechanism yet, so there is nothing whose absence could be measured.
**Stage design — MEASURED. Signal: a structural rule-statement count across the always-loaded files, calibrated against the one hand count on record.** Claude's recommendation, agreed by the user.
The count is of structural rule-statements — bullets, bolded lead-ins, and lines inside the typed blocks — produced by a script, not by judgment. **The point that decides the shape: a signal does not need the true count.** It needs a figure that moves when the corpus grows and holds still when it does not. A proxy consistently off by a fixed factor works; a measure that is sometimes exact and sometimes not does not. Calibrating the proxy against the 2026-08-09 hand count of ~218 also gives the threshold a stated derivation, as [derivation-required-for-limits] will require — the 150–200 ceiling is re-expressed in the proxy's own units rather than left as a bare number in a different currency.
It behaves correctly under eviction, which is why this proxy and not another: consolidating three bullets into one genuinely lowers the count, which is exactly what the maintenance techniques are for.
**The rejected alternative and the cost accepted.** A plain word count is more robust to formatting changes but sits further from "an instruction" and is harder to argue as a derivation. Either way the cost is the same and is accepted rather than solved: the number stops being the thing the research measured. The 150–200 ceiling came from research about instructions, and what gets tracked is a proxy for them.

**Stage design — AUDITED. Signal: the three-lens sweep fires when the count Measured already computes is over the ceiling.** Claude's recommendation, agreed by the user.
Today the sweep (`resources/method-compliance-audit-checklist.md`) has no trigger and runs only when a /plan happens to file an `[audit]` item, which is how the corpus reached ~218 before anyone counted.
**The obvious alternative — audit every N sessions — fails twice.** N would be a bare number with no derivation, which [derivation-required-for-limits] bans; and a periodic duty is exactly the post-legislative-scrutiny shape Constraint D's research condemns, at 7.6% coverage.
**Keying it to the count avoids both and adds no machinery.** The threshold is already derived, the measurement already exists, and the relationship is the honest one: being over the ceiling *is* the reason to run a sweep, because rules accumulated past what a session can hold are what the three lenses look for.
**Constraint A is satisfied, and the reasoning matters for the other stages too.** Audited is not downstream of Measured *completing*: both read the same computed number independently at the same moment, and neither has to run first. If Measured were deleted, Audited would compute the number itself. Sharing an input is not the dependency Constraint A forbids — being gated on another stage having finished is.
**The gap accepted, and where it belongs.** Below the ceiling no audit ever fires, so drift that is not growth — a rule going stale, a prohibition that should have been an action — goes uncaught until the corpus grows across the line. That hole is real and is left to the Maintained stage rather than patched here.

**Stage design — BORN. Teeth: a close-time disposition line in the LOG entry, on a mechanically detected trigger.** Claude's recommendation, agreed by the user.
**Claude's own earlier assessment was wrong and is corrected here**, because the correction is what makes this stage buildable. Decision 2 recorded Born's signal as "approximate at best". It is not: the files holding method rules are an enumerable set, so a commit touching `plugin/si-plugin/docs-b/`, `resources/self-authoring-rules.md` or `CLAUDE.md` is visible from git with no judgment involved.
**The three parts.**
1. **Teeth** — a session that authored or amended a rule in the method's own text cannot close until its LOG entry carries a disposition line: the gate was run and what it decided, or it was not needed and why. Copied deliberately from FAQ-sync, the one mechanism in this project with proven teeth, and for its stated reason — a required artifact turns a silent omission into a visible one, because "not needed because X" is a claim a later reader can disagree with and a missing line is a gap anyone can see.
2. **Trigger** — mechanical, on the close's staged file set. This is *stronger* than FAQ-sync, whose own trigger ("is this change user-facing?") cannot be detected at all and has to ride a close-time read.
3. **Board signal** — LOG entries that should carry a disposition line and do not, computed by matching LOG against git.
**It over-fires, and that is the design rather than a defect.** Touching `docs-b/` for a typo is not authoring a rule, but a false fire costs one line — "not needed, typo fix". FAQ-sync makes exactly this trade and it is why it works.
**Residence: host-only, in `CLAUDE.md`, not the shipped done docs.** Consumers never author method rules, so the obligation would misfire for them. The item's own open question is answered the way it anticipated.
**The gate's admission test applied to this rule, which the item asked for as the honest test of it.** It passes on the cheaper route: this is an extension of FAQ-sync's shape to a second subject rather than a freestanding rule, so it is authored as an amendment and consumes no new slot.

**Stage design — MAINTAINED. Signal: near-duplicate rule statements detected across the corpus.** Claude's recommendation, agreed by the user.
**The trap avoided, named first because it is the one this whole item exists to escape.** The natural design is "maintenance is what you do when the audit tells you to", and that is a direct Constraint A breach — eviction downstream of Audited running is cause 4 of the merge cycle verbatim, compression permanently behind machinery that never ran.
**Why duplicate detection is the right independent signal.** It *is* codification — one subject, one rule, stated once — which is the eviction technique the gate never absorbed at all. It is mechanical: near-match detection across the always-loaded files needs judgment only to resolve a flag, never to raise one. It catches drift that is not growth, which is precisely the hole Audited's ceiling trigger leaves open. And it rests on evidence rather than invention: four filed findings are this exact shape — [done-rules-section-duplicates-body], [next-rules-section-duplicates-body], [setup-rules-section-duplicates-body] and the cross-doc case in next.md — all four found by hand in a single audit by someone who happened to look, where a script would surface them continuously.
**The artifact half, re-homed rather than re-decided.** §2 Eviction — consolidation, recasting, the staleness test — plus "when moving a why, don't take an operative statement with it" splits out of `resources/self-authoring-rules.md` into a maintenance doc, exactly as this item already recorded. The user's rule was a document per procedure, keyed to where in the cycle it is opened; with the cycle retired that reads better rather than worse — **keyed to which signal opens it.** The duplicate signal names the maintenance doc.
**The cost accepted.** Near-duplicate detection produces false positives, since two rules may legitimately say similar things in different contexts. It is a flag for a human to judge, never a gate — the same standing as the placement-contradiction flags in [nothing-audits-the-cleared-region].

**Stage design — REPEALED. Signal: a live rule naming a term on the retired list.** Claude's recommendation, agreed by the user.
**This is where the sunset research finally transfers, and it had not been made concrete anywhere before now.** Constraint D established that a sunset clause works because inaction repeals while a duty to review fails because inaction is silent, and that time-based expiry does *not* transfer — no calendar pressure here, and a doc that silently expires is not safe. The transferable part was named as "the default-state principle, not the calendar", and nobody had said what that means in practice.
**The concrete form: retiring a mechanism automatically puts every rule that mentions it into question.** The retirement is the event; every surviving reference becomes a repeal candidate the moment it happens. Inaction — leaving the references standing — produces a visible signal. No number, no calendar.
**The evidence, and it is the most-repeated failure in the whole record.** Five FAQ entries documenting retired mechanisms; [claude-template-references-retired-test-flavor] inviting users to prepare for a retired test flavor; the retired "batch" vocabulary surviving across several docs. Every one found by hand, late, by someone who happened to look.
**What it needs to work: retirements recorded where a script can read them.** Today they live in LOG prose. The design is a short retired-terms list appended at the close that does the retiring, **folded into Born's disposition line rather than added as a second close obligation** — one line, one place, carrying both what the gate decided and what this session retired.
**Why a stored list does not contradict Decision 2.** Decision 2 says the *board* is computed. The retired-terms list is source data, like the queue itself — authored once at the moment of the event, not state that must be kept in sync with anything. The distinction to hold: derived state is computed, recorded events are stored.

**Decision 3: the board's delivery surface is the session-start read that [hook-emits-counts-not-the-graph] and [nothing-audits-the-cleared-region] are already building.** Claude's call, taken rather than asked, as low-stakes and following from work already cleared.
Those two items build `queue_digest.py` and extend the session-start facts emitter to carry computed flags. The five stage signals are the same kind of fact arriving at the same moment, so they ride the same surface rather than inventing a second one. This also means the lifecycle work inherits their constraints — chiefly the 10,000-character hook output cap, which bounds how much any signal may say.

**Decision 4: a signal that fires files a capture, once, and then gets out of the way.** Claude's recommendation, agreed by the user. This is the answer to the question that killed every previous attempt — what stops the board becoming wallpaper.
**Two options ruled out first.** Escalating a signal over time needs a bare number, which [derivation-required-for-limits] bans. Showing only *new* signals and going quiet on standing ones recreates silent inaction, which is the precise failure Constraint D exists to prevent.
**The design.** The board's job shrinks to one question per stage: is there an outstanding signal, and does it already have a capture? The work itself goes where all work goes — Unprocessed, ordered by the ladder, counting toward the throughput floor, impossible to ignore without the omission being visible in the queue.
**Three reasons it beats simply accepting a standing notice.** It matches the method's own routing rule exactly — a finding that reveals work to do becomes a capture, and a permanent banner is a finding that never became work. It converts inaction into accumulating cost rather than a flat notice, which is the sunset shape properly transferred: the default state does the work. And it stops the board being a thing anyone must read — nobody acts on a board; everyone already acts on the queue.
**Duplicate captures are the risk and the guard is cheap:** the signal counts as satisfied while an open capture with the matching slug exists.

#### A deleted blocker is indistinguishable from a shipped one, and the two documents that describe the case disagree and both omit deletion [deleted-blocker-has-no-branch]
Captured by you 2026-08-11 — you asked what happens to items whose blockers have gone stale or been deleted. The verification and the diagnosis below are Claude's, from reading both texts at processing time.
**The situation.** A blocker that is deleted leaves the held item naming a slug that is not in the queue. So does a blocker that shipped. From the queue alone the two are identical: both are simply absent.
**The two authorities disagree, and this was read rather than recalled.** `plan.md`'s below-line revisit says `blocker missing or not a real queue item -> a fault; surface it and fix it this session`. `post_tool_use.py:347` says the opposite — "three causes and only one is a fault: the blocker has already shipped and been removed, it is in flight (a run has taken it into `_build.md`), or the reference is wrong." **And neither lists deletion at all.** The lint's three causes are shipped, in flight, and wrong reference. Deletion is a fourth cause, and it is the only one where the correct response is neither lifting the item nor repairing the reference.
**Why deletion needs its own branch rather than folding into the others.** A blocker is deleted because someone judged it not worth doing, and that judgment frequently undermines the held item's own premise — the held item was designed on the assumption that its blocker would happen. **Why it fails silently, which is the reason it is worth building.** LOG *can* distinguish the two — a shipped item has a build entry, a deleted one is recorded in a /plan close's queue changes — but nothing instructs the session to look for that difference. The revisit says "read shipped-ness off LOG", and a session that finds no ship record has no branch to take: the cheapest available readings are "must have shipped, lift it" or "the reference is wrong, repair it", and both are wrong.
**The build — three parts, at two different moments, and the split is deliberate.**
1. **`plan.md`'s revisit gains a fourth branch:** blocker recorded as *deleted* in LOG → surface the held item for re-examination rather than lifting or repairing it. Surfacing, not deciding: re-examining a held item whose premise may have died is a fate decision, and those are the user's at /plan. This keeps the revisit's existing property that nothing else in it is a question for the user, by making this the one case that is.
2. **`post_tool_use.py:347`'s message is corrected to name four causes**, adding deletion. **The claim as it currently stands.** `SPEC.md` calls multi-item /next "unattended in practice — the autonomous build mode the Principles name", and the Principles say execution sessions trend toward pure execution, "stopping only for what genuinely needs the user". In practice a run stops in at least three ways: a `[user]` item is walked through live, one step at a time; a `[freeform]` item halts it outright; and at the end the run simply stops, because **/done is a command the user runs** — nothing closes the session on its own. So a run left alone finishes its builds and then sits there, uncommitted, until someone comes back.
**Why this is worth more than a wording fix.** The word shapes real decisions. `[user]` and `[audit]` lines are placed end-preferred *because* a stop inside a contiguous build run interrupts an otherwise unattended sequence — that rule only makes sense if the run is meant to be left alone. And the readiness line was made the run's sole bound on the same reasoning. If "unattended" is aspirational rather than true, several settled decisions rest on an overstatement.
**What a design has to settle, and your condition is the hard part.** Where `[user]` items land. Today end-preferred placement batches them at the end of the cleared region, which is the right instinct but only a tie-adjustment — a genuine dependency still puts a `[user]` item mid-run, and then the run stops in the middle whatever the word claims. Options to weigh: whether a truly unattended run must refuse to include `[user]` items at all and leave them to a separate walk-through session; whether the readiness line grows a second meaning (build up to here unattended, then stop for the human); or whether the honest answer is to stop calling it unattended and describe it as what it is — a run that clears vetted work and pauses where a person is genuinely needed.
**The self-closing half carries a real tension, not just work.** A run that ran /done on itself would commit without the user present, and the commit message is one of only two things the method still shows before it happens — precisely because a commit is hard to unwind and never becomes file content. So auto-closing either overrides that rule or needs a form of it that survives nobody being there. That has to be settled before, not after.
**Files (rough):** `SPEC.md` (the Multi-item /next paragraph and the Principles), `plugin/si-plugin/docs-b/next.md` (the run's stopping behaviour), `docs-b/done-plan.md` (end-preferred placement, whose rationale rests on this), plus an FAQ entry — a user reading "unattended" and walking away is exactly who this misleads. Relates to [arbitrary-run-length-capping] and [processed-reorder-mostly-unnecessary] (which keeps end-preferred placement on this same reasoning).
