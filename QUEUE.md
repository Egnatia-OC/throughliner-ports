# QUEUE

Two sections. **Processed** — work discussed and agreed, ordered top-to-bottom; /next builds from above the `--- Cleared to run above this line ---` marker. **Unprocessed** — captured, not yet fully processed; the next /plan weighs each item. A work item is a `#### ` heading (its description) with a `[slug]` at the end of that line and its rationale in the block beneath. A leading `[audit]` / `[user]` tag names how it's executed; no tag means a build. A work item carrying a security or privacy risk gets a `Red flag · State: …` marker — the flag rides the work.

#### Stop session_start silently writing a payload sample carrying the user's absolute path into their repo [session-start-writes-payload-sample-into-repo]
Split out of [audit-hook-doc-reconciliation] at its processing, 2026-08-07 (audit finding B6), because it carries a privacy risk the rest of that item does not and would have been built inside a documentation pass where nobody would look at it twice.
Red flag · State: cleared — cleared by designing the fix in-session, recorded here: the silent write stops, the committed file is deleted, and the already-published path string is routed to the history rewrite that is already going to touch every commit. The user was told plainly what was exposed and what deleting the file does and does not achieve.
**What the code does.** `session_start.py`'s `_record_payload_once` (`:259-277`) writes `resources/research/session-start-payload-sample.json` into the project whenever that folder exists. Nothing documents it — not SPEC, not the FAQ, not a procedure doc — so no user has any reason to know it happens or to look for the file.
**What was found in this project, checked rather than reasoned about.** The file exists, is **tracked and committed**, and holds `cwd` — the absolute path of the project folder, including the Windows account name. This repo is public, so that path is readable by anyone and is in the history permanently.
**The severity, stated in both directions so it is neither inflated nor waved off.** For this project it is a smaller exposure than one already known and queued: every commit here carries the user's real email address, which [history-rewrite-third-party-scrub] exists to remove, and that rewrite already rewrites every commit — so this path string can ride along in the same pass rather than needing an operation of its own. What makes it worth its own item anyway is the **mechanism**, which is consumer-facing: any user whose project has a `resources/research/` folder gets their own absolute path written there silently, with no doc telling them, no gitignore covering it, and every reason to commit it without noticing.
**The build.** Decide whether the sample is wanted at all — it was presumably written to capture a real payload for research, which is a one-off need already served, so deleting the mechanism is the honest default over gitignoring it or asking permission at runtime. Remove the write, delete the tracked file from this project, and add the `cwd` string to the replacement set that [history-rewrite-third-party-scrub] applies so the published copies go with the rest. If the mechanism is kept in any form, it must be documented in SPEC and the FAQ and must never write into a consumer's repo unasked.
**Say plainly at build time what deletion does not do:** removing the file forward does not remove it from the history, which is exactly why the rewrite is the route for the published copies.
**Files:** `plugin/si-plugin/hooks/session_start.py`, `resources/research/session-start-payload-sample.json` (deletion), and a note added to [history-rewrite-third-party-scrub]'s replacement set. Relates to [audit-hook-doc-reconciliation] (the parent it split from), [history-rewrite-third-party-scrub] (which carries the published half).

#### Make post_tool_use check adoption before writing the editing-state closing marker, so unadopted folders stop accumulating markers they never opened [editing-state-closing-marker-ignores-adoption]
Split out of [audit-hook-doc-reconciliation] at its processing, 2026-08-07 (audit finding B7). Kept separate because it changes a **published contract another application is built against**, which deserves its own scrutiny and its own log entry rather than riding inside a documentation sweep.
**The asymmetry, verified by reading both hooks at processing.** `pre_tool_use.py` returns early when `SPEC.md` is absent (`:564-566`), so the **opening** marker is written only in adopted projects. `post_tool_use.py` writes the **closing** marker at `:481`, *before* its `SPEC.md` check at `:486`. **The audit asked the user to decide which side moves; it does not need deciding, and that is recorded so it is not re-opened.** SPEC already states the intended behaviour in the editing-state contract's own limits: *"the signal only exists where the plugin is installed and the project adopted."* The documentation is right and the code contradicts it, so the code moves.
**One thing the build must not break.** post_tool_use's placement carries a deliberate comment — the closing marker is written before the **QUEUE.md** gate because the signal covers every edited document, not only the queue. That reasoning is correct and must survive. The bug is that a single `SPEC.md` check is serving two different jobs in that function: "is this project adopted" and "does the queue lint apply". Separate them, rather than moving the marker below a gate that exists for the lint.

#### Retire the "Plan session here" marker — it was documented in six places and never implemented in either docset [audit-plan-marker-implement-or-retire]
**Decided at processing, 2026-08-07: retire, the user's call.** The fork was implement-or-retire, and the two directions cost very differently — implementing means a new halt in next.md plus a place-and-remove step in plan.md, which the method then maintains and tests forever; retiring means deleting the references. **The honest cost, recorded so it is not discovered later as a surprise:** the readiness line marks *where* the boundary is and carries no *reason*. Retiring the marker gives up the ability to say why a particular point in the queue needs planning attention. Judged worth it, because a reason nothing acts on is a comment, and the item's prose lift-condition already carries reasons for the work it belongs to.
**The finding is worse than the capture stated, established by grep at processing rather than inherited.** The marker appears in **no procedure doc in either docset** — not only docset B, but the frozen 4.8 docset A as well. #### The `captured by you` credit is unreliable in two ways: it only resolves for one reader, and it gets applied wrongly with nothing to catch it [provenance-credit-second-person-ambiguous]

The credit means the project's user, and the convention is deliberate: [provenance-labelling-reconsideration] shipped at `ea272f6`, dropping mandatory provenance for an asymmetric default-AI scheme where an unmarked item is Claude's and only a user-raised item carries a credit. **That decision is not in question** — the asymmetry is sound and cheap. **Problem 1 — it resolves only for one reader.** The credit is direct address, so it works only if the reader is the person it was written for. That always holds in a solo project. **Problem 1 is resolved by the user's decision, 2026-08-05: record a real first name, an alias, or another identifier at /setup, and credit captures to it.** Claude had recommended a one-line queue-header explanation instead, on the grounds that a name writes a person into a repo that may be public. **The user's framing already answers that** — offering an *alias* gives multi-user disambiguation with none of the exposure, so the objection applies to a name-only design and not to this one. ```

                                     the user's own document
rejected: name-only, no alias     -> writes a real person into every item of a

kept:     an identity recorded at /setup — real name, alias, or other, the

   of a proposal        no rule at all today. An override is rationale arriving

**The gap.** Throughliner assumes one person, working with Claude, recording rationale as they go. A structural fallback was also raised: give the contributor an **area** of the codebase, so drift is contained at a boundary the log can honestly describe rather than interleaved through everything.
**What must not be lost at processing: the gap cannot be fully closed, and saying so is part of the answer.** Part of a shared project will have thinner history than the rest. That is a cost of having the collaborator, not a fault to engineer away, and a design that pretends otherwise will produce a mechanism nobody follows.
**Consumer-facing, not host-only.** Any user of this method who works with anyone else hits this, and it is invisible until someone asks why a decision was made and the log has nothing.

#### Claude corrupted QUEUE.md by editing against a line it had only seen truncated by a shell command [edit-against-truncated-shell-output]
By Claude, observed live 2026-08-07 during this session's own /next run, and filed under the standing rule that any observation of Claude's behaviour is a testing outcome.
**What happened.** To find the end of the queue, Claude ran `tail -3 QUEUE.md | cut -c1-120`, which printed the last lines **truncated at 120 characters**. It then used one of those truncated lines as the `old_string` of an Edit. Because Edit matches on substrings, the truncated text matched the *start* of the real line and the replacement was spliced into the **middle** of it, leaving the token `PLACEHOLDER` embedded in a work item's prose.
