**Audience-framing anchor and skill-output language audit**
The plugin ships to external non-coders, not the person developing it. Right now skill output leaks internal-mechanism language into the user's view — names like "(per why-pipeline)", labels like "staleness sweep", terms like "disposition", and meta-comments like "clear in its substance" all reference procedure-doc internals the user has never seen and has no context for. The opposite also happens: bare action labels surface with no user-facing context, leaving the user waiting through "sweep" or "verify" without knowing what's being checked. Both fail the same audience. Adding an audience-framing anchor in this project's CLAUDE.md is what prevents the next audit from being needed — once Claude is reading "the plugin's users are external non-coders" at session start, language choices in skill docs and live narration shift to match. The audit pass cleans up what's already there.

Build:
- This project's CLAUDE.md: add an explicit "Audience" section establishing that the plugin's users are external non-coders (not Alex), and that anything skills cause Claude to say to the user — chat narration, drafts, prompts, status lines — must read cleanly without referencing internal procedure terms. Place it where it'll catch the eye of any session editing skill docs.
- Audit pass A across the four skill procedure docs (setup.md, plan.md, next.md, done.md): find every instruction that has Claude surface a procedure-internal label or reference (rule names, phase numbers, pipeline labels, step references, terms like "disposition" / "staleness sweep" / "why-pipeline"). For each, either rewrite into plain English the user understands, or mark the line silent if the information is bookkeeping with no user value.
- Audit pass B across the same four docs: find every bare action label that surfaces to the user with no context (e.g. "sweep", "verify", named steps with no description). Rewrite each so the user knows what's being checked and why they're waiting.

Test:
- Re-read the four skill docs after edits. Scan for any remaining internal-term references and any remaining bare action labels. Report findings.
- Mentally walk through what each skill's chat surface would look like during a session (/setup, /plan, /next, /done) and check that nothing the user would see references internals they don't have context for.

**Pull "one item at a time" rule into behaviour.md**
Alex's global CLAUDE.md carries a detailed rule about sequencing multi-part responses — one per message when the next action depends on the previous, count upfront, no preview, alternatives are the one exception. The plugin currently delegates this to the user's CLAUDE.md via the tag-precedence note in behaviour.md, which means it only governs unlabelled steps and free conversation when the user has it set. On any install without that rule, skills' close-outs and walkthroughs become bundle-prone. The [SEQUENCE] tag already covers procedure steps that explicitly carry it, but the broader principle — applying to any multi-part response across the session — needs to be plugin behaviour, not user preference. The Communication section is the right home.

Build:
- behaviour.md: add a "Sequencing multi-part responses" rule under Communication. Cover: one item per message when the user's next action depends on the prior one, state the count upfront, don't preview upcoming items, close-outs and walkthroughs are where the pull to bundle is strongest, the one inversion is alternatives the user is choosing between (because the choice requires seeing them together).

## Captures

Captured outside /plan. Picked up and routed during the next /plan session.

- When /plan decides no Test section is needed for a batch, that decision should be [SILENT] — no need to narrate "no test section because..." to the user.
- /done hash backfill is self-defeating: it commits, writes the short hash into LOG/log.md + index.md, then `git commit --amend` — but amending rewrites the commit to a new hash, so the recorded hash never matches the final commit. Confirmed this session: commit was 13c4612, post-amend HEAD is 44ab617, LOG records 13c4612. Every entry is affected. Fix: record the hash in a separate follow-up commit instead of amending, or stop recording hashes and reference by date/summary instead.
- During /plan, the promote/park/drop call comes before the batch entry is drafted, so the user approves a direction without seeing concrete outputs — they can't fully know what they're approving. Two candidate fixes: (a) Claude frames the work in concrete-output terms when recommending promotion, so the call is informed; (b) move the promote question to after the entry is drafted. (b) risks repeated re-drafting and fatigue from re-reading full entries. Surfaced live this session: user approved promotion of a three-part conceptual item with nothing concrete in front of them. Overlaps with the parked Sizing-gates-rework idea (concrete outputs as the readiness gate).
- Add a "don't collapse rationale into structure" rule to behaviour.md. Reasons exist as prose. Don't force them into one-line summaries, dedicated why-fields, or typed taxonomies (e.g. "UX reason / functionality reason"). Both collapse meaning — a line truncates, a taxonomy is never complete. Preserving rationale means carrying the prose forward. Surfaced this session designing the why-pipeline; the why-pipeline batch encodes it specifically for capture→batch→log flow, but the general principle belongs in behaviour.md so it prevents the same mistake elsewhere.
- /next shouldn't dump the full batch at session start. A two-or-three-line summary is enough — the user can open QUEUE.md if they want the full text. Currently /next.md Step 1.4 instructs "Batch title and all entry text from QUEUE.md" which re-renders content the user already wrote and can read anytime. Surfaced live this session: full batch re-rendered when the user already knew what was in it.
- Commit messages should always be delivered as copyable text (code block or similar), not inline prose. In the desktop app, select + Ctrl+C copies the entire message rather than the highlighted text, so an inline commit message can't be lifted out. Alex updates the chat title to match the commit message every /done, so this trips every session. Fix candidate: done.md Step 2.4 instructs Claude to present the drafted commit message in a fenced code block when asking for approval. Same likely applies anywhere else a string is meant to be copied verbatim (push messages, paste-ready prompts).

- push-and-rezip step 8 doesn't stage sweep-modified files. The pre-push consistency sweep (step 2 Pass B) tightens prose in templates and skill docs to keep them aligned with procedure changes, but step 8's stage list — zip, archive, plugin.json, LOG/ — doesn't include whatever the sweep touched. Sweep edits get orphaned in the working tree, surviving across sessions until a future /done unwittingly bundles them into an unrelated commit. Surfaced this /done session: four files (plugin/si-plugin/docs/next.md, plugin/si-plugin/docs/setup.md, plugin/si-plugin/templates/CLAUDE-TEMPLATE.md, plugin/si-plugin/templates/faq-template.md) had prose-tightening from a prior push attempt sitting uncommitted; build edits to next.md and setup.md layered on top before the mix was caught. Recovered via `git checkout HEAD` on the two mixed files and re-applying just the build change; the two templates remain orphaned for the next push. Two failure modes worth deliberating: the staging gap itself (sweep can modify files step 8 doesn't track), and the cross-session persistence (orphans sit in the working tree with no signal at session start, so a later build can layer on top). Fix candidates: stage sweep-modified files explicitly in step 8, have the sweep produce a manifest step 8 reads, or surface uncommitted state at session_start so it's visible before a build begins.
