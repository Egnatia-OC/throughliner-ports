# QUEUE

Two sections. **Processed** — work discussed and agreed, ordered top-to-bottom; /next builds from above the `--- Cleared to run above this line ---` marker. **Unprocessed** — captured, not yet fully processed; the next /plan weighs each item. A work item is a `#### ` heading (its description) with a `[slug]` at the end of that line and its rationale in the block beneath. A leading `[audit]` / `[user]` tag names how it's executed; no tag means a build. A work item carrying a security or privacy risk gets a `Red flag · State: …` marker — the flag rides the work.

#### Give `[user]` handover items a complete lifecycle: handover names its close, a completion-ask detects done work, and /done + /plan can close a finished one [user-handover-lifecycle]
By Claude, designed in a 2026-07-26 /plan pass. Merges three captures — [user-handover-no-completion-path], [completed-user-line-no-closeout], [cleared-line-vs-upstream-queued-dep] — which are three views of one gap: once /next hands over a `[user]` item, nothing detects it got done, records it, or removes it, so a finished handover strands in Processed and /next re-hands it back as unbuilt (observed live: Metro admin 2026-07-20, scrolly-thing 2026-07-16).

**The design, settled in-session:**

**1. Handover names its own close.** When /next hands over a `[user]` item, it tells the user how completion gets recorded — run /done to record it, or raise it at the next /plan. Today the handover just stops, so the user doesn't know what closes the loop.

**2. Completion-ask on the next session.** When a session (/next pre-flight or /plan Step 1) meets a handed-over `[user]` item still in Processed, it **asks** "did you complete this?" rather than silently re-handing it over. Detection is by asking, not by scanning the filesystem for an expected artifact — decided against the artifact-check because it needs each `[user]` item to declare a produced file, which is fragile and often doesn't apply (a handover can be a device check, not a file). Artifact-check is left as a possible later enhancement, not built here.

**3. A defined close for a completed `[user]` item.** Log it under its slug and remove it from Processed. Lives in **both** /done (user runs /done right after finishing) and /plan (user completed it async and mentions it at planning), because completion can land either way. done.md's current "no /done closes a `[user]` line" is the exact text that changes.

**4. Dependent re-clearing is [plan-no-below-line-revisit]'s job, not duplicated here.** When a `[user]` item closes, the items it blocked (below the cleared marker) need re-evaluating for promotion — the same revisit machinery item [plan-no-below-line-revisit] asks for. This build records the dependency and leaves the general revisit to that item.

**Item 3's placement lesson is mostly already encoded** — plan.md's Step 3 already places ready `[user]` work above the marker and holds it below only for a pending prerequisite. This build's scope on item 3 is a verification pass of that wording plus, if it isn't crisp, one explicit anti-pattern note ("don't hold a `[user]` item below the marker merely because it's the user's to run").

**Files (self-scoped by /next):** next.md / next-build.md (handover names its close; pre-flight completion-ask); done.md + the done-family close routing (add the completed-`[user]`-item close, change the "no /done closes one" text); plan.md (Step 1 completion-ask; verify Step 3 placement wording); plugin-behaviour.md (the `[user]`-lifecycle rule); SPEC.md (user-visible change to /next handover and /done — syncs both descriptions); a faq-template.md entry + its index line (consumers meet the completion-ask and the new close); README feature-list check at build.

#### Build a mechanical queue-reorder mover in the plugin, so /plan's close-out sort is reliable at any queue length [reorder-has-no-move-primitive]
By Claude, from the 2026-07-24 /plan close and processed 2026-07-25. /plan's close-out reorder asks Claude to re-sort the queue sections, but the only edit tool is exact-string replace — so moving a work item means retyping its entire prose block verbatim, twice. Items run several hundred words, so on a long queue the sort silently degrades to a partial move (observed: this session moved only a three-item cluster and left the tail unsorted), and a single transcription slip would corrupt an item with no error. Decision (2026-07-25): fix it with a mechanical mover, not by accepting partial sorts (option a — gives up the sort the queue depends on) or by keeping items short (option b — contradicts the settled capture-authoring standard that items keep full detail for the user to co-read).

The mover is a script shipped **in the plugin package**, alongside the hooks — not the companion CLI. The companion CLI (from [session-sizing-and-break-lines]) needs a separate always-running process the project was wary of; the mover needs none — it runs once when asked, rearranges, exits, exactly the shape of the existing hooks. /plan's close-out reorder step invokes it: Claude supplies only the desired slug order, the script rewrites QUEUE.md so the full text moves byte-for-byte with no prose passing through Claude's hands, and it self-checks (same set of slugs and same block contents before and after, or it refuses to write). Consumers get it on reinstall.

Design questions the build settles: (1) how the skill locates the installed script — hooks are invoked by Claude Code at known paths, but a skill-invoked script must be found at its per-machine install location; solvable, but the mechanism must be chosen. (2) The form of the ordering input. An ordered list of slugs is exactly what the mover needs, which makes the "give the queue an index like LOG's" idea one candidate form of that input. Lean: keep the ordered slug list **ephemeral** — used for one rearrange and discarded — rather than a persistent queue-index doc. The why: a standing index invites Claude to reason and decide from the compressed short lines instead of the real work items, the exact proxy-reasoning the method forbids (LOG's index is safe only because it's a find-then-open aid, never a decision surface). Ephemeral input gets the safe-reorder payoff with no standing proxy to decide from. Relates to [session-sizing-and-break-lines] (companion-CLI boundary) and the queue's growth generally.

#### /plan presumes close when Unprocessed empties instead of offering a neutral "anything else?" [plan-assumes-close-after-last-capture]
Captured by you. Observed in testing. When the last Unprocessed item is processed, /plan leans toward closing — sometimes running the wind-down re-scan straight away — rather than asking whether the user has more to capture or discuss; and when the user does raise a further capture after that point, /plan files it but re-leans to close instead of returning to a neutral off-ramp.

Fix in plan.md, keyed on one principle: an empty Unprocessed is not a signal the session is over. (1) The last-item checkpoint off-ramp is neutrally worded — "anything else to capture or discuss, or close out?" — not a close-lean. (2) A neutral end-of-queue gate fires when Unprocessed empties, and the wind-down re-scan + Step 3 close only proceed once the user actually chooses to close. (3) After a further user-filed capture, return to the same neutral "anything else?" — the "close by who raised it" rule in plugin-behaviour.md already prescribes this for user-raised captures; the plan.md flow must honour it rather than re-leaning to close.

Does not conflict with [collapse-redundant-progress-gates]: that trims redundant gates at the session opening; this ensures one neutral off-ramp at the end of the queue.

**Files (self-scoped by /next):** plan.md (Step 2 checkpoint off-ramps + wind-down re-scan positioning; the end-of-queue neutral gate). No SPEC/FAQ change — interaction wording, not a new feature.

#### A /migrate capability for bringing old-format projects onto the current queue model [migrate-skill]
Captured by you. The plugin is global, so reinstalling the new SI already updates the hooks and skills for every project — what's "on the old version" is a project's docs, not the code. On inspection of a real old project (`.si-version` 1.13.0-test1, pre-two-section model), the only real conversion is QUEUE.md: its old `## Red flags` / `## Batches` / `### Parked` / `## Deferred tests` / `## Captures` shape has to become the `## Processed` / `## Unprocessed` two-section model with `####` work lines, slugs, provenance, and per-line red-flag markers. The other docs need little or nothing: LOG/ is already per-entry files + index.md (matches the new model), CLAUDE.md settings are auto-topped-up by session_start, and SPEC.md is format-agnostic.

The conversion needs judgment, not a script. Example from the real project: its red flags are "accepted" and "resolved" with no remaining work, and the new model forbids a bare red-flag line with no work attached — so each must be judged (becomes a work line, or is done-history that moves to LOG). A find-and-replace can't make that call. So the capability is a guided conversion pass — a `/migrate` skill, or a documented checklist Claude follows.

Facets to design:
- Detection is mechanical, early (Claude-surfaced). session_start gains an "adopted-but-stale-format" state alongside its existing unadopted / adopted / active-build detection. When it sees an old format it stops the normal load and tells the user to run /migrate first — before a full /plan or /next spends context on the old scaffolding. Extends the `.si-version` comparison session_start already runs.
- /migrate is its own session, closed by /done (which writes a LOG entry recording the migration), so the user then clears or starts fresh for the next skill, per the README's one-skill-per-session advice.
- Version-delta knowledge needs a maintenance trigger (Claude-surfaced). /migrate needs a running record of what structurally changed between which versions, keyed to version. #### File-granularity split pays off for the non-coder-building-with-AI case [ai-file-granularity-payoff]
By Claude (from SI testing on the Metro-admin roster→calendar converter, 2026-07-21). Testing a real single-file HTML tool surfaced a method-level finding about when to split a tool into multiple files. The conventional dev trade-off says: under file:// you can only split via `<script src>` tags (classic scripts), which share one global namespace — so you get separate files but not true module isolation, making the "one file's edit can't break another" benefit only partial. That framing under-weights the AI case. The payoff isn't compiler-enforced isolation — it's that smaller, single-purpose files are easier and safer for an AI to edit: the edit's blast radius is one file, the AI reads and reasons over less at once, and a mistake is contained by file boundary rather than by language scope. So the split is worth its distribution cost (zip-and-extract per version) specifically because AI does the editing — a payoff that doesn't show up in the traditional coder's calculus. For a non-coder building with AI, this might not be known so it needs to be provided for in SI.
Caveat — the counter-force that bounds the split: AI reasons less well across files than within one. So content the AI needs to reason over as a connected whole — a stretch it must hold in mind at once, like the SI QUEUE itself — should stay in a single file, even where splitting would otherwise be tidy. The rule that falls out: split by independent unit (a self-contained platform path, a standalone tool), keep interdependent content that's reasoned across together. Worth folding into method guidance on when to recommend multi-file structure to non-coder users.
