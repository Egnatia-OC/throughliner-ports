#### Publish an editing-state signal other apps can read, so a live editor knows when Claude is writing [editing-state-signal-for-companion-apps]
Captured by you 2026-08-06 and designed at the same session. **Placed at the top of Processed on unblock-potential, in its most literal form: a separate project of yours is queued and explicitly waiting on this item's output.** You asked that the shape be settled here rather than taken from your sketch, so it is settled below; the two answers you need are the location and the format, both stated explicitly.
**The requirement, in your words.** mdreader is a Markdown reader and writer for Windows (Electron, open source, deliberately plain), built because you read and edit Markdown documents while Claude Code is editing those same documents live. It needs to show a marker and hold off your typing while Claude writes, so the two of you don't land on top of each other. **You rejected inferring this from file-change timing, and the reasoning is the design input that matters most:** an app can see *that* a file changed but not *who* changed it, and can never know Claude has finished rather than paused to think — and a wrong guess locks you out of your own document mid-sentence.
**The core decision: this is a HEARTBEAT, not a lock — and that is what makes it safe.** A plain on/off flag has one catastrophic failure: a session that crashes, is killed, or loses its connection between starting a write and finishing one leaves the flag stuck on, and the reader locks the user out of their own document permanently. That is the exact harm the timing-guess approach was rejected for, reintroduced by the fix. So the marker always carries a timestamp, refreshed on every write, and a reader treats a stale marker as "not editing" regardless of what the flag says. **Staleness is the safety property, not a detail.**
**What the signal can and cannot honestly say, stated plainly because the whole point is to replace a guess with a fact.**
```
CAN say:  a write by Claude is in progress right now      # who: solved
          which files that write targets                  # scope: solved
          when the last write happened                    # recency: solved
CANNOT:   that Claude has FINISHED rather than paused
```
The last one is not solvable by any mechanism available, and pretending otherwise would be the same false promise. What changes is that the reader is no longer *guessing*: it knows a write is in flight, and it knows exactly how long it has been quiet, so its policy is built on facts rather than on inference from modification times. **The hook reports facts; the reader decides policy.** Deliberately so — mdreader knows what its user is doing and the hook does not, so any timeout baked into the hook would be a policy decision made in the wrong place.
**Location (deliverable 1).** `<project-root>/.throughliner/` — the project root being the folder the Claude session was opened in, which is the folder holding `SPEC.md` and `QUEUE.md`. A reader with a document open walks up the directory tree until it finds a `.throughliner/` directory, exactly as tools locate `.git/`.
**Filename and format (deliverable 2).** One file **per session**, named `editing-<session-id>.json`, holding:
```json
{
  "version": 1,
  "active": true,
  "updated": "2026-08-06T15:42:07.123456+00:00",
  "files": ["C:/absolute/path/to/the/file/being/written.md"],
  "session": "<opaque session id>",
  "pid": 12345
}
```
`version` leads and is non-negotiable: this is a contract another application is built against, so it must be able to recognise a format it does not understand and fall back safely. Timestamps are ISO 8601 with an explicit UTC offset. `files` carries absolute paths, so a reader can hold off typing **only in the affected document** rather than blocking everything — a strictly better experience than a global lock, and free once the paths are already known to the hook.
**Why one file per session rather than one shared file.** Two Claude sessions in one project is a supported shape and has already caused real damage here ([concurrent-session-support] records a live corruption incident). With a single shared file, session A finishing a write would set `active: false` while session B is mid-write, and the reader would let the user type into a document Claude is actively editing — precisely the harm this feature exists to prevent. Per-session files make the reader's rule trivially correct: **editing is happening if ANY file in the directory is `active` and fresh.**
**Recommended reader policy, published as guidance rather than enforced.** Treat `active: true` as editing. Treat `active: true` with `updated` older than ~30 seconds as a dead session and ignore it — that is the crash case. Treat a missing directory or an unreadable file as "not editing" and never as an error: **the signal must fail open**, because most projects will never have this plugin installed at all, and a reader that blocks on absence would be broken everywhere else.
**What gets built.**
1. `hooks/pre_tool_use.py` — before an Edit/Write/MultiEdit, create `.throughliner/` if absent and write the marker with `active: true`, the target path, and a fresh timestamp. **Must never block or fail the tool call**: any error writing the marker is swallowed silently, because a companion-app convenience must not be able to stop the user's actual work.
2. `hooks/post_tool_use.py` — after the same tools, rewrite the marker with `active: false` and a fresh timestamp, keeping the last-written path. Same never-fail rule.
3. `hooks/session_start.py` — delete this project's stale marker files (any whose `updated` is older than an hour) so crashed sessions leave no litter. This is housekeeping, not the safety mechanism; staleness already protects the reader.
4. `docs-b/setup.md` — add `.throughliner/` to the project's `.gitignore` when scaffolding. This is transient session state and must never be committed; it also carries absolute local paths, which is exactly the machine-layout detail this project already avoids publishing.
5. `SPEC.md` — a new described capability, and the published contract itself: location, filename, fields, versioning promise, and the fail-open rule. The contract lives in SPEC because SPEC is product truth and another application now depends on it.
6. `templates/faq-template.md` + `faq-index-template.md` — what the directory is, why it appears, and that it is safe to delete.
**The name is deliberate and is tied to the rename.** `.throughliner/` rather than `.sovereign-implementer/`, because the product rename is decided, the GitHub repo has already been renamed, and this is a **published contract another app builds against** — shipping the old name would guarantee a breaking change to an external consumer later. Recorded so nobody "corrects" it to match the current plugin id ([rename-to-throughliner], [github-identity-changed-underneath-the-project]).
**Two known limits, recorded rather than discovered later.** Writes made through Bash or PowerShell are not covered, because `PostToolUse` only matches the edit tools and a shell command's target file is not reliably knowable — the same gap [shell-writes-bypass-file-scope-lock] addresses from the enforcement side. And the signal only exists where the plugin is installed and the project adopted; everywhere else the directory simply never appears, which the fail-open rule already handles.
**Files:** `plugin/si-plugin/hooks/pre_tool_use.py`, `plugin/si-plugin/hooks/post_tool_use.py`, `plugin/si-plugin/hooks/session_start.py`, `plugin/si-plugin/docs-b/setup.md`, `SPEC.md`, `plugin/si-plugin/templates/faq-template.md` + `faq-index-template.md`. Docset A is frozen and this is a new capability, so docs-b only. #### Guard against Claude hand-building what an existing tool generates, and stop a stated fact about the user's setup being re-argued every session [prefer-the-generator-over-hand-building]
Captured by you 2026-08-06, from a live and repeating pain in another project. **Placed at the top of Unprocessed rather than appended**, because it is a recurring cost being paid now, in real sessions, rather than a design question waiting its turn.
**What happens.** Starting a new Android project, Claude builds it from scratch and gets stuck in Gradle configuration — and the user cannot tell what it is doing or why, so they cannot steer it out. **Strand one — the generator was never considered.** Almost every project type has a canonical scaffolder that produces a correct, conventional starting point in seconds: Android Studio's new-project wizard, `cargo new`, `npm create vite`, `django-admin startproject`, `dotnet new`. Hand-assembling the same thing file by file is slower, produces a non-standard layout, and fails in exactly the places the generator exists to get right — build configuration most of all. Gradle is the paradigm case: it is not a thing to be reasoned out from first principles, it is a thing to be generated correctly and then edited.
**This is the missing counterweight to a rule the method already ships, which is why it belongs on that rule rather than beside it.** `docs-b/plugin-behaviour.md` already says to reach for a CLI tool before handing the user a GUI walkthrough — the bias being corrected there is Claude *not doing enough itself*. The pairing has to be stated, or fixing one direction keeps producing the other.
**Strand two — a stated fact about the user's setup did not survive, and that is the worse half.** The user said they have Android Studio, repeatedly, and it changed nothing. Under this method's own routing rules that fact has an owner: it is a project constraint, so it belongs in a project doc that is read every session, not in the conversation where it dies at the session boundary. Re-arguing a settled environment fact is a failure the method has machinery for and simply never pointed at this class of fact. **Note this is not fixed by better listening** — the same conversation may not exist next session at all.

#### Finding a referenced queue item is hard work for the user, and the queue they are reading may not be the queue on disk [queue-pointer-hard-to-follow-and-possibly-stale]

**Two problems, and they compound.** The first is navigation: a pointer is a plain `.md` link that lands at the **top** of a 460-line file, so every lookup is a scroll or a search — and once a checkpoint has passed, later messages refer to the item by bare slug only, with no heading text to search for. **A note on how the first attempt at this test failed, because it is a method lesson and not just a mishap.** The test was first built as two files whose names differed only by extension — `viewer-refresh-ab-test.md` and `viewer-refresh-ab-test.py` — and the user was asked to open the right one from a link. If their open view is a snapshot, then a pointer emitted right after a write can land them on text that does not yet include it — so they may approve, or fail to find, a version that no longer exists. #### The Claude desktop app's sandbox blocks local toolchains, and every project rediscovers it the expensive way [desktop-app-sandbox-blocks-local-toolchains]
By Claude, from the session transcript the user supplied 2026-08-06 (preserved at `resources/testing/scrolly-thing-next-2026-08-05-transcript.md`). **Placed at the top of Unprocessed** because it is a live constraint on every Windows desktop-app user right now, not a design question.
**The finding, established in that session by isolating the failure layer by layer rather than by inference.** The Claude desktop app is an MSIX-packaged Windows application (`C:\Program Files\WindowsApps\Claude_…`), so everything it launches inherits a locked-down package sandbox. That sandbox permits *binding* an AF_UNIX socket but refuses *connecting* to one — which is exactly what Java's NIO `Selector` needs, and therefore what every Gradle build needs. Plain TCP loopback works, which is why the surfaced error (`Unable to establish loopback connection`) points away from the real cause. Android Studio runs at full trust and compiles the same project fine, side by side.
**Tried and ruled out in that session, recorded so none is re-attempted:** the sandbox override in both PowerShell and Bash, `--no-daemon`, forcing the legacy `WindowsSelectorProvider`, redirecting `java.io.tmpdir` off the short `ALEX2~1` path, and launching Gradle as a fully detached process. All still start inside the sandbox, which is why none changed anything.
**Corroborated externally, three independent reports:** [Microsoft Q&A on Java NIO selectors in MSIX packages](https://learn.microsoft.com/en-us/answers/questions/5599711/microsoft-technical-support-request-java-nio-selec), [anthropics/claude-code#41432](https://github.com/anthropics/claude-code/issues/41432), [PortSwigger/mcp-server#82](https://github.com/PortSwigger/mcp-server/issues/82).
**Why this is method work and not just one project's problem.** It cost that project **two sessions** — one that declared victory on a false positive, and one that took the failure apart properly. Any user doing JVM, Android or Gradle work from the desktop app will hit the identical wall, get the identical misleading error, and have no way to attribute it to the app rather than their own setup. The method's whole purpose is that a non-coder is not left holding a diagnosis they cannot make. **This is a knowable, already-diagnosed constraint, so making each project rediscover it is a pure loss.**
**The untested workaround, stated as a prediction rather than a fact.** Running Claude Code from a terminal — an ordinary full-trust process — should escape the sandbox entirely, and both external reports mention the command working outside the packaged app. It was not tested, because a session inside the sandbox cannot test it. **Verify before publishing it as advice**, per the check-what-the-tool-documents rule; an untested workaround in a FAQ is worse than none.
**What to settle at processing.** Whether this becomes a documented constraint (a FAQ entry plus a line in the install guide), an active check (something notices a Gradle/JVM toolchain in the project and says so *before* a build tries), or both. The active check is the one that would actually have saved those two sessions — nobody reads a FAQ entry for a problem they do not know they have. Also weigh how far the finding generalises: the blocked operation is AF_UNIX connect, so anything else depending on it fails the same way, and framing this as "a Gradle problem" would under-describe it.
**Files (rough):** `templates/faq-template.md` + `faq-index-template.md`, `INSTALL.md`, possibly `docs-b/next-build.md` or a hook if an active check wins, `SPEC.md` if it becomes described behaviour. Relates to [prefer-the-generator-over-hand-building] (the guard whose evidence this is), [move-to-vscode-extension] (a full-trust surface that would remove the sandbox entirely — this is a second, independent argument for it), [harness-misbehaviour-diagnosis-order].
