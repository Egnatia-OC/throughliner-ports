#### A consumer's SPEC grows forever with nothing to evict or measure it — ship SPEC-maintenance rules derived from the self-authoring gate [shipped-spec-maintenance-rules]
Captured by you 2026-08-12 at /plan. Your question, and you drew the host/target line yourself: might SPEC benefit from some of our self-authoring rules — not for this project, but shipped, so that when the method is deployed against a real external project it carries built-in SPEC-maintenance rules derived from them. The analysis below is Claude's.
**The structural analogy is real and holds.** `resources/self-authoring-rules.md` exists because the always-loaded rule corpus grew monotonically — every session could add, nothing ever removed, and nobody counted until it was at ~218 instructions. SPEC has the identical growth shape: every user-facing change adds a paragraph under the sync gate, nothing evicts, and no measure exists. It is read at every planning session today and, once [spec-is-write-only-during-builds] ships, at every build run too — so its cost is paid more often than the rule corpus's, not less. **Three of the gate's four parts transfer; one does not, and the difference matters.**

- **The rationale split transfers.** The gate's rule that reasoning leaves the operative statement and lives in the record that decided it applies directly: SPEC carries a lot of why-we-chose-this prose that is LOG material.

#### Add a lightweight post-close "done delta" — commit everything since the last /done without a full-session rescan [done-delta-close]
Captured by you — filed after `fa2f8e5`. /done is expensive: the full close re-scans the whole session's discussion (wind-down re-scan), runs the spec-sync gate, reorder, marker positioning, advisory management, LOG authoring, and staleness sweep. When a /done has already committed this session and the tail only filed a few captures, the full ritual is overkill — most steps no-op, but Claude still pays the reading/reasoning cost to *reach* each no-op. (Seen live 2026-08-01: a second /done banked six post-close captures; nearly every step was a silent no-op, yet the full path was still walked.)
**The idea:** a delta close that handles only *everything since the last /done commit* — stage the new changes, write a light delta LOG entry, commit — while **bounding the rescan to since-the-last-close** instead of the whole session, and skipping reorder/marker/advisory steps when nothing relevant changed.
**This coexists with, doesn't replace, the free path:** post-close captures already ride the next session's commit ([post-close-tail-state]), so doing nothing is still valid. The delta close is the explicit "bank it now, cheaply" option for when the user wants it.
**Design questions (for /plan):**
- **Trigger:** separate mode/command, or auto-detected? Auto-detect is cleaner — /done notices a commit already happened this session and switches to the delta path — but "already committed this session" needs a reliable signal (a session marker, or git log since session start).
- **Keep vs skip:** commit + light LOG entry kept; whole-session wind-down shrinks to since-last-commit; reorder/marker/advisory fire only if the delta touched them. Preserve the full close's safety (nothing unrouted) without re-paying its cost.
- **LOG shape:** a fresh delta entry (as this session did with render-verify-and-captures.md) vs appending to the prior entry.
**Relates to:** [post-close-tail-state], the done-family dedup audit findings (done.md is already heavy — a delta path should reuse the shared core, not duplicate it), and captures-filed-after-commit.
**Files (rough):** done.md (the delta-close path + its trigger), possibly session_start.py if a session-commit marker is needed, SPEC/FAQ if user-visible.
