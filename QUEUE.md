#### Fix `reorder_queue.py`'s blindness to a marker above all items — it breaks every reorder of Processed, not just greenlighting [reorder-mover-marker-at-top-blind]
Filed after `fa24343`; processed 2026-08-03. **Three occurrences in two days, all with the same by-hand workaround.** Twice the marker was relocated manually via Edit before the mover would run; the third time the session avoided the move entirely and reworded an item instead — a worse fix chosen because the right one was unavailable. #### Never stage the `-testN` suffix: a recognised-signature carve-out that leaves plugin.json dirty rather than committing it [test-suffix-plugin-json-close-noise]
Captured by you — filed after `fa24343`; processed 2026-08-03. Every rezip bumps `plugin.json`'s `-testN` test suffix as a working-tree-only change, never committed until the next real Push (which drops the suffix and commits a clean version). Between a rezip and that push the file sits dirty, so the commit core's out-of-scope-dirty-path check surfaces it at *every* close — predictable noise.
**The premise is confirmed and the outcome is worse than the capture assumed.** `plugin.json` is not dirty today because the suffix was **committed**: the repo's committed version is `1.16.0-test4`, staged in `ea50872` — an ordinary session close, not a release. **The noise got resolved the wrong way, and that is the real finding.** Faced with the same file surfacing at every close, a session made it stop by staging it. That is the path of least resistance, and the current wording leaves it open — the check surfaces the file and asks, and "commit it" is an available answer. #### Check the documented contract before blaming the tooling — and before building on it [harness-misbehaviour-diagnosis-order]
Captured by you 2026-08-03 — filed after `d682117`; processed the same day. That session spent most of its length diagnosing a dead `session_start` hook. Two hypotheses were built and argued in detail: that the desktop app silently drops oversized injected context, and that it doesn't run `SessionStart` hooks at all. Both were wrong. The actual cause was that our own hook emitted an output shape Claude Code doesn't accept. One search found the documented contract and three matching issues in about a minute. That search should have been the first move, not the fourth.
**The ordering rule.** When something in the harness misbehaves — a hook, a skill not loading, a setting apparently ignored — check our own conformance to the documented contract first, then look for the problem already being reported, and only then theorise about a bug in the tool. The default assumption is that we are wrong, because our code is unverified against the contract while the harness is used by very many people. That session inverted the default and came close to reporting someone else's tool broken for our own defect.
**Extend it to design time, not just debugging time (added at processing).** The same failure exists one step earlier and this project has now hit it twice. Phase 3's docset detection was *built* on a `model` field the documentation explicitly declines to guarantee — and the hook's own docstring cited the project's research saying so. Nobody read the contract at design time either. So the rule covers depending on a harness behaviour as well as blaming one: before building on it, check what is actually guaranteed. Two instances in one project makes this a pattern, not a hypothetical.
**State separately: *it ran* and *it worked* are different claims.** Running the hook through the CLI with `--include-hook-events` showed its full output in the event stream, and that was read as proof the injection worked. It was not — that flag echoes a hook's raw stdout whether or not the harness accepts it, and the run failed authentication before any model call. Evidence for "the thing executed" is routinely mistaken for "the thing had its effect." This is the most transferable lesson in the item and should be its own rule, not a closing paragraph.
**Confirmed twice in this session, recorded as evidence rather than assertion.** Reading the published hooks contract settled the `model`-field question in a single fetch, which is what turned [docset-b-inert-on-desktop-app] from a bug hunt into a design decision. And checking for existing reports before filing anthropics/claude-code#83475 and #83476 was the same discipline pointed outward.
**Wording constraint, because this ships to consumers.** A non-coder does not know what an issue tracker is, that one exists, or how to search it. The rule must read as plain guidance — "before assuming the tool is broken, check what it says it does, and see whether someone has already reported this" — with the mechanics kept out of the user-facing wording. Write it for someone who has never opened GitHub.
**Where it lands.** Method-general and it helps consumers, so it belongs in the shipped behaviour rules near the existing research-offer rule it extends. The never-report-outward-before-ruling-out-our-own-code half also touches the consumer feedback channel, which handles the mirror case of routing method problems out.
**Docset A is frozen, so this lands in `docs-b` only.**
**Files:** `docs-b/plugin-behaviour.md` — the Research and evidence filing section, or a short new rule beside it. Relates to [session-start-output-not-reaching-sessions], [hook-liveness-and-schema-testing], [docset-b-inert-on-desktop-app], and the research at `resources/research/session-start-hook-output-schema.md`.

#### Write approval-time text straight to its doc and link it, instead of pasting in chat — remote the only exception [write-first-link-dont-paste]
Captured by you (2026-08-02), processed the same day. Approval-time text whose destination is a Throughliner doc — a capture, a work item, a LOG entry, a SPEC or CLAUDE.md edit — is written to that doc first and surfaced as a link, and the user approves against the file rather than against a chat paste. **Remote mode is the only exception:** on a phone, opening the file is impractical, so the text is surfaced inline there as it is today. **The strongest argument, which the capture didn't state: this deletes a branch rather than adding one.** The render rule today has two cases — doc-resident text gets a pointer, text not yet written is always inline "since there's nothing to point at." Write-first removes the second case entirely: write it, and it's resident. One rule instead of two. Lead the build with this.
**Boundary — doc-destined text only (settled at processing).** Not every approval-time output is headed for a file. A commit message isn't (Claude runs the commit), and neither is a recommendation or an option set. Those keep today's behaviour, because there is nothing to write them to and no link to give. Without this clause the rule would try to write a commit message somewhere in order to link it.
**The reject path must be specified, not assumed (settled at processing).** "Revert on reject" is load-bearing and isn't free: nothing is committed mid-session, so reverting means editing the text back out, and getting it wrong leaves rejected content in the file. The build states plainly what happens on a no — remove exactly what was written, confirm by re-read, say so. This buys back explicitly the safety that showing-first currently gives for free.
**What is genuinely lost.** A transient window in which a tracked file holds unapproved text. If a concurrent session or a crash lands in that window, unapproved content persists. Small but real, and it interacts with [concurrent-session-support].

Filed as anthropics/claude-code#83475.
**So the build must never emit a line-anchored link to a `.md` file** — that is the one form that fails, and it fails silently while still looking clickable. Code files keep their line anchors.
**And because a markdown link can only reach a file, never a position, every pointer carries the target's exact heading text** so the user can search straight to it rather than scanning. This is not decoration: landing at the top of a 480-line queue and being told "it's in there" is the failure mode the pointer has to avoid, and searchable heading text is what converts a scan into a copy-paste. The user chose this over the alternative of pasting fresh drafts inline, on the grounds that the heading text makes the search cheap and it is the version that actually cuts the token cost.
**Lift-condition: cleared 2026-08-03.** Link reliability was the only thing holding this below the line, and it is now understood and dependable within the constraint above. Ready to build.

Design the two together; they may collapse into one build.
