# QUEUE

Two sections. **Processed** — work discussed and agreed, ordered top-to-bottom; /next builds from above the `--- Cleared to run above this line ---` marker. **Unprocessed** — captured, not yet fully processed; the next /plan weighs each item. A work item is a `#### ` heading (its description) with a `[slug]` at the end of that line and its rationale in the block beneath. A leading `[audit]` / `[user]` tag names how it's executed; no tag means a build. A work item carrying a security or privacy risk gets a `Red flag · State: …` marker — the flag rides the work.

**Authoring a rule for the method's own text? Run [`resources/self-authoring-rules.md`](resources/self-authoring-rules.md) first.**

#### Feed a summary of the work cycle into every /plan and /next, because sessions keep reasoning without it [cycle-summary-at-every-skill-opening]
Captured by you 2026-08-12 at /plan, in your own words: we really need to start feeding a summary of the build cycle into every plan and next, because the lack of understanding of the basics of how it runs is affecting things — and this is the second plan session in a row where you have had to explain it. The instance below is Claude's.
**The instance, from minutes before you said it.** Processing the rule-corpus cluster, Claude recommended running the `[audit]` first and the eviction second, fed by its findings. On being reminded that an audit files to Captures rather than editing, Claude *reversed the recommendation* — reasoning that the audit could no longer feed the build because its findings would need a planning session first. That reasoning is wrong at the most basic level: **audit → captures → /plan → work items → /next is the cycle**, not an obstacle to it. An intervening /plan is the normal path, not a defeater. The original ordering was right and was abandoned for a bad reason.
**Why this is worth a mechanism rather than a note.** Nothing in the always-loaded rules or in `plan.md` states the cycle end to end. The rules describe the pieces — what an audit does, what a capture is, what /plan may process, what /next may build — and a session is left to assemble the loop from fragments. It assembles it wrong under pressure, and it does so *while sounding confident*, which is what makes it expensive: the user has to catch it, and has now caught it twice in consecutive sessions. A recurrence across sessions with no shared memory is evidence about the documents, not about one session.
**Where it should live, to settle at processing.** `docs-b/plan.md` and `docs-b/next.md` are fetched when their skill runs, so a short cycle summary at each opening costs nothing against the always-loaded ceiling — which is the argument for putting it there rather than in `skill-nonspecific-rules.md`. Weigh the shape: a four- or five-line loop stated once, read by Claude and not narrated to the user, versus a longer explanation that would itself become drift. Note the FAQ already explains the cycle to *users*; this is the same content aimed at Claude, and whether one text can serve both is worth asking before writing a second.
**This is not a self-hosting concern and must not be built as one — the user's judgment, stated when the item was filed: any project could benefit from it.** The instances happened here, which makes it tempting to treat as a dev-project quirk and put the summary in this project's `CLAUDE.md`, where consumers would never see it. That would be wrong. Nothing about the failure depends on developing the method: a consumer's session assembles the same loop from the same fragments, and a consumer has *less* to assemble it from, since they never read the development history that fills the gaps here. They are also far less likely to catch a confident wrong answer, because they do not know the cycle well enough to contradict it — which is the whole reason they are running a method. So the summary ships in `docs-b/plan.md` and `docs-b/next.md`, reaching every project.
**Processed 2026-08-12. The design turns on one point: it must be written as a cycle with the return edge named, not as a list of steps.** A linear "capture → plan → build → close" list would not have prevented either instance, because both failures were about a loop *closing* — an audit's findings travelling back round to become work. Claude reasoned that an audit could not feed a build because a planning session sat between them, which is only wrong if you can see the return edge. So the forward path is not the content; the return edges are.
**The text to place, drafted here so the build has it rather than re-deriving it:**
```
The work cycle. Every piece of work travels the same loop.
  STANDING — anything noticed, by anyone, at any moment, becomes a
     capture in Unprocessed. Not a stage: it is available throughout.
     Any session may file one; no session but /plan may process one.
  1. /plan — think and organise. Processes a capture: kept into
     Processed, or deleted. Keeping settles how it runs — build,
     [audit], [user], [freeform] — and where it sits.
  2. /next — build. Takes the top piece of ready work from above the
     readiness line and builds it, top-down, several back-to-back.
  3. /done — record what happened, and commit.
  4. Then the session ends and a fresh one starts. The loop's boundary
     is a new session with no memory of this one, which is why every
     return edge below routes through a FILE and never through what
     someone remembers.
  5. RETURN EDGE — an [audit] edits nothing. It files findings as
     captures, which re-enter at the standing step and become work at
     step 1. A planning session between a finding and its build is the
     cycle working, not an obstacle to it.
  6. RETURN EDGE — a build that discovers something files a capture and
     carries on. The discovery re-enters at the standing step.
  7. [user] work is walked through, never built. It leaves the loop only
     when the user has done it.
```
**Three changes taken from the public build-cycle page at flintcraft.tech/build-cycle, checked at the user's suggestion.** (1) **The session boundary was missing.** That page ends the loop with "/clear or open a new chat to start fresh", and it belongs here: the loop's boundary is a fresh session with no memory, which is the reason every return edge must route through a file rather than through what anyone remembers. Without it the block described a loop that looked like it could be held in one head. (2) **Vocabulary aligned to the page's** — "/plan — think and organise", "/next — build", "/done — record what happened, commits" — so Claude and the user name the stages the same way, which is cheap insurance against the narration drift the compliance sweep looks for. (3) **Capture promoted from a step to a standing affordance**, matching the page's "at literally any time"; as step 1 it read as a stage that comes before the others, which is wrong.
**What the page does NOT carry, so the two are complementary rather than duplicates:** the return edges, the flavors, and the readiness line are all absent from it. That is correct for a public explanation and is why this block is not simply a copy of it.
**Where it goes, and why not the always-loaded file.** `docs-b/plan.md` and `docs-b/next.md`, at each doc's opening. Both are fetched when their skill runs, so this costs nothing against the always-loaded ceiling — which matters given [rule-corpus-over-ceiling] is open on that very count. Read by Claude, never narrated to the user: it is orientation, not something to recite.
**One text or two.** The two openings can carry the same block. Steps 3 and 6 matter more to /next and step 2 more to /plan, but a session that reads the whole loop is the point, so tailoring it per skill would reintroduce the partial view this fixes.
**The FAQ question, settled rather than left open.** The FAQ explains the cycle to *users* and stays as it is. This block is aimed at Claude and lives in the procedure docs. One text cannot serve both: the FAQ's job is to reassure a non-coder about what happens to their idea, and this one's job is to stop a session mis-reasoning about routing. Merging them would blunt both.
**Weigh against the admission gate.** This adds text to two procedure docs. Its defence is a pointed-to failure with two instances, which is exactly what the gate asks for.
**Files:** `plugin/si-plugin/docs-b/plan.md` and `plugin/si-plugin/docs-b/next.md` — the block above at each doc's opening. No FAQ, SPEC or README change: nothing user-facing changes.
**Files (rough):** `plugin/si-plugin/docs-b/plan.md` and `docs-b/next.md` (an opening cycle summary), possibly `FAQ/faq.md` if the same text serves both audiences. #### The keep-check has no rule for a mixed item — half fully specified, half not designable yet — so a session invents its own framing [keep-check-has-no-mixed-item-rule]
Captured by you 2026-08-11 after catching the mishap that exposed it. Mixed authorship: you identified that the wrong question had been asked and asked whether a rule was at fault; the diagnosis below is Claude's.
**What happened.** Processing [write-first-report-without-write], Claude found one half fully specified (three docs contradicting the write-first rule) and one half not designable (why a shipped, correctly-worded rule fails to fire). Instead of putting the real choice to you, Claude asked whether to split the item or keep it whole — a filing question — and you corrected it: the question was whether to design the mechanism now or defer that half to a later /plan.
**Why this is a gap in the doc rather than only a slip.** `plan.md`'s keep-check has two limbs — name the files that change and what changes inside them — and an item failing either is sharpened or skip-deferred, **never kept**. Its skip-to-defer recommendation likewise addresses an item that will not design out this session. Both are written about a **whole** item. Neither says what to do when one item contains both states, which is common. With no rule to reach for, the session invented a framing, and the invented framing hid the decision that was actually the user's.
**The analogous rule that already exists, and is the model for the fix.** The same document decomposes a mixed Claude-prep-plus-user-action item: Claude-doable parts become build items, the irreducible user action becomes a single `[user]` line, cross-referenced by slug. There is no equivalent for buildable-plus-undesigned.
**What it let through, which is the concrete cost.** The item was kept with its second half failing the second limb, papered over by a close condition requiring the unbuilt half to be re-filed as a capture at close. That is a workaround for a check that should have stopped the keep.
**Settled at processing 2026-08-12, from a worked example the same session produced.** The rule is **not** "always split" and **not** "may be kept whole": it is that **the mixed state is surfaced to the user as a choice about designing, not about filing.** The question is *"shall we design the remainder now, or split it off?"* — never *"shall I split this item or keep it whole?"*, which is what Claude asked the time this was captured, and which hid the decision that was actually the user's.
**If the answer is design it now,** the item is designed to completion in-session and kept whole. **If the answer is split**, the split is mechanical and follows the decomposition rule this document already carries for Claude-prep-plus-user-action work:
```
buildable half   ->  kept into Processed, passing both limbs on its own
undesigned half  ->  returned to Unprocessed with the design progress
                     made so far written into its prose, its own slug,
                     cross-referenced from the kept half by slug
```
**The worked example, from this session rather than invented.** [spec-is-write-only-during-builds] arrived mixed: its *role* half — do builds read SPEC, where does the sync gate live — was fully designable, and its *size* half — how much of SPEC is implementation detail that should leave — was not, since answering it needed research that had not been done. The choice was put to the user as a design question, the role half was designed and kept, and the size half went back to Unprocessed as [spec-carries-implementation-detail] carrying the research finding that had prompted it. The same session did the reverse for [rule-corpus-over-ceiling], absorbing a diagnosis item that could not stand alone — which is the tell that these are two directions of one operation, not two rules.
**Why the framing matters more than the mechanics.** Both outcomes are cheap and reversible. What is not recoverable is the user never being asked: a keep that papers over a failing limb — as the captured instance did, with a close condition requiring the unbuilt half to be re-filed later — is a workaround for a check that should have stopped it, and it ships an item that will stall a run.
**A second clause for the same block, carried here on 2026-08-12 when [findings-in-unprocessed-never-flagged] was deleted into this item: make "is this a finding rather than work?" an explicit part of the second limb.** Today it is an implication of it — ask what changes inside which files, get "nothing", and a session has to realise for itself that the item is a finding whose home is `resources/` or the LOG under the three-way triage. Saying it outright costs one clause and names the routing.
**Why that deleted item was not built as a detector, recorded so the detector is not re-proposed.** It asked to extend the placement-contradiction detector's signal 2 — an item whose file list names nothing to change — from Processed into Unprocessed. That does not transfer: in Processed an empty file list is a contradiction, because the item is marked ready to build; **in Unprocessed it is normal**, since a capture is undesigned by definition. The signal would fire on most of the section and be learned past. What actually catches these is the keep-check, which fired correctly every time it was reached — on the five rationale-growth measurements, and on [this-run-grew-what-it-measured] the same day. The residual gap is *delay* rather than detection: a finding sits until the next /plan reaches it. The cost of that delay — findings inflating queue counts and competing for processing order — is real, mild, and bounded by the next planning session. The genuine risk accepted in deleting it: those five sat for a day, were found only because someone went looking, and one carried a caveat that only held bound to the others, so a partial read could mislead.
**Files:** `plugin/si-plugin/docs-b/plan.md` — the keep-check's two-limb block (the mixed case, the question to ask, and the finding-versus-work clause), and the existing decomposition sub-step (the split's mechanics, cross-referenced rather than restated). Relates to [write-first-report-without-write] (the captured instance) and [merged-plugin-verification-remainder] (what happens when an unbuilt half rides a closed item's prose).

#### The throughput floor counts Unprocessed blockers while the below-line lift fires on shipped, and nothing states the difference [floor-and-lift-use-different-tests]
Captured by you 2026-08-11 — you stated, as a rule, that a below-line item should only ever be blocked by something in Unprocessed, because a blocker sitting in Processed would never be processed and the held item would never clear. The diagnosis below is Claude's.
**The inference was wrong, and it was reasonable.** The below-line revisit lifts on **shipped per LOG**, not on processed: a blocker in Processed-above is built by /next, leaves the queue, and the next /plan's revisit lifts the held item without /plan ever touching the blocker. That is not theoretical — three items lifted at the opening of this very session by exactly that route, and four more are one /next run from lifting.
**Where the inference comes from, which is why this is a documentation defect rather than a user error.** The throughput floor genuinely does count blockers **in Unprocessed**, and correctly so: those are the ones a *planning* session can move, where a blocker in Processed needs a build. So the method has two tests keyed on different sections — one for what a /plan session should prioritise, one for when a held item may be lifted — and **no document puts them side by side or says they are different questions.** Reading either alone, the other's criterion looks like an inconsistency or an error.
**The real failure mode is one section over, and it is worth naming in the same place.** What genuinely strands work is a blocker that is *itself held below the line* — a chain — which is why chains are signal 3 of [nothing-audits-the-cleared-region]'s detector. A chain that terminates is slow; one that loops never resolves.
**Settled at processing 2026-08-12 as a clarifying clause, not a rule.** It restates what two existing steps already do and adds no obligation, which is the shape the admission gate pushes toward and the reason it consumes no slot.
**The text to place, drafted here:**
```
Two tests, different questions — they are not inconsistent.
  the lift  asks "has this already SHIPPED?"  -> read off LOG
  the floor asks "what can THIS session
                  unblock?"                    -> counts blockers in
                                                  Unprocessed only
A blocker sitting in Processed needs a BUILD, not a planning session, so
it is not the floor's business: /next builds it, it leaves the queue, and
the next revisit lifts what it held.
The case to watch is a blocker that is ITSELF held below the line — a
chain. One that terminates is slow; one that loops never resolves.
```
**It is stated once, at Step 1's below-line revisit**, which is both the earlier of the two in the document and the earlier of the two in a session. The start-of-processing floor derivation names it by reference rather than restating it, per the cross-doc convention that a second copy is what drifts.
**Live evidence from the session that settled it, which is why the clause is worth its space.** Three items lifted at that opening purely on the shipped test, none of which the floor had counted; the floor itself derived to zero on the same queue. And the chain case occurred in the same session: [worktree-override-hook] was blocked by [concurrent-session-support], which was itself held below the line — the exact shape the last line warns about. It resolved by both being deleted, which is a resolution but not a reassurance.
**No FAQ entry.** Nothing user-facing changes: this clarifies reasoning Claude does, and the behaviour a consumer sees — items lifting when their blockers ship — is unchanged.

Relates to [nothing-audits-the-cleared-region] (whose signal 3 is the chain case) and [hook-emits-counts-not-the-graph] (whose fourth bucket makes an absent blocker visible).

#### Claude treated "continue" at the checkpoint as approval of the next item, collapsing recommend-agree-execute into one move [continue-read-as-approval]
Captured by you 2026-08-12 near the end of a long /plan, in your own words: Claude has been doing "kept and cleared" on my "continue", which is novel behaviour; it is supposed to be your recommendation, then my response, we reach agreement, then you offer continue — this has collapsed all of that. You let it run for the session rather than stopping it each time. The diagnosis is Claude's.
**What "continue" actually answers.** At the checkpoint, `plan.md` offers four off-ramps — continue to the next item, skip it, close out, raise something else. "Continue" answers *which item comes next*. It is not a decision about that item, which has not been analysed yet at the moment the word is said.
**What Claude did instead.** Presented the next item, gave a recommendation, wrote the item, moved it into Processed and reported "kept and cleared" — all in one turn, repeatedly, across most of the session. The user's decision point disappeared: by the time they could respond, the thing was done.
**The rule that was misapplied, which is why this is not simply carelessness.** `plan.md` permits folding the recommend into the action *"when the user already agreed during the interview"*, and states that a keep can fold because the user can reject what was written and have it reverted. Claude treated the checkpoint's "continue" as that prior agreement. It is not: the fold clause is about agreement reached *while discussing the item in question*, and here there had been no discussion of the item at all. **The revert-availability argument makes folding safe, and safety is not the same as authorisation** — that conflation is the mechanism of the failure and the thing a fix has to name.
**Settled at processing 2026-08-12: the fold clause gets a hard precondition. The wording fix was weighed and NOT taken.**
```
A recommend may fold into the action ONLY when the agreement was
  - about THIS item, and
  - given in the exchange now happening.
Not a prior turn. Not an adjacent item. Not a general "keep going",
"continue", or "yes" answering a different question.
Absent that, the recommendation stands alone and WAITS.
```
**Why the precondition and not the wording.** The wording candidate — that the checkpoint lists "continue" beside three options which genuinely *are* dispositions, so it reads as one of them — is true and cheaper, and it explains why the mistake is easy to make. It does not explain why the mistake was *permitted*, and that is the fold clause: nothing in it requires the agreement to be about the item being kept, and nothing bounds when it was given. A clause that permits the failure is not fixed by making the failure less tempting.
**The precondition restores the default the document already describes**, so it adds a bound rather than a mechanism: recommend, wait, act. That is the cheapest admissible shape, and it is why this consumes no new slot.
**Build it in one pass with [plan-still-carries-a-close-of-its-own].** Both edit the checkpoint's off-ramp list — that item rewords the fourth ramp to "run /done", this one bounds what "continue" on the first ramp may authorise.
**The instance is worth keeping in view while authoring.** It ran for most of a long session, over a dozen items, and the user let it flow rather than stopping each time — so the correction arrived as one late report rather than a dozen interruptions. A rule written from a single caught instance would underrate how quietly this compounds.

#### Add a ladder rung: at file order, offer the items closest to the session's loaded context [ladder-rung-for-context-adjacent-items]
Captured by you 2026-08-12, and it is a standing request rather than a new idea — your words: for the last few /plan sessions you have been asking Claude to cover items already close to topics in memory when it is almost time to close, and you think this should be a rung on the ladder. The shape below is yours too: when the last rung is reached, Claude tells the user and offers a set of items close to the current context, asking whether they want that, or to proceed in order, or to run /done.
**Why the ladder is the right home rather than a close-time prompt.** The fallback ladder in `plan.md` is applied and narrated, never offered, and its bottom rung is file order — position in the section, which is the rung that means "nothing else distinguishes these". That is precisely the moment context-adjacency becomes the best available discriminator, and it is the only rung where the tie-break costs nothing, because by definition no stronger reason is in play.
**Why it is worth real money, measured on the session that produced the request.** Processing [spec-carries-implementation-detail] required SPEC.md read in full — 6,159 words — which had already been read at that session's opening, so the measurement that made the item decidable cost nothing. A later session would have paid the whole read to reach the same point. The same held for the worktree items (documentation already fetched), the board items (the counter already run) and the queue-mechanics items (both tests already exercised that session). Context-adjacency is not a convenience; it is the difference between an item costing its own research twice or once.
**This rung is OFFERED, unlike every rung above it, and that exception needs stating rather than smuggling.** The ladder's stated discipline is that it is internal, applied, never presented as a choice — because ordering is Claude's to own. This rung breaks that, deliberately: only the user knows whether they have appetite for more items or want to stop, and the offer is as much "shall we continue at all" as "in what order". Whoever authors it must say why the exception exists, or a later reader will delete it for violating the rule directly above it.
**Settled at processing 2026-08-12: a step that FIRES when file order is reached, not a sixth rung. The user chose this over a true rung, on Claude's recommendation and reasoning.**
```
The ladder is unchanged — file order stays the bottom rung.
Reaching it TRIGGERS one offer:

  "Nothing left distinguishes these by priority. Some are close to what
   we've already loaded this session — <named set>. Take those, work
   through in order, or run /done?"

  user takes the set   ->  process those, in the order given
  user declines        ->  file order, exactly as the rung says
  user runs /done      ->  the session ends there
```
**Why a triggered step rather than a rung.** Every other rung *sorts* the section — it answers "which item first". Context-adjacency does not sort; it **selects a handful** that happen to be cheap right now. Forcing it into rung shape would leave one entry behaving unlike the other five, which is how a list stops being read. As a trigger, file order remains literally true: it is what runs if the offer is declined, so the offer is a chance to do better *before* falling back, not a replacement for the fallback.
**The exception must be stated in the text, not smuggled.** The ladder's stated discipline is that it is internal, applied, never offered — ordering is Claude's to own. **This step asks.** The justification, which belongs in the doc beside it: only the user knows whether there is appetite for more items, so the offer is as much *shall we continue at all* as *in what order* — and that is a question about the user's time, which was never Claude's to own. Without that sentence a later reader deletes this for contradicting the rule directly above it.
**Still open at build, and genuinely open.** How the adjacent set is chosen, stated well enough to be repeatable rather than improvised — candidate: items whose files, research or subject matter this session has already read, which is checkable against what was opened rather than judged. And how large the set may be: it must stay a short named list, or it becomes the wall of options the method keeps removing. Three to six is the instinct; it needs a reason before it is written, since a bare number is what [derivation-required-for-limits] bans.
**The measured case for it, from the session that asked for it.** Processing [spec-carries-implementation-detail] needed SPEC.md read in full — 6,159 words — already read at that session's opening, so the measurement that made the item decidable cost nothing. A later session pays the whole read to reach the same point. The same held for the worktree items, the board items and the queue-mechanics items. This is not a convenience: it is the difference between an item's research being paid once or twice.

#### Notice an isolated session's unmerged work and offer to merge it, so nothing is stranded on a branch or deleted at exit [concurrent-session-support]
Originally by Claude at the user's request and designed across 2026-07-29, 2026-08-01 and 2026-08-09 as branch-per-session. **Reshaped 2026-08-11 to merge-at-close only, on the user's decision** — their words: agreed on just merge at close; detection of branching, then offer to merge. The reshaping and the mechanics below are Claude's.
**What was cut, and why it is not a loss.** Branch creation, the cloud-sync check and the live-session awareness note are gone. The item existed to stop two live sessions colliding, and branch-per-session cannot do that: one working tree has one `HEAD`, so two sessions in the same folder share a branch whatever a hook creates. Where isolation genuinely exists the harness provides it, and [isolation-model-is-not-ours-to-choose] shipped the detection that reads which case is in force. Finding 2 (project-level `_build.md`) shipped separately as [session-scope-the-working-file] and is out of scope here.
**The gap that survives, confirmed against Claude Code's own worktree documentation 2026-08-12.** The harness creates a session's isolated worktree and branch, and **never merges it back**. At the end of an interactive worktree session it prompts keep-or-remove, and *removing deletes the worktree directory and its branch along with all the work in them*. So the failure this item now addresses is not collision — it is a session's work sitting unmerged on a branch nobody is tracking, one prompt away from being deleted by a user who reads "remove" as tidying up. Evidence: `code.claude.com/docs/en/worktrees`, the Clean up worktrees section.
**The constraint that shapes the whole mechanism, and it is why the merge cannot simply run at /done.** Git refuses to update a branch that is checked out in another working tree. A session inside a worktree therefore cannot merge itself into `main` while the main checkout has `main` checked out — the merge has to run *from* the main checkout. That inverts the old design: the close cannot be the merging moment for the isolated case.
**Mechanics.**
- **In an isolated session's close:** commit everything, then say plainly which branch the work is on and that it is not yet merged — and warn, in those words, that choosing "remove" at exit would delete it. This is the highest-value half and costs almost nothing.
- **In a main-checkout session's start:** detect branches carrying unmerged commits that look like session branches, and *offer* to merge them. Offer, never do it silently — the user's stated shape.
- **On an unresolvable conflict:** leave the branch in place and say plainly that the work is safe on it. The user never sees raw conflict markers.
- The isolation detection this keys on already exists in `session_start` and is not rebuilt.
**The isolated case has never been observed on this machine, and the item is kept knowing that.** The user challenged the premise the moment it was stated — if sessions branched automatically we would have seen it, since git runs at every close — and they were right. `git worktree list` shows only the main checkout and the shelved Codex port; this project has never had a session worktree or a session branch. The documentation says the desktop app gives every new session its own worktree, which is the same discrepancy [isolation-model-is-not-ours-to-choose] recorded as unexplained. So this item is written for a case that is real in the product and unproven here. It is cheap and silent when isolation is absent — the detection already exists and everything else hangs off it — but **it must not be described as solving the remote-start problem** until the isolated case is actually observed. Claude implied that at processing and the user caught it.
**A second finding from the same documentation check, worth carrying into the build.** A new worktree branches from the repository's default branch *on the remote* by default, not from local `HEAD` — so a desktop session's worktree may not contain unpushed local commits, and a user can find their isolated session missing work they made minutes earlier in the main checkout. Whether the method says anything about this is a build-time call, not settled here.
**Rejected designs, kept so they are not re-proposed.** (1) Queue-only branching — a per-session copy of QUEUE.md with a bespoke merge; smaller blast radius but it means trusting a hand-rolled merge for one file. (2) Detect-and-warn on liveness by working-file mtime with a pre-write stop-and-ask; superseded by letting sessions diverge and reconciling after. (3) Staleness detection generally — the user's position is that a session should be *closed* properly rather than left to go stale. (4) Branch creation by the method, cut above.
**Two sibling items were deleted on 2026-08-12 and their content is carried here, so neither route is reinvented.**
[worktree-override-hook] proposed a default-off `WorktreeCreate` hook returning the existing project folder instead of forking a new one, resting on `resources/research/remote-control-limitations.md`, which established the hook exists and takes a name and returns a path. **Why it lost:** Claude Code checks any path offered as an isolation worktree and refuses one whose git metadata resolves into the main checkout, or that contains the protected checkout — because from such a directory an ordinary git command would act on the real project rather than the isolated copy. Returning the existing tree is exactly that case, so the hook would be refused rather than merely risky. Source: `code.claude.com/docs/en/worktrees`, the "Claude Code refuses to use a worktree" section. **Do not read that as closing every hook route:** the same documentation says a worktree *without* git metadata — one a `WorktreeCreate` hook created — can pass the check. #### Builds read SPEC and are checked against it; the sync gate moves to the /plan close [spec-is-write-only-during-builds]

#### Nothing checks a rule-gate disposition against what the commit actually did — the signal only checks the line exists [rule-gate-disposition-is-unverified]
Captured by you 2026-08-12 at /plan, mid-processing of [rule-gate-dispositions-missing]. Your question: what checks the dispositions against what was queued. The answer and the proposed check are Claude's.
**Nothing does.** The board's BORN signal reports commits touching the rule files whose LOG entry carries no `Rule gate:` line. It is a **presence** check. A session that added four rules and wrote `Rule gate: not needed — typo fix` satisfies it completely, and nothing anywhere contradicts that.
**Why that is the failure family this method already knows.** A claim Claude makes about its own work, with nothing verifying it, is exactly what the `Stop` hook was built for — it catches a response reporting a queue item as filed when the item is not in the queue. The disposition obligation was itself adopted on the reasoning that a required artifact turns a silent omission into a visible one. That reasoning holds against *omission* and does nothing against a **false** artifact, and nobody had separated the two.
**A mechanical check exists and reuses machinery already built.** `resources/rule_signals.py` counts structural rule-statements in the always-loaded corpus — the source of the 234 figure. Counted before and after a commit, it yields a delta. **A commit whose always-loaded count rose while its LOG entry says the gate was not needed is a contradiction detectable with no judgment.** That is the case that actually occurs — the gate skipped and the line written anyway. It cannot tell whether a gate that *ran* ran honestly, and it should not claim to.
**Settled at processing 2026-08-12. It runs as a sixth board signal, NOT as a check at the close — and that placement is the item's whole point.** A check at the close would be the session judging its own disposition in the same breath as writing it, which is the self-report problem this item exists to close, wearing a different hat. The board runs at the *next* session's start, over a commit that is already written and cannot be edited to suit the check. Later and cheaper is exactly right here; earlier would be worthless.
**The check, stated so the build does not have to invent it.** For each commit in the signal's window that touches the rule files, compute the always-loaded rule-statement count at that commit and at its parent — `git show <rev>:<path>` piped through the existing counter, so no new counting logic. Then:
```
count ROSE  +  LOG entry says "Rule gate: not needed"   ->  FLAG
count ROSE  +  LOG entry says "Rule gate: run — ..."    ->  fine
count FELL or unchanged                                 ->  fine, always
```
**One-directional by design.** An eviction pass lowers the count and owes no disposition defence, so a fall is never a finding. Only the rise-with-"not needed" pair is a contradiction, and it is the case that actually happens: the gate skipped and the line written anyway.
**What it cannot do, and must not claim.** It cannot tell whether a gate that *ran* ran honestly — a dishonest "run — considered and kept" defeats it completely. It catches omission-dressed-as-disposition, not bad judgment. Say so where the signal is described, because a check that over-claims is worse than none: it makes the corpus look guarded when it is only partly guarded.
**The proxy caveat rides with it.** The count is explicitly a proxy and does not claim to be the true instruction count, so the signal reports a *contradiction between two artifacts* rather than a measured fact about rules. That is still worth having — the two artifacts are supposed to agree, and their disagreeing is checkable with no judgment.
**Build it in the same pass as [rule-gate-dispositions-missing].** Both are `resources/rule_signals.py` edits to the same signal family, and that item's baseline constant bounds this one's window too — without it, this check would run over commits that predate the obligation and flag every one of them.
**Files:** `resources/rule_signals.py` (the delta computation and the sixth signal), and `CLAUDE.md`'s disposition block if the limit above is worth stating where the obligation lives. Host-only — the board is a development artifact, not in the plugin package. Relates to [rule-gate-dispositions-missing] (built together) and [behaviour-rules-read-is-enforceable] (the four-tier ordering of how strongly a rule can be enforced — this sits at the required-artifact tier, not the hook-denial tier).

#### An "unattended" /next run is not unattended: it stops for [user] items and never closes itself [unattended-run-is-not-unattended]
Captured by you 2026-08-11 in the post-close tail. Your words: an unattended run is not actually an unattended run — it stops for user items and doesn't automatically run /done on itself; we can design that, but it needs consideration of where user items land.
**The claim as it currently stands.** `SPEC.md` calls multi-item /next "unattended in practice — the autonomous build mode the Principles name", and the Principles say execution sessions trend toward pure execution, "stopping only for what genuinely needs the user". In practice a run stops in at least three ways: a `[user]` item is walked through live, one step at a time; a `[freeform]` item halts it outright; and at the end the run simply stops, because **/done is a command the user runs** — nothing closes the session on its own. So a run left alone finishes its builds and then sits there, uncommitted, until someone comes back.
**Why this is worth more than a wording fix.** The word shapes real decisions. `[user]` and `[audit]` lines are placed end-preferred *because* a stop inside a contiguous build run interrupts an otherwise unattended sequence — that rule only makes sense if the run is meant to be left alone. **What a design has to settle, and your condition is the hard part.** Where `[user]` items land. Today end-preferred placement batches them at the end of the cleared region, which is the right instinct but only a tie-adjustment — a genuine dependency still puts a `[user]` item mid-run, and then the run stops in the middle whatever the word claims. Options to weigh: whether a truly unattended run must refuse to include `[user]` items at all and leave them to a separate walk-through session; whether the readiness line grows a second meaning (build up to here unattended, then stop for the human); or whether the honest answer is to stop calling it unattended and describe it as what it is — a run that clears vetted work and pauses where a person is genuinely needed.
**The self-closing half carries a real tension, not just work.** A run that ran /done on itself would commit without the user present, and the commit message is one of only two things the method still shows before it happens — precisely because a commit is hard to unwind and never becomes file content. #### The 20% index-line cap was derived from three entries, and 87 existing lines break it [index-cap-sample-was-three-entries]
Filed 2026-08-11 by Claude at the close of the run that shipped [index-line-length-proportional-cap], from measuring the whole index rather than a sample.
**What the measurement says.** Applying the cap across `LOG/index.md` finds **87 lines over 20%**, with the worst at 48%. The pattern is clear and was invisible in the original sample: the violations are overwhelmingly SHORT entries carrying ordinary-length lines — a 96-word entry with a 46-word line reads at 48% while saying nothing excessive. The three entries measured at processing were 968, 1,055 and 1,738 words, all long, which is why they all passed comfortably.
**This is not an argument that the cap is wrong, and the distinction matters.** The cap was written as a ceiling that freezes current practice, and against long entries it does exactly that — every one of the 21 entries written in this run came in under it, most between 13% and 18%. What the corpus shows is that the derivation's *sample* was unrepresentative of entry length, not that a proportion is the wrong shape.
**Three options, none taken here because this is a fate decision.** Re-derive the figure against the full distribution rather than three cases, which is what [derivation-required-for-limits] would actually require of a limit stated today. Or scope the cap to entries above some length, which reintroduces a bare number and should be resisted. Or accept that 87 historical lines are grandfathered and the cap binds only new ones — cheapest, and honest so long as it is written down rather than left as drift.
**The uncomfortable reading, recorded because it is the one a later auditor should test.** A limit whose own corpus violates it 87 times is close to the failure [derivation-required-for-limits] was written to prevent — a number that fires against correct work. It was measured, which is more than the 1,200-word ceiling ever was; it was just measured on too little.
