#### The queue cannot express "ready, but must run alone", and the rename is now behind twelve items that will share its run [no-way-to-mark-work-that-must-run-alone]
Filed 2026-08-12 by Claude mid-/plan, from a state this session created, and processed in the same session at the user's direction — they chose to settle it before running /next rather than supervise a run by hand.
**The state.** [rename-to-throughliner] carries an explicit instruction in its own prose: it must not share a run, because the folder rename invalidates every path naming that folder, so a half-landed rename leaves paths pointing at a folder that no longer exists — finish it or do not start it. Its answer to that was positional: sit last in the cleared region so a run reaches everything else first. This /plan cleared twelve items ahead of it. /next works the cleared region top-down and finishes at the readiness line, so a single invocation would build twelve items and then begin the rename in the same run.
**Why the positional answer was never sufficient, which this session makes visible rather than causes.** Placing an item last does not stop a run reaching it; it only decides when. The instruction "must not share a run" has no mechanism behind it at all — it is prose that a run is trusted to honour, and /next's documented behaviour is to keep going to the line. With one item ahead of it the gap between instruction and mechanism was invisible. With twelve it is not.
**Why this is a real gap rather than this one item's problem.** Any large atomic change has the same shape: a rename, a folder move, a migration that invalidates paths midway. The method will meet it again, and until now the only tools available were a tag that means something else and a position that does not bind.

Mechanical, no judgment, and it composes with the readiness line rather than replacing it.
**The three rejected routes, with why each lost.** Widening `[freeform]` is the closest fit and is wrong on meaning: `[freeform]` marks work /next must **not** build, and this is work /next **should** build, just not alongside anything else — widening it would give one tag two meanings and blur the precise case it exists for. That was about danger; this is about solitude.) Making it /plan's discipline — never clear other work above a solo item — is unwritten and fails silently, since a later /plan clears something and nobody notices the constraint broke. Doing nothing was weighed and lost on the evidence: the instruction has sat in the rename's prose for days with nothing acting on it, and the protection so far has been luck.
**The honest limit, not to be softened.** This binds /next and nothing else. It does not stop a person building the item alongside other work by hand, and the marker must not be described as guaranteeing the item runs alone — only that an unattended run will not sweep it up.
**What the build must check rather than assume, per this project's hook-enforced-format rule.** Grep the literal marker text across the repo before the build starts, so the file list is complete. The expectation is three sites — `plan.md` for how the marker is written and when it is placed, `next.md` for the run bound, and the queue lint's valid-field set in `post_tool_use.py` — but the queue lint held no list of valid flavors when `[freeform]` was added, so whether it needs anything here is a thing to verify either way, not to guess.

#### CONTRADICTED reads a multi-item run's mixed dispositions as a contradiction, and every large run will trip it [contradicted-flags-mixed-disposition-runs]
Filed 2026-08-12 by Claude, immediately after repairing the disposition format made the signal readable enough to expose this. The flaw is the detector's; the format error that hid it was Claude's.
**What it does now.** `_log_dispositions` maps a commit hash to a *set* of disposition kinds found across all LOG entries naming that hash. CONTRADICTED fires where that set contains `not needed` and the always-loaded count rose. On a sixteen-item run every entry carries the same commit hash, so one item legitimately recording `not needed` — a script fix, a test-fixture repair, a hook change — puts `not needed` in the set for the whole commit, while a *different* item in the same commit authored a rule and correctly recorded `run` with the count rising because of it. The signal reports a contradiction between two artifacts that do not in fact disagree.
**Why it surfaced only now.** Every disposition in the recent entries was written as `**Rule gate:**` in bold, and the detector matches `^Rule gate:` at line start, so none of them was visible at all. Unbolding them made BORN correct and simultaneously gave CONTRADICTED enough input to misfire: it went from one commit flagged to three (`e5d169b` +5, `0ae69d6` +1, `b51d205` +2). All three are multi-item runs.
**This is not an argument that the check is worthless.** Its stated job — catching a commit whose LOG claims the gate was not needed while the corpus grew — is real, and on a single-item commit it does exactly that with no judgment required. The defect is that a commit is the wrong unit once a run ships sixteen items under one hash.
**The route, chosen by the user at /plan on 2026-08-12 from three Claude set out.** Fire only where **every** disposition naming the commit says `not needed`. It is checkable today with the data already collected, it silences all three current false fires, and it keeps the single-item case the check was built for working exactly as before.
**The two rejected routes, with why they lost, so neither is re-proposed.** Keying the check on the LOG *entry* rather than the commit is the correct shape and is not buildable now: it needs a per-entry attribution of the rule-statement delta, and the delta comes from a `git show <rev>:<path>` diff that is per commit by construction. Doing nothing and documenting the limit was weighed on the strength of the signal's own hedging message, and lost because the check would go on firing falsely at every large run — and a check that cries wolf gets skimmed past, which is the exact failure this project fights hardest.
**The cost of the chosen route, recorded rather than left to be discovered.** A mixed run in which one item genuinely authored a rule and wrongly recorded `not needed` will now pass silently, because a sibling entry in the same commit recorded `run`. That is a real loss of coverage, accepted in exchange for a signal that does not fire falsely on every large run.
**One thing to preserve.** The existing text is careful to say the check cannot tell whether a gate recorded as *run* ran honestly. The rework must keep that limit stated rather than quietly implying broader coverage.
**The build.** In `resources/rule_signals.py`, `signal_contradicted` changes its test from "the disposition set for this commit contains `not needed`" to "every disposition naming this commit is `not needed`". `_log_dispositions` already returns the full set, so no change is expected there — confirm rather than assume. The signal's printed message is reworded to say what it now means, keeping the honest-`run` limit intact. Verify by running `python resources/rule_signals.py .` and seeing CONTRADICTED go quiet on `e5d169b`, `0ae69d6` and `b51d205`.
**A SECOND defect found 2026-08-12 in the post-close tail, and one of the three commits above is not a multi-item run at all — check this before building.** `b51d205` committed exactly two files: `CLAUDE.md` and one LOG entry whose disposition reads `run`. It should never have been flagged. It was, because a *different* entry — `LOG/2026-08-12-pre-tool-use-schema-checks-failing.md`, which belongs to `e5d169b` and says so in its own heading — mentions the string `b51d205` in its prose, describing a test reproduced "against a detached checkout of `b51d205`". `_log_dispositions` attributes a disposition to a commit by matching the hash **anywhere in the entry**, so a prose mention of any commit silently donates that entry's disposition to it.
**What that means for the chosen route.** The every-disposition-must-say-not-needed rule does silence `b51d205`, because the set becomes `{run, not needed}` — so the verification step above will pass. **It passes for the wrong reason**, and the misattribution survives underneath: a future commit can still inherit a `not needed` from an unrelated entry that merely names it, which under the new rule would *mask* a genuine contradiction rather than create a false one. The failure direction inverts, which is worse to detect.
**So the build carries a second change:** attribute a disposition to a commit only from an entry whose **heading** names that commit, which is the position the backfill writes and the one the entry's own identity rests on. Prose mentions of a hash are commonplace — this project's entries cite prior commits constantly — and must not count. Verify both: CONTRADICTED goes quiet on all three, *and* an entry mentioning a foreign hash in prose no longer contributes its disposition to that commit.
**Files:** `resources/rule_signals.py`. Host-only — not in the plugin package, and consumers never author method rules, so no SPEC or FAQ change follows. Relates to [rule-gate-runs-at-close-not-at-authoring] (which moved the disposition to authoring time) and [board-header-counts-inert-signals] (the other board-reporting item filed the same session).
**Processed 2026-08-12 and cleared to run**, placed after [plan-quiet-list-fixture-also-stale] and before [rename-to-throughliner], which stays last because it must not share a run.

#### Superseded research leaves every item scoped against it silently wrong, and nothing connects the two [no-link-from-research-to-items-scoped-on-it]
Filed 2026-08-12 by Claude at the /plan wind-down, from the largest thing that happened in the session.
**What happened.** `resources/research/instruction-file-bloat-and-subtraction.md` supplied a ceiling of 150–200 instructions. That number had propagated into a constant in `resources/rule_signals.py`, a firing board signal, and the framing, title and success measure of three separate queue items. Re-validating it against the 5-series showed it roughly an order of magnitude too tight. Nothing anywhere connected the research file to the work scoped off it — the propagation was found by working through the affected items by hand, and only because the user asked for the re-validation.
**Why it generalises.** Research is filed precisely because it will be re-read and reused, so a research file is an upstream dependency of everything that cites it. But citation runs one way: an item names the file, the file names nothing. When a finding is superseded, there is no path from the correction back to the decisions built on it, and those decisions do not announce that they rest on anything.
**The item's own honest bound has been overtaken, which is what changed the decision.** It was filed saying this was the first known instance, caught, and that a mechanism costs standing effort against a rare event — the shape the method usually declines. The count is no longer one. [gate-still-declares-the-old-ceiling], processed in this same /plan, is a second confirmation: the same superseded figure had reached the self-authoring gate's opening argument, further than the four queue items the original sweep found. And [index-cap-sample-was-three-entries] is a third of the same shape — a bound derived from three entries, propagated, then falsified by 87 existing lines. Three instances is a different argument from one.
**The route, chosen by the user at /plan on 2026-08-12.** A research file that is superseded gains a **`Superseded by:`** line at its top, and the queue digest flags any work item whose prose names a research file carrying one. The correction is written once, at the moment someone already has that file open for the re-validation, and the detection is mechanical rather than remembered.
**The two rejected routes, with why they lost.** A "what cited this" list maintained on the research file was rejected because it is maintained by hand and goes stale the moment one person forgets to add a line — and it fails *silently*, which is precisely the failure mode being fixed, so it would leave the appearance of coverage with none of it. Doing nothing was weighed seriously, as the item asked, and lost on the count: the argument for it rested on one caught instance, and there are now three.
**The coverage limit, written in at the user's instruction and not to be softened later.** This catches only items that *name the research file in their prose*. An item scoped on a finding it never cites stays invisible, and no mechanism proposed here reaches it. The check must say so where it is documented, so it is never read as complete coverage — the same standard this project holds the board's signals to.
**The build.** Document a `Superseded by: <path or item>` convention for files under `resources/research/`, written at the top of the superseded file at the moment it is superseded. Add a check to `scripts/queue_digest.py` that scans each work item's prose for `resources/research/` filenames, opens each named file, and flags the item where that file carries a `Superseded by:` line — reported alongside the existing placement contradictions, which is where a flag-don't-decide finding already belongs. State the prose-citation limit in the digest's own output or its documentation.
**Files:** `plugin/si-plugin/scripts/queue_digest.py` (the new check), **`SPEC.md`**, plus the convention documented wherever `resources/research/` filing is described, and a FAQ entry — the digest ships, so a consumer who files research sees the new flag.
**SPEC.md is named deliberately, at the /plan close's spec-sync gate on 2026-08-12.** SPEC describes what the digest reports — the placement contradictions it surfaces and the principle that they are surfaced and never acted on. This adds a new flag to that same output, so SPEC's list becomes incomplete when it ships. Naming SPEC.md here lets it move in the same commit as the behaviour. #### The keep-step's destination-first move keeps corrupting QUEUE.md on its second write, three times in one session [keep-move-second-write-corrupts-queue]

**What the procedure says.** `plan.md`'s keep-step prescribes two writes in one turn — add the item to Processed at its placement, then remove it from Unprocessed — and gives a good reason for that order: if something interrupts between the two, the item exists in Processed and only a stale copy needs cleaning, where the reverse order would lose the text entirely.
**What actually went wrong, three times.** The failure is never the first write. It is the second, and it took three distinct forms in one session. Once the removal matched the newly-written Processed copy instead of the Unprocessed original, silently undoing the move and leaving the file exactly as it started. Once the repair edit spliced a `#### ` heading into the middle of a neighbouring item's paragraph, which briefly made two work items unreadable as work items. Every one was caught and repaired, and the digest confirmed a clean file each time.
**Why it happens.** After the first write the file contains two near-identical copies of the same text, and the removal is expressed as an exact-string match. The two copies differ only in their tail — the processed version's rationale is rewritten, the heading and opening paragraphs usually are not. So the most natural string to reach for is ambiguous by construction, and an edit tool that requires uniqueness will either refuse, match the wrong one, or match a fragment. The window the procedure calls "one turn" is exactly the window in which the file is most hostile to a string match. **This is structural, not carelessness** — the procedure already asks for care and got three failures from a session that had read it.
**The route, chosen by the user at /plan on 2026-08-12: document the sequence, do not add machinery.** The keep-step's move becomes three edits rather than two. Third, delete the placeholder-marked block by that now-unique heading. The destination-first safety property is unchanged: an interruption still leaves the item present in Processed rather than in neither section.
**The evidence for the placeholder technique, and its honest weight.** It was found by trial in the session that filed this, and it worked on every attempt after it was adopted — including the hardest case, a relocation that had to move an item to a different position as well as across sections. An earlier technique, anchoring the removal on the *preceding* item's final unique line, also worked but depends on a unique neighbour existing. A handful of successes against three failures is a lead rather than a proof, and the build should say so rather than presenting the sequence as guaranteed.
**Why not the queue tool, which is the instinctive answer.** Routing the move through `resources/reorder_queue.py` or a purpose-built queue tool is heavier than the problem: it is a second mechanism to maintain and to keep in step with the format, and the failure here is a string-matching hazard that a sequencing change removes outright. The scope-lock already points at a queue tool for *large* queue edits, and that stays true; this is not one.
