The wider class the caller-side check would catch is a logic bug in the script itself, which is real but is what the script's own test suite is for.
**The defect being fixed is the false report, not the failed write.** A delete that fails loudly costs a retry, which this run demonstrated: the identical command succeeded a moment later. A delete that reports success and does nothing breaks the guarantee the whole design rests on — that an item still showing in QUEUE.md means exactly one thing, not built yet.
**One trap to build in rather than discover.** If the cause is the Drive sync layer this project sits on, a plain read-back may be served the same cached content the write went into and pass anyway — a verification that cannot fail for the exact reason it exists. **Fresh evidence from this session, recorded because it is a data point and not a resolution.** `--delete` and `--move-section` were both run here and both landed, confirmed by the digest. That is consistent with the original observation — one failure in six — and does not narrow the cause.
