#### The INBOX has no way to correspond with a project whose name is itself sensitive [inbox-privacy-for-sensitive-correspondents]
Captured by you 2026-08-14, during a /plan session, from your own observation that this raises further issues on INBOX privacy. Your instruction that a particular correspondent's identity and path must not be recorded anywhere is what surfaced it.
Red flag · State: cleared
**Cleared 2026-08-14 by designing it out, not by acceptance.** The three decisions the item said were unsettled were made in a /plan session and are recorded below. Mixed authorship: the user raised the capture and the underlying instruction that surfaced it; she also proposed keeping the address book in the gitignored `INBOX/` folder and referencing it from CLAUDE.md, which turned out to be the design already in force and therefore to change nothing about the risk. The two decisions that close it were Claude's recommendations and the user's agreement.

**Decision 1 — the address book is write-and-send only.** A session may pass a recorded path to a send. It may never quote the path, never name a correspondent in any document, and never carry either into chat. This is the decision that actually closes the hole, because the exposure was never publication: `INBOX/` is gitignored on every path already, so the file is not published, and the risk is that a session reads it and copies a name into QUEUE.md or a LOG entry, which are committed. Locating the file differently does not reach that; restricting what may be done with its contents does. It also answers the item's third open question — what a session may read from the address book — so that is not a separate decision.

**Decision 2 — an outbound send checks the recipient's ignore rules and refuses until the user approves.** Before writing a message into another project's folder, confirm that project's `INBOX/` is actually covered by its `.gitignore`. Where it is not, say so plainly and do not send until the user says go. This is one more limb on a check that already runs — the sender already confirms the recipient has a mailbox and says so when it creates one — rather than a new mechanism. The alternative of sending with a warning was rejected: a warning at the moment of sending is the kind that gets clicked past, and the cost of being wrong lands in a repository neither party can see.

**The situation, described without instancing it.** Some projects are private in a way that goes past "not published": the folder name alone can identify a real person and a sensitive matter. The INBOX design assumes correspondents are ordinary projects whose names are unremarkable, and it has no notion of one that is not.
**Four exposures, and only the first is currently mitigated.** (1) The address book records a correspondent's absolute path the first time one is supplied, automatically and with no ask. It lives inside `INBOX/`, which `.gitignore` covers, so it is not published — but it sits in plain text on disk and any session in this project may read it and carry a name out of it into a document that *is* committed. (2) An outbound reply is written into the recipient's own folder, so a file from this project appears inside a private repository whose ignore rules this project does not control. (3) An inbound message may carry the sender's name or content, and nothing at the sending end requires anonymity — the one that prompted this identified itself only as "a project running throughliner 1.20.0-test2", which was the sender's discretion, not a rule. (4) Anything an inbound message produces is processed into QUEUE.md, which is committed and public; the scrub checklist is the only thing standing between a sensitive sender's details and a public repository, and that checklist is Claude checking its own writing.
**What the flag is about, stated plainly.** The gitignore protects against publication and nothing else. It does not stop a name reaching a committed file by way of a session that read the address book, and it does not reach the recipient's repository at all.
**What the two decisions do and do not reach.** Exposures 3 and 4 — an inbound message identifying its sender, and that content being processed into a committed QUEUE.md — are downstream of nothing this project controls: the sending end's discretion, and the scrub checklist, which is Claude checking its own writing. They are not closed by this item and must not be described as closed. What is closed is the route out of the address book, and the route into a repository this project cannot see.

Files: `plugin/throughliner/docs-b/feedback-and-inbox.md` — add the write-and-send-only restriction to the address-book section, and add the recipient-gitignore limb to the send flow, including the refuse-until-approved wording. `SPEC.md` — the INBOX paragraph states what the address book records and what sending guarantees; both gain a sentence, and the sentence about `INBOX/` being gitignored gains the clarification that this protects against publication only. `plugin/throughliner/templates/faq-template.md` plus its index line in `faq-index-template.md` — a user meeting a refused send needs an answer to why their message did not go, and the entry says what to do about it.

#### A cloud session runs on a clone, which the isolation check reads as a shared tree and advises wrongly [clone-reads-as-shared-tree]
Filed 2026-08-14 by Claude, from the user's screenshot of a cloud session's initialization steps.
**What the evidence shows.** A Claude Code cloud session — one started from the mobile or web app against the GitHub repository — reports its startup as: set up a cloud container, **cloned repository**, run setup script, started Claude Code. It does not use a worktree. It works on a clone inside a container, and its work reaches this machine only as a pushed branch.
**The defect.** `session_start` decides which parallel-session advice to give by comparing `git rev-parse --git-dir` against `--git-common-dir`: they differ in a linked worktree and match in a main checkout. **In a clone they also match**, because a clone *is* a main checkout. So a cloud session is classified as a shared tree and receives the shared-tree advice — that two appends to different parts of QUEUE.md do not collide and the file-modified warning will catch it if they do. Both halves are false there. The session is fully isolated, nothing it writes is visible to any other session, and the file-modified warning cannot fire across a container boundary.
**Why this is worse than the worktree case rather than the same.** The worktree branch of the advice at least describes isolation, so a session reading it is warned that a capture will not reach the other side. A clone gets the branch that tells it collisions are handled — the one piece of advice that actively misleads.
**The shape of the fix, to settle at processing.** The isolation model has three cases, not two: main checkout, linked worktree, and clone-in-a-container. The two-way comparison cannot distinguish the first from the third, so a third signal is needed. Candidates to weigh: an environment marker the cloud runner sets, whether the checkout's path lies outside the user's own project folder, or whether `origin` is present while the local path is a container-style location. Each needs checking against a real cloud session rather than reasoned about — this capture asserts the defect, not the detection method.
**What must not be assumed.** That the advice merely needs rewording. The clone case wants its own third branch saying that work reaches the main machine only as a pushed branch and that a capture filed there is invisible until it merges. Relates to [cleared-sessions-may-never-get-a-worktree], [worktree-scan-cannot-classify-branches] and [concurrent-session-support], and to `resources/research/worktree-isolation-and-desktop-sessions.md`, which covers worktrees and does not mention clones at all.

**The detection method, measured rather than guessed, 2026-08-14.** A live cloud session was asked to report its git layout and environment. Both `--git-dir` and `--git-common-dir` resolved to the same `.git`, confirming an ordinary clone rather than a linked worktree — which is exactly why the two-path comparison misclassifies it. The environment carries the discriminator:

```
CLAUDE_CODE_REMOTE_ENVIRONMENT_TYPE=cloud_def…   # the one to key on
CLAUDE_CODE_ENTRYPOINT=remote_mobile
IS_SANDBOX=yes                                    # broader; other sandboxes may set it
```

Key on `CLAUDE_CODE_REMOTE_ENVIRONMENT_TYPE`: present means a cloud clone, whatever the git comparison says. `IS_SANDBOX` is rejected as the signal because it describes sandboxing generally rather than this environment, and a false positive would hand an ordinary session the wrong branch of the advice.

**Absence must mean "not cloud", and the check falls back to today's behaviour.** These variable names are undocumented, so a rename is a live risk. Written this way, a rename loses the improvement; written the other way, it produces a confident wrong answer. Also worth capturing at build time: the container was `sandbox-ccr-default`, running Claude Code 2.1.42, entered from mobile.

**What gets built.** `session_start.py` gains a third isolation case ahead of the existing two-path comparison, and the always-loaded advice table gains a third branch for it — work here reaches the main machine only as a pushed branch, and a capture filed here is invisible to every other session until that branch merges. `resources/research/worktree-isolation-and-desktop-sessions.md` gains a section on the clone case, since it currently reads as though worktrees were the only isolation mechanism.
