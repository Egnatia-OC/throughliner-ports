# QUEUE

Two sections. **Processed** — work discussed and agreed, ordered top-to-bottom; /next builds from above the `--- Cleared to run above this line ---` marker. **Unprocessed** — captured, not yet fully processed; the next /plan weighs each item. A work item is a `#### ` heading (its description) with a `[slug]` at the end of that line and its rationale in the block beneath. A leading `[audit]` / `[user]` tag names how it's executed; no tag means a build. A work item carrying a security or privacy risk gets a `Red flag · State: …` marker — the flag rides the work.

#### Flip the approval flow to write-first-then-report, gated by one test: does a revert fully undo it [write-first-approval-flow]
Raised by the user, 2026-08-09, and adopted in practice from the moment they asked — so the method's text lags the working practice until this builds. The design below is Claude's, settled in the same session with the user's agreement; their own stated want was simply to stop having drafts pasted into chat.
**What changes.** Today Claude drafts text in chat, the user approves it, then Claude writes. After this, Claude writes first and reports briefly what landed. plan.md's ground rule ("never write to QUEUE.md without showing the exact text first — the message immediately before any write must contain the text verbatim") and plugin-behaviour.md's approval-time-outputs rule both invert rather than relax.
**The one test that decides which moments flip, rather than a list to memorise: does a revert fully undo it?**
- **Yes → write first, then report.** Queue items and captures, LOG entries, SPEC edits, and ordinary file edits during a build. All are tracked in git, so rejection costs a revert and nothing else. The user reads the text in the doc, which is where it lives anyway.
- **No → keep showing first.** Two kinds. A **commit message**, because a commit is materially harder to unwind than a file edit, and because it never becomes file content, so "write it first" has no meaning for it. And anything that **leaves the machine** — the feedback report at flintcraft.tech/report, an outbound INBOX message to another project ([cross-project-inbox]) — where a revert cannot reach the copy already delivered.
A single test rather than an enumerated carve-out list, deliberately: the gate's wording rule asks for qualification expressed as structure, and one test survives new approval moments being added later, whereas a list silently omits them.
**The report after the write.** One line naming what landed and where — a pointer to the doc in local mode, never a re-paste of the text just written, which would spend the tokens the flip exists to save. It must be specific enough to object to without opening the file, because the risk this trade introduces is not rejection, it is a user *not noticing* and a later commit sweeping unapproved text in.
**The trade, stated in the rule rather than discovered.** Show-first guaranteed unapproved text never reached disk. Write-first means the file briefly holds content the user has not agreed to. In a git repo that is cheap and recoverable; the honest cost is that rejection becomes a revert rather than a non-event, and the user has to be told so once.
**One thing it improves rather than costs.** The write-then-verify-then-point rule exists because pointers were once emitted for writes that never happened. Write-first removes the gap that failure lived in: the write is real before anything is reported.
**A dependent rule inverts with it, found by using the new flow, 2026-08-09.** The keep-step currently instructs: remove the item from Unprocessed **first**, then add it to Processed — explicitly because "the drafted Processed item is already approved and on screen, so nothing is lost if something interrupts between the two writes." Under write-first nothing is on screen, so that justification is gone and remove-first becomes the lossy order. The move must reverse: **write the item into Processed first, then remove it from Unprocessed.** The cost the original order was avoiding — a brief window where the item shows in both sections, which reads as an uncleaned duplicate — is the lesser one, and it can be narrowed to a single turn. Found in practice during the session that decided the flip, not reasoned about in advance.
**Supersedes the ordering half of [approval-flow-token-doubling-simplification].** That item reached the same flip from the token-cost direction and gated it on harness issue anthropics/claude-code#77134. The ordering is decided here and is not gated on the harness: if #77134 lands it only makes the report cheaper to render. That item keeps its remaining scope — the harness-dependent rendering and its convergence with the view-in-doc machinery.
**Files:** `docs-b/plan.md` (the ground rule and the keep-step), `docs-b/plugin-behaviour.md` (the approval-time outputs rule and the write-then-verify-then-point ordering), `docs-b/next-build.md` and `docs-b/done.md` (their approval moments), plus a FAQ entry — a consumer told that Claude always shows text before writing will notice this change.

#### Name most-unblocking-first as the default in /plan's entry ask, and give the order a fallback ladder that degrades silently [plan-entry-ordering-default]
Raised by the user, 2026-08-09, whose wording for the ask was near-verbatim: *"is there anything else you want to prioritise, or are you ready to go through items in order of most unblocking first?"* The ladder below is Claude's design, settled in the same session.
**The evidence.** Mid-session the user asked whether anything in the queue would become unblocked soon and therefore make sense to process now. That question produced the best sequencing decision of the session — three clusters worth taking, and one to deliberately avoid because it would write into a corpus about to be inventoried. **Half of it already exists, which makes this an amendment.** plan.md's start-of-processing step already orders surviving items by unblock-potential and narrates a throughput floor. It runs *silently, after* the entry ask, so the user is never offered the choice and never learns the option is there. Naming it in the entry ask costs one clause on a question that already fires.
**The opening has two beats, in this order (user's correction, 2026-08-09): drop first, then order.**
1. **The droppable set, as the first ask.** The existing triage bulk-drop pass — items with a one-sentence uncontestable reason they are not worth doing, presented as one numbered set the user contests by number. This is what the user identified as overlapping the ladder: there is no point ordering items that are about to be deleted, and dropping changes what is left to order. If nothing is obviously droppable, this beat does not fire and the opening is just beat 2.
2. **The ordering ask, one question with a stated default:** anything you want to prioritise, or shall I work through them most-unblocking-first? One question, not a menu — the only alternative offered is the user's own priorities.
**This moves the triage pass earlier in the procedure.** Today the entry ask sits in Step 1 and the bulk-drop pass sits at the opening of Step 2, so the user is asked what to discuss, then shown a drop set, then the reorder runs silently. The two asks merge into one opening in the order above, and the Step 1 "anything to discuss?" question is absorbed by beat 2 rather than surviving alongside it — three opening questions where two will do is the shape this fixes.
**The ladder is internal, applied and never offered.** It decides what "most-unblocking-first" degrades to when nothing unblocks anything, and it is surfaced only through the one-line narration the throughput floor already emits. This is what keeps the ask one question while still giving the order a defensible basis:
1. **An uncleared red flag in Unprocessed** — unaddressed data-exposure or privacy risk. First, because the cost of leaving it is a breach rather than a delay, and session_start already surfaces open flags so the signal exists.
2. **Unblock-potential** — the user's default, and what nearly every session will actually use.
3. **Decay** — an item whose premise is going stale, or whose evidence only holds while the observation is fresh. The 2026-08-09 revert is the standing proof that stale premises are expensive and announce themselves least.
4. **Cheap to settle** — items decidable in one exchange, which clears volume so the queue stops reading as heavy.
5. **File order** — position in the section, the existing fallback.
**One deliberate deviation from the user's stated default, flagged rather than slipped in.** They asked for most-unblocking-first as the top rung; it sits second, under uncleared red flags. Rung 1 fires rarely, so in practice the default the user meets is theirs — but when a live risk is sitting in the queue, throughput should not outrank it.
**The empty-queue rung already has a home.** plan.md Step 1's "seed the queue from SPEC" fires in the thin-queue/rich-SPEC state and can be invoked manually at any time, so the user's "ideation session" is that step offered by name. If SPEC is thin too, the offer is an ordinary conversation about what they want next. **Anti-invention guardrail, explicitly:** ideation must not become a new session type, mode, or container — there is no fifth state. It is an offer made inside /plan.
**Roughly volume-neutral under the gate.** The ask exists, the reorder exists; the ladder is new text but it replaces an unstated oldest-first fallback with a stated one, and it lives in the step rather than in always-loaded prose.
**Files:** `docs-b/plan.md` (Step 1's entry ask, which is absorbed into beat 2; the Step 2 triage bulk-drop pass, which moves up to beat 1; the start-of-processing reorder, which gains the ladder), plus a FAQ entry — the entry ask is the most-seen moment in the method, so a changed default is user-visible.
