#### The `captured by you` credit is unreliable in two ways: it only resolves for one reader, and it gets applied wrongly with nothing to catch it [provenance-credit-second-person-ambiguous]
Captured by you 2026-08-03 — you asked who "you" refers to in a provenance line, then challenged a credit that turned out to be wrong.
The credit means the project's user, and the convention is deliberate: [provenance-labelling-reconsideration] shipped at `ea272f6`, dropping mandatory provenance for an asymmetric default-AI scheme where an unmarked item is Claude's and only a user-raised item carries a credit. **That decision is not in question** — the asymmetry is sound and cheap. Both problems below sit inside it.
**Problem 1 — it resolves only for one reader.** The credit is direct address, so it works only if the reader is the person it was written for. That always holds in a solo project. It stops holding for a repo that goes public ([scrub-gate-before-approval], [setup-repo-privacy-and-publishing]), for a project handed on, or for any second reader — where "captured by you" points at nobody identifiable.
**Problem 2 — and this one is worse — the credit gets applied wrongly, and nothing catches it.** Live instance the same day: [reorder-mover-marker-at-top-blind] carried a `captured by you` credit from filing. It records a script throwing an internal error during a /done close — something only Claude could have seen. The user had no way to observe it. The credit was then *inherited unchecked* through a full processing pass, and only caught because the user happened to say it didn't feel like theirs.
**Why that's the more serious half.** An ambiguous credit is a reading problem; a wrong credit corrupts the record. The queue's purpose is preserving who decided what, and a mis-credit silently attributes thinking to the wrong party — in the direction that flatters the user's involvement, which is exactly the direction nobody will question. It also survives processing, because a rewrite preserves the provenance line as given rather than re-deriving it.
**Measured at processing, 2026-08-05: 40 of the queue's 55 items carry a `captured by you` credit.** Framed carefully, because the number is suggestive rather than diagnostic — it is entirely consistent with being true, since there is one user and they are the developer, so they do raise most things. What it does establish is that the credit discriminates almost nothing in practice: a marker on three-quarters of items tells a reader little, and a single wrong credit is well camouflaged among them. That is the condition under which the known mis-credit survived a full processing pass unnoticed.
**Problem 1 is resolved by the user's decision, 2026-08-05: record a real first name, an alias, or another identifier at /setup, and credit captures to it.** Claude had recommended a one-line queue-header explanation instead, on the grounds that a name writes a person into a repo that may be public. **The user's framing already answers that** — offering an *alias* gives multi-user disambiguation with none of the exposure, so the objection applies to a name-only design and not to this one. The user's reason: "you" breaks down as soon as a project has more than one user, and the header line only ever worked because this project has exactly one.
```
rejected: "captured by the user"  -> unambiguous but colder, and the second
                                     person is part of how the queue reads as
                                     the user's own document
rejected: name-only, no alias     -> writes a real person into every item of a
                                     possibly-public repo
kept:     an identity recorded at /setup — real name, alias, or other, the
          user's choice, with the alias route offered plainly
```
**Three things the build must settle rather than assume.**
1. **The multi-user case the field exists for.** A single stored field records *one* identity, so where two people genuinely share a project, the second person's captures would be credited to the first — the exact failure this is meant to fix, reintroduced. Decide between a per-session confirmation, a field explicitly scoped to "the project's primary user", or something else. Do not leave this to inference.
2. **The ask is a solicited identifier, so it is governed by the private-information rules.** /setup must say plainly, at the moment of asking, that the answer is written into committed project docs — and offer the alias in the same breath. /setup already detects repo visibility, so a public repo should lead with the alias option rather than mentioning it as an afterthought.
3. **What happens to the 40 existing credits.** A new field protects new items and does nothing about those already written. Migration is [provenance-credit-audit]'s territory; this item must not silently assume it happens.
**Problem 2 — a filing-time test, plus re-derivation at the keep-step.** State the test in words: *could the user have observed this unaided?* And require the keep-step to re-derive the credit from the discussion rather than inherit the filed one, because inheritance is precisely how the known bad credit survived processing. No lint — this is a judgment a hook cannot make, so it is a wording fix.

#### Design proactive rationale-nudging: Claude asks for the *why* without nagging [throughline-feature-elevation]
Captured by you (2026-07-30); reframed 2026-08-01. Earlier threads are gone: thread (a) — the why-pipeline → "throughline" rename — folded into [rename-to-throughliner]; thread (b) — user-provenance on rationale — folded into [provenance-labelling-reconsideration] (2026-08-01) for one consistent provenance scheme. Because this is the titular feature — durable rationale that survives a forgetful session — it should be genuinely excellent. **Designed 2026-08-05 from that session's own evidence, which resolved the crux and changed the mechanism.**
**The finding: the productive nudge is a proposal, not a question.** Almost none of that session's rationale came from anyone asking "why". It came from Claude stating a recommendation *with its reasoning* and the user disagreeing. The clearest case is this queue's own [provenance-credit-second-person-ambiguous]: Claude recommended a queue-header line and gave its grounds; the user overrode it with "'you' breaks down when there are multiple users", and that sentence is now the item's rationale. The same shape produced the rationale on [lint-blind-to-readiness-marker], [docset-a-completion-ask-inconsistency] and [merge-and-fold-without-asking].
**Why that reframing dissolves the nagging problem rather than managing it.** A "why do you want that?" question arrives empty and makes the user do the work, which is exactly what nags. A proposal costs the user nothing when they agree — one word — and when they disagree, the reason arrives attached, because people justify corrections for free and resent interrogation. So "when can the nudge fire without nagging" is hard to answer for a question and easy for a proposal: wherever a decision is being made.
**The moments, now nameable:**
```
/plan keep-step    ->  a recommendation carries its reasoning explicitly.
                       Mostly making existing practice a rule, not a new beat.
the close          ->  where a decision's rationale is written down.
a user OVERRIDE    ->  the highest-yield moment of the three, and the one with
   of a proposal        no rule at all today. An override is rationale arriving
                        unbidden; nothing currently says to capture it as such.
```
**One suppression limb, non-negotiable:** don't propose where the answer is predictable. [merge-and-fold-without-asking] is the user saying plainly that a whole class of Claude's asks was redundant, filed the same day. A nudge design that ignores that reinvents the behaviour the user asked to stop.
**Rejected: sharpen-and-skip for a dedicated design pass.** Legitimate and offered; the user chose to keep it, because the crux is settled and the remaining questions are build-sized rather than design-sized. Recorded so the option isn't re-proposed as though it had been overlooked.
**Cost to weigh at build:** a proposal-with-reasoning spends tokens every time, and the same session established that approval-time token cost lands hardest on Pro users ([approval-flow-token-doubling-simplification]). The suppression limb is what keeps this affordable, so it is part of the feature rather than a refinement.
**Files:** `docs-b/plugin-behaviour.md` (the throughline section — the nudge's proposal form and its suppression rule), `docs-b/plan.md` (the keep-step: a recommendation carries its reasoning), `docs-b/done.md` (capturing rationale at a user override), SPEC.md if its description of the throughline changes, README feature-list sync, and a FAQ entry. #### Shell commands bypass the file scope-lock entirely — `pre_tool_use.py` only guards Edit/Write/MultiEdit [shell-writes-bypass-file-scope-lock]
By Claude, from this session's scope-lock audit; filed at your request.
**The finding.** `pre_tool_use.py:391` reads `if tool_name not in ("Edit", "Write", "MultiEdit"): return 0`, so the file-scope enforcement below it never runs for Bash or PowerShell. Those tools route to the git-safety checks only (`:348–386`), which match four git patterns and consult `build_files` not at all. During a fully scope-locked build, `sed -i`, a `>` redirect, `cp`, `mv`, or `Set-Content` writes any file on disk with nothing noticing.
**Why it matters more than the other known holes.** [plan-scope-lock-gap-and-emergency-path] and [post-close-tail-state] both record the lock being *off* in a named state — planning, and the post-close tail. This is different: the lock is *on*, the session believes it is contained, and one tool class walks around it. It is the only hole in the one layer that can't be skipped by instruction, so every doc-level scope rule rests on a floor with a gap in it.
**What has masked it.** The user's global instructions forbid shell redirection for writes on stale-mount grounds, and the procedure docs never reach for shell writes, so no session has exercised the path. That is convention, not enforcement, and it doesn't ship to consumers.
**What to weigh at design.** Whether to parse shell commands for write intent (fragile — the same pattern-as-data limit the git checks already acknowledge at `:63–68`), or to deny the small set of obvious file-writing forms during an active build and name the Edit/Write alternative in the denial, or to accept it and say so plainly in SPEC rather than describing a containment the hooks don't provide. Note the third option interacts with SPEC's already-overstated scope-lock description, which [plan-scope-lock-gap-and-emergency-path] flags for the same reason.
**Independent corroboration, 2026-08-04.** The user shared a scope-lock tool built separately for someone else, on a different agent platform (Codex, alongside a memory tool called Hermes). It solves the same problem and hit the same gap, which makes its reasoning a second data point rather than an opinion.
**It reached option three deliberately.** Its documentation lists shell-side writes as a known, accepted gap in v1, with the reason stated: blocking them reliably means parsing arbitrary shell, which produces false denials — and **false denials train workarounds**, so the false-denial failure is the worse one. That phrasing is worth keeping; this project has the underlying idea in its anti-invention rule but has never said it this compactly about enforcement specifically. It also names its own honest consequence: the gap is closed behaviourally, by an instruction not to route around denials, and not mechanically.
**But it does not accept the whole gap, and this is the part that changes the options above.** It catches one case — a structured patch envelope invoked through the shell — by matching the command name and extracting the target paths from the envelope. That is narrower than "deny a small set of obvious file-writing forms" and it carries no false-denial risk, because a structured envelope either parses or it doesn't. Weigh it as the leading candidate.
**Two convergences worth recording, because they confirm existing directions rather than opening new ones.** The tool fails open on any error, which is the direction [unscoped-advisory-fires-once-ever] already establishes as the safe one here. **The source is kept** at `resources/research/scopelock-independent-implementation/` — its README, the hook implementation, and its agent-instruction fragment. Read the implementation directly rather than this summary when building; the hook payloads are another platform's, but the structure of the checks transfers. The always-editable scope-file question it raises is filed separately as [scope-file-editable-vs-locked].

#### Should the file that defines a build's scope be editable during the build, or locked? [scope-file-editable-vs-locked]
Captured by you 2026-08-04, from comparing this method's scope-lock against an independently-built one (source at `resources/research/scopelock-independent-implementation/`).

**Files (rough):** `plugin/si-plugin/hooks/pre_tool_use.py` (whether `_build.md` is writable during a build), `docs-b/next-build.md` (the halt-and-ask path), `SPEC.md` (the scope-lock's described behaviour). This matters twice over: it rules out a file-format change as a fix (see [doc-filetype-switch-for-line-links]), and it makes anthropics/claude-code#84017 a general viewer bug rather than a markdown-rendering one.
**A note on how the first attempt at this test failed, because it is a method lesson and not just a mishap.** The test was first built as two files whose names differed only by extension — `viewer-refresh-ab-test.md` and `viewer-refresh-ab-test.py` — and the user was asked to open the right one from a link. They opened the wrong one and lost the observation. The project's CLAUDE.md records that the user scores in the bottom 10th–25th percentile on symbol search, which is exactly the skill "pick the correct one of two near-identical strings" demands. The redesign removed the choice entirely: one file, one link, one unmistakable name. **The general lesson: when a step needs the user to identify something, the design should remove the discrimination rather than rely on it.**
**The consequence for the method is immediate and larger than the annoyance.** Write-first-then-point assumes the user can read what was just written by following the pointer. If their open view is a snapshot, then a pointer emitted right after a write can land them on text that does not yet include it — so they may approve, or fail to find, a version that no longer exists. The remote-mode inline paste never had this failure. **Interim mitigation while this stands: pair every pointer with either an inline paste or an explicit instruction to click away and back.**
**The workaround is itself a cost, reported 2026-08-05.** Searching within the file flips the desktop viewer out of rendered display into code mode — a smaller, narrower font that is immediately harder to read — and switching back to the rendered view returns the document to the **top**, discarding the position the search just found. So the suggested remedy for "the link lands at the top" is a workaround that ends by putting you back at the top, in a less readable font. Filed as anthropics/claude-code#84018; it is harness behaviour, not method behaviour. The stale-viewer finding below is filed as anthropics/claude-code#84017. Both were duplicate-checked before filing and neither had a prior report.
**Why this matters more than the inconvenience.** The whole write-first-then-point rule rests on the user being able to read what was written, in place, and approve it there. If the pointer is hard to follow *and* the view can be stale, then approval-in-place is weaker than the method believes — the user may be approving from a version that no longer exists, which is exactly the failure pasting inline never had. That makes this a question about a load-bearing rule, not a UI annoyance.
**Relates directly to [doc-filetype-switch-for-line-links]**, which is the item holding the line-anchor question: if `.md` links could land on a line, the navigation half of this largely dissolves. Placed next to it deliberately for that reason. Also relates to [write-first-link-dont-paste] (the rule at stake) and [approval-flow-token-doubling-simplification] (which is weighing the same write-first ordering from the token side).
**Files (rough):** `docs-b/plugin-behaviour.md` (the working-mode and view-in-doc rendering rules), possibly `docs-b/plan.md` (whether later references re-carry the heading text). No fix should be designed before the staleness test is run.

#### Weigh switching the docs off `.md` to get working per-line links — gated on the two Claude Code issues, and not tested cleanly yet [doc-filetype-switch-for-line-links]
Captured by you 2026-08-04 — you asked whether moving the docs to a different filetype could buy reliable per-line linking until the desktop app's `.md` link bug is fixed, and noted that if it felt good there'd be no reason for it to stay temporary.
**Confirmed, on pre-existing tracked files (desktop app 2.1.219):** a plain `.md` link opens the file at the top; an `.md` link with a `:N` line suffix is dead; `.py` and `.json` links with `:N` open at the exact line. Filed as anthropics/claude-code#83475.
**What a switch would buy — two things, not one.** Line anchors, so a pointer lands on the item rather than the top of a 480-line queue; **and editability**, since code-view files get an editable buffer with a save affordance while `.md` is read-only in the viewer (anthropics/claude-code#83476). Both are things this session filed issues about.
**The constraint is narrower than feared (checked against the docs, not assumed).** Only two files are locked to `.md`: each `SKILL.md`, required by exact name with YAML frontmatter, and `CLAUDE.md`, which Claude Code auto-loads by name. Supporting files carry **no** extension constraint — the skills documentation lists templates, example outputs, executable scripts and reference docs as bundled resources. The procedure docs are supporting files reached by an explicit path from `SKILL.md`, so they are free. QUEUE, SPEC, LOG and templates are free too.
**The worry that prompted the question is unfounded, and worth recording so it isn't re-raised.** Extension does not change how Claude reads a document — files are read whole through the same tool whatever the extension, so nothing about cross-item reasoning over the queue would fragment. Line anchors are a viewer affordance for the human only.
**The testing was inconclusive and must not be read as a result.** Newly created `.markdown`, `.mdx`, `.txt` and `.py` files at the repo root all failed to open with a line suffix — but so did `.py`, which demonstrably works elsewhere. So the test vehicle was broken, not the extensions: the failing files were new, untracked and at the repo root, while every working example was pre-existing, git-tracked and in a subdirectory. **Nothing was learned about whether prose extensions can line-anchor.** One real observation did survive: a `.markdown` link opened but rendered with no underline and no hover state despite being clickable — an affordance mismatch of the same family as anthropics/claude-code#81817.
**The costs, which are why this isn't obviously worth doing.** Losing rendered markdown in the viewer matters for a long structured queue read by a non-coder. And the `.md` extension is hook-enforced and named throughout the lint, templates and procedure docs, so a switch is a large ripple that must be scoped by grepping every literal occurrence per CLAUDE.md's rule — **and reverting costs the same again**, which is what makes "temporary" the wrong frame.
**Tested 2026-08-05, and it removes a reason someone might expedite this: a format switch would NOT fix stale display.** The user asked to expedite this item specifically to get faithful display of freshly-written text when following a link from chat. A live test the same session showed a `.py` file goes stale in the open viewer exactly as a `.md` file does (anthropics/claude-code#84017), so the caching is per-document, not per-format. Switching formats would buy line anchors and editability and would leave freshness untouched — the very thing the expedite was for. Recorded here because "surely a code file would refresh" is an intuitive assumption that would otherwise be re-made. Detail in [queue-pointer-hard-to-follow-and-possibly-stale].
**Gated on the two issues, deliberately.** If #83475 is fixed, `.md` gains line anchors and this becomes pure cost. If #83476 is fixed, `.md` becomes editable and the second reason evaporates too. Choosing the method's file format around an undocumented quirk of one app build is the trap [harness-misbehaviour-diagnosis-order] names. **Revisit when either issue moves**, or if the app's behaviour changes.
**What holds today regardless:** the heading-text pointer settled in [write-first-link-dont-paste] — a plain link plus the target's exact heading text — works now, needs no format change, and survives either outcome.
**Files (rough):** none unless adopted; adoption would be a hook-enforced-format change touching `post_tool_use.py`, every procedure doc, templates, and CLAUDE.md, scoped by the literal-value grep. Relates to [write-first-link-dont-paste], [desktop-native-md-open-vs-editor-field], [harness-misbehaviour-diagnosis-order].

#### Claude volunteered memory as a destination instead of the project docs — correct by the rule, and nothing in the project can see what landed there [memory-destination-invisible-to-the-record]
Captured by you 2026-08-05, from a screenshot of a close in another project running the method. Recorded as an observation to settle at processing, not as a verdict — the behaviour may be exactly right, and the interesting part may be what it exposes rather than what it did.
**What happened.** At a close, Claude surfaced a discovery — a local build tool's daemon producing a loopback error that reads as a firewall block — and reasoned that it is a fact about **the machine**, not about that project: any project running a similar local build tool could hit it and get the same misleading diagnosis. It noted the fact was recorded in that project's CLAUDE.md, "which is right for this project, but a session in another project would never see it", and offered to save it to memory as "the one place that travels across all your projects". It asked rather than acting.
**On the rule as written, that is correct, and the reasoning matched the rule almost exactly.** The memory-boundaries rule says memory must never hold the project's records — behaviour observations, design decisions, project state, procedure gaps — and that it is a good home for what no project doc owns: user preferences, working style, **cross-project facts**. A machine-level tooling fact is the paradigm case of the last one. It also asked instead of writing, which is the shape the method wants.
**So the finding is not misbehaviour; it is a visibility gap the rule creates and does not address.** Memory does not travel with the project and the user cannot read it. The rule accepts that for things no project doc owns — but it never asks what happens when such a fact **later turns out to matter for this project**. Nothing in the queue, the spec or the log points at it, and no session can enumerate what memory holds. The record has a destination it cannot see into, and the rule licenses writing there without leaving a trace anywhere the project can find.
**What to weigh.** Whether a memory write that arose *inside* a project should leave a one-line trace in that session's LOG entry — not the content, just that a cross-project fact was saved and roughly what about — so the project's own record shows the destination was used. That would cost one line, needs no mechanism, and is checkable by a human reading the log. Against it: it is a second record of something deliberately routed elsewhere, and it risks re-creating in the LOG the duplication the boundary rule exists to prevent. Also worth deciding whether "ask before saving to memory" is a rule anywhere or was this session's own good judgment — if the latter, it may be worth making explicit, since the user cannot audit what they cannot read.
**Do not turn this into a prohibition on memory.** The boundary rule's own history is that a blanket "not to memory" was found both too strong and too weak, and was deliberately replaced. This item is about visibility, not about restricting the destination.
**Files (rough):** `docs-b/plugin-behaviour.md` (the memory-boundaries rule and the routing section), `docs-b/done.md` (if a LOG trace line is adopted). Relates to [no-standard-names-for-workflow-docs-vs-user-files] (both concern where things are recorded and under what name).

#### A "file modified on disk since you last read it" warning should stop work, not be reasoned past [disk-change-warning-should-halt]
By Claude, surfaced at the 2026-08-05 close's wind-down re-scan and approved for filing.
**What happened.** The Edit tool reported "the file had been modified on disk since you last read it" twice during one planning session. Both times the warning was attributed to the session's own queue-mover invocations — a plausible explanation, since the mover does rewrite the file between reads — and work continued. The second warning was a concurrent session having destroyed an item's heading (see [concurrent-session-support]'s live instance). The corruption then rode two further edits before anyone noticed, and was found only because an item could not be moved by slug.
**Why the plausible explanation is the trap.** The mover genuinely does modify the file, so there is always an innocent reading available. That makes the warning *reliably* dismissible, which is worse than a warning that fires rarely: the innocent case trains the response to the dangerous one. The same shape as the method's own note that persistent advisory flags train a reader to ignore the lint.
**The rule to weigh, and it is one line:** on a disk-change warning for a method doc, stop and establish what changed before the next write — a cheap `git status` and a re-read — rather than inferring the cause. The check costs seconds; the failure it catches is silent corruption reaching a commit.
**Deliberately narrow.** This is about the *method's own* documents (QUEUE.md, SPEC.md, LOG/), where a session is reasoning over the whole artifact and a silent change invalidates that reasoning. It is not a general rule about every file in a build, which would fire constantly and get ignored — the exact failure being described.
**Files (rough):** `docs-b/plugin-behaviour.md` (Tool use, or the file-safety section). Relates to [concurrent-session-support] (the incident), [lint-blind-to-readiness-marker] (which gains the mechanical check for the damage this would have caught behaviourally).

#### A /plan session can process in a different order from the queue's file order, and nothing records that it did [plan-session-order-diverges-from-file-order]
By Claude, surfaced at the 2026-08-05 close's wind-down re-scan and approved for filing.
**What happened.** The session ordered its work by unblock-potential at the start — the two hook findings, then the queue-rot pair, then the docset-A freeze question — and worked from that list. It did **not** reorder QUEUE.md to match, because doing so would have meant either restating the full section order or moving items one at a time to positions the mover cannot express directly. So for the whole session the file's order and the session's order disagreed, and the only record of the real order was the session's own working file, which is deleted at the close.
**Why it matters more than it looks.** plan.md states that position in the file *is* the processing order — "an item placed next to its relatives is processed there by design". A session that silently works a different order isn't wrong, but it makes that sentence untrue, and it means an interrupted session resuming from the file alone would pick up in a different order than the one that was reasoned about. The method's own principle is that the files must suffice on their own and conversation memory is never a dependency; here the ordering decision lived only in memory and in a file scheduled for deletion.
**What to weigh.** Whether the start-of-processing reorder should actually *apply* its order to the file rather than only narrate it (which the mover makes cheap for a whole section, and would make the file the single source of order); or whether the session order is legitimately a session-local view and what should change is plan.md's claim that position is the order. Note the second option is honest but weaker — it gives up the property that a fresh session inherits the reasoning.
**Files (rough):** `docs-b/plan.md` (the start-of-processing reorder and the "position is the order" claim), possibly `scripts/reorder_queue.py` if applying a partial order needs a cheaper invocation.
