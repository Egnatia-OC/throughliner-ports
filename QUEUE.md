**Cruise control skill — design session (the consumer-facing end-goal)** **[cruise-control]**
Status: Unparked 2026-06-23 — blocker met. The /goal-formalization arc ([close-shipped-slug-crosscheck] + [formalize-goal-session]) shipped, and goal sessions have been run for over a week, proving the multi-batch close mechanics before the human comes out of the loop. This is a dedicated design session, not a single buildable batch — its output is the design decisions that spawn the build batches, so the next /plan works it as design (the autopilot prerequisites [no-planning-in-execution], [queue-plan-markers], [audit-findings-bulk-approval] all shipped; full no-approval auto-file of audit findings is in this item's own design scope, while interactive audits keep bulk approval).

Deployment prerequisite: [dependency-tracing-pass] — dependency tracing must be solid before the human comes out of the loop (concern #2's foundation). Designed 2026-06-29; the build batches [dependency-tracing-pass] + [readiness-line] now carry it, and the unattended run waits on them shipping.

Cruise control is the consumer-facing end-goal: a skill that runs build→commit→build→commit through a batch (or multiple batches) unattended, stopping only when it hits something requiring user input. The /goal-formalization arc was step 1 — it built the multi-batch close mechanics (shipped-slug cross-check, multi-thread LOG) that cruise control inherits, while a human still bookends the run; cruise control then adds the autonomy, the gate, and the unskippable judgment on top. Key design concerns: (1) wording that doesn't pressure Claude to push through uncertainty — Resolved 2026-06-25: a blocking uncertainty is one whose resolution is a decision the user owns (a design choice, a materially-ambiguous requirement, a product-truth question) → halt-and-record; technical "how" uncertainty Claude resolves as normal building → proceed. The test is categorical (whose call is this?), not a confidence threshold (how sure am I?), because LLMs calibrate confidence poorly but identify decision-ownership reliably — so the gate keys on the category, which sidesteps the field's poor-calibration caveat. Ambiguous category (mine or theirs?) defaults to the user's, the safe side, mirroring capture routing's ambiguous→park default. Reuses the existing plugin-behaviour rule "uncertain about a choice the user owns → ask", with "ask" → "halt-and-record" under autonomy. (2) dependency management when Claude decides when to wrap a batch, (3) /done judgment steps can't get skipped for speed. Resolved 2026-06-26: autonomy removes the human, not the steps. /done already forbids skipping its judgment steps even when the user says "just commit" (done.md Rules); an unattended run's throughput pressure is the same force, so the same rule covers it — cruise control runs the full close per batch, no fast path. The already-mechanical gates carry enforcement with no human watching: the shipped-slug cross-check (which already names cruise-control closes), the out-of-scope dirty-path detection, and the done-build spec-sync gate. The one new wrinkle, parallel to the subagent ask-gate resolution in (8): the judgment steps that currently end in a user approval get an unattended answer — the wind-down re-scan auto-files everything it surfaces (filing commits to nothing, and the real keep/drop/promote decision already waits for a later /plan, so nothing is lost and the run keeps moving), and the push offer doesn't arise (per-batch commit only, per concern 10). Red-flag screening runs as normal; an open flag it raises feeds the gate in concern (4). Builds with cruise control — a small reframe of done.md's no-skip rule plus the wind-down re-scan's unattended auto-file. (4) the red-flags gate — any open red flag blocks the unattended run, only resolved or accepted flags let it proceed, and a user who leaves a flag open stays on hand to approve each step (the gate is a hook reading the three flag states defined by [red-flags-screen-rule]). Resolved 2026-06-26: any open flag blocks, full stop — the earlier "in the active scope" qualifier is dropped, because judging a risk's relevance to the active batch is a call a mechanical hook can't reliably make, on the one category you least want it guessing, and the SPEC already gates on any unaddressed flag (so dropping it also reconciles the concern with the SPEC — no SPEC change). Clearing the gate is one step: mark the flag resolved (designed out) or accepted (risk read, user chooses to proceed). The gate is not only a check at the door — because screening runs the whole time, a flag raised mid-build is open by definition and flips the run to an immediate halt-for-the-user (write BLOCKED, exit), the same move as a SPEC change; an open risk and driving unattended are mutually exclusive. Known limit, named not fixed: the gate blocks on flags that were raised, but can't block a risk never noticed — that is the screening's job ([red-flags-screen-rule]), which runs every session including unattended, so screen-then-gate is a pair and the gate alone isn't total coverage. (5) the handoff-claim-marking format — whether a handoff / context prompt marks which claims are user-vouched versus Claude-authored, or whether the standing "Claude-authored handoff content is unverified until the user confirms it" rule (already in CLAUDE.md) suffices (folded in from the /goal fork, item 9, 2026-06-16). Resolved 2026-06-26: the standing rule suffices — no claim-marking format is added. Cruise control takes its instructions from the queue, which is user-vouched by construction (every batch was user-approved in /plan), so there is no mixed Claude-authored directive whose claims would need marking; the only Claude-authored thing a run reads is its own working-state file on resume, read as mechanical state, not as a user claim — which the standing rule already covers. Goal sessions are the other place a Claude-authored directive could mix claims, but a human is present there to confirm, the rule working as intended. CLAUDE.md's interim caveat is dropped accordingly — the fork is closed. (6) a build that discovers it needs a SPEC change is an owner decision under autonomy — it halts the unattended run, like an open red flag, since a product-truth change can't be self-approved (folded in from [retire-spec-edit-batch-type], 2026-06-25); (7) batch granularity under autonomy — how small a change still earns its own batch and its own LOG entry. The reframe from the 2026-06-25 /plan: the costly part of a tiny build is the full cycle (plan → /next → /done → commit), not the LOG entry, which is cheap; goal sessions already prove several granular per-batch LOG entries can share one session and one commit. Cruise control removes the per-cycle attention cost (Claude runs them unattended) but hands Claude the wrap-decision — when to close one batch and open the next, and how small a change still gets its own LOG entry. The principle to preserve: keep each change's why granular (cheap, and the multi-year / two-minds retrieval value the user flagged) without forcing a tiny unrelated change to wait to be bundled, and without blurring several unrelated whys into one entry. Same judgment as concern (2), on the granularity axis. Folded in from the 2026-06-25 /plan granularity discussion; (8) the run's response taxonomy — what cruise control does when it hits something it can't just build (prior-art research filed: resources/research/autonomous-build-loop-design.md). Three categories. **Route-and-continue**, the common case: anything an attended session would surface that does not block progress — captures, ideas, observations, and any user-run / point-and-click test — gets written down (captures to Captures, user-run tests to Deferred tests) and the run continues. No one is sitting there to hand it to, so filing replaces handing-over; the deferred-test machinery already has a user-run lane, so this is a routing rule, not new plumbing. **Halt-for-the-user**, the rare case: only genuine proceed-blockers — an open red flag in scope (concern 4), a needed SPEC/product-truth change (concern 6), or a blocking uncertainty it can't resolve (concern 1). **Hard-stop**, the mechanical safety net the field treats as mandatory: an iteration ceiling, no-progress detection (same error / empty diff / failing test repeats N times), and a per-run budget ceiling — fires regardless of category, the guard against the runaway-cost failure the subagent incident already hit once; steal the "write BLOCKED to a file and exit" mechanism for the stuck case rather than thrashing. Refined 2026-06-30 (user): the dependency-on-unverified-work guard is primarily a **plan-time** guard, not a run-time one. /plan must not clear a batch to run if it depends on a batch whose verification is still pending (a deferred point-and-click or user-run test not yet run). So "cruise control builds B on unverified A" should not arise inside the cleared region at all — B stays below the readiness line until A's test clears, and a run finishes cleanly at the line. The run-time rule (cruise control declines to build a batch depending on an unverified one) stays only as a backstop / defense-in-depth — the user explicitly rejected making the run-time check the sole mechanism. Gap to settle in the cruise-control design: the readiness definition ([dependency-tracing-pass]) counts a dependency's "producer" as built work, but doesn't distinguish built-and-verified from built-with-verification-deferred; under autonomy that distinction matters, so the readiness line / dependency tracing must represent and check verification-pending status of a dependency. Scoped to cruise control (attended /next keeps the user in the loop, so built-but-unverified is less dangerous there). Ask-under-autonomy resolved 2026-06-26 (the [autonomy-ask-gate-collision] capture, folded in here — what an unattended run does when a permission "ask" fires): the only "ask" the plugin itself creates is the subagent ask-gate — every other owner-decision risk (push, device access, a destructive git op, a SPEC change) is already handled by another concern (the red-flags gate (4), the SPEC-change halt (6), the deny hooks, test-deferral (8)), none of which is a pop-up Claude waits on, so the ask question reduces to subagents. Decision: cruise control uses no subagents by default. The only exception is a build that plainly matches one of three context-overflow cases — a large or multi-repo codebase sweep, a large document-set/archive synthesis, or a large log/big-file analysis (the cases where one corpus genuinely won't fit a single context window; research: resources/research/subagent-genuine-need-cases.md). A subagent is a token-cost tool, not a context tool — it runs ~15× the tokens — and an unattended run must never spend that silently, so research, which burns tokens without overflowing context, stays default-against too. (run-time) Cruise control never spawns a subagent the plan didn't approve; an unforeseen mid-run need is a halt-for-the-user (write BLOCKED, exit), not a silent inline workaround, because a build suddenly needing one it wasn't scoped for signals the batch was bigger than planned — surface it, don't paper over it. (9) the loop driver — cruise control has no human bookends, so the skill itself picks work from the queue unprompted, loops build→close→build→close, and triggers its own end. This skeleton is what goal sessions get from the human who starts, steers, and closes the run; cruise control must supply it, and the gates and the response spine all hang off this loop. Resolved 2026-06-25 — the loop shape, steps (a)–(h): (a) pick the top batch; (b) gate-check before building — open red flag in scope or unsatisfied dependency → halt and wait; (c) build, scope-locked to its files; (d) verify — run every Claude-runnable check, route user-run tests to Deferred tests without waiting; (e) close-and-commit the batch (LOG entry, shipped-slug cross-check, commit — durable); (f) check the limits (iteration / budget / no-progress → stop the run); (g) next batch until the queue is exhausted, a halt fires, or a limit stops it; (h) run-end pass — the single staleness sweep plus a summary of what ran and what awaits the user. Two halt-triggers live inside the build (step c), not only at the gate: a needed SPEC/product-truth change and a blocking uncertainty it can't resolve, each stopping the same way (write BLOCKED and exit), losing nothing because prior batches are already committed; (10) commit cadence — goal sessions land one commit at the end of the whole run (safe only because a human bookends a single sitting), but [cruise-control] is specified build→commit→build→commit, a commit per batch. The fork: close-and-commit each batch as it finishes, or one goal-style close at run-end. It changes how the inherited close machine wires up — the shipped-slug cross-check and the deferred/staleness sweeps run once at a single close today, but would run per batch (or split) under per-batch commits. Surfaced 2026-06-25. Resolved 2026-06-25: per-batch close-and-commit, with a single light run-end pass for the cross-run sweeps (staleness). The why: an unattended run with no one watching must durably commit each finished batch so a crash, a budget stop, or a halt loses nothing and leaves a clean resume point; goal's single-commit model is safe only because a human bookends one sitting. The per-batch close runs the per-batch parts (LOG entry, shipped-slug cross-check, commit, defer this batch's user-run tests); the staleness sweep runs once at run-end. (11) how a run is invoked and bounded — surfaced 2026-06-27. Resolved direction: no plan-time labelling of "autonomous" batches, and no run-to-the-end-of-queue. Cruise control is invoked explicitly when the user wants it and runs the queue top-down, stopping at the readiness line ([readiness-line]) — the general "good to proceed above here" boundary /plan maintains every session, which cruise control inherits as its run bound (a clean finish at the line, distinct from a mid-run halt). So /plan is not a per-run ritual: you plan to fill the queue as you already do, and invoke cruise control to work what's cleared — the "do many" version of /next. Lean: a separate skill, because it's a loop (many batches) not a per-batch type, so bolting it onto /next's per-batch router muddies it; doc-efficiency is preserved not by avoiding the skill but by reusing next-build.md / done-build.md per batch rather than duplicating them, leaving the new skill as just the loop plus the autonomy adaptations (auto-decline subagent, auto-file wind-down, no push, the gates, the hard-stops).
