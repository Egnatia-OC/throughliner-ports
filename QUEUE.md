# QUEUE

Two sections. **Processed** — work discussed and agreed, ordered top-to-bottom; /next builds from above the `--- Cleared to run above this line ---` marker. **Unprocessed** — captured, not yet discussed; the next /plan weighs each item. A work line is a `#### ` heading (its description) with a `[slug]` at the end of that line and its rationale in the block beneath. A leading `[audit]` / `[user]` tag names how it's executed; no tag means a build. Red flags are ordinary work lines carrying a `Red flag · State: …` marker.

#### Trigger a README feature-list sync when a user-facing feature is added or removed, and fix the current README staleness [feature-additions-require-readme-edit]
Captured by you. Adding or removing a user-facing feature has no reliable trigger to keep the public README's feature list current, so shipped features silently vanish from the README while it drifts. 2. **Immediate fix in the same build**: update README.md to the current method — add /cruise (five commands now), replace the stale "spec read-only during builds" and "current batch" language with the two-section work-line model.

Host-only concern (consumers don't maintain the method's README), so the trigger rule lives in CLAUDE.md, not shipped plan.md. Relates to [self-hosting-reproducibility] (both self-hosting-integrity concerns).

#### File /next and /done forward recommendations as an advisory top-of-queue capture that /plan consumes [next-recommendation-not-queued]
Captured by you. At the end of /next (and /done), Claude often recommends what to plan or build next, but that lives only in chat, so acting on it depends on the user remembering — the next-ness-lives-in-memory failure. Fix: record it durably on the single capture mechanism, with a lifecycle that keeps it advisory rather than dictation.

Design (decided 2026-07-13):
- **File it as a capture, framed as advice.** When /next or /done makes a concrete "do X next" recommendation, file a capture worded as "Last session advises processing X next" (plus the reasoning). The advisory framing is deliberate: a fresh /plan has its own read and may see things differently than the last session, so the note must stay open to interpretation, never a command.
- **Placed at the TOP of Unprocessed, not appended.** /plan reads captures top-down, so the advisory sits first, orienting the upcoming session to what the last one recommended.
- **Consumed and cleared, not processed.** The note is never run through keep/delete like work and never moves into Processed. Once the /plan session and the user agree the processing/build order, the advisory has done its job and is deleted immediately. It's a transient orientation handoff, not a work line.
- It's a good closing ceremony — it orients the user to whichever work is coming next.

Build scope — Files: plugin-behaviour.md (the advisory-capture concept, top placement, consume-and-clear lifecycle), next.md and done.md (close step: file the advisory note when a concrete forward recommendation was made), plan.md (recognize the note, let it inform the order discussion, delete it once order is agreed), faq-template.md + faq-index-template.md (a consumer meeting "Last session advises…" atop their queue will ask what it is), SPEC.md if a product-truth sentence is warranted.

Relates to [plan-reorder-by-unlock-potential] (the advisory note is an input to that /plan-close reorder).
