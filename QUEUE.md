#### A consumer's SPEC grows forever with nothing to evict or measure it — ship SPEC-maintenance rules derived from the self-authoring gate [shipped-spec-maintenance-rules]
Captured by you 2026-08-12 at /plan. Your question, and you drew the host/target line yourself: might SPEC benefit from some of our self-authoring rules — not for this project, but shipped, so that when the method is deployed against a real external project it carries built-in SPEC-maintenance rules derived from them. The analysis below is Claude's.
**The structural analogy is real and holds.** `resources/self-authoring-rules.md` exists because the always-loaded rule corpus grew monotonically — every session could add, nothing ever removed, and nobody counted until it was at ~218 instructions. SPEC has the identical growth shape: every user-facing change adds a paragraph under the sync gate, nothing evicts, and no measure exists. It is read at every planning session today and, once [spec-is-write-only-during-builds] ships, at every build run too — so its cost is paid more often than the rule corpus's, not less. And a consumer is worse off than this project: their SPEC grows as their app grows, and nothing will ever tell them.
**Three of the gate's four parts transfer; one does not, and the difference matters.**
- **Admission transfers.** "Does this sentence belong in SPEC, or downstream?" is precisely the question [spec-carries-implementation-detail] found unanswered.
- **The rationale split transfers.** The gate's rule that reasoning leaves the operative statement and lives in the record that decided it applies directly: SPEC carries a lot of why-we-chose-this prose that is LOG material.
- **Staleness transfers.** A SPEC sentence describing a retired mechanism is the same defect as a live rule naming a retired term, which the board's REPEALED signal already detects in shape.
- **The ceiling does NOT transfer, and shipping it would be a mistake.** The 150–200 figure exists because a model follows only so many *instructions* reliably. SPEC is reference, read for content, not followed as instruction — so the compliance argument behind the number is absent, and only the token cost carries over. More decisively, **SPEC has a floor the rule corpus does not have**: it must describe the product as it actually is, so it cannot be compressed past that without becoming false. A rule can always be evicted; a true sentence about a live feature cannot.
**To settle at processing.** Where the shipped rules live — most likely `docs-b/plan.md`'s SPEC ground rule rather than a new always-loaded section, since that is where a SPEC edit is decided and it is fetched rather than always-loaded. Whether a measure ships at all, given the ceiling does not: a growth *report* with no threshold may be the honest form. And whether any of this is authored before [spec-carries-implementation-detail] is settled here, since this project is the worked example.
**Weigh against the admission gate itself** — this proposes adding rules, so it must pass the gate it is derived from, and the cheapest shape is plausibly one clause on the existing SPEC ground rule rather than a new document.

#### Pre-generating every index-entry candidate at scope-lock is speculative spend that a long run mostly wastes [index-candidates-pregenerated-for-items-never-reached]
Filed 2026-08-13 by Claude mid-/next, from measuring this run's own first turn at your request. Filed after the last committed close, so it belongs to no committed session record.
**What the rule says.** `next.md`'s lock-scope step pre-generates a candidate index entry for **each** Claude-work item before the build starts — artifact touched plus nature of change — so that /done can reuse it verbatim if the item builds as planned, or re-author it if scope shifted.
**The live instance.** This run locked scope over 23 items and wrote 23 candidates, roughly 2,500 output tokens. The run was interrupted after ten. Thirteen of those candidates describe work that has not happened, will be written again by a later run, and are deleted with the working file at the close. The reasoning behind pre-generating is sound and is not being called wrong — it is that the shape is cheapest to produce while the item's intent is fresh. What is wrong is doing it for the whole run at once.
**Why it is structural rather than a slip.** The cost scales with run length while the benefit does not: a candidate is only ever redeemed by an item that actually builds, and no run is guaranteed to reach its end. It is the same shape as the close-cost finding from another project — an unconditional per-item cost with nothing permitted to notice how many items there are.
**The obvious fix and its objection, both for processing.** Generate each candidate at the moment its item is ticked, alongside the progress line, so the count matches the work done. The objection is that the candidate exists partly to be written *before* the build, as a readiness check on whether the item is describable — moving it after the build loses that, and it is the same check the keep-step already runs at /plan. Weigh whether that check is doing real work at the lock step or is redundant there.
**Files (rough):** `plugin/si-plugin/docs-b/next.md`, the lock-scope step. Shipped, not host-only. Relates to [close-cost-depth-line-never-surfaces] and [build-log-restates-plan-rationale] — all three are per-item close-and-record costs that scale with run size.

#### Rationale keeps being written into the shipped procedure docs, against the rule that says it belongs in the LOG [rationale-written-into-shipped-docs]
Filed 2026-08-13 by Claude mid-/next, from its own conduct in the session that filed it, after you asked what had made the turn expensive.
**The rule being broken.** `resources/self-authoring-rules.md` states it plainly: the operative statement stays bare, and why a rule is worded as it is — which alternative lost, what the trade-off was — goes to the LOG entry that decided it. The research it cites is explicit that why-clauses travelling with every rule are the over-prescription the 5-series guidance says degrades output.
**What actually happened, in this session.** Most edits this run added a why-paragraph beneath the rule they were writing: an evidence sentence, a rejected-alternative note, a stated limit. Each one felt load-bearing at the time. That is precisely the shape the gate's purpose-clause section describes — every author believes their own rule is the edge case — and the gate has a test for it that was not applied per paragraph: delete the sentence and read what remains, where a complete instruction means what you deleted was rationale.
**Why this is a method finding and not only one session's slip.** The queue already carries [invented-rationale-compounds-past-the-shipped-rule], recording that a shipped provenance rule is not holding in practice and that every pass copies the excess forward. This is the same failure in a different register, and it now has a third instance beside the checkpoint recital and the bolded dispositions: a rule that is read, understood, and then not followed by the session that just read it. The pattern across all three is that nothing surfaces the rule at the moment of writing.
**One honest complication for whoever processes this.** The judgement is genuinely hard at the keyboard, because the gate itself admits *operative* purpose clauses — a reason needed to apply the rule correctly is reclassified as part of the rule, not stripped. So the failure is not "any why is wrong"; it is that the reclassification test was not run, and its absence defaults to keeping the prose.
**What is deliberately not proposed.** No hook — this is not mechanically detectable, and the project has already refused checks that cannot fire honestly. The existing home for it is the self-authoring-compliance lens in `resources/method-compliance-audit-checklist.md`, and this session's own edits to `docs-b/` are a fair first target for that sweep.
