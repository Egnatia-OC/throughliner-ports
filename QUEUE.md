#### Make the shell-write guard fail loudly on a computed target, and fire the queue lint after Bash as well as after Edit and Write [shell-write-guard-computed-path-gap]
Found in use during the 2026-08-09 /next run that built six cleared items; processed 2026-08-09. The guard's own error text already names this as a known gap rather than a bug: it recognises a script write whose target path is written out literally, and does not recognise one whose target is computed at runtime. One run hit both sides of that line, which is what makes it worth fixing rather than leaving as a documented limitation.
**What actually happened.** Removing the six built items from QUEUE.md was done with an inline `python -c` that assigned the path to a variable first (`p='QUEUE.md'`). The guard did not fire. The script then matched the cleared-to-run marker string against its *first* occurrence in the file — which is inside the header paragraph describing the marker, not the marker itself — and wrote a QUEUE.md with the header fragment duplicated and all six items still present. A later heredoc against the same file, this time with the path written literally, was blocked correctly, and its error text pointed at `scripts/reorder_queue.py`, which then did the job cleanly by slug.
**So the guard was right and the gap was the whole cost.** Every part of the design worked except detection: the tool it recommends exists, addresses items by slug, and produced a byte-exact 77-line deletion with no marker ambiguity. The corrupting write happened only because a one-line variable assignment was enough to look like something else. The corruption was caught by an unrelated `git status` a few steps later — nothing in the run would have surfaced it otherwise, and a /done close would have committed it.
**The gap, located precisely (read 2026-08-09).** `PY_OPEN_WRITE` and `PY_PATH_WRITE` in `hooks/pre_tool_use.py` both require a quoted literal path *inside* the `open(...)` or `Path(...)` call, because `structured_write_targets()` needs a path to test against the protected set. Any indirection at all defeats them.
**The decision — two small pieces, not the two directions the capture proposed.** The capture offered widening detection (treat a script importing `io`/`open`/`pathlib` and naming any project doc as a write) or a post-hoc structure check, framed as alternatives. Widening is rejected: it guesses at script text and buys false positives on read-only scripts. And the two are not alternatives — they catch different classes, so both halves below are wanted.
**1. Fail loudly on a computed target.** Match a write-mode `open()` or `.write_text()` / `.write_bytes()` in a python invocation *regardless of whether the path is literal*. When the target can't be read, the guard cannot tell whether it is protected — so it denies and says exactly that: the target is computed at runtime, write the path literally so it can be checked, or use the mover. This is the capture's own second title ("make the gap fail loudly instead of silently") and it converts a silent hole into a visible one with no guessing. Accepted cost: a python script writing to the scratchpad with a computed path is denied too, and must write its path literally.
**2. Fire the queue lint after Bash.** `post_tool_use.py` runs the QUEUE.md structure lint after Edit and Write only, so a shell write bypasses it entirely — which is why the corruption sat unnoticed until an unrelated `git status`. Firing it after Bash catches the class whatever wrote it, and it stays advisory, exactly as it is today.
**The narrower lesson, worth keeping whatever is built:** matching a structural marker by its first textual occurrence is unsafe in any file whose header describes its own format. QUEUE.md's header quotes the cleared-to-run marker verbatim, so a first-occurrence search on that string will always find the prose, never the marker.
**Files:** `plugin/si-plugin/hooks/pre_tool_use.py` (`PY_OPEN_WRITE`, `PY_PATH_WRITE`, `structured_write_targets()` and the deny message), `plugin/si-plugin/hooks/post_tool_use.py` (fire the lint after Bash), `resources/testing/test_pre_tool_use_shell_writes.py` (cases for the computed-path deny). Relates to [reorder-mover-marker-at-top-blind] — both are defects in the queue-editing toolchain, so they build well together.

#### Below the line means blocked by a named queue item and nothing else — restore `Blocked by: [slug]` as a lint-checked field and retire prose lift-conditions [below-line-means-blocked-by-an-item]
Captured by you, 2026-08-09. Your rule, in your own words: nothing is ever supposed to be below the line unless something in Unprocessed blocks it, and if the blocker is a thing in the world then it should be described in Unprocessed so that it actually gets asked about in /plan.
**What today's model does instead.** An item shelved below the cleared-to-run marker records its blocker as a *sentence* in its own prose — "cleared once [slug] is built and verified", "after a full computer restart" — and /plan re-reads those sentences each session and classifies them. The blocker is therefore not itself work anyone picks up. It is a note inside another item.
**The failure that proves it, from this queue.** `[statusline-context-reader]` sat below the line for weeks with a genuine user action buried in its lift-condition sentence. Nothing acted on it, because a sentence inside another item's prose is invisible as next-work. It was only filed as a `[user]` line on 2026-08-09, at which point it immediately became visible as work. One item's prose had been holding another item's job.
**The decision.** Below the line means exactly one thing: this item is blocked by a named queue item. Every other reason to shelve is not a reason — if the item is designed and buildable and nothing in the queue blocks it, it goes above the line. If it is waiting on something in the world, that something is described as its own item in Unprocessed, where /plan will process it, and this item names it as its blocker.
**The mechanism, and the reversal it involves.** Restore `Blocked by: [slug]` as a real field, lint-checked for a slug that resolves and sits above the item. **This reverses `ee99142` (2026-07-31)**, which deliberately ruled out `Blocks:`/`Depends on:` headers and any dependency lint on the grounds that they would resurrect the stale-header machinery the two-section recut removed. The reversal is argued, not assumed: that decision was itself reversed once already at `f832385`, on the evidence that prose dependencies kept failing and shelved items sat waiting for a planning session that had nothing to add — and the 2026-08-09 emergency revert removed the field accidentally rather than by decision. The staleness worry is answered by the lint: a header goes stale silently, a lint-checked slug reference does not.
**Why a checkable field is what makes the rule real.** Without it, "below the line means blocked by an item" is a convention a session can drift from with nothing noticing. With it, the below-line population is derivable rather than remembered: an item below the line with no resolving `Blocked by:` is a lint error, not a judgment call. This is what the prose model could never give.
**What this retires.** Prose lift-conditions, and the classification machinery /plan runs over them — the mechanically-checkable / Claude-downstream / user-only / still-waiting split in the below-the-line revisit. Under the new model the revisit is a slug check: has the blocker shipped? The downstream-action test folded into that classifier becomes unnecessary too, because its whole job was catching a lift-condition waiting on an action nobody had filed — which the new rule forbids by construction.
**A migration is part of the build, not a follow-up.** Every item currently below the line carries a prose lift-condition and must be converted: lift it if nothing blocks it, or file its blocker as an item and point at it. Do this in the same build, or the queue keeps two models at once.
**Interaction with the rule audit, to be handled deliberately.** This adds a rule while `[self-authoring-rules-compliance-audit]` is about to count rules against a ceiling. It must pass `resources/self-authoring-rules.md` like any other — and it is a strong candidate for net subtraction rather than addition, since it retires the four-way classifier and the downstream-action test in exchange for one field and one lint check. Build it before the audit so the audit counts the settled text.
**Files:** `plugin/si-plugin/docs-b/plugin-behaviour.md` (Below-the-line revisit, Work-item states, Dependency ownership's no-headers line), `plugin/si-plugin/docs-b/plan.md` (Step 1 revisit), `plugin/si-plugin/docs-b/done-plan.md` (marker placement, lift-condition recording, and its explicit no-headers guard), `plugin/si-plugin/hooks/post_tool_use.py` (the new lint), `QUEUE.md` (the migration), `SPEC.md` and a FAQ entry (user-visible queue behaviour). #### Build the pre-approval scrub gate: a mechanical secret scan, a pre-write checklist at the three authoring moments, and a stated limit that stops it over-claiming [scrub-gate-before-approval]
Red flag · State: cleared
Captured by you — raised mid-/done, filed after `9cd1e51`; processed 2026-08-09. Throughliner users often have public repos, so QUEUE.md, LOG entries and work items must never carry revealing content — personal names, case details, secrets, third-party data. Today scrubbing is ad-hoc: Claude de-personalised a capture by hand in the session that raised this.
**The crux this exists for, in the capture's own framing:** Claude narrating "I removed X and Y for Z reason" cannot guarantee the text presented for approval is actually clean. The human approves meaning, not a byte-level scrub, so a missed detail ships to a public repo silently. That is the thing a design has to answer honestly rather than paper over.
**The design (2026-08-09), three parts.**
**1. A mechanical scan — the only part that guarantees anything.** A check in `post_tool_use.py` over QUEUE.md, SPEC.md and `LOG/`, matching high-confidence secret shapes only: private-key headers, API-key prefixes, long hex/base64 tokens, email addresses. Deterministic, no judgement, and therefore no false confidence. Advisory, exactly like the existing queue lint. Firing *after* the write is the right fit rather than a compromise, because the approval flow is now write-first — the text is on disk by the time anything is reported, so an after-write flag is the earliest honest moment.
**2. A pre-write checklist at the three authoring moments** — filing a capture, keeping a work item, writing a LOG entry. Claude checks against a stated list (personal names, case details, third-party data, credentials, identifying file paths) *before* the write rather than after. This is where "is this case detail revealing?" is judged, because no pattern can judge it.
**3. A stated limit that stops the gate over-claiming.** Part 2 is Claude checking its own work, which is precisely what the crux above says cannot be guaranteed. So the gate must never be described to a user as "your artifacts are scrubbed". A gate that over-claims is **worse than no gate**, because the user publishes more freely believing it worked. This is the same line the method already holds on red flags: provide risk-addressing, don't promise risk management. The real protection for a public repo is not publishing the artifacts at all — the gitignore-everything option in [setup-repo-privacy-and-publishing].
**Rejected:** describing the gate as a guarantee, or building only the mechanical half. Patterns catch credentials and miss the thing that actually leaks here, which is ordinary prose about a real person or a real case.
**Red flag — cleared 2026-08-09 by informed acceptance, not by design.** Designing the gate does not remove the exposure: the leak is live until this ships. The user was told plainly that queue items and LOG entries written between now and that build may carry revealing content into a repo that could be published, and chose to proceed with the fix queued rather than hold the work. Recorded here and in the session's LOG entry as the consent trail.
**Files:** `plugin/si-plugin/hooks/post_tool_use.py` (the scan), `plugin/si-plugin/docs-b/plugin-behaviour.md` (the pre-write checklist and the stated limit), `plugin/si-plugin/docs-b/plan.md` and `done.md` (the authoring moments), `SPEC.md` and a FAQ entry (user-visible, and the FAQ is where the limit must be stated in plain words). Relates to [setup-repo-privacy-and-publishing], which depends on this and must not encourage publishing before it ships.
