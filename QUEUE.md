# QUEUE

Two sections. **Processed** — work discussed and agreed, ordered top-to-bottom; /next builds from above the `--- Cleared to run above this line ---` marker. **Unprocessed** — captured, not yet fully processed; the next /plan weighs each item. A work item is a `#### ` heading (its description) with a `[slug]` at the end of that line and its rationale in the block beneath. A leading `[audit]` / `[user]` tag names how it's executed; no tag means a build. A work item carrying a security or privacy risk gets a `Red flag · State: …` marker — the flag rides the work.

#### Filing a correction to an existing work item must disarm that item in the same breath, or the corrected item runs anyway [correction-must-disarm-the-corrected-item]

#### The release ritual says nothing about branches, so its mechanical trigger fires where releasing would defeat the merge gate [release-ritual-silent-on-branches]
Captured by you 2026-08-07 — the question was raised at a close and you decided to hold, which settles this instance but not the rule.
**What happened.** A /done close on the work branch `overnight-blitz-2026-08-06`, thirteen commits ahead of main, ran the release check exactly as written: commits since the last release touched `plugin/si-plugin/`, so the check returned "release due". The ritual is deliberately mechanical — *"don't ask whether a release is warranted… if the commits touched the plugin, it releases"* — and that mechanical quality is load-bearing, because welding release to a readiness judgment is what stopped releases happening at all. **But the ritual never says which branch a release comes from**, and the answer is not obvious.
**Why it is a gap rather than a rule to bend.** Two consequences of releasing from a branch, both real. First, it would publish work that has not passed the **pre-merge differential audit gate** — built the same day, recorded in CLAUDE.md, and stating that a branch does not reach main until that audit has run and its repair captures are cleared. A release puts the code in front of consumers, which is further than a merge does, so releasing from an unmerged branch defeats that gate more completely than merging without it would. Second, the version line forks: v1.19.0 came from main, and a release cut from a branch carries work main lacks, so the next main release either skips a version or overwrites the story.
**The decision made here, and its scope.** You chose to **hold the release until the merge** — soak, run the differential audit, clear its captures, merge, then release from main. The work is pushed and safe either way. That settles this close. It does not settle the rule, which is why this exists: the next branch close will hit the identical fork and have to stop again.
**The counter that has to be answered, not ignored.** Holding delays a **privacy fix** reaching consumers — the removal of a hook silently writing the user's absolute path into their repository. Any rule written here must say what happens when a held release contains something that is actively exposing users, because "hold until merge" as an unqualified rule would have made that call automatically and wrongly. The red-flag triage already has the distinction the answer probably needs — actively spreading versus sitting still.
**To settle at processing.** Whether the trigger gains a branch condition (fires only on main), or whether branch releases are legitimate and get their own version convention; how a spreading-risk fix escapes a hold; and whether the merge gate and the release trigger should reference each other explicitly, since each was written without the other in view. Note that the mechanical-trigger rule bars adding a *quality* condition — "is this good enough to publish" — and a branch condition is not that, but the distinction should be stated in whatever is written so nobody later reads it as a licence to re-add judgment.
**THE FORK IS RESOLVED AT PROCESSING, 2026-08-07: the trigger gains a branch condition, and it fires only on `main`.**
**Why that does not reintroduce the judgment the mechanical trigger exists to remove — state this in the written rule, because it will be misread otherwise.** The ritual bars a **quality** condition: "is this good enough to publish?" is a question with no answer, and asking it is what stopped releases happening at all. A branch check is not that question. `git rev-parse --abbrev-ref HEAD` is the same *kind* of check as "did the commits since the last release touch `plugin/si-plugin/`" — mechanical, answerable, no judgment, no readiness assessment. The rule must say so explicitly, or a later reader takes a branch condition as precedent for adding conditions generally.
**Why the alternative was rejected.** Legitimising branch releases with their own version convention **permanently forks the version line**: v1.19.0 came from main, a release cut from a branch carries work main lacks, and the next main release must either skip a number or overwrite the story. That is a durable cost accepted for a temporary situation, and the situation resolves at every merge anyway.
**The spreading-risk escape, which the capture correctly insisted must be answered: the escape is to MERGE SOONER, never to release from the branch.** The red-flag triage already distinguishes *actively spreading* from *sitting still*. So a held release containing an actively-spreading fix is grounds to expedite the **merge**, which unblocks the release, preserves the single version line, and keeps the pre-merge differential audit gate intact rather than stepping around it. One escape route, built entirely from machinery that already exists, and it never requires anyone to decide whether a release is "warranted".
**This is live rather than hypothetical, and it belongs on the merge decision.** The currently-held release contains the removal of a hook that was silently writing the user's absolute project path into a public repository ([session-start-writes-payload-sample-into-repo]). Under this rule that is an argument for merging sooner — not for a branch release — and it is a factor to weigh on [merge-blitz-2026-08-06-to-main] when that greenlight is considered.
**The two rules must reference each other.** The merge gate in CLAUDE.md's branch-cycle section and the Release ritual were each written without the other in view, which is exactly how the silence arose. The Release ritual gains the branch condition and a pointer to the gate; the branch-cycle section gains a line saying a release fires from main after the merge, not from the branch.

#### The editing-state signal's runtime behaviour is undocumented, so every consumer has to rediscover that it fires per edit rather than per build [editing-signal-runtime-semantics-undocumented]

**Finding one — the signal is per-edit, not per-build.** The opening hook writes `active: true` and the closing hook writes `active: false`, so a twenty-file build turns the signal on and off twenty times. ```
mtime wrongly OLD   -> marker reads stale -> "not editing" -> nothing held.
   (origin stamp        FAILS OPEN. The user is never locked out.
    preserved)
mtime wrongly NEW   -> reader holds off slightly too long. Mild, self-clearing.

written_at from a   -> a DEAD session looks permanently current -> the user is

#### The `captured by you` credit is unreliable in two ways: it only resolves for one reader, and it gets applied wrongly with nothing to catch it [provenance-credit-second-person-ambiguous]
Captured by you 2026-08-03 — you asked who "you" refers to in a provenance line, then challenged a credit that turned out to be wrong.
The credit means the project's user, and the convention is deliberate: [provenance-labelling-reconsideration] shipped at `ea272f6`, dropping mandatory provenance for an asymmetric default-AI scheme where an unmarked item is Claude's and only a user-raised item carries a credit. **That decision is not in question** — the asymmetry is sound and cheap. Both problems below sit inside it.
**Problem 1 — it resolves only for one reader.** The credit is direct address, so it works only if the reader is the person it was written for. That always holds in a solo project. It stops holding for a repo that goes public ([scrub-gate-before-approval], [setup-repo-privacy-and-publishing]), for a project handed on, or for any second reader — where "captured by you" points at nobody identifiable.
**Problem 2 — and this one is worse — the credit gets applied wrongly, and nothing catches it.** Live instance the same day: [reorder-mover-marker-at-top-blind] carried a `captured by you` credit from filing. **Why that's the more serious half.** An ambiguous credit is a reading problem; a wrong credit corrupts the record. The queue's purpose is preserving who decided what, and a mis-credit silently attributes thinking to the wrong party — in the direction that flatters the user's involvement, which is exactly the direction nobody will question. It also survives processing, because a rewrite preserves the provenance line as given rather than re-deriving it.

That is the condition under which the known mis-credit survived a full processing pass unnoticed.
**Problem 1 is resolved by the user's decision, 2026-08-05: record a real first name, an alias, or another identifier at /setup, and credit captures to it.** Claude had recommended a one-line queue-header explanation instead, on the grounds that a name writes a person into a repo that may be public. **The user's framing already answers that** — offering an *alias* gives multi-user disambiguation with none of the exposure, so the objection applies to a name-only design and not to this one. ```

                                     person is part of how the queue reads as
                                     the user's own document
rejected: name-only, no alias     -> writes a real person into every item of a

kept:     an identity recorded at /setup — real name, alias, or other, the

1. **The multi-user case the field exists for.** A single stored field records *one* identity, so where two people genuinely share a project, the second person's captures would be credited to the first — the exact failure this is meant to fix, reintroduced.
