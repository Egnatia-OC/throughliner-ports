#### Design the rule-lifecycle system — one whole design for how a method rule is born, measured, maintained, audited and repealed [rule-lifecycle-system]
Filed 2026-08-09, mixed authorship: the user named the failure — the session was designing processes within processes, going in circles, not thinking big or methodically enough — and Claude drew the stages together; the user confirmed filing it as one item.
**What it replaces.** A session spent settling fragments separately: whether the self-authoring gate splits into an authoring doc and a maintenance doc; whether the maintenance doc absorbs the compliance-audit checklist; what triggers an audit; whether the release ritual runs a count. Each answer kept spawning the next question because each was a piece of one undesigned whole.
**The stages, as scaffolding for the design rather than the design itself:**
- **Born** — the authoring gate (`resources/self-authoring-rules.md`). It exists and works, and nothing loads it automatically. The only structural pointer was a line in `CLAUDE.md` firing on Claude noticing "I am about to author a rule"; a second pointer was added to QUEUE.md's header on 2026-08-09, where /plan and /next both read at every session opening, so the gate can no longer be missed for lack of knowing it exists. **What remains, folded in here from the deleted [self-authoring-gate-teeth]:** a pointer makes the gate visible but does not make it run, and nothing produces evidence either way, so a session that skips it looks exactly like a session that ran it — the failure the soft FAQ-sync check had before it was given teeth. The proposed shape, by direct analogy: a session that authored or amended a rule in the method's own text cannot close until it writes a disposition line into its LOG entry — the gate was run and what it decided, or it was not needed and why. The required artifact is the point: "not needed because X" is a claim a later reader can disagree with, and a missing line is a gap anyone can see. Open questions it carries: whether the trigger ("did this session author a method rule?") is any more mechanically detectable than FAQ-sync's was, and if not whether it rides the same close-time read; whether it belongs in the shipped done docs or stays host-only by residence in `CLAUDE.md`, almost certainly the latter since consumers never author method rules; and whether the gate's own admission test should be applied to this rule, which would be the honest test of it. Note this stage's teeth must satisfy constraint A — a close-time disposition fires on a close that always runs, so it is not downstream of anything.
- **Measured** — the always-loaded instruction count against the 150–200 ceiling. First produced 2026-08-09 (~218); nothing re-produces it. A candidate trigger discussed: the release ritual runs the count only — cheap, mechanical, files a capture if over, never blocks the release. The full sweep can't run at release because its findings need /plan and /next before release could proceed (the user caught this).
- **Maintained** — the eviction techniques: codification, consolidation, recasting, from `resources/research/legal-drafting-for-tight-rules.md`. Codification (one subject, one rule, stated once) was never absorbed into the gate at all.
**The section-level split, recorded rather than left as a gesture.** The user's observation was that `resources/self-authoring-rules.md` currently mixes rules about *authoring* a rule with rules about *maintaining* the rules that exist. Which is which:
```
stays with authoring:   Additions are not free · §1 Admission · §3 Distribution
                        §4 Wording · Rationale lives outside the operative rule
moves to maintenance:   §2 Eviction (consolidation, recasting, the staleness test)
                        "When moving a why, don't take an operative statement with it"
                        — it fires during a subtraction pass, not at authoring
```
**Document count: not two, and the axis is cycle position rather than topic.** Claude recommended collapsing to two documents (a gate and a maintenance doc absorbing the compliance checklist) and the user rejected it with the better argument: different procedures are carried out at different points in the cycle, so a document per procedure, keyed to where in the cycle it is opened. Splitting by topic produces documents nobody knows when to open — which is cause 1 above, a procedure that has to be re-described because nothing says when it applies.
**And the doc set must be defined against the actual build cycle, not an abstract one.** The worked example that settled it: an audit yields captures, which require /plan to process and /next to build. So an audit cannot sit at a moment that must complete immediately — which is why Claude's earlier "run the audit at release" proposal was wrong, and why even "run only the count at release" needs re-examining against constraint A. The user's own placement, agreed as a starting point for the design: **the cycle may end on a release, or begin after one.** A release is a natural cycle boundary; the audit belongs early in a cycle, with its captures processed and built before the release that closes it.
- **Audited** — the deep three-lens sweep (`resources/method-compliance-audit-checklist.md`). Today it has no trigger; it runs when a /plan files an `[audit]` item, which is how the corpus reached ~218 before anyone counted.
- **Repealed** — a rule's exit. No process exists at all today.
**The precedent, read 2026-08-09 rather than left as a warning.** Before the emergency revert the project already tried to design a cycle system — the merge cycle: branch → blitz → soak → differential audit → reconcile → merge → branch again. It failed persistently, and the user's recorded words at the time were that it *"is still a total mess that looks different every single time. This was literally the thing that was going to save our project and instead here we are."* Its record survives only in reverted git history: commits `335fa97`, `7a4b377` (LOG entry `2026-08-09-merge-cycle-as-queue-machinery.md`) and `7dd5d2b` (the regressed-state note). Four causes, each of which this design must answer rather than inherit.
**1. It lived as prose conventions, and was rewritten across three consecutive sessions.** No single artifact owned it, so it looked different every time it was described. A cycle that is re-described is a cycle that is re-invented.
**2. Nothing enforced any phase.** The blitz ran when the user asked, the audit ran only because the user pushed, and the merge gate existed only if whoever wrote the merge item happened to remember it. Every phase depended on the user re-explaining the cycle to whichever session was in front of them — the exact working-memory dependence the queue exists to remove.
**3. The attempted fix carried the same weakness it was fixing.** Seeding the phases as ordinary queue items was attached to a documented step at rebranch, on the reasoning that a convention honoured in one written place beats a mechanism nobody built. It then shipped *after* the branch it needed to seed, so that branch had no cycle items at all until they were seeded by hand. A trigger that is a documented step can be missed, and this one was, immediately.
**4. The consequence that condemns the obvious design, and the reason it is stated here.** Compression was gated behind a full-corpus audit, which was gated behind a merge, which was gated behind the cycle. The user's finding: the one mechanism that would shrink the docs was permanently downstream of the machinery that kept growing them, and it never ran once.
**Two hard constraints follow, and they bound the design rather than advise it.**
**Constraint A — no stage may be downstream of another stage completing.** Each stage is reachable on its own, from a trigger that fires whether or not anything else ran. This directly rules out the shapes proposed in the session that filed this item: "run the count at release" and "sweep when queued" both place maintenance behind something else finishing, which is cause 4 with new names.
**Constraint C — the research is cross-cutting, so every procedure is designed against both bodies of it.** The user's point: the syntax research bears on authoring *and* on maintaining, so the research must not be partitioned along the document split. Worked both ways: the subordination test from `resources/research/legislative-prose-syntax.md` tells an author to write a rule as a subordinate unit where it can be, and tells an audit which standing rules should have been subordinate and are not — and codification and consolidation cannot decide what may merge without it. Likewise `resources/research/legal-drafting-for-tight-rules.md` supplies amendment-versus-freestanding to authoring and consolidation and recasting to maintenance. Assigning one research file to one procedure doc would split findings that each procedure needs whole. Each procedure's design reads both.
**Constraint B — every session must know where the cycle currently stands, without being told.** The user's words: every session had no clue about the merge cycle until they told it to pull it up. So if there is a larger cycle the project is always at some stage of, the current stage is state the project holds and a session reads at start — the same way it reads the queue — not knowledge carried in the user's head and re-supplied each time. A cycle whose position only the user knows is a cycle only the user can run.
**Constraint D — inaction must produce a signal, because a duty to review does not. Added 2026-08-10 from `resources/research/legislative-review-cycles.md`, researched at the user's request on their point that law is where this project already borrows its drafting rules.** Law runs two shapes of cycle and only one of them works. A sunset clause expires a provision unless someone re-enacts it, so the default state does the work and the busy party must act to keep the rule. Post-legislative scrutiny is a duty to review, and it fails at scale: only 7.6% of 344 eligible UK Acts between 2005 and 2017 received any scrutiny at all, and where reports did land, 61% of recommendations across seventeen reports were rejected, ignored or answered indeterminately — with acceptance falling to zero for substantial recommendations. The committees that own the duty rarely find the time, because they already carry the primary work.
All three of this item's recorded failures — the merge cycle, the rule corpus reaching ~218, the FAQ stale since June — are post-legislative-scrutiny-shaped: a duty to review whose non-performance is silent. So the design's test for any stage is not "does a trigger exist" but "what does inaction produce". Three further findings from the same research bound the design rather than advise it: **scope the obligation narrowly** (the UK system exempts routine, spent and otherwise-reviewed Acts by design, and a cycle claiming the whole corpus achieved 7.6% coverage); **give maintenance a standing owner** rather than making it a duty of whichever /plan or /next session is running, since those sessions are already fully occupied — which is how the corpus reached ~218 uncounted; and **size findings small**, because substantial recommendations had a zero acceptance rate. Note what does *not* transfer: time-based expiry has no obvious meaning here, since the project has no calendar pressure and a doc that silently expires is not safe. The transferable part is the default-state principle, not the calendar.
**The prior question about this design's own size, folded in 2026-08-10 from the deleted [lifecycle-design-may-be-the-wrong-answer].** Research at `resources/research/universal-behaviour-doc-prior-art.md` found no prior art for the apparatus this project grew around `plugin-behaviour.md` — admission gates, instruction counting against a ceiling, trickle-down and trickle-up audits, multi-lens sweeps. The wider ecosystem meets the same accretion failure and answers it by keeping the always-loaded file small and fetching everything else, so the apparatus's cost should be counted against the artifact that necessitates it — and that artifact is being retired by [extract-skill-nonspecific-rules]. **The bound on that argument is the user's, and it is why the standalone item was folded rather than acted on:** retiring one document does not put the rest of the docset on a cycle, and the need for cyclical review is evidenced three times over independently of it. So this is a question about how much *apparatus* the born stage needs, not an argument that the lifecycle is unnecessary.
**The design's subjects include user-facing documentation, not only rules. Folded in 2026-08-10 from the deleted [lifecycle-must-cover-the-faq-not-just-rules], which was the user's capture.** All five stages above take a *rule* in the method's own text as their subject, so the design could be completed in full and the FAQ would still have no cycle around it. The FAQ is not a rule; it is user-facing documentation whose accuracy decays whenever the method changes underneath it, and it has been stale since 2026-06-18 with five of eighteen entries documenting mechanisms that no longer exist. The user's point in filing it: this is the third instance of one shape — the merge cycle failed because nothing enforced a phase, the corpus reached ~218 because the audit had no trigger, and the FAQ rotted because sync only fires when a session happens to land a user-facing change, so it cannot catch drift in an area nobody has touched. [faq-sync-hard-gate] shipping in `4f5e167` therefore does not close it, and [faq-backfill]'s stated precondition reads as met while the underlying gap stands.
**Subject and scope are different axes, and the design must hold both without trading one for the other.** Widening the subject to documentation pulls against Constraint D's narrow-scope finding, which is a real tension rather than a wording problem: the cycle that claimed all 344 Acts achieved 7.6% coverage. The resolution to design toward is that documentation is named as a covered subject while the *obligation* stays narrow and default-signalling — not "review the FAQ periodically", but something small enough to be honoured whose non-performance is visible. [faq-backfill] is sequenced after this design rather than before it.

Folding is still right — a design input filed where the design will not read it is the failure the method already names — but if another fold or two lands here, split this item by stage before attempting to build it.

#### Give every session its own git branch, merged back at /done, so concurrent sessions stop colliding [concurrent-session-support]
By Claude at the user's request; designed across 2026-07-29, 2026-08-01 and 2026-08-09. The user wants SI safe for running concurrent sessions — a /plan and a build at the same time. The contention is real rather than theoretical: /next's close removes shipped items from Processed and repositions the cleared-to-run marker, so a /next close and a /plan session can both rewrite QUEUE.md's structure at once.
**Direction settled 2026-08-09 — full-project branching, not queue-only.** Two options were weighed. Queue-only branching would give each session its own copy of QUEUE.md merged at close: a much smaller blast radius, and the contention really is about QUEUE.md. It lost because it means writing and then trusting a bespoke merge for one file, and it does nothing about the remote-merge pain, so [worktree-override-hook] would survive it. Full-project branching borrows git's merge instead of hand-rolling one, and it collapses two queue items into one. The user chose this option after both were put side by side. The risk carried forward: branch-switching under a live app, in a folder a cloud client is syncing, is where this could bite a non-coder.
**Mechanics.**
- `session_start` creates the session's branch; naming is automatic (`session/<date>-<id>`) so the user never types or sees a branch name unless something goes wrong.
- Uncommitted hand-edits present at session start come along onto the new branch rather than being stashed. Stashing is where a non-coder loses their own work.
- `/done` merges the branch back into main and deletes it. Claude resolves conflicts silently and surfaces only what it cannot settle safely — the user never sees raw conflict markers.
- On an unresolvable conflict the branch is left in place and the user is told plainly that their work is safe on it.
- A session that ends without /done leaves an unmerged branch. This is recoverable, since the work is committed and the branch is named, but `session_start` needs a check that notices leftover branches and offers to merge them, or they accumulate silently.
- `.git/index.lock` retry-and-backoff: two closes landing at the same instant make git's brief lock error one of them. Minor robustness, but it belongs here.
- Cloud-sync detection: a startup check for whether the project folder is being synced by Drive, OneDrive or Dropbox, surfaced to the user. These clients make their own conflict copies and file locks, which is a separate failure mode from in-repo concurrency and is not fixed by branching.
- The session_start awareness note — telling a session that another is live — stays as previously designed.
**No blocking between sessions, recorded because it was the user's question and the answer is not obvious.** Each session merges its own branch whenever it closes; one session can /done while another is still running, and neither waits on the other. A session only feels the other at all when both edited the same region of the same file, and then it resolves at its own close rather than waiting.
**Rejected designs, kept so they are not re-proposed.** (1) Detect-and-warn — liveness by working-file mtime, a pre-write stop-and-ask recheck — superseded by merge-at-close, which lets sessions diverge instead of policing writes. (2) Staleness detection generally: the user's position is that a session should always be *closed* properly rather than left to go stale, so design for that instead of detecting it after the fact. (3) The old framing that the hard half is outside SI's control because of Drive conflict copies — that is the user's personal environment, not a method-general truth, and most users are not on Drive.
**Relates to** [worktree-override-hook], which names this as its blocker: if merge-at-close makes merging painless then forking is fine, and that item gets deleted rather than built. Decide its fate as part of this build.
**Files (confirm at build):** `hooks/session_start.py` (branch creation, leftover-branch check, cloud-sync detection, the awareness note), `docs-b/done.md` + `docs-b/done-plan.md` + `docs-b/done-build.md` (merge-at-close), `docs-b/plugin-behaviour.md` (safe concurrency), `SPEC.md`, `README.md` feature list, plus a FAQ entry.
**Two findings folded in 2026-08-10, both surfaced while processing [restore-plan-file-gate] and both bearing on whether this design works as written. The user asked the question that found the first; the reasoning is Claude's.**
**Finding 1 — branch-per-session does not isolate concurrent sessions, which is the case it was designed for.** A branch checkout is per-working-tree: one folder has one `HEAD`, so two sessions open on the same project folder are always on the same branch, whatever `session_start` creates. The design therefore isolates *sequential* sessions and does nothing for *concurrent* ones. Real isolation of two live sessions needs separate worktrees — which is [worktree-override-hook], the item this design was going to delete as unnecessary. **Answer this before building.** The design was reached across three sessions and cleared, so the premise failing is worth surfacing at planning time rather than at the first build.
**Finding 2 — `_build.md` is project-level, and that is already wrong today.** The behaviour rules permit a planning session in one chat alongside a build in another. `_build.md` sits in the project root, so the planning session sees it present, concludes it is inside a build, and the scope-lock applies the build's file list to writes that session never agreed to. This predates any branching work and does not wait on it.
**The fix, which this item should carry:** hooks receive `session_id`, so the working file is session-scoped and every check that keys on it asks the question it actually means — is there a build *for this session*. That is a rename with ripple rather than a redesign. Ripple to trace by grep at build: `plugin/si-plugin/docs-b/next.md`, `done.md` and the done family, `plugin/si-plugin/hooks/pre_tool_use.py` (the scope-lock's existence check), and the behaviour rules' one-build-at-a-time and parallel-sessions text. [restore-plan-file-gate] keys its own gate on the same file, so the two must agree on whatever it is called.
**Returned unbuilt 2026-08-10** when the /next run carrying it was stopped after two items.
**Held below the line 2026-08-11, and it must not be built as written.** Research that session (`resources/research/worktree-isolation-and-desktop-sessions.md`) established that session isolation belongs to the harness rather than to us: a worktree exists so edits in one session never touch another's, Claude Code enforces that by blocking edits into the main checkout, and the desktop app documents a worktree per new session. Together with Finding 1 above — one working tree has one `HEAD`, so branch-per-session cannot isolate concurrent sessions — the design's stated purpose is answered by something we do not control. The direction reversed twice inside one discussion, which is itself the reason this is held rather than rewritten in passing.

#### An "unattended" /next run is not unattended: it stops for [user] items and never closes itself [unattended-run-is-not-unattended]
Captured by you 2026-08-11 in the post-close tail. Your words: an unattended run is not actually an unattended run — it stops for user items and doesn't automatically run /done on itself; we can design that, but it needs consideration of where user items land.
**The claim as it currently stands.** `SPEC.md` calls multi-item /next "unattended in practice — the autonomous build mode the Principles name", and the Principles say execution sessions trend toward pure execution, "stopping only for what genuinely needs the user". In practice a run stops in at least three ways: a `[user]` item is walked through live, one step at a time; a `[freeform]` item halts it outright; and at the end the run simply stops, because **/done is a command the user runs** — nothing closes the session on its own. So a run left alone finishes its builds and then sits there, uncommitted, until someone comes back.
**Why this is worth more than a wording fix.** The word shapes real decisions. `[user]` and `[audit]` lines are placed end-preferred *because* a stop inside a contiguous build run interrupts an otherwise unattended sequence — that rule only makes sense if the run is meant to be left alone. And the readiness line was made the run's sole bound on the same reasoning. If "unattended" is aspirational rather than true, several settled decisions rest on an overstatement.
**What a design has to settle, and your condition is the hard part.** Where `[user]` items land. Today end-preferred placement batches them at the end of the cleared region, which is the right instinct but only a tie-adjustment — a genuine dependency still puts a `[user]` item mid-run, and then the run stops in the middle whatever the word claims. Options to weigh: whether a truly unattended run must refuse to include `[user]` items at all and leave them to a separate walk-through session; whether the readiness line grows a second meaning (build up to here unattended, then stop for the human); or whether the honest answer is to stop calling it unattended and describe it as what it is — a run that clears vetted work and pauses where a person is genuinely needed.
**The self-closing half carries a real tension, not just work.** A run that ran /done on itself would commit without the user present, and the commit message is one of only two things the method still shows before it happens — precisely because a commit is hard to unwind and never becomes file content. So auto-closing either overrides that rule or needs a form of it that survives nobody being there. That has to be settled before, not after.
