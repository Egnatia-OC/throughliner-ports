## Batches

Worked top to bottom. Each batch is one /next session — builds first, then tests.

**Audience anchor in this project's CLAUDE.md**
The plugin ships to external non-coders, not the person developing it. Without an audience anchor in this project's CLAUDE.md, skill docs drift — language meant for the developer leaks into chat output the user sees. Adding an Audience section makes the distinction visible to any session editing skill docs, so future skill-doc work writes for the right audience by default.

Build:
- This project's CLAUDE.md: add an Audience section establishing that the plugin's users are external non-coders (not the person developing the plugin), and that anything skills cause Claude to say to the user — chat narration, drafts, prompts, status lines — must read cleanly without referencing internal procedure terms.

**Pull "one item at a time" rule into behaviour.md**
Alex's global CLAUDE.md carries a detailed rule about sequencing multi-part responses — one per message when the next action depends on the previous, count upfront, no preview, alternatives are the one exception. The plugin currently delegates this to the user's CLAUDE.md via the tag-precedence note in behaviour.md, which means it only governs unlabelled steps and free conversation when the user has it set. On any install without that rule, skills' close-outs and walkthroughs become bundle-prone. The [SEQUENCE] tag already covers procedure steps that explicitly carry it, but the broader principle — applying to any multi-part response across the session — needs to be plugin behaviour, not user preference. The Communication section is the right home.

Build:
- behaviour.md: add a "Sequencing multi-part responses" rule under Communication. Cover: one item per message when the user's next action depends on the prior one, state the count upfront, don't preview upcoming items, close-outs and walkthroughs are where the pull to bundle is strongest, the one inversion is alternatives the user is choosing between (because the choice requires seeing them together).

Surfaced twice this session: I framed both the trickle-up audit and the output tag overhaul as candidate batches when both are planning work whose output is decisions, not changed files. Without a structural rule, this becomes a judgment call each time and defaults to whatever shape the previous capture took. Naming the recurring shapes (audits, reviews, reconciliations/drift checks, design exploration) gives the routing decision a clear test.

Build:
- plan.md Ground rules: add a rule pairing the existing "Never build during /plan" — never queue thinking work as a batch. Name the four shapes (audits, reviews, reconciliations/drift checks, design exploration), include the test (if the main work is figuring something out rather than executing on a decision, it's planning work), and state that thinking work runs inside /plan and spawns batches as output. Place it right after "Never build during /plan."

**Verbatim-copy strings in fenced blocks; combine commit approval**
In the desktop app, Ctrl+C copies the whole assistant message, so strings the user needs to lift verbatim (commit message, commit body, paste-ready prompts) only work as copy targets when each one sits in its own fenced code block. Commit message and body are the most frequent case — every /done. Currently they're presented and approved as separate steps, which is redundant; they can be displayed together as two adjacent copyable blocks and approved in one go. A general rule in behaviour.md keeps this from drifting back as other copy-need cases surface.

Build:
- behaviour.md: add a rule that strings the user is meant to copy verbatim must be presented in fenced code blocks. Cover the why (desktop app Ctrl+C copies the whole message, so only fenced blocks give a clean copy affordance). Examples: commit messages, commit bodies, paste-ready prompts.
- done.md Build close-out Section 2.4 (commit step): rewrite to present the commit message title and commit body each in its own fenced code block in the same message, then ask for a single approval covering both.
- done.md Plan close-out Section 3 (commit step): same change.

**Backfill LOG hashes at the start of /plan and /next**
The current /done flow writes LOG with `[HASH]` placeholder, commits, runs `rev-parse` to fill in the hash, then amends — but the amend changes the hash, so the recorded value is stale (13c4612 / 44ab617 this session). Move the infill out of /done entirely: /done leaves the placeholder committed. The next /plan or /next session, at start, finds any `[HASH]` placeholders in LOG/log.md and LOG/index.md and fills them with the hash of the commit that introduced the entry. The infill is just a working-tree edit; whatever commit that session later makes folds it in — no separate commit, no amend, no two-commit flow.

Build:

- done.md Plan close-out Section 3 (commit step): same simplification.

No new commit; the infill is uncommitted working-tree state that the session's next commit picks up.

**Tighten Why-pipeline preserve and retrieve rules**

Both edits serve the same end: when the user asks "why is the app like this?", the answer needs to exist as preserved prose AND be findable.

Build:
- behaviour.md Why-pipeline > Preserve: expand the existing rule to explicitly name the three collapse-shapes — one-line summaries, dedicated why-fields, typed taxonomies (e.g. "UX reason / functionality reason"). The expansion must include its own why woven in as inline prose (not a labelled field) so the rule models what it asks for: each shape loses meaning differently — a line truncates the reasoning behind a decision; a taxonomy is never complete and forces nuance into the closest pre-defined slot.

- Repo installation guide for Claude — add a subpage (or top-level doc) to the GitHub repo aimed at a Claude Code session that a user has pointed at the repo URL. When a non-coder pastes the repo address into Claude and says "install this for me," Claude should be able to read this page and walk them through getting SI installed in their desktop app. Covers: what SI is in one line, that it's a desktop-app plugin (not a CLI install), where to get the zip (plugin/si-plugin.zip in the repo), and the desktop-app install steps. Audience for the page is Claude reading on the user's behalf, not the user directly.

- Claude is reluctant to volunteer research because doing so means admitting it doesn't know something — a face-losing move it avoids. Develop prompting around the research mechanism that reframes volunteering to research as the smart, capable move rather than an admission of ignorance, so Claude offers it at the right moments instead of waiting to be reminded the internet exists. Three angles to build the reframe on: (1) Neutral, blame-free framing — AI and software move fast, so any time the work depends on an external system, library, or API, checking the latest guidelines / release notes is just normal diligence, not a knowledge gap. (2) Stakes for the user — building on stale or under-researched assumptions risks the user spending a week building the wrong thing, which is very costly to undo; research protects against that. (3) How it reads to the user — Claude constantly needing reminders that research is possible looks bad; volunteering research at the right moments is NOT evidence of weak training and doesn't make Claude look dumb, it looks smart and capable — like it has tools and knows when to use them. The reframe needs to land all three so Claude internalizes research-volunteering as face-saving, not face-losing.

- Put the options Claude offers on a spectrum so the user can see there's more than what's listed, without forcing Claude to exposit endless build options. The problem: Claude typically gives a bounded range of options — that's deliberate (exhaustively listing every file type / approach would get tiresome and overload the user), but the cost is the user isn't in the driver's seat; they only steer among what Claude chose to surface. Idea: let Claude hint that other file types / workarounds / approaches exist by arranging the options it *does* give along a spectrum (e.g. easy → hard, or some other axis, possibly more than one axis), and signalling that there could be further options off one end or both ends. This keeps the visible list short while telling the user "there's more this way if you want it," putting them back in control of how far to push. Scale by altitude: for component-level choices, a single easy→hard spectrum. When reasoning about whole strategies / applications / fields (not just components), hint across two or three spectra at once, laid out in a tabular format. Research hook: Claude should be explicitly instructed to web-search whenever asked to expand the spectra (push past the ends / add more axes) — the off-the-ends options are exactly where Claude's own knowledge is thinnest, so expansion should pull from current sources. Overlaps with the research-volunteering capture above (same instinct to reach for the web at the right moment); the spectrum mechanism could be one concrete trigger for that behaviour.

- Rethink the line/character limits on LOG index entries — the "index entries must be ~one line" instinct is probably a wrong move. Asking, not deciding. It traces to forgetting that Claude doesn't read an index the way a human does: a human needs terse, scannable titles; Claude doesn't, so index entries don't need to be tiny. This matters beyond LOG formatting — the short-index constraint is part of what justifies keeping builds small for "higher retrieval granularity" (the limit-builds → limit-index-title chain that feeds the coherence test in the parked sizing-gates item). If index entries can be longer, that justification weakens. Open question is the right limit *mechanism*, two candidate shapes: (a) absolute — index entries capped at ~10 lines of some character width, log entries capped at roughly double that; (b) relational — index entries no longer than ~30% the size of the log entry they represent. The relational version likely needs much less thinking from Claude for a similar result, which is itself a reason to favour it. Pick the limit that yields good retrieval with the least cognitive overhead.

- Unify all length-limiting under the incoming batch-splitting logic, and retire the 5-test rule. Decision: the 5-test verification-burden rule goes. Batch-splitting becomes the single mechanism Claude is ever advised to use to limit length, applied uniformly to both build and test batches. Extend the same logic to /plan sessions, which tend to drag out: at the start of a plan session Claude decides up front the point at which it'll suggest /compact — not /clear, because clearing mid-session is the wrong tool when Claude needs to keep reasoning across many accumulated choices, whereas compact trims size while preserving that working context. Open design piece: what signal Claude uses to set that compact point at session start, before actual session length is known (ties to the word-count / turn-count yardstick question in the parked sizing-gates item).

- Reframe "name concrete outputs" as the batch-readiness gate — the test that distinguishes batch-ready from still-a-capture. Extracted from the parked sizing-gates item as a standalone, concrete change in its own right. Pending review and roll-in to a new batch.

- Coherence test survives, but reframed and re-justified. Keep it as a batch prerequisite, but drop the weird indirect framing ("explain the batch in one sentence without multiple 'and's") — state it directly to Claude as what it actually is: a test of whether the build can be summarised into an index entry. Mechanism bonus: that summary can be pre-generated pre-build and then reused as the index entry (valid as long as the build went exactly as planned). The real justification — and the part to preserve — is that the reasoning behind the existence of each product feature must stay findable via the index; the coherence test exists to protect that findability. Surface that justification explicitly and let it filter up in true why-pipeline fashion (capture → batch → log/index), rather than leaving it implicit in a one-sentence rule.
