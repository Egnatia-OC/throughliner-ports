#### A /migrate capability for bringing old-format projects onto the current queue model [migrate-skill]
Captured by you. The plugin is global, so reinstalling the new SI already updates the hooks and skills for every project — what's "on the old version" is a project's docs, not the code. On inspection of a real old project (`.si-version` 1.13.0-test1, pre-two-section model), the only real conversion is QUEUE.md: its old `## Red flags` / `## Batches` / `### Parked` / `## Deferred tests` / `## Captures` shape has to become the `## Processed` / `## Unprocessed` two-section model with `####` work lines, slugs, provenance, and per-line red-flag markers. The other docs need little or nothing: LOG/ is already per-entry files + index.md (matches the new model), CLAUDE.md settings are auto-topped-up by session_start, and SPEC.md is format-agnostic.

The conversion needs judgment, not a script. Example from the real project: its red flags are "accepted" and "resolved" with no remaining work, and the new model forbids a bare red-flag line with no work attached — so each must be judged (becomes a work line, or is done-history that moves to LOG). A find-and-replace can't make that call. So the capability is a guided conversion pass — a `/migrate` skill, or a documented checklist Claude follows.

Facets to design:
- Detection is mechanical, early (Claude-surfaced). session_start gains an "adopted-but-stale-format" state alongside its existing unadopted / adopted / active-build detection. When it sees an old format it stops the normal load and tells the user to run /migrate first — before a full /plan or /next spends context on the old scaffolding. Extends the `.si-version` comparison session_start already runs.
- /migrate is its own session, closed by /done (which writes a LOG entry recording the migration), so the user then clears or starts fresh for the next skill, per the README's one-skill-per-session advice.
- Version-delta knowledge needs a maintenance trigger (Claude-surfaced). /migrate needs a running record of what structurally changed between which versions, keyed to version. A notes doc that isn't kept current is worse than none — it silently misses the newest breaking change — so it needs a self-hosting rule: whenever a build changes the queue/doc format, it records a migration note keyed to the version. Same shape as the existing README-sync and SPEC-sync triggers.
- Version pickup already half-exists. `.si-version` records which plugin version scaffolded the project and session_start already reads it; /migrate reads it to know which version to migrate from. Build on it, don't reinvent it.

Interim reality: until /migrate ships, every old project is migrated by heavier manual judgment in a session opened on that project (the user is doing the `Stephanie abuse` project this way first). So there's mild priority — each old project stays a heavy manual job until the skill exists.

Open design questions: skill vs. documented checklist (hinges on how many projects — a handful, spread over time); how the format-era check distinguishes "needs migration" from an ordinary version bump that broke no format; whether /migrate closes via /done or its own close; and the exact shape and home of the migration-notes doc. Relates to [self-hosting-reproducibility] (both are self-hosting-integrity concerns).

A companion mechanism set as the status line (or a hook) could write the current % to a file each update, and /next could read it after each line and wrap at a threshold (~40%) — approximating "run until X% then wrap" and partly automating session sizing. Unverified specifics for the design pass: whether the desktop app's status-line payload carries the %, whether the desktop app allows a custom status-line command, file freshness vs. read timing, Windows support. Tradeoff: adds a companion-CLI / status-line dependency — an expansion beyond the pure-plugin design, so an option to evaluate, not decided. If reliable, could supersede manual session-break lines; if not, session-break lines + plan-time sizing remain the fallback.

#### Decide once and for all what a work item is called, and audit the docs for inconsistent terms [work-item-terminology]
Captured by you. Design pass: settle the vocabulary, then sweep the docs. Likely carries an [audit] sub-pass for the doc sweep.

#### Reconsider whether work-item provenance labels earn their keep — and the mixed-authorship problem [provenance-labelling-reconsideration]

#### A queue line that changes a hook-enforced format must name the hook that enforces it, not just the docs that describe it [format-change-names-its-enforcer]
By Claude. Observed 2026-07-15 building [redflag-cleared-uncleared-model]. The work line named its scope as "plugin-behaviour.md, plan.md, next.md, session_start.py's red-flag surfacing, SPEC" — but the three red-flag states were also hard-coded in post_tool_use.py's valid-state set, which would have rejected every new `State: cleared` marker as invalid, and named in done.md, done-build.md, done-plan.md, done-audit.md, setup.md, CLAUDE-TEMPLATE.md, and two faq-template.md entries plus their index anchors. The pattern: a change to a format or enum the hooks enforce ripples to every doc naming the values, the hook validating them, and the consumer-facing templates and FAQ explaining them. Nothing at plan time traces that ripple, so the file list gets written from the design discussion rather than from a grep. /next's self-scoping did catch it — but only by stopping mid-run to ask for a scope expansion, which is exactly the interruption an unattended run shouldn't need. Candidate fix: a CLAUDE.md wiring rule in the same family as "A new batch type touches four places". Design question for /plan: whether this is a plan-time authoring rule, a mechanical grep when a line names a format change, or an accepted cost of self-scoping.
