#### Drop mandatory provenance; keep an explicit user-credit marker, default-AI [provenance-labelling-reconsideration]
Captured by you; decided 2026-07-29. Today every work line carries a required author label ("captured by you" / "by Claude"), lint-enforced. Change it to a one-directional convention: **unmarked lines are assumed to come from the AI; a line gets an explicit user-credit only when the user personally raised, pushed through, or wrote it.** No AI-authorship label is ever written — the AI is the default, so labelling it is noise (and Claude-as-author is externally disliked). The user credit is retained on purpose: the user may want things they personally originated or fought for credited to them explicitly, and the default-AI assumption is exactly what makes an unmarked line safe to read as not-necessarily-theirs.
**How this handles mixed authorship:** when the user supplies the decisive rationale or pushes a Claude suggestion through, the line is credited to the user — the credit tracks who *stood behind* the item, not who typed each fragment (full fragment-level tracing is impossible and was never the goal). When in doubt, leave it unmarked (default AI); the marker is for genuine user ownership.
**Why change it:** the old mandatory label was unused, inaccurate under mixed authorship, and impossible to trace fully; forcing a "by Claude" on every line added noise no one read. The asymmetric convention keeps the one signal that has value (this was the user's) and drops the one that didn't (labelling the default author).
**Extended to rationale-level provenance (folded from [throughline-feature-elevation] thread 1, 2026-08-01):** the same asymmetric convention applies one level down — to the *rationale* carried capture → processed → log, not just the work-item author. A piece of reasoning is assumed Claude's unless it's explicitly credited as the user's stated intention (their *why*), marked inline in the prose where the rationale lives. This is a **prose convention, not a lint-enforced field** — consistent with the why-pipeline's rule that rationale is prose with no dedicated why-field, so it adds nothing to the hook-format ripple below. It only touches where rationale is authored: plan.md's keep-step, next-build.md and done.md (where reasoning is re-authored forward), and plugin-behaviour.md's why-pipeline section. Design the two levels as one consistent scheme.
**This is a hook-enforced-format change — trace the ripple by grepping the format at build time**, per CLAUDE.md's rule. The lint (`post_tool_use.py`) stops *requiring* a provenance field and instead simply permits an optional user-credit; the build must name every place the requirement lives: `post_tool_use.py`, plugin-behaviour.md (Captures line format), plan.md (the keep-step draft), setup.md, CLAUDE-TEMPLATE.md, the queue/faq templates, and any FAQ entry describing provenance.
**Files:** determined by the build-time grep of the provenance format (candidates above); includes SPEC.md if any SPEC sentence describes the label, README feature-list if applicable, and a FAQ update; plus the rationale-provenance surface (plan.md keep-step, next-build.md, done.md, plugin-behaviour.md why-pipeline) as a prose convention, not a lint field.

#### Build the light 5-series docset (Fable 5 + Opus 5) + session-start model detection; freeze the 4.8 docset as fallback [fable-docset-model-detection]
Captured by you; fork resolved and reframed 2026-07-31 via research at resources/research/opus-5-instruction-compliance.md. Opus 5 shipped 2026-07-24, which is what let us settle the long-open strategic gate.
**The fork, resolved.** Opus 5 is *not* "as fussy as 4.8" — it's fussy in the opposite direction. 4.8 under-steers (literal; needs explicit scope and a why-clause riding every rule or it slips — which is why docset A is heavy). Opus 5 over-does (self-verifies, expands scope, verbose by default); Anthropic's guidance for it is subtraction, not addition. Fable 5's guidance says the same — over-prescription degrades it. So Fable 5 and Opus 5 **converge**: both want a lighter, less-prescriptive docset. That collapses the old "N per-model docsets" worry to **two**.
**Architecture (decided this /plan):**
- **Docset A (current, heavy):** frozen — the known-good 4.8 fallback, so a bad migration never strands us with no working plugin (user's non-negotiable). Not actively developed after freeze.
- **Docset B (new, light):** authored by *subtraction* from A; becomes the active docset the method evolves on. Serves Fable 5 + Opus 5.
- **Session-start detection** picks B for the 5-series, A for 4.8, defaulting to **A** (the safe one) when the `model` field is absent. Feasibility already confirmed: SessionStart can receive `model`, not guaranteed present — hence the A-default fallback (resources/research/sessionstart-hook-model-detection.md).
**Freezing A is what dodges the dual-maintenance drift trap:** two docsets differing only in prescription density would normally have to be edited twice and drift apart. Because only B is live, there's no sync burden. This is also why B is a **separate hand-authored docset, not a live overlay on a shared core** — "lighter everywhere" is cross-cutting and doesn't factor into a tidy local delta (the overlay risk flagged in the research).
**Three ordered phases (a future /plan splits these into their own build lines when this lifts):**
1. Rewrite CLAUDE.md's Model-target rule from single-4.8 to this two-docset model (4.8 frozen fallback + active light 5-series), recording the decision and its reasoning.
2. Author docset B by subtraction from the **deduped** docset A.
3. Wire session_start detection + the absent-model fallback to A.
**Dedupe-first ordering (user, 2026-07-31):** B must be authored from a *clean* A, not a bloated one, or redundancy carries straight into the new docset. So [method-docset-dedupe-why-audit] runs, its findings are applied to A, and that application is the **last real work on A before it freezes** — a natural freeze boundary. Phase 2 depends on that being done.
**Candidate authoring style for B — pinned to two familiar formats, still to validate (user + research, 2026-08-01, resources/research/pseudocode-format-for-skill-docs.md):** author B in a **layered hybrid** — a typed signature (*what* the rule/step is) + a concrete template/example (*how*) + a *thin* prose layer for genuine nuance the 5-series still needs. Stay inside Anthropic's skill conventions (YAML frontmatter, progressive disclosure, ~500-line SKILL.md ceiling). Still a **validate**, not decided: the measured gains are on task-completion benchmarks, not governance-doc adherence or Fable/Opus 5 specifically — pick the register against real 5-series output when authoring. **Explicitly excluded from docset A:** this compresses by shedding why-clauses, the load-bearing rationale 4.8 needs — applying it to A would regress rule-following (the same reason [method-docset-dedupe-why-audit] is not a word-cut pass).
**Alternatives weighed and rejected:** two full per-model docsets (drift — every edit made N times); a live shared-core+overlay (prescription density is cross-cutting, won't express as a local delta); "defer the split, keep running A on Opus 5" (viable since Opus 5 runs acceptably on 4.8 prompts out of the box, but user chose build-now).
