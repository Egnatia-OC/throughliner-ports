Two sections. **Processed** — work discussed and agreed, ordered top-to-bottom; /next builds from above the `--- Cleared to run above this line ---` marker. **Unprocessed** — captured, not yet fully processed; the next /plan weighs each item. A work item is a `#### ` heading (its description) with a `[slug]` at the end of that line and its rationale in the block beneath. #### Adopt the branch rhythm: differential consistency audit before every merge to main, full-corpus audit only at big boundaries [pre-merge-differential-audit]

#### Generalise the ripple-grep: any batch that alters a rule greps for its other statement sites, and every hit lands in Files or gets a leave-alone line [ripple-grep-for-rule-changes]

#### Claude corrupted QUEUE.md by editing against a line it had only seen truncated by a shell command [edit-against-truncated-shell-output]
By Claude, observed live 2026-08-07 during this session's own /next run, and filed under the standing rule that any observation of Claude's behaviour is a testing outcome.
**What happened.** To find the end of the queue, Claude ran `tail -3 QUEUE.md | cut -c1-120`, which printed the last lines **truncated at 120 characters**. It then used one of those truncated lines as the `old_string` of an Edit. Because Edit matches on substrings, the truncated text matched the *start* of the real line and the replacement was spliced into the **middle** of it, leaving the token `PLACEHOLDER` embedded in a work item's prose.
**It was caught immediately and reverted**, and a follow-up grep plus `git diff --stat` confirmed the file was clean — but nothing except Claude's own attention caught it. The queue lint would not have: the damage was inside a rationale line, so the structure stayed valid — every heading present, both sections intact, one marker.
**Why it is worth a rule rather than a shrug.** This is a fourth instance of the same family already recorded three times — a clearly-stated rule slipping under local pressure — but with a new and specific mechanism: **the model treated shell output as if it were file content.** The file-reading tools return complete lines; shell pipelines routinely do not, and `cut`, `head -c`, column-limited `git log --oneline` and a truncated `grep` output all produce text that *looks* like the file and is not. An Edit built on that is a silent corruption, not an error.
**The decisive property, named at processing 2026-08-07 because the fix depends on it: you cannot tell from shell output whether it was truncated.** A line cut at 120 characters looks exactly like a 120-character line. There is no marker, no ellipsis, nothing to notice. That is why the rule must key on the **source** of the text rather than on inspecting the text — there is nothing to inspect. The same trap covers `cut`, `head -c`, column-limited `git log --oneline`, a pager, and a grep whose match window clipped the line.
**What gets built,** in `docs-b/plugin-behaviour.md`'s file-safety section, beside the modified-on-disk rule its neighbours already sit among: an Edit's `old_string` comes from a tool that returns the file's **bytes** — Read, or a grep returning whole lines — never from shell output. Stated in its general form as well, since it is broader than Edit: **text that has passed through a display-formatting command is not a copy of the file.**
**Mechanical enforcement is settled as impossible, recorded so it is not re-opened.** A hook sees the tool call, not where the string came from, so there is no route. This ships as a rule, and its honest standing is that this same day recorded four other instances of loaded rules slipping under local pressure. The rule is the only lever available, not a confident one.
**SECOND POINT, folded in 2026-08-07 at your approval from [placeholder-token-written-into-queue-as-scaffold] (now deleted): a method document is never scratch space. The fold added no files** — same file, same section, same damage class.

**Why it is a distinct mechanism rather than a repeat.** The truncated-output failure came from **misreading** — a wrong source for a string. **The risk is not the token's lifetime.** It is that any interruption between the two edits commits it — a crash, a context loss, or the user redirecting mid-turn leaves the token in a tracked file with nothing flagging it. So the gap is real rather than the existing rule having been ignored.

But that is a **shell write to a file**, which the method already denies: `pre_tool_use` mechanically blocks scripted file-writes during a build, and outside a build the planning file-gate asks first. So the hang is a symptom of reaching for something already barred, not an independent hazard — and no second rule should be written for it.

#### The method has no story for an AI-driven collaborator, so a shared project's rationale record covers only one person's half [collaborator-has-no-claude-and-method-does-not-port]
By Claude, from the 2026-08-07 close of the OpenCode-PR conversation. Appended beside its siblings — all three came out of the same exchange.
**The situation that exposed it, established from what the contributor actually said rather than inferred.** He has no Claude subscription, so he cannot run the method at all; his stated reason for building the port was *"I wanted to broaden your horizon and have a way to work together as I have no Claude at the moment"* — the port was a means of collaborating, not an end. He does not want to adopt the method generally, only to work on the one shared project. And he works through an AI harness, so his contributions arrive as large machine-generated changes rather than small hand edits.
**The gap.** Throughliner assumes one person, working with Claude, recording rationale as they go. A second contributor outside that produces changes with **no rationale in the record at all** — and the method explicitly forbids the obvious patch, because reconstructing intent from a diff is the thing it rules out ("this change is here and I cannot account for it" is the sanctioned output). So the project's own why-pipeline covers one half of a two-person codebase and cannot be made to cover the other.
**Two candidate mechanisms, both weighed in that conversation and neither built.** Asking for prose rationale in pull requests fails on volume: a hand-written paragraph over an AI-scale change collapses fifty decisions into one label, which is the exact compression the why-pipeline exists to prevent. The better-founded idea is that **the rationale be AI-written too** — the contributor asks his own tool to write the reasoning into the PR before opening it, which needs no discipline, no Claude and no method, and is the only thing that scales with the change volume because it is produced by the same thing producing the changes. A structural fallback was also raised: give the contributor an **area** of the codebase, so drift is contained at a boundary the log can honestly describe rather than interleaved through everything.
**What must not be lost at processing: the gap cannot be fully closed, and saying so is part of the answer.** Part of a shared project will have thinner history than the rest. That is a cost of having the collaborator, not a fault to engineer away, and a design that pretends otherwise will produce a mechanism nobody follows.
**Consumer-facing, not host-only.** Any user of this method who works with anyone else hits this, and it is invisible until someone asks why a decision was made and the log has nothing.
**Scoped at processing 2026-08-07 to what the method actually controls — and the scoping is the design decision, not a trimming of it.**
**The reservation that drove it, stated rather than buried.** The AI-written-rationale route is the right idea and the only one that scales, because it is produced by the same thing producing the changes. But it depends entirely on a person **outside the project** choosing to do it. The method cannot enforce it, cannot verify it, and cannot detect its absence. Writing it up as a *mechanism* would produce precisely what this item warns against: something nobody follows. So it ships as **the ask to make**, framed as an ask, never as a step the method performs.
**The crediting half is NOT this item's, and that was checked rather than assumed.** [provenance-credit-second-person-ambiguous] already owns the multi-person question and names it as one of three things its build must settle rather than infer — a single stored identity field would credit a second person's contributions to the first, *"the exact failure this is meant to fix, reintroduced."* This item points at that one for the credit **format** and does not re-decide it. What this item owns is different and narrower: whether an outside contributor's reasoning enters the record **at all**.

**The correct behaviour is already written in this same script, on a different path.** `delete_item()` carries an explicit re-anchor branch: when the marker was anchored to the item being removed, it re-anchors to whatever now precedes it, with a comment stating the marker keeps its position. Branching is what prevents the damage; merge-at-close is the cost of having branched, not the mechanism that saves you.

Branch-per-session doesn't: it costs almost nothing when uncontended, because a merge with no divergence is a fast-forward and effectively invisible. **It is free when you are working alone and pays exactly when you are not** — which is the property you want, since concurrency is unpredictable and the protection has to already be in place when it happens.

#### The `captured by you` credit is unreliable in two ways: it only resolves for one reader, and it gets applied wrongly with nothing to catch it [provenance-credit-second-person-ambiguous]
Captured by you 2026-08-03 — you asked who "you" refers to in a provenance line, then challenged a credit that turned out to be wrong.
The credit means the project's user, and the convention is deliberate: [provenance-labelling-reconsideration] shipped at `ea272f6`, dropping mandatory provenance for an asymmetric default-AI scheme where an unmarked item is Claude's and only a user-raised item carries a credit. **That decision is not in question** — the asymmetry is sound and cheap. Both problems below sit inside it.
**Problem 1 — it resolves only for one reader.** The credit is direct address, so it works only if the reader is the person it was written for. That always holds in a solo project. It stops holding for a repo that goes public ([scrub-gate-before-approval], [setup-repo-privacy-and-publishing]), for a project handed on, or for any second reader — where "captured by you" points at nobody identifiable.
**Problem 2 — and this one is worse — the credit gets applied wrongly, and nothing catches it.** Live instance the same day: [reorder-mover-marker-at-top-blind] carried a `captured by you` credit from filing. It records a script throwing an internal error during a /done close — something only Claude could have seen. The user had no way to observe it. The credit was then *inherited unchecked* through a full processing pass, and only caught because the user happened to say it didn't feel like theirs.
**Why that's the more serious half.** An ambiguous credit is a reading problem; a wrong credit corrupts the record. The queue's purpose is preserving who decided what, and a mis-credit silently attributes thinking to the wrong party — in the direction that flatters the user's involvement, which is exactly the direction nobody will question. It also survives processing, because a rewrite preserves the provenance line as given rather than re-deriving it.
**Measured at processing, 2026-08-05: 40 of the queue's 55 items carry a `captured by you` credit.** Framed carefully, because the number is suggestive rather than diagnostic — it is entirely consistent with being true, since there is one user and they are the developer, so they do raise most things. What it does establish is that the credit discriminates almost nothing in practice: a marker on three-quarters of items tells a reader little, and a single wrong credit is well camouflaged among them. That is the condition under which the known mis-credit survived a full processing pass unnoticed.
**Problem 1 is resolved by the user's decision, 2026-08-05: record a real first name, an alias, or another identifier at /setup, and credit captures to it.** Claude had recommended a one-line queue-header explanation instead, on the grounds that a name writes a person into a repo that may be public. **The user's framing already answers that** — offering an *alias* gives multi-user disambiguation with none of the exposure, so the objection applies to a name-only design and not to this one. The user's reason: "you" breaks down as soon as a project has more than one user, and the header line only ever worked because this project has exactly one.
```
rejected: "captured by the user"  -> unambiguous but colder, and the second
                                     person is part of how the queue reads as
                                     the user's own document
rejected: name-only, no alias     -> writes a real person into every item of a
                                     possibly-public repo
kept:     an identity recorded at /setup — real name, alias, or other, the
          user's choice, with the alias route offered plainly
```
**Three things the build must settle rather than assume.**
1. **The multi-user case the field exists for.** A single stored field records *one* identity, so where two people genuinely share a project, the second person's captures would be credited to the first — the exact failure this is meant to fix, reintroduced. Decide between a per-session confirmation, a field explicitly scoped to "the project's primary user", or something else. Do not leave this to inference.
2. **The ask is a solicited identifier, so it is governed by the private-information rules.** /setup must say plainly, at the moment of asking, that the answer is written into committed project docs — and offer the alias in the same breath. /setup already detects repo visibility, so a public repo should lead with the alias option rather than mentioning it as an afterthought.
3. **What happens to the 40 existing credits.** A new field protects new items and does nothing about those already written. Migration is [provenance-credit-audit]'s territory; this item must not silently assume it happens.
**Problem 2 — a filing-time test, plus re-derivation at the keep-step.** State the test in words: *could the user have observed this unaided?* And require the keep-step to re-derive the credit from the discussion rather than inherit the filed one, because inheritance is precisely how the known bad credit survived processing. No lint — this is a judgment a hook cannot make, so it is a wording fix.

#### Design proactive rationale-nudging: Claude asks for the *why* without nagging [throughline-feature-elevation]
Captured by you (2026-07-30); reframed 2026-08-01. Earlier threads are gone: thread (a) — the why-pipeline → "throughline" rename — folded into [rename-to-throughliner]; thread (b) — user-provenance on rationale — folded into [provenance-labelling-reconsideration] (2026-08-01) for one consistent provenance scheme. **The finding: the productive nudge is a proposal, not a question.** Almost none of that session's rationale came from anyone asking "why". ```

```
                       Mostly making existing practice a rule, not a new beat.
the close          ->  where a decision's rationale is written down.
a user OVERRIDE    ->  the highest-yield moment of the three, and the one with
   of a proposal        no rule at all today. An override is rationale arriving
                        unbidden; nothing currently says to capture it as such.
```
**One suppression limb, non-negotiable:** don't propose where the answer is predictable. [merge-and-fold-without-asking] is the user saying plainly that a whole class of Claude's asks was redundant, filed the same day. A nudge design that ignores that reinvents the behaviour the user asked to stop.

**Cost to weigh at build:** a proposal-with-reasoning spends tokens every time, and the same session established that approval-time token cost lands hardest on Pro users ([approval-flow-token-doubling-simplification]). #### Reading a hook as a Python module silently changes the installed-host build stamp, the one signal the method uses to tell whether host-side changes are live [reading-a-hook-changes-the-build-stamp]
By Claude, observed live 2026-08-07 during the planning session, and surfaced at that session's wind-down re-scan.
**What happened.** To compare the target's content stamp against the installed host's, the session ran `import session_start` against `plugin/si-plugin/hooks/`. Python wrote `plugin/si-plugin/hooks/__pycache__/` as a side effect. That folder sits **inside the directory the stamp is computed over**, so the target's build stamp changed — and when the session restarted mid-run, the hook reported a **different installed-host stamp** (`5c17250013e3` → `14738a328230`) than it had at the session's start. Nothing had shipped. The bytecode was deleted once noticed, before any commit.
**Why it is worth filing rather than shrugging at.** The build stamp is not a convenience — it is the mechanism that replaced *asking the user what is installed*. `/plan` compares the two stamps to decide whether host-side changes are live, and a mismatch is read as "the host has not been reinstalled since the last host-side change, so host-side tests are not live yet". A stamp that moves because somebody **read** a hook produces exactly that reading with no change behind it, and the wrong conclusion is the confident-looking one: a session would defer host-side verification that was in fact fine.
**Two things make it more than a one-off.** Reading a hook as a module is a natural thing to do — it is how you check what a hook actually computes, which the method actively encourages ("check what the tool says it does" before theorising). And the residue is invisible in the ordinary signals: `git status` does not show `__pycache__` if it is gitignored, and the stamp difference looks precisely like a legitimate pending change.
**To weigh at processing.** Whether `content_stamp()` should exclude `__pycache__` and other generated artifacts outright — which looks like the honest fix, since bytecode is not part of the plugin's content in any sense the stamp means — or whether the answer is a convention against importing hooks. The exclusion is strictly better if it works: it removes the failure rather than warning about it, and both the rezip and release rituals already delete `__pycache__` precisely because it is not plugin content, so the stamp treating it as content contradicts the rituals either side of it. Check whether anything else generated lands inside the stamped tree.
