**Define index-entry shape and reframe coherence test as findability gate**
The "index entries must be ~one line" instinct in the LOG conventions is the wrong constraint. The index is Claude-facing, read during why-pipeline retrieve to decide which log entry to open. What an index entry needs isn't shortness — it's enough specificity to make that open/skip decision without reading further: the artifact touched and the nature of the change. Length is whatever that takes (usually one line, sometimes two). The same definition does double duty: the parked sizing-gates coherence test ("can Claude explain the batch in one sentence without multiple 'and's") was a weird proxy for findability all along — restate it directly as "can you write the index entry now, before building?" If yes, the batch is ready and the entry can be pre-generated. If no, the batch isn't coherent enough — keep interviewing. The rule lives in plugin-behaviour.md so /plan applies it as the readiness gate, /next pre-generates the entry at batch-confirm time (reusable as the final index entry if the build runs as planned), and /done writes it (or its reauthored form) at close.

State explicitly that the index is Claude-facing, not user-facing — terseness for human scannability isn't the criterion. No absolute length cap; length follows from the content requirement (typically one line, sometimes two for multi-thread sessions). Reference from Why-pipeline > Retrieve.
