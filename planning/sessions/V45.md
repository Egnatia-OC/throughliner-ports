# V45 — Automated vs. manual test split + non-UI test types

## Goal

Extend the method's after-build test model to (1) formally recognise four test types instead of one, and (2) accommodate automated Claude-run tests alongside manual user-run tests. The current model assumes every test is "look and click" UI interaction verified by the user — which blocks the method from serving non-UI projects (CLI tools, plugins, hooks, MCP servers, data pipelines) and pushes mechanical pass/fail checks onto the user when Claude could verify them faster and more reliably.

Single biggest method-level change to the build cycle since V27 (after-build subagent). Touches the after-build subagent, TEST-LOG row format, build-batch test specification, and the after-build prompt language.

## Outputs

- Four test types formally named, defined, and exemplified in VOCABULARY.md:
  1. **Look and click** (UI interaction) — user-verified, optionally screenshot-assisted
  2. **Run and read** (command execution) — fully Claude-automatable
  3. **Trigger and observe** (integration/trigger) — fully Claude-automatable
  4. **Generate and inspect** (artifact inspection) — fully Claude-automatable
- TEST-LOG row format extended: new columns for **test type** and **verifier** (Claude vs. user). Existing 8-column spec becomes 10-column.
- After-build subagent updated:
  - Distinguishes "Claude has already verified X" from "please manually check Y" in the recap
  - Runs the Claude-automatable test types as part of after-build (vs. handing them to the user)
  - Opens TEST-LOG rows with type + verifier populated; Pass/Fail filled in by Claude where automatable
- Before-build subagent updated: decides per-batch test specification during batch lock-in. Mechanism: either a `Tests:` sub-section (peer to `Files:` and `Inputs:`) or an extension of the Inputs line. Decide at session start.
- Build batch format updated in BACKLOG-TEMPLATE.md (and DOC-STRUCTURE.md) to include test specification
- Crash course.md updated with four-test-type explanation and verifier distinction

## Open questions for this session

- **When do automated tests run?** Three positions:
  - **During the build** — batch-executor runs tests as it goes; failures halt the batch
  - **After the build** — after-build runs an automated pass before prompting the user
  - **Both** — batch-executor for in-build sanity checks, after-build for final pass

  Leaning: **after the build**, because batch-executor's halt-on-failure semantics complicate the existing "ticked vs. unticked files" mechanism. Revisit if real use shows in-build tests are needed.

- **Test specification: `Tests:` sub-section vs. extension of `Inputs:`.** V44 ships an `Inputs:` line for build batches. Tests could be a second peer sub-section, or an Inputs-line item ("test spec for this batch"). Leaning: peer sub-section — tests are operationally distinct from inputs (inputs are read, tests are executed), and separating keeps the format readable.

- **TEST-LOG row format: 10 columns vs. nested.** Adding two columns (type, verifier) keeps the flat shape but widens the row. Alternative: nested sub-row per test under one component row. Leaning: flat — nested adds parser complexity for marginal readability gain.

- **Trigger-and-observe automation: what's the test harness?** This test type covers hooks, webhooks, scheduled tasks. Claude can pipe fake input into a hook script (as the dev project's BUILD-METHOD.md describes for manual smoke tests). Does the method ship a thin harness pattern, or leave per-project? Leaning: leave per-project for V45, surface a harness pattern later if multiple projects converge on the same shape.

- **Backwards compatibility for existing TEST-LOG rows.** Taskflow's TEST-LOG has rows in the current 8-column shape. Migration on `/adopt` case 4: backfill type column with "look and click" (Taskflow's only type so far) and verifier column with "user". One-time, mechanical.

- **Relationship to TEST-LOG row pruning** (separate OPEN-QUESTIONS entry, parked for V44+ once row-count data exists). The two interact: a pruning mechanism that uses "verifier" or "type" as a pruning axis would compose. Worth flagging at session start; doesn't force shipping pruning here.

## Risks / dependencies

- **Largest change to the build cycle since V27.** After-build's responsibility expands meaningfully — it now runs tests, not just opens rows for the user to fill. Get the boundary right between "Claude ran and recorded" and "user must verify."
- **TEST-LOG schema change is permanent.** Once consumer projects scaffold with the new shape, reverting requires migration. Get the column shape right in one pass.
- **Depends on V42** for non-GUI vocabulary — without it, the language for non-UI test types ("the operator," "the downstream system," "the integrating developer") isn't settled and this session would shadow-decide it.
- **Depends on V44** for the Inputs-line mechanism — the natural model for per-batch test spec is a peer of Inputs. Could ship without (invent an isolated `Tests:` sub-section), but the surface is cleaner if both arrive together.
- **Three of four graduation prerequisites shipped after this session.** Only distributed fold-ins (V44) remains, and it ships before this session. After V45, the graduation meta-goal becomes promotable on its own evaluation — would mean the dev project starts using the plugin for its own work. Out of scope for V45 itself.
- **Real Taskflow evidence weak for non-UI types.** Taskflow is a GUI app; it doesn't exercise the new test types. The session ships the model on first-principles design; real validation needs a non-UI consumer project (most likely the dev project itself post-graduation).
