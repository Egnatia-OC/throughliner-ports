# V45 — Distributed fold-ins + BACKLOG open-questions section

## Goal

Two structural changes to how the method parks work-in-progress, shipped together because they reshape the same docs:

1. **Distributed fold-ins.** Move proposed-content-for-other-docs out of a centralised section in BACKLOG.md and into a fold-in section at the bottom of each destination spine doc (UX.md, MANIFEST.md, and BACKLOG.md itself for BACKLOG-specific fold-ins). Locked docs gain an append-only carve-out in PreToolUse, mirroring V38's footer-stamp carve-out pattern.
2. **Open-questions section in BACKLOG.md.** Give consumer projects the parking-lot mechanism this dev project's OPEN-QUESTIONS.md has been load-bearing for. Section sits at the bottom of BACKLOG.md, scanned by the planning subagent during its existing drift-check sweep at the top of every planning session.

Plus one supporting change folded in because the structural rewrite already touches the same surfaces:

3. **`Inputs:` line for build batches.** Each batch gains an `Inputs:` line listing non-standard reads specific to that batch — an OPEN-QUESTIONS entry, a specific additional doc, a research artifact, an external reference. Foundational docs (UX.md, BACKLOG.md, MANIFEST.md, CLAUDE.md) are read every session by SessionStart, so `Inputs:` only lists what's beyond the standard set. Closes the gap the dev project's `Vxx.md` *Inputs* sections currently cover.

## Open questions for this session

- **Relationship between open-questions section and existing planning-batch `Blocks:` mechanism.** Both park unresolved work. Do they merge (open questions become the single mechanism, planning batches retire), coexist (planning batches stay for design work that's mid-decision, open questions for parking-lot-only entries), or split by lifecycle stage? Leaning: coexist initially, revisit after a real planning session uses both.
- **Append-only carve-out: detection mechanism.** V38's `is_footer_only_edit()` checks the edit is a single footer stamp at the very end. Fold-in append needs to check the edit only adds lines within the fold-in section. Likely shape: scan the diff, verify all changed/added lines fall inside the fold-in section's start/end markers. End marker is the end of file unless a later section exists.
- **Planning subagent: scan output shape.** Open-questions scan surfaces entries to the planning conversation. Does the subagent list every entry, or filter by trigger condition? Each entry has a *Next step* with trigger conditions; the scan could evaluate triggers and surface only entries whose conditions match the current state. Heavier but reduces noise.
- **Migration path for existing BACKLOG.md fold-ins.** Taskflow's BACKLOG.md (and the dev project itself, if it ever adopts) has existing centralised fold-ins. `/setup` case 4 (refresh) could migrate them to distributed locations, or the next planning session could do it manually. Leaning: `/setup` case 4 handles it — one-time migration on next plugin update.
- **`Inputs:` line: format.** Bullet list under the batch header? Comma-separated inline? Match the format of existing batch sub-sections (`Files:`, `Blocks:`). Leaning: bullet list, one input per line, with a one-line rationale per input ("OPEN-QUESTIONS entry X — design source for this batch's confirmation protocol").

## Risks / dependencies

- **Largest structural rewrite of the upcoming sessions.** Touches every spine-doc template, every relevant subagent, the PreToolUse hook, DOC-STRUCTURE, VOCABULARY, Crash course. Get the structural decisions right before the rewrite begins — reversing after templates ship is expensive (consumer projects scaffolded against the old shape).
- **Append-only carve-out is security-shaped.** PreToolUse carve-outs widen the writable surface of locked docs. V38's footer-stamp carve-out is narrow (one stamp at end-of-file); fold-in carve-out is broader (any append within a section). Get the section-boundary detection right; an over-broad carve-out lets Claude silently edit locked docs by mis-detecting the boundary.
- **Depends on no earlier session.** Could ship in any order relative to V43/V44, but placed at V45 because (a) V43–V44 are higher-priority operational improvements, (b) V48 (test split, renumbered from V46 in session v43) consumes V45's Inputs-line mechanism for per-batch test specs.
- **Unblocks V48 (test split) and is a prerequisite for the graduation meta-goal.** Two reasons to ship this before V48: open-questions section gives V48's design decisions a place to park between sessions, and Inputs line is the natural carrier for V48's per-batch test spec.
