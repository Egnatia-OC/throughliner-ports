# V25 — TEST-LOG.md mechanism + protocol

## Goal

Add the test-completion log to the method as a new operational tracking doc (sibling of `MANIFEST.md`, not source-of-truth). Lock down the test-confirmation protocol that gates between *After every build* and the next planning session: every test on the list accounted for as Pass / Fail / Skipped before a new build can start. The After-build subagent (V26) will enforce this gate; this session ships the prose mechanism that V26 implements.

## Inputs

- V18–V24 outputs
- `NO-CODE-METHOD.md` → *After every build* (the phase that gains the test-confirmation step), *During planning* (the phase that reads TEST-LOG.md), *Method contract* (the phase that gains the protocol rules)
- `DOC-STRUCTURE.md` (gains a TEST-LOG.md structure section)
- The Sonnet draft produced in V20 planning (canonical column shape, five protocol rules, phase-based pruning logic) — Alex has the file locally; pull it into this session as the starting shape.

## Outputs

- New doc class: **TEST-LOG.md** as an operational tracking doc with the table format (ID, Test Description, Component, Status, User Notes, Session / Version, Confirmed Explicitly). Pruning rule: phase-based, not session-based — a record's validity ends when the component is substantially changed or the feature is removed.
- `templates/TEST-LOG-TEMPLATE.md` + plugin-side copy at `plugin/templates/TEST-LOG-TEMPLATE.md`.
- `DOC-STRUCTURE.md` gains a **TEST-LOG.md structure** section describing the table shape, the Status options (Pass / Fail / Skipped — with reason required), and the Confirmed Explicitly column.
- `NO-CODE-METHOD.md` gains **five protocol rules**, placed by phase:
  - **Rule 1 — Never infer completion** → *Method contract → Required of Claude* (load-bearing for the test-confirmation gate).
  - **Rule 2 — Resolve "all others good" before recording** → *After every build* (explicit read-back step before the recap can close).
  - **Rule 3 — No new build until the test session is closed** → *Method contract → Prohibited of Claude* (sibling to "do not add features not listed in the current batch prompt"). Becomes a hard gate on the build cycle.
  - **Rule 4 — Skipped ≠ Passed** → *Vocabulary* (Pass, Fail, Skipped each get a one-line definition; Skipped explicitly requires a reason and remains open).
  - **Rule 5 — Retest after change** → *During planning* (added as a **fourth drift check**: TEST-LOG.md ↔ what's been touched since each test was recorded; substantially-changed components have their test records flagged for retesting).
- `templates/CLAUDE-TEMPLATE.md` path block gains a `TEST-LOG.md` entry under *Where the docs live*.
- `Crash course.md` updated (parity item this session): *The files* section gains a TEST-LOG.md bullet alongside MANIFEST.md; *Three disciplines that do most of the work* may gain a fourth discipline (test-confirmation gate) — final placement decided this session.
- Commit tagged `v25`

## Success criteria

- `TEST-LOG.md` template scaffolds into a new project via `/init-project` (or its V27 equivalent).
- A test note pasted in a planning session triggers the *During planning* drift check that surfaces TEST-LOG.md entries whose covered components have been changed since the record was made.
- The five protocol rules are findable in `NO-CODE-METHOD.md` at the correct phases, with load-bearing-for annotations where the rule is a contract item.
- A reader of the updated Crash course can see why TEST-LOG.md exists and how the test-confirmation gate works.

## Open questions for this session

- TEST-LOG.md template: empty table with a placeholder row, or empty table with HTML-comment instructions (same pattern as MANIFEST.md)?
- The fourth drift check (Rule 5) needs "substantially changed" to mean something operational — define by file-touch count, by line-change threshold, by Claude's judgement with a reasoning trail, or leave to Claude with a prompt-level rule?
- Should the test-confirmation gate be enforced by hook (PreToolUse on Edit/Write that would start the next build) or by subagent prompt body (After-build subagent refuses to close until the user has accounted for every test)? V26 will implement whichever this session decides.
- Where in *After every build* does Rule 2's read-back step land — before the MANIFEST update, after the recap, or as its own labelled step?

## Risks / dependencies

- The protocol changes touch *After every build* (V26's territory) — V26's subagent prompt will reference these rules, so V25 must land before V26 can build cleanly.
- The "substantially changed" judgement is fuzzy; first real builds (V30 e2e test) may reveal the rule produces too many false-positive retest requests, or misses real component changes — refinement likely.
- The test-confirmation gate creates a hard stop in the build cycle; if a user paths around it (manually starts a new build), the log integrity breaks. Hook enforcement is stronger but adds a Claude-Code-specific dependency to a doc the prose-only rewrite (per OPEN-QUESTIONS *prose-only rewrite of the method*) will need to handle.
