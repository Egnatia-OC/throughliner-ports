# V34 — Consumer-method git workflow

## Goal

Give consumer projects a recommended git discipline plus a structural safety-guard, so a mid-session corruption (Drive sync, parallel sessions, Obsidian locks, or — in V35's case — an E2E test going sideways) has an easy revert path. Two deliverables, deliberately scoped lean:

1. **A *Recommended habits* line** in NO-CODE-METHOD (or wherever it lives post-V32): "tag and push after every shipped build batch." Wording mirrors the dev-project's own discipline; consumer-side framing.
2. **A PreToolUse safety-guard hook** that denies `git reset --hard` and `git push --force` from main Claude with a deny-reason pointing the no-coder at the correct recovery path.

Stop-hook auto-commit (drives tags + pushes after batch-executor's last file ticks) is **deferred to a future opt-in session** — one researched user who tested it at scale rolled it back. Lean shipment now; revisit once Taskflow's first cycles surface evidence.

- `plugin/docs/NO-CODE-METHOD.md` (post-V32 state) — receives *Recommended habits* line wherever V32 locates that content
- `plugin/hooks/` — receives the new PreToolUse hook (extends existing PreToolUse rather than adding a fresh one — confirm at session open)
- `plugin/.claude-plugin/plugin.json` — hook registration

  3. Confirm plugin-bundled hooks install into `settings.json` automatically vs. require user copy-paste (research draft flagged this as uncertain)

Note: action item 2 from the original research notes (read GitButler's `but claude stop` implementation) is **deferred** — only relevant if Stop-hook auto-commit ships, which V34 doesn't.

## Success criteria

- The two destructive commands are blocked from main Claude with a clear deny-reason; non-destructive git ops are unaffected
- Recovery path from a corruption incident is documented in plain English the no-coder can follow without prior git fluency
- TEST-LOG rows for the smoke test
- Action item 1 (`.git/index.lock` contention measurement) recorded in BUILD-LOG so future Stop-hook session has the baseline

## Open questions for this session

- **Hook extension vs. new file.** Does the safety-guard extend an existing PreToolUse hook (V19 lock enforcement, V25 supporting checks, V29 unadopted-folder enforcement) or land as a new file? Cleaner to extend if the matching pattern fits; new file if the deny logic diverges.
- **Skill walkthrough scope.** Ship a `/git-discipline` skill explaining habits + first-time setup in V34, or defer to a separate small session? Skill adds polish but isn't load-bearing for the safety-guard.
- **`--no-optional-locks` recommendation.** Once research action item 2 lands, decide whether the consumer method recommends this launch flag for Claude Code (mitigates the `.git/index.lock` contention).

## Risks / dependencies

- Depends on V32 (NO-CODE-METHOD retirement) — *Recommended habits* line lands wherever V32 distributed those rules
- Depends on V33 — if V33 ships a consumer-side BUILD-LOG, V34's habit recommendation can reference "tag and push after the BUILD-LOG entry is written" as a concrete close-step
- Hook deny logic must not block the recovery commands the deny-reason recommends — failure mode is locking the no-coder out of their own escape hatch. Smoke-test both directions.
- Windows `.git/index.lock` contention is real (CC's background `git status --porcelain` polling); the hook itself should avoid frequently-firing git ops
