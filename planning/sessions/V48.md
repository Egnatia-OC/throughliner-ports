# V48 — Automated vs. manual test split + non-UI test types

> **Renumbered from V46 → V48 in session v43 (2026-05-22)** when permission-mode UX harmonization took the V43 slot, displacing the vocabulary sweep to V47 and this session (which depends on vocab) to V48.

## Goal

Extend the method's after-build test model to (1) formally recognise four test types instead of one, and (2) accommodate automated Claude-run tests alongside manual user-run tests. The current model assumes every test is "look and click" UI interaction verified by the user — which blocks the method from serving non-UI projects (CLI tools, plugins, hooks, MCP servers, data pipelines) and pushes mechanical pass/fail checks onto the user when Claude could verify them faster and more reliably.

Single biggest method-level change to the build cycle since V27 (after-build subagent). Touches the after-build subagent, TEST-LOG row format, build-batch test specification, and the after-build prompt language.

## Positions going into the session

Decided in chat-time discussion (2026-05-21) following surfacing of `research/platform-capabilities-audit.md`. Pre-committed leanings, not session outputs — V48 the session may revisit if implementation surfaces something these positions didn't account for.

- **Slice by what's being checked, not by test type.** The earlier framing "look-and-click = user; the other three types = Claude" is type-bound. The better cut is content-bound: structural/factual checks (does the button exist, is the element red, does this click navigate to the right screen) go to Claude in every test type, including look-and-click. Judgement/taste/visual-nuance checks (does this feel right, is this the experience I want to ship, did this change introduce friction) go to the user. Same slice in all four test types. The verifier column carries the distinction per row, not per type.

- **Screenshot/vision-based UI evaluation off the table for now.** Vision models still hallucinate around layout/colour/font edges, the failure mode is "confidently calls a broken UI fine," and the compute cost is high in a pricing landscape that isn't reliably improving (the $20-Pro deletion attempt being a recent data point). Within look-and-click, Claude does text-output checks only: DOM structure via `preview_inspect`, console output via `preview_console_logs`, network state via `preview_network`, navigation via `preview_click`. Screenshots and visual judgement stay with the user. Reopen if vision reliability and pricing both shift.

- **The no-coder learning loop is not a method-level reason to keep manual testing.** It's a per-user silver lining for those who appreciate slow learning. Designing the method to make all consumers do mechanical testing Claude could handle would be patronising. The slicing above already preserves the user role in the parts that need taste; that's the principled limit.

## Open questions for this session

- **Residual Claude Preview design questions (post-position-setting).** With screenshots off the table and slice-by-what's-being-checked settled (see *Positions going into the session*), what remains: (a) does after-build run a Claude structural pre-pass — `preview_inspect`, `preview_console_logs`, `preview_network`, `preview_click` — before prompting the user, or only on demand? (b) recap language to distinguish "Claude verified these structural checks" from "please manually look at these taste/judgement points" — likely a clean two-section recap format. (c) verifier-column shape — likely same column structure with per-row verifier values, not a column split.

- **When do automated tests run?** Three positions:
  - **During the build** — batch-executor runs tests as it goes; failures halt the batch
  - **After the build** — after-build runs an automated pass before prompting the user
  - **Both** — batch-executor for in-build sanity checks, after-build for final pass

  Leaning: **after the build**, because batch-executor's halt-on-failure semantics complicate the existing "ticked vs. unticked files" mechanism. Revisit if real use shows in-build tests are needed.

- **Test specification: `Tests:` sub-section vs. extension of `Inputs:`.** V45 ships an `Inputs:` line for build batches. Tests could be a second peer sub-section, or an Inputs-line item ("test spec for this batch"). Leaning: peer sub-section — tests are operationally distinct from inputs (inputs are read, tests are executed), and separating keeps the format readable.

- **TEST-LOG row format: 10 columns vs. nested.** Adding two columns (type, verifier) keeps the flat shape but widens the row. Alternative: nested sub-row per test under one component row. Leaning: flat — nested adds parser complexity for marginal readability gain.

- **Trigger-and-observe automation: what's the test harness?** This test type covers hooks, webhooks, scheduled tasks. Claude can pipe fake input into a hook script (as the dev project's BUILD-METHOD.md describes for manual smoke tests). Does the method ship a thin harness pattern, or leave per-project? Leaning: leave per-project for V48, surface a harness pattern later if multiple projects converge on the same shape.

- **Backwards compatibility for existing TEST-LOG rows.** Taskflow's TEST-LOG has rows in the current 8-column shape. Migration on `/adopt` case 4: backfill type column with "look and click" (Taskflow's only type so far) and verifier column with "user". One-time, mechanical.

- **Relationship to TEST-LOG row pruning** (separate OPEN-QUESTIONS entry, parked for V45+ once row-count data exists). The two interact: a pruning mechanism that uses "verifier" or "type" as a pruning axis would compose. Worth flagging at session start; doesn't force shipping pruning here.

## Risks / dependencies

- **Largest change to the build cycle since V27.** After-build's responsibility expands meaningfully — it now runs tests, not just opens rows for the user to fill. Get the boundary right between "Claude ran and recorded" and "user must verify."
- **TEST-LOG schema change is permanent.** Once consumer projects scaffold with the new shape, reverting requires migration. Get the column shape right in one pass.
- **Depends on V47** for non-GUI vocabulary — without it, the language for non-UI test types ("the operator," "the downstream system," "the integrating developer") isn't settled and this session would shadow-decide it.
- **Depends on V45** for the Inputs-line mechanism — the natural model for per-batch test spec is a peer of Inputs. Could ship without (invent an isolated `Tests:` sub-section), but the surface is cleaner if both arrive together.
- **Three of four graduation prerequisites shipped after this session.** Only distributed fold-ins (V45) remains, and it ships before this session. After V48, the graduation meta-goal becomes promotable on its own evaluation — would mean the dev project starts using the plugin for its own work. Out of scope for V48 itself.
- **Real Taskflow evidence weak for non-UI types.** Taskflow is a GUI app; it doesn't exercise the new test types. The session ships the model on first-principles design; real validation needs a non-UI consumer project (most likely the dev project itself post-graduation).
