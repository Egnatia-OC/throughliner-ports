# V33 — Consumer-side audit trail + frame-correction sweep

## Goal

Three coupled additions to the consumer method, all touching *After every build*. Combined into one session because they edit the same docs and components — three separate sessions would each sweep the same surface.

1. **Consumer-side `BUILD-LOG.md`** — a persistent per-build narrative (What shipped / Decisions taken and why / Pivots and surprises / Carried forward), mirroring the dev-project's BUILD-LOG. Consumer projects currently lose the "why" trail on `/clear`: after-build produces a recap, but it lives only in chat. UX.md has user-need rationale (intent-level only); MANIFEST has element descriptions (no per-build narrative); BACKLOG is forward-looking; TEST-LOG is per-behaviour. No doc captures "this build shipped X because of Y, and surprise Z came up during it."
2. **`planning/drafts/<topic>.md` pattern for consumer projects** — a destination-agnostic carryover for substantive chat content not yet ready to commit to a specific doc. BACKLOG's *Fold-ins pending* is destination-specific (source-of-truth doc content); drafts/ holds everything else — drafts, comparison tables, structural sketches, protocol rules, column shapes, option matrices. Same lifecycle as the dev project's: commit at "good enough to walk away from," delete at consumption, dead-ends pruned with a one-line note in BUILD-LOG.
3. **Frame-correction sweep at *After every build*** — when a build substantively changes how a feature works, pending planning batches in BACKLOG and `[FOLD-IN PENDING]` blocks that reference the old behaviour get reviewed for absorb-risk. Dev-project added this at session-close in V29 after V29's own scope file hit a pre-V23 frame. Same failure mode would hit consumer projects' planning batches at some point.

## Open questions for this session

- **BUILD-LOG vs. chat recap.** Where does after-build's existing chat-time recap sit relative to the new BUILD-LOG entry? Likely both happen — BUILD-LOG entry is the persistent record, chat recap is the in-session announcement. Confirm at session open.
- **Frame-sweep operating scope.** Candidates: planning batches in BACKLOG naming the changed frame; UX.md entries cross-referencing the changed feature (flagged `[FOLD-IN PENDING]` since UX.md is read-only); pending `[FOLD-IN PENDING]` blocks themselves. Pick before drafting the sweep logic.
- **Frame-sweep ownership.** After-build (right after the build that corrected the frame, while change is fresh) vs. next session's planning open (with BACKLOG settled). Dev-project does it at session-close; consumer-side may differ.
- **Drafts placement in spec.** Sub-section under *Editing surfaces*, or its own section? Lighter lift vs. heavier presence.
