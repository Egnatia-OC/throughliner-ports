# V28 — Safety net + unified `/adopt` skill-command

## Goal

Prevent loss of user work when someone installs the sovereign-implementer plugin and points Claude Code at a folder that already contains substantial pre-existing work — a partway codebase, foreign-method docs, anything that isn't a fresh greenfield. At session start, the plugin detects the untrusted-folder state (no method version footer in `CLAUDE.md`, folder non-empty) and halts via `systemMessage`, directing the user to a single command, `/adopt`. `/adopt` unifies what was previously planned as separate `/new-project`, `/migrate`, and `/init-project` (V19) commands, branching across four folder states (empty / existing code with no docs / existing code with foreign docs / already method-managed) and never destroying anything without explicit user confirmation.

The unified shape resolves V28's previous open questions from earlier scoping: yes, `/new-project` and `/init-project` are the same command (both fold into `/adopt`); yes, migration auto-detects on session start, via the SessionStart-hook trust check rather than a separate auto-detect mechanism.

## Outputs

- **SessionStart hook extension.** Adds "method footer absent from `CLAUDE.md` AND folder non-empty" detection; emits `systemMessage` halt directing the user to `/adopt`. Trusted folders (footer present) and genuinely-empty folders (no real code) get silence — the warning channel is reserved for actual halts so users don't tune it out.
- **`agents/adopt.md`** — the adopt subagent (handles the branching dialogue and the four case flows)
- **`skills/adopt/SKILL.md`** — the skill-command entry point
- **`/adopt` four-case branching:**
  - *Empty folder* → run the four new-project questions, write answers as a `[FOLD-IN PENDING]` block in `BACKLOG.md` per the existing new-project route mechanism, scaffold templates with version footers
  - *Existing code, no docs* → backup confirmation; then choose between: reverse-engineer docs from code (see open question below); scaffold fresh docs alongside existing code; or cancel
  - *Existing code, foreign docs* (`CLAUDE.md` present but no method footer) → backup confirmation; then choose between: migrate (per the existing migration route mechanism, queuing `[FOLD-IN PENDING]` blocks); overwrite with explicit confirmation; or leave alone. Dialogue anticipates the "user ran Claude Code's built-in `/init` recently" case explicitly so users don't feel punished for using a built-in
  - *Already method-managed* (method footer present, user invoked `/adopt` anyway) → offer refresh-templates-to-current-version, or "did you mean to run this elsewhere?"
- **`NO-CODE-METHOD.md` updates.** Add "Detect untrusted folder" as a sibling to "Detect template state" in *At session start*. Add the trust-state entries to *Vocabulary*. Replace every reference to `/init-project` with `/adopt`. Fold the *New-project route* and *Existing-docs migration route* sections into descriptions of `/adopt`'s case branches.
- **`Crash course.md` update.** Cover the safety net at narrative altitude — the user-visible behaviour and the rationale (preventing loss-of-work for users installing the plugin into folders full of existing work). Replace `/init-project` references with `/adopt`.
- **Plugin README addition.** One line telling users to run `/plugin` after install to confirm Sovereign Implementer is loaded. This is the agreed visibility mechanism — the statusline route was ruled out (`${CLAUDE_PLUGIN_ROOT}` not supported in user `settings.json`, so absolute paths with cache hashes would be the only option, too fragile across plugin updates for non-developer users).
- **This project's `CLAUDE.md`.** Update references to `/init-project` (currently in *Which CLAUDE.md is which* and *Plugin install status*) to `/adopt`.
- Commit tagged `v28`

## Success criteria

- SessionStart hook, invoked directly against a fixture folder (no method footer, non-empty), returns the expected halt JSON with the `systemMessage` field populated
- `/adopt` branches correctly to each of the four cases when invoked against fixture folders matching each state
- `/adopt` in an empty directory walks through the 4 new-project prompts and writes a `[FOLD-IN PENDING]` block to `BACKLOG.md` containing the answers (the V27-original criterion, now case 1)
- `/adopt` in a project with structurally-non-conforming docs surfaces gaps, walks them in spec order (UX → additional SoT docs → BACKLOG → MANIFEST), and queues `[FOLD-IN PENDING]` blocks for source-of-truth doc edits (the V27-original criterion, now case 3)
- Both flows respect the read-only enforcement (no direct `UX.md` writes) and the discussion contract on `BACKLOG.md` edits
- No reference to `/init-project` remains anywhere in the codebase or descriptive docs after the rename (verified via `grep`)
- `NO-CODE-METHOD.md`'s *At session start* reads coherently after the new bullet is added — surrounding sentences still parse, routing logic stays consistent
- `Crash course.md`'s session-shape narrative incorporates the safety net without losing readability
- Doc-code parity audit at session close finds no gaps between the new hook/command behaviour and the descriptive docs

Live Claude-Code-runtime testing is **deferred** to the live-install session (per `CLAUDE.md` → *Plugin install status*). This session ships script-validated only — hook script direct invocation, parser script CLI runs, code review against real project files.

## Open questions for this session

- **Reverse-engineering tool scope.** Case 2 (existing code, no docs) ideally offers "reverse-engineer docs from your code" as a path. That sub-flow could be a substantial subagent on its own. Decision needed during the session: ship the reverse-engineer path here, or scope it to a later session and have case 2 ship with only "scaffold fresh and fill alongside" available? The escape clause from `CLAUDE.md` → *Doc-code parity* applies — surface the scope mid-session and decide together rather than forcing fold-in.
- **"Folder non-empty" threshold.** What counts as substantial pre-existing work for the trust check? `README` + `.gitignore` alone shouldn't trigger the halt. A directory with `src/` and a build manifest definitely should. Define a concrete rule the hook can apply — likely a count of source files plus presence-of-build-manifest heuristics.
- **Vocabulary naming for the trust state.** *Trusted folder / untrusted folder* is the working terminology. Alternatives worth considering: *adopted / unadopted*, *initialised / uninitialised*, *managed / unmanaged*. Decide in light of how the user-facing dialogue reads.
- **`/adopt` dialogue wording per case.** The dialogue resolves the command name's semantic ambiguity (user adopts method vs. method adopts folder — both readings are plausible from the name alone; the dialogue makes which one is happening explicit). Draft, review in chat, lock before shipping.
- **Legacy-footer compatibility.** Folders managed under a pre-`/adopt` plugin version may not have the footer in the exact form the new check expects. Confirm `CLAUDE-TEMPLATE.md`'s footer format has been stable across versions, or handle the legacy-footer case in the detection logic so existing method users don't get halt-warned spuriously.

## Risks / dependencies

- **Live-install dependency.** Per `CLAUDE.md` → *Plugin install status*, the plugin has never run inside Claude Code as of V23. This session can only ship script-validated; live verification waits for the live-install session. If live behaviour diverges from script predictions, that's a cost paid in the live-install session, not here.
- **Timing risk against live-install.** The data-loss risk this session prevents only materialises once the plugin is live-installable. If the live-install session lands before V28 ships, users could install between live-install and V28 and hit the unprotected case. Either live-install lands after V28, or V28 moves earlier in the roadmap.
- **Doc-code parity audit is heavier than usual.** Renaming `/init-project` → `/adopt` plus folding the new-project/migration route sections into `/adopt`'s case branches is a method-level rewrite touching `NO-CODE-METHOD.md`, `Crash course.md`, the templates, and this project's `CLAUDE.md`. Budget audit time accordingly.
- **Reverse-engineering tool blow-up risk.** If scoped in and not given clear bounds, the subagent could dominate the session. Have the escape clause ready before committing.
- **Vocabulary churn cascade.** Adding new trust-state entries may cascade into wording changes elsewhere in `NO-CODE-METHOD.md` and `Crash course.md`. Catch during the doc-code parity audit, not after.
- **`/init` collision priming.** Claude Code's built-in `/init` is a documented entry point users may run before they discover `/adopt`. If they do, they get a generic `CLAUDE.md` with no method footer, which the new check correctly flags as foreign-docs. Case 3's dialogue must anticipate this explicitly.
- **Fold-in queue growth.** `/adopt`'s case 1 and case 3 branches write `[FOLD-IN PENDING]` blocks; original V27 risk of queue growth (user not following up with fold-ins) still applies.
