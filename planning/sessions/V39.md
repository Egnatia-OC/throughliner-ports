# V39 — MANIFEST schema + direct-edit drift detection

## Goal

Decide whether MANIFEST.md gains a path field (and in what format), implement if yes, and extend drift detection to catch in-file content changes by direct-edit users — resolving the remaining shapes from the V22 partial fold-in. The schema decision in OPEN-QUESTIONS #10 is the unlock for stronger drift catching from #14; doing them together avoids touching the same files twice.

## Inputs

- `planning/OPEN-QUESTIONS.md` entries:
  - "MANIFEST.md schema gap blocks PreToolUse read-before-edit enforcement"
  - "Method response to direct-edit users (developers)" — remaining shapes after V22 partial fold-in
- `plugin/templates/MANIFEST-TEMPLATE.md` and `templates/MANIFEST-TEMPLATE.md` (both sides)
- `plugin/agents/after-build.md` — MANIFEST auto-update logic
- `plugin/docs/DOC-STRUCTURE.md` — MANIFEST.md structural spec
- `NO-CODE-METHOD.md` docs-only side — read-before-edit rule, Required of Claude
- PreToolUse hook source — where a read-before-edit check would land
- Taskflow's `MANIFEST.md` — real-world example of current shape and row count

## Outputs

- **Schema decision:** does MANIFEST.md gain a paths field? In what format? (Flat list, glob patterns, directory-level?)
- If yes: updated MANIFEST-TEMPLATE.md (both sides), DOC-STRUCTURE.md (both sides), after-build.md update logic, NO-CODE-METHOD.md (docs-only)
- If yes + enforcement chosen: PreToolUse read-before-edit check implemented (option A or B from OPEN-QUESTIONS working notes)
- Drift detection extension for in-file content changes — the gap V22's file-level-only check left open
- Decision on remaining shapes #2 (developer-mode entry point) and #3 (explicit non-audience declaration) for direct-edit users
- Two OPEN-QUESTIONS entries removed

## Success criteria

- Schema decision made and implemented (or consciously deferred with documented reasoning)
- If path field added: read-before-edit enforcement testable via smoke test
- Drift detection catches file-level AND in-file changes from manual edits (or a conscious decision that in-file is out of scope with documented reasoning)
- Doc-code parity clean across both sides of the two-write rule
- Migration path documented if MANIFEST format changes affect existing consumer projects

## Open questions for this session

- **Which enforcement shape?** A (PostToolUse tracks reads + PreToolUse checks), B (inline deny-with-context — PreToolUse denies with MANIFEST + UX entries inlined in deny reason), or C (convention-only, no schema change). Depends on schema decision.
- **In-file content change detection mechanism.** Hash-based? Timestamp-based? Git-diff? What's the minimum that catches real drift without false positives on a no-coder's machine?
- **Developer-mode entry point vs. explicit non-audience.** Does the schema + drift work make shapes #2 and #3 moot (better detection = developers can use the method as-is), or do they remain distinct concerns?
- **Migration path.** If MANIFEST gains a paths field, do existing consumer MANIFESTs need updating? Can after-build populate paths incrementally as components are touched, or does a one-time migration run?

## Risks / dependencies

- Schema change ripples to MANIFEST-TEMPLATE.md, after-build update logic, and potentially every existing consumer's MANIFEST.md. Migration path needed if format changes.
- Heaviest of the three batches. May need splitting after planning starts — the MANIFEST schema decision could be session-sized on its own if the drift-detection shapes prove complex.
- Benefits from Taskflow having shipped several real batches first (more MANIFEST rows = better schema design). If Taskflow hasn't built much by the time V39 runs, the schema decision has less real data to inform it.
- Depends on V38 only in that V38's lock-rule changes might affect how the read-before-edit check interacts with the PreToolUse stack. No hard blocker.
