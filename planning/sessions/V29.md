# V28 — Safety net + unified `/adopt` skill-command

## Goal

Prevent loss of user work when the sovereign-implementer plugin is pointed at a folder with pre-existing work (partway codebase, foreign docs — anything non-greenfield). At session start the plugin detects an untrusted folder (no method version footer in `CLAUDE.md`, folder non-empty) and halts via `systemMessage`, directing the user to `/adopt`. `/adopt` unifies the previously-planned `/new-project`, `/migrate`, and `/init-project` (V19) commands, branching across four folder states (empty / existing code, no docs / existing code, foreign docs / already method-managed). Nothing is destroyed without explicit confirmation.

Resolves earlier scoping questions: `/new-project` and `/init-project` collapse into `/adopt`; migration auto-detects via the SessionStart-hook trust check, not a separate mechanism.

## Open questions for this session

- **Reverse-engineering tool scope.** Case 2 ideally offers "reverse-engineer docs from your code" — but the sub-flow could be a substantial subagent on its own. Decide in session: ship it here, or scope it later and have case 2 ship "scaffold fresh and fill alongside" only? Escape clause from `CLAUDE.md` → *Doc-code parity* applies — surface the scope mid-session and decide together, don't force fold-in.
- **"Folder non-empty" threshold.** What counts as substantial pre-existing work? `README` + `.gitignore` shouldn't trigger; `src/` plus a build manifest definitely should. Define a concrete rule for the hook — likely source-file count plus build-manifest presence.
- **Trust-state vocabulary.** Working terms: *trusted / untrusted folder*. Alternatives: *adopted / unadopted*, *initialised / uninitialised*, *managed / unmanaged*. Decide against how the user-facing dialogue reads.
- **`/adopt` dialogue wording per case.** Dialogue resolves the name's ambiguity (user adopts method vs. method adopts folder — both plausible from the name; dialogue makes which is happening explicit). Draft, review in chat, lock before ship.
- **Legacy-footer compatibility.** Folders managed under pre-`/adopt` plugin versions may not match the new check's expected footer form. Confirm `CLAUDE-TEMPLATE.md`'s footer format has been stable, or handle legacy footers in detection logic so existing method users don't get halted spuriously.

## Risks / dependencies

- **Live-install dependency.** Per `CLAUDE.md` → *Plugin install status*, the plugin has never run inside Claude Code as of V23. Script-validation only this session; live verification waits for the live-install session. Divergence between script and live behaviour is a cost paid there, not here.
- **Timing risk vs. live-install.** The data-loss risk this session prevents only materialises once the plugin is live-installable. If live-install lands before V28, users could install in the gap and hit the unprotected case. Either live-install lands after V28, or V28 moves earlier.
- **Heavier-than-usual doc-code parity audit.** The `/init-project` → `/adopt` rename plus folding new-project/migration routes into case branches is a method-level rewrite touching `NO-CODE-METHOD.md`, `Crash course.md`, the templates, and this project's `CLAUDE.md`. Budget audit time accordingly.
- **Reverse-engineering tool blow-up risk.** If scoped in without clear bounds, the subagent could dominate the session. Have the escape clause ready before committing.
- **Vocabulary churn cascade.** New trust-state entries may cascade into wording changes elsewhere in `NO-CODE-METHOD.md` and `Crash course.md`. Catch during the parity audit, not after.
- **`/init` collision priming.** Claude Code's built-in `/init` is a documented entry point users may run before discovering `/adopt`. If they do, the resulting generic `CLAUDE.md` (no method footer) correctly trips the foreign-docs check. Case 3's dialogue must anticipate this explicitly.
- **Fold-in queue growth.** `/adopt` cases 1 and 3 write `[FOLD-IN PENDING]` blocks; V27's queue-growth risk (user not following up) still applies.
