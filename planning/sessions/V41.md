# V41 — Vocabulary sweep / non-GUI generalisation

## Goal

Resolve two vocabulary-level method questions in a single sweep: (1) generalising "user-observable behaviours" and related UX.md phrasing for non-GUI projects (CLI tools, backend services, MCP servers, scripts), and (2) disambiguating the method's "planning" phase from Claude Code's "plan mode" feature. Bundled because both require a grep-and-rewrite pass across every canonical doc on both sides of the two-write rule — doing them together amortises the parity audit.

## Inputs

- `planning/OPEN-QUESTIONS.md` entries:
  - "UX.md adaptation for non-GUI projects"
  - "'Planning' vocabulary collision with Claude Code's 'plan mode'"
- `NO-CODE-METHOD.md`, `DOC-STRUCTURE.md`, `VOCABULARY.md` (both sides — repo root + `plugin/docs/`)
- `plugin/hooks/universal-behaviour.md`
- All subagent bodies under `plugin/agents/`
- All templates (both sides — `templates/` + `plugin/templates/`)
- `Crash course.md`

## Outputs

- **Non-GUI decision:** generalise vocabulary across all docs, add non-GUI guidance section to DOC-STRUCTURE.md, or create a separate spine-doc template. Leaning: vocabulary generalisation + guidance section (lightest lift, preserves "user" anchor where it fits for GUI projects).
- **"Planning" disambiguation decision:** rename the method's planning phase, add a vocabulary note, or hybrid. Leaning: vocabulary disambiguation note in VOCABULARY.md + Crash course mention (lightest lift; full rename is high-churn for uncertain gain).
- Updated canonical docs (both sides) reflecting both decisions
- Updated subagent bodies, templates, Crash course as needed
- Two OPEN-QUESTIONS entries removed

## Success criteria

- A non-GUI project's UX.md entries read naturally under the new vocabulary or guidance
- "Planning session" and "plan mode" are unambiguous to a reader encountering both for the first time
- No regression in Taskflow-relevant wording — GUI projects must still read naturally
- Doc-code parity clean across both sides of the two-write rule

## Open questions for this session

- **Non-GUI: which shape?** Vocabulary generalisation ("observable outcomes" / "testable behaviours" replacing "user-observable behaviours") vs. guidance section in DOC-STRUCTURE.md explaining how non-GUI projects should name their "user" and shape their entries. May do both — generalise the vocabulary AND add a guidance paragraph.
- **"Planning" disambiguation: which shape?** Rename the phase (heavy), vocabulary note (light), or hybrid (rename subagent only). Real Taskflow use may have surfaced the confusion by the time this session runs — if not, leaning toward vocabulary note only.
- **Does Taskflow evidence inform either decision?** Both questions were raised in V30 review, pre-E2E. If real Taskflow use hasn't surfaced either friction by V41, that's weak evidence the problems are theoretical. May downgrade one or both to vocabulary notes rather than structural changes.

## Risks / dependencies

- Largest grep-and-rewrite surface of the three batches. Every canonical doc, both sides, plus Crash course, plus subagent bodies, plus templates. Risk of introducing inconsistency in the sweep itself.
- Vocabulary changes are permanent — reverting after publication is expensive. Get it right in one pass.
- No hard dependencies on V39 or V40. Could run in any order, but last position lets real Taskflow use confirm whether the problems are real before committing to the sweep.
