# V41 — Git-diff drift detection + direct-edit confirmation protocol

> **Renumbered from V40 in session v40 (2026-05-21)** when the two-write shelving session took the v40 slot. Content unchanged except for the renumbering and the two-write trim noted below.

## Goal

Extend the planning subagent's drift detection to catch in-file content changes using git-diff, and add a per-change confirmation protocol for manually-edited files. Resolves the remaining shapes from the V22 partial fold-in of the "Method response to direct-edit users" OPEN-QUESTIONS entry. Second half of the original V39 scope.

## Decisions made (pre-session planning, 2026-05-21)

- **Detection mechanism: git-diff.** Run `git diff` (or `git status`) against the last tagged commit at the start of every planning session. Catches both file-level and in-file changes. Assumes git, which the method already assumes.
- **Confirmation protocol.** Each flagged change is surfaced to the user individually. User confirms "yes, that was me" or "no, something's wrong." Confirmed changes: Claude checks for conflicts with build batches in BACKLOG.md. If conflict, flag and discuss. If no conflict, accept and update docs (MANIFEST.md, and a lightweight fold-in for UX.md if the change implies a UX update). Unconfirmed changes flagged as unexpected.
- **Shapes #2 and #3 deferred.** Developer-mode entry point and explicit non-audience declaration both deferred until a real developer tries the method and reports friction. Shape #1 (tighten detection + confirmation protocol) is the shipped answer.

## Success criteria

- Planning subagent runs `git diff` against last tag and surfaces changed files not attributable to the most recent build batch
- User is walked through each flagged file individually with a confirm/deny prompt
- Confirmed changes are checked against BACKLOG.md build batches for conflicts
- Non-conflicting confirmed changes are accepted with doc updates (MANIFEST.md paths, UX.md fold-in if applicable)
- Conflicting changes are flagged with clear explanation of the conflict
- Doc-code parity clean (plugin side — repo-root docs-only set is frozen at V39 per v40 shelving)
- Smoke-testable via `--plugin-dir` (make a manual edit in a fixture project, open a planning session, verify the change surfaces)

## Open questions for this session

- **Integration with existing drift checks.** Does git-diff become a fifth drift check, or does it fold into the existing check 2 (MANIFEST ↔ codebase)? Check 2 currently operates at the doc level; git-diff operates at the file level. Leaning: fifth check, run before the existing four, because its output feeds into them.
- **What counts as "attributable to the most recent build batch"?** The Files: sub-section lists what the batch-executor touched. Any diff outside that list is a candidate for the confirmation protocol. But what about after-build's MANIFEST.md update, or BUILD-LOG.md writes? Need a clear boundary for "expected changes."
- **Lightweight fold-in shape.** When a confirmed manual edit implies a UX.md update, what does "lightweight" look like? A full `[FOLD-IN PENDING]` block, or something simpler? Leaning: standard `[FOLD-IN PENDING]` — the mechanism already exists, no reason to invent a lighter one.

## Risks / dependencies

- Depends on V39 (MANIFEST paths field). Git-diff detection works without paths, but the output is richer with them — "this file changed, and it maps to MANIFEST entry X" vs. just "this file changed."
- Git-diff against last tag assumes the project tags. The method recommends tagging but doesn't enforce it. Fallback: diff against last commit? Or require tagging as part of this session?
- Confirmation protocol adds a new interactive step to the start of every planning session. If git history is clean (no manual edits), the step is silent. If noisy (many changes), it could dominate the session. Consider a threshold or summary mode for large diffs.
