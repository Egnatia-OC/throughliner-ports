# V26 — After-build subagent

## Goal

Build the after-build subagent: updates `MANIFEST.md` for anything created/renamed/deleted in the batch, generates the plain-English build recap with `[Requested]`/`[Suggested]` labels, prompts the user to test and `/clear`.

## Inputs

- V18–V25 outputs (V25 introduced the TEST-LOG.md mechanism and protocol that this subagent enforces)
- `NO-CODE-METHOD.md` → *After every build* (including the V25-added test-confirmation steps)
- `TEST-LOG.md` schema in `DOC-STRUCTURE.md` (V25)

## Outputs

- `agents/after-build.md` — after-build subagent definition
- Triggering mechanism: Stop hook detects "no more batches" condition and routes to after-build, OR PostToolUse hook detects batch completion, OR `/after-build` slash command (decision this session)
- After-build subagent enforces the test-confirmation gate from V25 (read-back of "all others good," every test accounted for as Pass/Fail/Skipped before the session can close)
- Commit tagged `v26`

## Success criteria

- After a successful Taskflow batch, `MANIFEST.md` is updated for any created/renamed/deleted named elements
- Build recap appears in chat with `[Requested]`/`[Suggested]` labels and plain-English descriptions of changes
- User is prompted to refresh, test, and `/clear`

## Open questions for this session

- Triggering: which mechanism? (Stop hook routing the cleanest; PostToolUse may double-fire; slash command requires manual user invocation.)
- `MANIFEST.md` auto-update — fully automatic (subagent decides), proposed-with-confirmation (subagent shows changes, user accepts), or assistive (subagent suggests and user edits)?
- How to label `[Requested]` vs `[Suggested]` — track inside the batch itself, or derive from chat history?

## Risks / dependencies

- `MANIFEST.md` auto-updates may conflict with mid-session edits or with edits the user has made directly
- Recap quality depends on the after-build subagent having visibility of the batch's actual changes — needs the batch's diff or the file list of touched files
