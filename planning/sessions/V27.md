# V27 — After-build subagent + planning subagent extension + test-confirmation gate hook

## Goal

Implement the test-confirmation gate machinery whose prose V26 shipped. Per V26's Q4 (Rule 2 relocated from *After every build* → *During planning*) and Q3 (hybrid enforcement: hook is load-bearing gate, subagent recap is UX), V27's work splits across three components:

1. **After-build subagent.** Owns *After every build* per `NO-CODE-METHOD.md`: updates `MANIFEST.md` for anything created/renamed/deleted, generates plain-English build recap with `[Requested]`/`[Suggested]` labels, **opens the test session** (appends blank-`Status` rows to `TEST-LOG.md` for each user-observable behaviour the recap names), prompts the user to refresh, test, and bring per-row outcomes to the next planning session. Does **not** do the per-row read-back — relocated to planning per V26.

2. **Planning subagent extension.** Adds the first sub-step from V26's *During planning* edit: per-row read-back of the previous build's pending `TEST-LOG.md` rows (Rule 2), updating each row's `Status` and `Confirmed Explicitly` as the user confirms. Existing V22-built planning flow then proceeds normally (dedupe completed batches, drift checks including the new fourth check from V26's Rule 5, etc.).

3. **Test-confirmation gate hook.** PreToolUse on Task with `subagent_type=no-code-method:batch-executor`. Reads `TEST-LOG.md`, finds rows whose `Session` matches the previous build batch's session (parsed from the consumer project's `BUILD-LOG.md` if present) and whose `Confirmed Explicitly` is `No`, denies invocation if any exist. **Hook fallback** when project doesn't keep `BUILD-LOG.md`: "any row with `Confirmed Explicitly: No` blocks" — strict but safe (V26 decision, confirmed).

Plus: **main-Claude session-open tripwire.** If `TEST-LOG.md` has previous-build rows with `Confirmed Explicitly: No`, main Claude routes to the planning subagent regardless of opener content. Tripwire injected via the SessionStart hook's `additionalContext`. (V26 confirmed this wires into V27.)

## Success criteria

- After a successful Taskflow batch ships, the after-build subagent runs end-to-end: `MANIFEST.md` updated for any created/renamed/deleted named elements; build recap appears in chat with `[Requested]`/`[Suggested]` labels and plain-English descriptions; `TEST-LOG.md` has new rows appended with today's `Date`, blank `Status`, `Confirmed Explicitly: No`, one row per user-observable behaviour the recap names; user is prompted to refresh, test, and bring per-row outcomes to the next planning session.
- User starts a new planning session after testing; planning subagent's first action is the per-row read-back of TEST-LOG pending rows. User can answer Pass / Fail / Skipped per row. Skipped responses prompt for a reason inline; Fail responses prompt for User Notes. Bulk answers ("the rest are fine") get pushed back with the next pending row's `Test Description` until every row is confirmed individually.
- After the read-back, the planning subagent proceeds through the existing dedupe + drift-check sequence, with the new fourth drift check (TEST-LOG ↔ what's been touched since each row was recorded, per V26 Rule 5) producing reasoning trails per flagged row.
- User attempts to `/build` while TEST-LOG has unconfirmed rows from the previous batch: PreToolUse hook denies with reason naming the unconfirmed rows by `#` and `Test Description`, and pointing the user at the read-back.
- Brand-new project with empty `TEST-LOG.md`: hook permits invocation. Project that doesn't keep `BUILD-LOG.md`: hook falls back to "any unconfirmed row blocks" mode per the V26 decision.
- Session-open with `TEST-LOG.md` having pending rows from the previous build: SessionStart hook injects the tripwire; main Claude routes the next planning to the planning subagent regardless of whether the opener is test notes, a feature request, a scope question, or conversational.

## Open questions for this session

- **After-build triggering mechanism.** Stop hook routing (cleanest per V25 precedent) vs. PostToolUse on batch-executor completion (may double-fire, requires deduplication) vs. `/after-build` slash command (manual user invocation, fragile). Lean: Stop hook. Confirm.
- **`MANIFEST.md` auto-update mode.** Fully automatic (subagent decides + writes), proposed-with-confirmation (subagent shows diff, user accepts), or assistive (subagent suggests, user edits). Independent of test-confirmation work. Lean: proposed-with-confirmation for files created/renamed (visible enough to matter); fully automatic for trivial entry-text updates.
- **`[Requested]` vs `[Suggested]` source.** Track inside the batch's plan in `BACKLOG.md` (auditable, but requires the before-build subagent to label items at planning time), or derive from chat history (lossy, brittle). Lean: from `BACKLOG.md` — requires a small label addition in the *Files: sub-section* item shape; surface that to V27 closing if approved.
- **Hook fallback boundary for BUILD-LOG present but unreadable.** V26 decided strict ("any unconfirmed row blocks") when no BUILD-LOG. This is the related but distinct case of BUILD-LOG existing but being malformed/truncated/unparseable. Lean: same — strict, preserves the safety property. Confirm.
- **TEST-LOG tripwire injection mechanism.** SessionStart hook `additionalContext` (V21 precedent) vs. injecting into `CLAUDE.md` at `/init-project` scaffold time. Lean: SessionStart hook — consumer-project `CLAUDE.md` is user-controlled and the rule has to fire even when the user customises their CLAUDE.md without preserving the tripwire instruction.

## Risks / dependencies

- V26 must ship before V27 can build cleanly. `NO-CODE-METHOD.md` prose, `TEST-LOG-TEMPLATE.md` (both copies), `DOC-STRUCTURE.md` spec, and vocabulary additions are all referenced by this session's code.
- Hook fallback for missing/unreadable `BUILD-LOG.md` is "any unconfirmed row blocks" per V26. This is safe but may surprise users in the edge case where `TEST-LOG.md` has manually-seeded rows pre-dating any build batch. Watch in first real Taskflow build.
- Planning subagent extension touches V22-built code. The doc-code parity audit at V27 close needs to verify the extended planning subagent body still aligns with `NO-CODE-METHOD.md` → *During planning* after V26's edits land — both the new first sub-step and the new fourth drift check.
- The TEST-LOG tripwire creates a hard routing constraint that may surprise users who expect "I asked a question, why am I being walked through tests?" The planning subagent's first read-back row needs to surface the why upfront: *"Before we get to your question — N pending tests from session X to confirm. First: <test description>?"*
- After-build subagent's `MANIFEST.md` auto-update may conflict with mid-build manual edits to MANIFEST.md (the user editing during build is rare but possible — see *Method response to direct-edit users* in `OPEN-QUESTIONS.md`). Resolution mode for that conflict deferred to first real occurrence.
