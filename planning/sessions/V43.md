# V43 — Permission-mode UX harmonization

> **Created in session v43, 2026-05-22.** Research in the same session confirmed that PreToolUse hooks fire in every Claude Code permission mode, including Auto mode and `--dangerously-skip-permissions` (bypass). The hook receives `permission_mode` in its input JSON but currently ignores it — all deny messages are mode-unaware.

## Goal

Audit every PreToolUse deny path against every Claude Code permission mode and design mode-aware responses — both messaging and, where needed, different behaviour. The core UX problem: a user in a permissive mode (Auto, Accept edits, bypass) who hits a method deny will naturally escalate through increasingly permissive modes; when none work, they'll conclude Claude is broken. Every deny must make clear that the block is a method rule, not a permission issue, and say what to do instead.

## Inputs

- `plugin/hooks/pre_tool_use.py` — all deny paths live here
- `plugin/scripts/project_state.py` — shared helpers (some deny-path logic may live here)
- `plugin/hooks/universal-behaviour.md` — documents the editing surfaces, fold-in mechanism, and prohibited behaviours that the denials enforce
- `plugin/docs/DOC-STRUCTURE.md` — structural rules the denials protect
- `plugin/docs/VOCABULARY.md` — term definitions for deny-message wording
- `Crash course.md` — user-facing explanation of the plugin; needs a section on the two-layer permission model
- Web research from session v43: hooks fire in all modes; `permission_mode` field available in hook input JSON; deny overrides even bypass mode

## The matrix

**Deny paths** (rows):

1. **UX.md / additional SoT doc lock** — read-only enforcement on source-of-truth docs
2. **Batch boundary enforcement** — `Files:` list blocks edits outside the current batch
3. **Test-confirmation gate** — blocks batch-executor while TEST-LOG has unconfirmed rows
4. **Unadopted folder gate** — blocks Edit/Write/MultiEdit + Task to method-subagent until adopted or opted out
5. **MANIFEST read-before-edit gate** — denies first edit on a MANIFEST-covered file with context inlined; retry succeeds
6. **Serves UX.md validation** — blocks build batches whose `Serves UX.md:` line doesn't resolve
7. **Destructive git commands** — blocks `git reset --hard`, `git push --force` with safer alternatives

**Permission modes** (columns):

1. **Ask permissions** (default) — user expects prompts; denials feel normal
2. **Accept edits** — user expects file edits to go through; method denials may surprise
3. **Plan mode** — Claude shouldn't be editing anyway; method denials may be redundant noise
4. **Auto mode** — user expects Claude to just do it; method denials are most confusing here
5. **Bypass permissions** — user explicitly said "skip all checks"; method denials are maximally confusing

For most cells, the current deny messages work fine — the user is in a mode where they expect Claude to be checked. The problem cells are Accept edits + any edit deny, Auto mode + any deny, and Bypass + any deny — where the user's mode selection implies "let Claude work freely" but the method still blocks.

## Outputs

- **Mode-aware deny messages.** Every deny message explicitly states this is a no-code method rule (not a Claude Code permission issue) and names the action to take instead. Messaging adjusts based on `permission_mode` — e.g., in bypass mode, an additional line like "Changing your permission mode won't affect this — this block comes from the no-code method plugin."
- **Behaviour changes where warranted.** For some deny-path x mode combinations, the hook should do something different — not just explain differently. Candidates to evaluate at session start:
  - Plan mode + edit denials: return `defer` instead of `deny` (let plan mode's own restrictions handle it, avoiding double-deny noise)?
  - MANIFEST read-before-edit in Auto mode: the deny-then-retry pattern may look like a glitch to the user; consider injecting context and allowing on first attempt?
  - Other combinations TBD at session start based on the full matrix walkthrough
- **Crash course update.** New section explaining the two-layer permission model: Claude Code's permission modes control whether the user gets prompted; the plugin's hooks control whether Claude is allowed to act at all. The two are complementary, not overlapping.
- **Forward-compatibility note for V45.** V45 (distributed fold-ins) will add an append-only carve-out for fold-in sections on locked docs. That carve-out will introduce a new "partial allow" path on the UX.md lock that needs its own mode-aware messaging. V43 designs the framework; V45 extends it.

## Success criteria

- A user in Auto mode who hits a UX.md lock denial reads the deny message and understands immediately: (a) this is a method rule, (b) changing permission mode won't help, (c) here's what to do instead
- A user in Plan mode does not see redundant method denials on top of plan mode's own edit restrictions
- No deny path produces a message that could be mistaken for a Claude Code permission issue
- Crash course explains the two-layer model clearly enough that a new user encountering it for the first time doesn't reach for permission-mode settings
- Doc-code parity clean (plugin side; repo-root frozen at V39)
- Smoke-testable via `--plugin-dir`: trigger each deny path in at least two permission modes (default + one permissive) and verify the deny message is mode-appropriate

## Open questions for this session

- **Which deny-path x mode combinations need behaviour changes, not just message changes?** The scope file lists candidates (Plan mode double-deny, MANIFEST retry in Auto mode). Full audit at session start — walk the matrix cell by cell.
- **Should SessionStart inject a one-line note about the two-layer model?** Currently SessionStart injects universal-behaviour rules. A short addition like "This project uses the no-code method plugin. Some edits are blocked by method rules regardless of your Claude Code permission mode — deny messages will explain what to do." could preempt confusion before the first denial fires. Trade-off: context cost vs. UX clarity.
- **Deny message format.** Current deny messages vary in style. Should V43 also standardise the format (e.g., every deny starts with a "[No-code method]" prefix, or every deny ends with a "what to do instead" line)? Scope creep risk — may defer format standardisation and only add mode-aware content.

## Risks / dependencies

- **No hard dependencies.** Can ship immediately — only requires reading the current hook code and rewriting deny messages + adding mode-branching logic.
- **Forward dependency from V45.** The distributed-fold-ins session will add a new PreToolUse carve-out (append-only on locked docs) that needs its own mode-aware messaging. V43 should design the framework in a way V45 can extend without redesigning.
- **Behaviour changes are riskier than message changes.** Changing what the hook *does* (e.g., returning `defer` instead of `deny` in Plan mode) could have unintended effects. Each behaviour change needs its own smoke test.
- **Seven deny paths x five modes = 35 cells.** Most cells are "current behaviour is fine." The audit's job is to identify the ~8-12 problem cells and design responses for those. Don't over-engineer the non-problem cells.
