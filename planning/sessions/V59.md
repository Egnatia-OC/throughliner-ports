# V59 — Graduation: dev project onto its own method

> **Promoted from OPEN-QUESTIONS in session v47 (2026-05-22).**

## Goal

Transition the no-code method's own dev project from its bespoke dev environment (Vxx scope files, BUILD-METHOD.md, OPEN-QUESTIONS.md, two-write rule) to using the method's own plugin — dogfooding sovereign implementer to build sovereign implementer. This is the capstone session: all four prerequisites have shipped by this point.

## Prerequisites (all shipped by V59)

1. **Distributed fold-ins + open questions section in BACKLOG** — V45. Gives the method a parking lot for unresolved questions (replaces OPEN-QUESTIONS.md) and restructures BACKLOG.md.
2. **Shelve the two-write rule** — Done in session v40. Repo-root docs-only set frozen; plugin side is sole operational source.
3. **Non-GUI vocabulary** — V47. Method language fits a plugin/method-spec project, not just UI apps.
4. **Test split + non-UI test types** — V48. Build cycle can verify plugin work (run-and-read, trigger-and-observe, generate-and-inspect test types).

## Inputs

- OPEN-QUESTIONS entry: "Graduate sovereign implementer development onto sovereign implementer"
- `BUILD-METHOD.md` — current bespoke dev manual; identifies what needs method-equivalent replacements
- `planning/OPEN-QUESTIONS.md` — content migrates to BACKLOG.md open-questions section
- All `planning/sessions/V*.md` files — content migrates to BACKLOG.md batches (or ADR-style batch files after V50)
- `planning/PLAN.md` — build-order carrier; role moves to BACKLOG/INDEX.md after V50
- `plugin/agents/adopt.md` — `/setup` runs against the dev project itself
- Consumer project's CLAUDE.md, UX.md, BACKLOG.md, MANIFEST.md, TEST-LOG.md, BUILD-LOG.md — the dev project gains these as spine docs

## Outputs

- Dev project adopted onto the method via `/setup` (likely case 2: existing code, no method docs)
- OPEN-QUESTIONS.md content migrated to BACKLOG.md open-questions section
- Remaining V-file scopes migrated to BACKLOG batches
- PLAN.md role replaced by BACKLOG/INDEX.md (or BACKLOG.md batch ordering)
- BUILD-METHOD.md assessed — parts that are method-general graduate to plugin docs; parts that are dev-project-specific stay as the project's CLAUDE.md or a project-specific doc
- UX.md created for the dev project — "user" is the no-coder using the plugin; "experiences" are the plugin's behaviours
- TEST-LOG.md created for the dev project — existing BUILD-METHOD.md smoke-test descriptions become test specifications
- OPEN-QUESTIONS entry removed

## Success criteria

- The dev project's next session runs entirely through the plugin — planning subagent, before-build, build, after-build — with no reference to BUILD-METHOD.md's bespoke procedures
- OPEN-QUESTIONS content is fully represented in BACKLOG.md's open-questions section; no information lost
- V-file scope content is fully represented in BACKLOG batches; no information lost
- The plugin handles a non-GUI project (itself) without vocabulary friction — confirms V47's generalisation works
- After-build's test model handles run-and-read and trigger-and-observe tests — confirms V48's test split works
- No regression in the plugin's behaviour for GUI consumer projects (Taskflow)

## Open questions for this session

- **What happens to BUILD-METHOD.md?** Parts are method-general (session open/close sequence, doc-code parity, testing semantics) and should already live in plugin docs by V59. Parts are dev-project-specific (three-number distinction, scope-file conventions, drafts-in-flight) and stay as project-specific docs. Identify and sort at session start.
- **What happens to PLAN.md?** If V50 shipped ADR-style numbering + BACKLOG/INDEX.md, PLAN.md's role is replaced. Archive it.
- **What happens to the `planning/` folder?** Sessions, drafts, INVENTORY, OPEN-QUESTIONS — all migrated or archived. The folder itself may persist for historical reference or be archived.
- **Should the dev project's UX.md use generalised vocabulary?** V47 introduces non-GUI vocabulary. The dev project is the first real test of whether that vocabulary works for describing plugin behaviours. If it doesn't, flag and feed back to V47's design.
- **Partial vs. full graduation.** Is there value in a staged transition (e.g. use the plugin for planning but keep BUILD-METHOD.md for session open/close) or should it be a clean cutover? Leaning: clean cutover — partial graduation means maintaining two systems.

## Risks / dependencies

- **Depends on V45, V47, V48 all being shipped and verified.** If any prerequisite has gaps discovered post-ship, graduation surfaces them — which is actually the point of dogfooding.
- **Largest single-session migration.** OPEN-QUESTIONS has 10+ entries; planning/sessions has 7+ scope files; BUILD-METHOD.md has substantial content. Migration must be thorough — dropped content is lost context.
- **Self-referential risk.** The plugin is being used to build the plugin. Bugs in the plugin affect the session building the plugin. Mitigate by having a known-good plugin version installed via `--plugin-dir` before starting the graduation session.
- **Emotional milestone.** This is the moment the method proves it can build itself. If it works, it validates the entire approach. If it doesn't, the failures are the most valuable feedback the project can get.
