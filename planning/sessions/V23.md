# V23 — Before-build + batch-executor + Stop hook + supporting PreToolUse hooks

## Goal

The build orchestration core — the user's two main motivating examples for the plugin: the Stop-hook build sequencer and the batch-executor subagent in fresh context. Plus the before-build subagent that locks the next batch's file list, plus the remaining PreToolUse hook checks (batch file-list enforcement, MANIFEST/UX read-before-edit).

## Inputs

- V18–V21 outputs
- `NO-CODE-METHOD.md` → *Before build* and *After every build* (the latter for the handoff to V25)
- `DOC-STRUCTURE.md` → *BACKLOG.md structure* (for parsing build batches)

## Outputs

- `agents/before-build.md` — before-build subagent (groups changes into batches, locks the next batch's file list, hands off)
- `agents/batch-executor.md` — batch-executor subagent (runs one batch per fresh context; receives batch instructions + declared file list via prompt)
- Stop hook script — reads `BACKLOG.md`, finds top unticked batch, returns `{"decision": "block", "reason": "<batch instructions>"}`. Respects `stop_hook_active` (one redirect per user turn).
- PreToolUse hook updated with: (d) MANIFEST/UX read-before-edit check, (c) batch file-list boundary check
- `/before-build` skill-command (delegates to before-build subagent)
- `/build` skill-command (alternative entry point for batch-executor; default flow is auto-continuation via Stop hook)
- **Batch-sizing principle** added to `NO-CODE-METHOD.md` → *Before build* — optimise for verification burden, not change count. Three sub-rules: split if a small batch would produce a long test list; bundle unrelated items if they introduce no new user-facing behaviour and don't interact; never fragment arbitrarily.
- **Pre-build verification estimate** added to the *Before build* recap — Claude states expected verification burden alongside change scope.
- **Mid-build re-batching carve-out** added to *Method contract → Prohibited of Claude* as sibling of the prerequisite carve-out — if implementation reveals the verification burden is much higher than estimated, halt, surface in chat, propose a split, label `[Re-batch, not in plan]` in the recap.
- Parity item landing this session: `Crash course.md` *"Each batch must be small enough to build and test in one session"* updated to reference verification burden.
- Commit tagged `v23`

## Success criteria

- A Taskflow build batch runs in batch-executor with isolated context
- Edit/Write attempts on files outside the batch's declared file list are blocked
- Stop hook redirects to the next batch after the current one finishes; respects `stop_hook_active` (no infinite loop)
- The user can gate between batches with a single keystroke (D1 from Chunk C: explicit user gating)

## Open questions for this session

- How does the batch-executor receive the declared file list — parsed from `BACKLOG.md` by the Stop hook and embedded in the redirect reason, passed via the slash-command argument, or both?
- How to handle the prerequisite carve-out (an unplanned change implementation reveals as necessary) — halt-and-confirm protocol in batch-executor's prompt, plus a hook escape hatch?
- Does `/build` take a batch identifier as argument, or always pick the top batch?

## Risks / dependencies

- Stop-hook infinite loop if `stop_hook_active` not respected (Opus risk #2) — must test the loop-exit path before declaring V23 done
- Batch-executor prompt budget — packing batch instructions + file list + universal-behaviour reminders may eat the context budget (Opus risk #5)
- Batch file-list parsing depends on `BACKLOG.md` shape — test against real Taskflow batches
- This is the largest single session — may split into V23a / V23b if it can't complete in one
