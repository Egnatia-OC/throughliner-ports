Why the rules

Every rule exists because something went wrong without it. Here's each one with the reasoning.

Push back rather than agree

Drift checks and red-flag surfacing assume Claude will push back when something looks wrong. If Claude defaults to agreement, those safety nets are disabled in practice even though the code still runs.

State regressions plainly

The close recap is your record of what happened. If Claude silently fixes a regression instead of reporting it, you lose visibility into what broke and whether the fix was actually right.

Lock batch scope once agreed

Scope creep during a build makes testing unpredictable, breaks the planning-gate filter, and undermines session predictability. If the scope needs to change, that's a new planning discussion — not a mid-build addition.

Five drift checks at different levels

Each check catches a different kind of desynchronisation: file-temporal, feature-to-feature, name-to-name, purpose-level, per-row code-touch. Bundling them into one check produces noise; separate passes catch what each is designed for.

Lock source-of-truth docs

Build sessions are the wrong environment for design changes. UX.md and other source-of-truth docs are read-only during builds so design decisions get proper deliberation in planning sessions.

No placeholders in source-of-truth docs

These docs are read by Claude at session start. Placeholders like [TODO] or [TBD] confuse the reader — is this an instruction or an unfinished thought? Every entry should be the actual instruction.

Project-specific UX principles

Generic principles ("be intuitive," "be fast") are too abstract to guard real decisions. Project-specific principles like "no date pickers, no shame" give Claude concrete criteria to push back against scope that violates them.

MANIFEST starts flat

Most projects never need sections in their MANIFEST. Pre-sectioning forces premature architecture decisions. Start flat; add structure only when navigability demands it.

BACKLOG is a folder, not four files

The proxy index (proxies/backlog.md) gives you one place to see what's outstanding. Per-batch files handle the content volume. The split is about content volume, not category.

"Risk accepted" as a labelled line

When you deliberately accept a trade-off (no week view, no offline mode), recording it as a labelled line keeps the reasoning on the page. Six months later, anyone asking "why not?" finds the answer without archaeology.

Per-row test read-back

Bulk confirmations ("all tests passed") silently flip rows the user didn't actually verify. Row-by-row read-back means every confirmation is deliberate.

Open questions are separate from batches

OQs have a different lifecycle — they’re non-blocking parking for things that need deliberation but shouldn’t stall the build pipeline. A batch is a commitment to build; an OQ is a question that needs answering before it can become a batch (or get dropped).

Before-build recap before building

/sovrecap validates the batch — checking the Serves line, populating file lists, proposing splits if too large. BACKLOG stays editable during the recap so you can discuss and adjust. Without this step, you’d commit to a batch with missing files, no test plan, or scope that should have been split.

PostToolUse validates doc structure

After Claude edits a method doc, a hook checks the result for structural correctness — parse errors, wrong column counts, missing sections. Catching these at write time prevents mistakes from propagating into docs that other hooks depend on. Warnings are advisory, not blocking.

Response-shape tags control verbosity

Tags like [SILENT], [BRIEF], [SEQUENCE], [DISCUSS], and [PROMPT] solve a specific problem: procedure docs need to specify not just what Claude does but how much it says. [SEQUENCE] means one step at a time. [PROMPT] means end with a clear next-action for you.
