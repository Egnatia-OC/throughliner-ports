Your docs

After /sovsetup, your project has six files and two folders. Together they act as guardrails — they hold your design decisions, queued work, and test outcomes so Claude knows where things stand at the start of every session.

The spine docs

CLAUDE.md

Entry point. Product overview (what it is, who it's for, what tension it solves, milestones) plus path block telling Claude where your docs live. Read every session.

_method/UX.md

Your app from the user's perspective. Every entry is something experienceable, with a "the user needs this because…" rationale. You maintain this — Claude can only read it.

_method/BACKLOG/

Deferred and queued work. The index (proxies/backlog.md) lists everything; each batch gets its own file with scope and build details.

_method/MANIFEST.md

Flat glossary of every named thing in your codebase. Name, file path, description, and a one-line rationale (why it exists). Claude maintains it during builds.

_method/test-log/

Per-session test files, one row per test, 10 columns. Claude writes files after builds; you confirm outcomes before the next build can start. Test session index lives in the BACKLOG proxy.

_method/build-log/

Per-build narrative files: what shipped, decisions made, surprises, and performance notes.

Also created by /sovsetup

_method/planning/drafts/

Holding area for ideas not yet ready for a specific doc. Zero maintenance burden.

_method/research/

Findings from Claude's research. Persists across sessions for future reference.

Additional source-of-truth docs

Projects can declare extra source-of-truth docs — things like SYSTEM-PROMPT.md, COPY.md, or PATTERNS.md. Same phase-aware rules as UX.md: editable during planning, locked during builds.
