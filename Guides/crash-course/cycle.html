The cycle

Every feature goes through two phases: planning and building. They alternate. A fresh Claude Code session (or /clear) separates them. Each skill can be invoked independently — you don’t have to follow the cycle in strict order. Skills that need prior state will tell you what to run first.

Planning sessions

Planning sessions decide what gets built. Three skills cover different planning modes:

  • /sovplan — structural planning. Confirms test results, runs drift checks, reorders/splits/merges batches, edits BACKLOG.
  • /sovdeliberate — OQ deliberation. Works through accumulated open questions: promote, drop, or re-park each one.
  • /sovideate — new ideas. Explores a fresh concept, assesses fit, routes it to an OQ, batch, or idea entry.

Source-of-truth docs (like UX.md) are directly editable by Claude during planning — no ceremony needed. You remove resolved batches and reorganise priorities.

Why two phases? Planning and build need different editing permissions. During planning, source-of-truth docs are open so you can shape what gets built. During build, they’re locked so the spec doesn’t drift mid-implementation — and source code is locked during planning so nothing gets built before the spec is ready. Phase detection is based on whether _method/active-build.md exists.

Build sessions

Build sessions ship engineering work. Three slash commands drive the process:

/sovrecap

Pre-build planning recap. Validates the Serves UX.md: line, populates inputs and file lists, proposes splits if the batch is too large. BACKLOG stays editable during the recap so you can discuss and adjust.

/sovbuild

Locks the batch and runs the build against the file list. A PreToolUse hook enforces file boundaries — Claude can only edit files listed in the batch. The batch is extracted into a snapshot file (_method/active-build.md), which serves two purposes: it gives phase detection an unambiguous signal (file exists = build in progress), and it unlocks BACKLOG for parallel planning or ideation in other sessions.

Close (/sovclose + /sovgit)

When the build finishes, invoke /sovclose. It runs in two turns: a judgment pass (updates MANIFEST, checks doc parity, runs tests, writes the recap and build-log entry, sweeps for stale references and unrouted ideas) then a mechanical pass (bumps version footers if needed, regenerates proxies, runs after-build steps, verifies everything via a pre-commit checkpoint). You can /compact between the turns. Then /sovgit walks you through commit, tag, and push in plain English.

Why close is mandatory. Skipping it leaves an orphaned snapshot that blocks all future builds. Close also writes the build-log entry (the shipped record), MANIFEST updates, and test rows. A PreToolUse guard blocks git commit when all files are ticked but close hasn’t run.

If something breaks (/sovrevert)

If a build goes wrong, /sovrevert walks you through undoing it — restoring the project to its last committed state. No git knowledge required.

Long sessions degrade quality. Claude has no visibility into its own context-window usage, so it can’t self-regulate. It will nudge you to /compact between skill invocations and when a build runs long. These are advisory — skip if you prefer, but compacting preserves context for the close steps. Mid-build compaction is blocked entirely (with a handoff prompt instead) because compaction during a build can silently drop critical context.

Between sessions

You /clear, refresh, and test. Use /sovtest for a guided walkthrough of each pending test, or test on your own and bring outcomes to the next planning session. The cycle repeats.

Sessions are stateless; the docs are the memory. BACKLOG, MANIFEST, TEST-LOG, and build-log tell each session where things stand. Nothing carries over from in-memory state.
