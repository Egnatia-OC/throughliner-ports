The cycle

Every feature goes through two phases: planning and building. They alternate. A fresh Claude Code session (or /clear) separates them.

Planning sessions

Planning sessions decide what gets built. Three skills cover different planning modes:

  • /sovplan — structural planning. Confirms test results, runs drift checks, reorders/splits/merges batches, edits BUILD-PLAN.
  • /sovdeliberate — OQ deliberation. Works through accumulated open questions: promote, drop, or re-park each one.
  • /sovideate — new ideas. Explores a fresh concept, assesses fit, routes it to an OQ, batch, or idea entry.

Source-of-truth docs (like UX.md) are directly editable by Claude during planning — no ceremony needed. You remove resolved batches and reorganise priorities.

Build sessions

Build sessions ship engineering work. Three slash commands drive the process:

/sovrecap

Pre-build planning recap. Validates the Serves UX.md: line, populates inputs and file lists, proposes splits if the batch is too large. BUILD-PLAN stays editable during the recap so you can discuss and adjust.

/sovbuild

Locks the batch and runs the build against the file list. A PreToolUse hook enforces file boundaries — Claude can only edit files listed in the batch.

Close (/sovclose + /sovgit)

When the build finishes, invoke /sovclose. It updates MANIFEST, checks docs for stale references, runs automatable tests, generates a recap, writes the build-log entry, sweeps for unrouted ideas, runs any project-specific close steps, and verifies everything via a pre-commit checkpoint. Then /sovgit walks you through commit, tag, and push in plain English.

If something breaks (/sovrevert)

If a build goes wrong, /sovrevert walks you through undoing it — restoring the project to its last committed state. No git knowledge required.

Long sessions degrade quality. Claude will nudge you to /compact between skill invocations and when a build runs long. These are advisory — skip if you prefer, but compacting preserves context for the close steps.

Between sessions

You /clear, refresh, and test. Use /sovtest for a guided walkthrough of each pending test, or test on your own and bring outcomes to the next planning session. The cycle repeats.

Sessions are stateless; the docs are the memory. BUILD-PLAN, MANIFEST, TEST-LOG, and build-log tell each session where things stand. Nothing carries over from in-memory state.
