# f9326dc — Projects can now send each other messages directly, through an INBOX folder scanned at session start, with the user approving every outbound message

The user raised this in their own words: they run several projects on the method and want them able to talk to each other, with a working precedent from a project they share with their partner that uses a plain `inbox/` folder files get dropped into. The design below — the scaffold, the scan, the triage routing, the never-auto-send rule, the scope-lock exemption — is Claude's.

What made it buildable rather than theoretical was a test at the previous planning session: Claude wrote a file into a neutral sibling folder outside the project and deleted it again, with no block and no permission prompt. So direct delivery is real, and a message never has to be carried between chats by hand. The only thing that had ever stopped it was the method's own rules, not the application.

Five pieces. `/setup` scaffolds `INBOX/` with an `INBOX/archive/` inside it. `session_start` scans this project's own mailbox and surfaces what's waiting in one line — the scan reads only its own INBOX and never goes looking through other projects for mail, which is the property that keeps the mechanism from becoming a surveillance surface. An arriving message routes through the existing three-way triage rather than getting a new one: work to do becomes a capture in Unprocessed, a finding goes to the LOG, evidence a later session must re-read verbatim goes under `resources/`; then the file moves to `INBOX/archive/` so it stops being surfaced every session. Outbound messages are written straight into the recipient's `INBOX/`, but only after the user has seen the exact wording and said yes. And the scope-lock now permits `INBOX/`, which was a confirmed gap: the write test succeeded outside a build, but during a `/next` build an outbound message would have been denied.

The scope-lock exemption is the one piece whose implementation had to differ from its siblings. Every other exemption is cwd-relative — the method docs, `resources/research/`, the scratchpad. An outbound message is written *outside* this project entirely, so no cwd-relative check could recognise it. The exemption therefore matches on an `INBOX` path segment, covering both directions at once. That is a deliberately loose match, and it is only defensible because the scope-lock is not what protects the user here: the approval is. Every outbound message is shown before it is written, which is the same human backstop the feedback report already relies on, for the same reason.

The red flag on this item was cleared at processing, by design rather than by acceptance, and this build implements what cleared it. The risk: a message written into another project carries content out of this one, and both mailboxes sit in git repositories that may be public, so an unscrubbed message is a route for private content to reach a published repo. The approval step is the substantive mitigation. Beyond it, `/setup` now asks once whether messages should be committed or kept out, stating plainly that keeping them out is the safe answer if the repository is or might become public — the gitignore offer the item called for. The scrub work in `[scrub-gate-before-approval]` covers these artifacts when it lands.

One thing kept separate on the item's explicit instruction: this is a second, independent channel. `.throughliner/` markers are live editing state a companion application reads; INBOX is for messages. The behaviour rules and the FAQ entry both say so in as many words, because the two are similar enough in shape to be merged by a later reader who doesn't know they were considered and kept apart.

This project's own `FAQ/` copy was deliberately not updated. It is 90 lines against the shipped template's 297 — already badly stale, which is what the queued `[faq-backfill]` item exists to fix. Adding one current entry to a stale copy would disguise how far behind it is.
