# 4f5e167 — The shell-write guard now denies a computed target instead of passing it, and the queue lint fires after shell commands as well as edits

The guard recognised a scripted write whose target path was written out literally and let through one whose target was worked out as the script ran. That was a deliberate fail-open, pinned as intended behaviour in the test suite so nobody would "fix" it — the reasoning being that guessing at a variable's value is fragile, and false denials train workarounds.

The evidence overturned it in a single day. Removing built items from QUEUE.md was done with a `python -c` that assigned the path to a variable one statement earlier; the guard did not fire, the script matched the cleared-to-run marker against its **first** textual occurrence — which is inside the header paragraph *describing* the marker — and wrote a queue with the header fragment duplicated and all six built items still present. A later heredoc against the same file, this time with the path written out, was blocked correctly. One variable assignment was the entire difference. The corruption was found several steps later by an unrelated `git status`; nothing in the run would have surfaced it, and a close would have committed it. It then happened a **second** time, inside the very session that diagnosed the first — which is the strongest evidence available that knowing about a gap does not close it, and that a mechanical guard is what is needed.

So an unreadable target now denies. The reasoning is that the guard cannot tell whether such a target is protected, and "cannot tell" must not resolve to "allow" for a check whose whole job is preventing a silent clobber. It does not guess at the path; it says plainly that the target is computed and names the three ways forward. The accepted cost is stated rather than left to be discovered: a script writing to the session scratchpad with a computed path is denied too, and must name its file. The old test case asserting the fail-open was **flipped rather than deleted**, so the reversal stays visible to anyone reading the suite.

The capture had offered widening detection as an alternative — treat any script importing `io` or `pathlib` and naming a project doc as a write. That was rejected: it guesses at script text and denies read-only scripts, and a case pinning exactly that now sits in the suite.

The second half closes the class rather than the route. The queue lint ran after Edit/Write/MultiEdit only, so a shell write bypassed it entirely — which is why the corruption sat unnoticed. It now fires after Bash and PowerShell too, linting the queue whatever wrote it, and it stays advisory exactly as before. That change verified itself live within minutes of installation: the first Bash command after the restart produced a lint report in the real app.

A narrower lesson worth keeping whatever else changes: matching a structural marker by its first textual occurrence is unsafe in any file whose header describes its own format.
