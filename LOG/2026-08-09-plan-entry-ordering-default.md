# [HASH] — /plan's opening became two beats — drop, then one ordering question with most-unblocking-first as the stated default — with a five-rung internal fallback ladder behind it

The user raised this on 2026-08-09, and their wording for the ask was near-verbatim what shipped: *"is there anything else you want to prioritise, or are you ready to go through items in order of most unblocking first?"* The ladder and the beat structure below are Claude's design, settled in the same session.

The evidence was a moment earlier in that session. The user asked whether anything in the queue would become unblocked soon and therefore make sense to process now. That question produced the best sequencing decision of the session — three clusters worth taking, and one to deliberately avoid because it would write into a corpus about to be inventoried. Claude never offered it. So the failure was not a missing capability: it was a capability the user had to think of.

That makes this an amendment rather than a new feature, and saying so is what kept it small. plan.md already ordered surviving items by unblock-potential and narrated a throughput floor — but it ran silently, *after* the entry ask, so the user was never offered the choice and never learned the option existed. Naming it in the entry ask costs one clause on a question that already fires.

The order of the two beats is the user's correction, not Claude's first shape: drop first, then order. They identified the overlap directly — there is no point ordering items that are about to be deleted, and dropping changes what is left to order. So the triage bulk-drop pass moved up from the opening of Step 2 into the session opening as beat 1, and it now simply does not fire when nothing is obviously droppable, rather than emitting a "nothing looks droppable" line. Beat 2 is the ordering question, one question with a stated default, and it **absorbs** the old "anything to discuss?" opening rather than surviving alongside it — three opening questions where two will do was the shape being fixed.

The ladder is internal, applied and never offered. It decides what most-unblocking-first degrades to when nothing unblocks anything, and it surfaces only through the one-line narration the throughput floor already emits. That is what keeps the ask a single question while still giving the order a defensible basis. Its rungs: an uncleared red flag in Unprocessed, then unblock-potential, then decay, then cheap-to-settle, then file order.

One deliberate deviation from the user's stated default is flagged rather than slipped in. They asked for most-unblocking-first as the top rung; it sits second, under uncleared red flags, because the cost of leaving a live data-exposure risk is a breach rather than a delay, and session_start already surfaces open flags so the signal exists. Rung 1 fires rarely, so in practice the default the user meets is theirs.

Two anti-invention points were held explicitly. The empty-queue case routes to plan.md's existing seed-the-queue-from-SPEC step, offered by name; if SPEC is thin too it is an ordinary conversation about what the user wants next. Ideation must not become a new session type, mode or container — there is no fifth state — and that guardrail is written into the step rather than left to be re-derived, because the generic prior fills the vacuum whenever nothing names the real move.

Volume-wise this is roughly neutral under the authoring gate: the ask exists and the reorder exists, and the ladder is new text that replaces an unstated oldest-first fallback with a stated one, living in the step rather than in always-loaded prose.
