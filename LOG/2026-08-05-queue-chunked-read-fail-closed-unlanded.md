# [HASH] — plugin-behaviour.md gains the page-to-completion rule for queue-wide reasoning; plan.md's read-state step points at it

Large-file reads in the desktop app come back capped — this blitz's own opening queue read returned a third of the file — and a session that reasons queue-wide from a partial view silently sees a different queue than the file holds. The truncation is not silent today (the harness warns plainly), but that protection is an undocumented harness behaviour whose wording, threshold or existence could change with nothing telling us — depending on it unchecked is the diagnosis-order trap. The rule, stated more precisely than the port stated it (the port said *stop*, which is too strong and would train false denials): page to completion before any queue-wide reasoning — ordering, dependencies, the readiness line, duplicate detection and the below-line revisit all require the complete queue; chunked reads are legitimate as transport; where the whole queue genuinely cannot be assembled, say so plainly and don't reason queue-wide. Home is plugin-behaviour.md's Tool use section, because /plan, /next and /done all read the queue and a rule living only in plan.md wouldn't reach them; plan.md's read-state step points at it. Docset A was considered and left alone: this is a new behavioural rule, not a self- or SPEC-inconsistency in A, so under the freeze rule it is development and stays out of A. Context carried from the item, deliberately: this treats the symptom — queue size is the cause, and nobody meeting this later should think the reading problem was solved.
