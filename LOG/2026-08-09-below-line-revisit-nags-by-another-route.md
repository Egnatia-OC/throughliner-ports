# f9326dc — A fourth branch for the below-line revisit's classifier: a lift-condition waiting on Claude's own work is done or reported, never asked about

The user reported the symptom — being asked questions at the start of a planning session about below-line work they shouldn't have been asked about. The narrowing recorded here is Claude's, from reading the shipped docs and testing them against those three questions; the user approved it rather than reasoned it. That attribution is stated because this run also built `[rationale-misattribution]`, which named this very item as one of its three instances of a credit written without the user's words behind it.

The original observation turned out to be already fixed, and testing it is what found the real defect. The downstream-action test recovered at `72f4fe9` is present in `docs-b/plan.md`, does apply to the whole user-only branch, and does not blind the revisit — conditions that pass it still join the consolidated question, so telling waiting from ready still works. Both checks the original capture asked for came back clean.

The gap is one the test's own structure creates. The classifier had three branches: user-downstream (file a `[user]` line), external event (ask once, batched), still-waiting (silent). It had no branch for a condition downstream of an action **Claude** has to perform. The test asks only whether the awaited event follows a *user* action, so when the answer is no, the condition "stands and joins the consolidated question" — and Claude-pending work falls straight through into the ask bucket. Correctly-followed rules manufacturing a question the user shouldn't be asked is the same failure shape the downstream-action test was itself written to remove, arriving by a different route.

Measured against the live queue, two of four below-line conditions were Claude-downstream. `[merged-plugin-live-verification]` waits on the plugin being rezipped and reinstalled, and `[working-mode-render-verification]` waited on a test rezip carrying the fixes — that second item was deleted later the same session when `[remote-control-opening-mention]` retired the mechanism it verified, so the two-instance evidence stands while the second example no longer resolves. Rezipping and reinstalling is Claude's own work: `CLAUDE.md` has Claude run the CLI itself, and the reinstall being wrongly handed to the user is a documented recurring mistake with its own note in that file. So "has it been rezipped?" is a question Claude should be answering, not asking.

The fix is a branch, not a paragraph, which is what let it pass the authoring gate without consuming an instruction slot: it amends the downstream-action test rather than standing beside it. The branch turns on the capability test that already exists for the `[user]` tag — can Claude do this at all? — and if the answer is yes, the condition is either resolved now or reported as pending Claude-work in the same one-line narration the mechanical checks already use. A hook can't do this: deciding whether Claude could perform an action is judgement, not pattern-matching, so sharper wording was the only route.

Applying the corrected classifier once to today's below-line items found exactly one thing beyond those two. `[statusline-context-reader]`'s lift-condition contains a genuine user-only action — running the status-line test across a full application restart, which Claude can neither perform nor witness — written as prose inside a build item rather than filed as its own line. Nothing had ever acted on it, which is precisely the user-work-evaporation failure the `[user]` tag exists to prevent: it was cheap to write as a rider on a restart that was going to happen anyway, and that framing is what kept it invisible. It is now `[statusline-restart-test]` in Unprocessed, carrying the rough walkthrough the item's prose already contained.
