# [HASH] — Migration-aware /setup: detect a content-but-no-SPEC project as a possible migration and frame it, with guardrails

From the Taskflow /setup re-run audit (findings F1–F5). /setup had no concept of a project already set up under other names: Step 1 keyed "already set up" on SPEC.md existing, so a folder with real content but no SPEC.md — an older-vocabulary or foreign source — was misread as a fresh start, and the session-start hook said the same ("files but no SPEC.md — it hasn't been set up"). The decision was detect-and-frame only: recognise the possibility and hand the actual mapping to Claude's judgment, with no guided mapping table. Detection stays generic — soften the wording, don't hardcode a list of old doc names — so it covers any source, old-SI or foreign.

setup.md's Step 1 now frames a content-but-no-SPEC folder as possibly a migration, recognised by what the existing docs do rather than by matching names. A new "Case B: migration framing" section carries four guardrails distilled from the audit's symptoms: state SPEC's purpose up front (product truth — what/who/how/why — not a UX or implementation manual); check each old doc's role actually fits its SI counterpart before renaming, and flag a mismatch for the user rather than blind-renaming; scrub the source's self-description out of the content, because a line like an old UX doc's "describes every functionality and UI element as the user experiences it" silently re-mandates the exhaustive detail SPEC is meant to leave out (renaming the file isn't enough — the old frame hides in the text); and state that SI docs live at the project root, since a source's path block or doc-location config doesn't carry over. The session-start hook's State 1 message was softened to match — "no SI docs yet … /setup can treat it as a migration" instead of "it hasn't been set up" (still compiles).

A setup-narration plain-language guard was also added, because the audit found internal terms leaking during a first-run /setup: in an unadopted project the session-start hook returns before loading the behaviour rules, so the plain-language rule isn't in context during /setup. The guard is self-contained and carries that why inline, sitting beside the existing note about why this doc carries no response-shape tags (same root cause). Finally, a new FAQ entry ("What if my project already has planning docs from another tool or an older version?") was added to the template and its index, and mirrored into this project's dogfood FAQ.

This entry also closes the run, so it records the run-level confirmation: this goal session followed the defined goal-session shape (an aggregate _build.md held as working state, a separate LOG entry per batch in one end-of-run commit, and a cross-checked close), which is exactly what the [formalize-goal-session] deferred test asked the next goal session to verify. That deferred-test line is therefore removed from QUEUE.md's Deferred tests as confirmed by this session's own activity.
