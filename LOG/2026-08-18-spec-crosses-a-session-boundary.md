# [HASH] — a build stops writing product truth, because the session that made a choice cannot be the one that certifies it

A run stopped in its second minute to ask for one SPEC sentence, and the user objected that the interruption was the wrong part. Claude's first design deferred the write to that same run's close, so the run would not stop.

**She refused it on the ground that is the whole of this decision: SPEC is managed across a session boundary so that no single instance of Claude both makes a choice and certifies it in product truth.** A close is the same session, so deferring moves the self-certification later rather than crossing anything. Claude had missed this twice before she stated it plainly, having reached past `CLAUDE.md`'s own text — which says of rule dispositions that one written as an item is built "improves attribution and restores no power to refuse", and that only /plan can refuse because nothing has been built yet. [build-wrote-its-own-gate-disposition] is that same failure already sitting in the queue.

The settled shape is three steps. The keep-step asks whether an item changes what SPEC says and **planning writes the sentence then**, with the user present. The build builds against it and never touches SPEC. Only on a miss does the build record the sentence, file it as work, and leave SPEC alone.

So SPEC leads the build rather than trailing it, which is what "read at build time" requires. The cost is stated on the item: on a miss, SPEC lags one planning session — visibly, as a queue item.

Her earlier batching instruction dissolved with it. Under this model a run owes no SPEC sentences at all, so the item was deleted after its evidence was folded across: deferring a SPEC write inside a run cost nothing and lost nothing.
