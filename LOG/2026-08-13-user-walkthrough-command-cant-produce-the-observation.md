# [HASH] — A walkthrough step must be able to produce the observation the item names

The check now runs at two sites at two weights, copying the shape the capability
check already uses. At `plan.md`'s keep-step, where a walkthrough is authored,
confirm the step can produce the observation — and where running the command is
harmless, run it. At `next.md`'s hand-off, the light form: confirm the step names
something that yields the evidence, with no experiment, no search and no
stopping.

It is a different question from the capability check beside it. That asks whether
Claude could do the *work*; this asks whether the *user's step* yields the
*evidence*.

The design question the item posed — `next.md` or `plan.md` — was a false choice,
because the method already runs this exact shape at both. The heavy site must be
/plan: the original instance was caught only because the user asked Claude to run
the command first, which nothing requires and which usually will not happen,
since the user is meant to run these.

The item's own `[user]` tag was removed as a mis-tag at processing. It was tagged
that way because the instance occurred inside a `[user]` walkthrough, but the
work is authoring a rule in the procedure docs, which is plainly Claude-work. An
item *about* user-work is not itself user-work.

Rule gate: run — admitted as an amendment at both sites, subordinate to the
existing two-site capability check. One recorded instance: a `--move` command
handed over to check whether an em-dash rendered, on a path that echoes no
heading at all.

FAQ: not needed because nothing a consumer sees changes except that the steps
they are handed work.
