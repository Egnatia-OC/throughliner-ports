**What that says about the queue, and it is not a criticism of it.** A capture is
true when written and then sits while the project moves underneath it. Nothing
re-reads captures; the below-line revisit re-checks lift-conditions, but only for
items already processed. So processing is the single moment an item is read
closely, and it is doing real work: two items would have been built against a
false picture, and one would have been designed as a code change when the code
was never the constraint.

**The status-line test stopped cycling, by being armed rather than scheduled.**
The user named the problem directly: *"it keeps cycling through every session, and
I keep rezipping and restarting and it keeps just never happening."* The cause was
structural. Every version of the instruction said to run the test *at* the next
restart, so every restart arrived with nothing configured, the occasion was wasted,
and the check rolled forward into the next advisory unchanged — twice. The fix was
to install the instrument instead: `resources/testing/statusline_context_probe.py`
registered as the `statusLine` command, writing to a durable marker outside the
repo. Its lift-condition is now "does the marker file hold lines?", which /plan
checks silently with nothing asked of the user. **The general lesson, sharper than
the one the previous rewrite produced: a condition that waits on someone catching
a moment will keep rolling forward — set the trap, then wait on the trap's
output.** The same lesson was written into the blitz plan for its delivery check,
which had failed the same way.

**Two rules arrived from the user rather than from the queue.** The first became
[prioritise-without-reorder]: where a request is really about *what gets attention
next*, hold a session-local focus order rather than paying to rewrite the queue,
and treat an explicit reorder request as a decision to check rather than an
instruction to execute. It collided with [plan-session-order-diverges-from-file-order],
which records the opposite worry, and the user resolved it — the focus order is
sanctioned as session-local, and the queue's "position is the order" claim softens
to "default order". The objection was never to a session having its own order; it
was to that order being undeclared while the doc claimed otherwise.

The second was a correction. [approval-flow-token-doubling-simplification] had
recorded the short-summary rendering as accepted *for this project*, leaving the

long because Claude needs the detail — the human needs understanding, not the
text. That reframes summarising as the feature rather than a concession, and it
exposed a contradiction between two shipped rules: the capture authoring standard
still says the human co-reads and approves the item text, while the doc-bound-text
rule says they read a summary. Fixing that contradiction is now the item's build.
Length caps were proposed and explicitly rejected — sufficiency governs.
