# [HASH] — Method problem reports go issue-first, with the web form as the fallback and a reply-check scheduled at send

The user's proposal, designed with her the same session. A method report is now offered as a GitHub issue on the plugin's own repository where the `gh` CLI exists — draft shown, explicit yes, and the offer states plainly that an issue is public under the reporter's own account. The web form stays for where the CLI is absent or the reporter prefers privacy, demoted to a fallback rather than evicted.

What the issue buys that the form never had is a return path. Answers come back through the opening correspondence scan shipped alongside this, and on the development side new consumer reports arrive as incoming issues the same scan surfaces.

The reply-check is hers, and it fires only where the sender actually wants a reply. At send time the session asks; on a yes the check method is agreed there — an issue's comments via `gh`, or for a form report an email route, where Claude checks what email connections exist in the session at that moment and asks whether any suits. One dated capture is then filed with the agreed method written into it, held by a `Not before:` date she approves, surfacing in a planning session once the date passes. Existing field, existing machinery, nothing stored elsewhere. No reply wanted, nothing filed.

Refused at planning: replacing the form entirely, since the no-CLI and privacy cases need it; and automatic reply-checking with no date, since the scan already covers issues and the dated capture is what guarantees a look for email routes the scan cannot reach.

Noted for later: the same-machine arm, still unprocessed, outranks both routes for the user's own projects once it is designed.
