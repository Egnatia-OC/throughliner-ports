**The three findings, each verified by re-reading both sides before filing.** The largest is a group of four doc-vs-hook mismatches, and the direction is uniform: in every case the code is right and the docs overstate or misattribute it. The behaviour rules claim the shell-write denial catches "a redirect, a heredoc into an interpreter, `Set-Content`, `sed -i`" when `structured_write_targets()` matches only a Python invocation carrying a literal quoted path — SPEC states that limit honestly, so the two shipped docs disagree with each other about the same mechanism, and the one that overstates is the one a session reads for its safety posture. The same section credits the red-flag scan to `pre_tool_use` (which has none) and asserts `session_start` "does not read work items" (it does — `_uncleared_red_flags()` parses headings and markers), so both halves of one parenthetical are wrong. It also claims the third never-rule is mechanically blocked when only its `--force` half is. And two inert leftovers: `pre_tool_use.py`'s docstring still says the Bash branch checks git safety "only", stale since this span made the shell-write check unconditional in that same branch, and `docs-b/next.md`'s frontmatter still names the deleted `docs/`.

The second finding is a genuine contradiction between two rules the span itself created a collision between, and it is filed standalone because which side loses is a design call. The new correction-disarms rule says a filing is *not complete* until the correction reaches the item it corrects, and offers "amend the corrected item" as a route available to any session — that availability is the point, since the motivating failure was a correction filed beside an item that then ran anyway. `next.md` says **"Halt rather than amend: rewriting a work item is processing, and /next does not process"**, and its reason is stated generally rather than scoped to the dispatch-return check it sits in. A /next session meeting a correction cannot tell whether writing it into the corrected item's block is mandatory or forbidden. A narrow reading survives; the *reasons* collide head-on, and the disarm rule's second route (move it below the line) collides harder, since repositioning against the readiness line is a readiness call reserved for /plan.

The third is a state finding rather than a text one: `FAQ/` on disk is **empty**. [faq-backfill]'s premise update from earlier the same day records that the folder was emptied by the untracking-plus-merge and then restored by copying the templates in. That restore has not held, and because the files are deliberately gitignored, git carries no copy and the loss left no diff — the session-start hook's own out-of-date report was the only thing that noticed. The correction belongs in that item's premise paragraph, which sits below the readiness line, so it is proposed for /plan rather than written by this run: amending a below-line item's premise is processing. Worth carrying into the concurrency and cloud-sync work — an untracked folder is invisible to git's recovery, so this whole class of loss is silent.

**One observation was deliberately not filed as a finding.** SPEC's description of the planning-session file gate omits `FAQ/` from the paths that pass quietly, and so does the hook's own ask message, while `_is_plan_quiet_path` does pass them. That quiet path shipped in an earlier branch, so it is outside this span and outside a differential audit's remit; it was filed at the close as an ordinary capture instead, with a note that it groups naturally with the doc-vs-hook repairs.

The cost is one /next invocation. That is the trade, and on this run it was plainly worth it.
