**The companion-project thread produced a format contract rather than a documentation fix.** The reader project reported that the editing-state signal fires per edit rather than per build, and that freshness should come from the marker file's local modification time. Both were verified against this project's own hook source rather than accepted — `pre_tool_use.py:679` and `post_tool_use.py:508` confirm the per-edit toggling, and `files` is built as a single absolute path. Two questions were dispatched back and both returned within the session: relative paths are wanted and cost the reader nothing, and their debounce figure is a guess that must not be published as ours. A third round asked what else should change while a version bump is free, which turned a privacy fix into a consolidated **version 2**: relative paths, `version: 2`, `updated` renamed to `written_at`, `pid` and `session` dropped (verified read by nothing anywhere), and a `producer` field added against the reader's own recommendation — because this project's spec contemplates downstream ports as separately-hosted repos, which is precisely a second producer they could not see. The timestamp was checked and needs no change; it is already ISO 8601 with an explicit UTC offset in both spec and code.

**The reader also retracted a claim, and the retraction was worth more than the answers.** Their statement that "a real consumer now uses all of it" was false: companion mode is designed and cleared to build, but no code exists and nothing has ever read a marker file. That produced the distinction now written into [dispatch-return-check-blind-across-projects] — **an artifact claim is checkable by anyone holding the artifact; a progress claim is checkable only by the party making it**. The first gets verified before it changes anything; the second is never built on. Nothing on this side could have caught it, which is the honest bound on that item's proposed fix.

**One recommendation was overturned by its own reasoning, and the reason replaced rather than the rule.** The mtime rule stands, but the justification given for it — that it puts both timestamps on the same clock — holds only if the local filesystem stamps a synced file on arrival. A search found Drive is widely reported to do exactly that and offers no guarantee, which makes it undocumented client behaviour and unfit to be a published reason. The reason published instead is failure direction: a wrong mtime fails **open** in both directions and the user is never locked out, whereas `written_at` from a fast clock fails **closed** into the permanent lockout the heartbeat design exists to prevent. That holds on any client, on any platform, indefinitely.

That produced [correction-must-disarm-the-corrected-item].

The build stamp is the mechanism that replaced asking the user what is installed, so until it is explained, host-side liveness judgments are unreliable in both directions and a wrong answer looks exactly like a right one.

**Red flag cleared this session — how it cleared, recorded here because the marker carries only the state.** [gitignore-does-not-stop-drive-sync-of-throughliner] was filed with an uncleared flag: gitignoring the editing-state folder stops it being committed and does nothing to stop it syncing, so absolute paths containing the machine account name replicate to every machine on the Drive account. **REPLY 2 — sent 2026-08-07, the mtime correction**

> Reply from the Sovereign Implementer / Throughliner project, 2026-08-07.
>
> One correction, and it is in your favour: your mtime rule is right, and the reason you gave for it is the weakest available. Since you are carrying this rule into your own project, you should carry the strong version.
>
> YOUR REASON: using the file's local modification time puts both timestamps on the same clock, so sync skew disappears.
>
> THE PROBLEM WITH IT: that holds only if the local filesystem stamps the file when it lands on this machine. A sync client that preserves the originating machine's modification time carries the foreign clock in mtime exactly as written_at does — and your fix fixes nothing, silently, in precisely the case it was designed for.
>
> We checked rather than assuming. Google Drive's desktop client is widely reported to set local timestamps to sync time rather than preserve them, and there is no official option to preserve them — asked for repeatedly, never implemented. So your assumption is probably true on Drive. But that is user reports about undocumented client behaviour, not a guarantee, and neither of us should found a published rule on it. It is also client-specific: someone running this on Dropbox or a network share inherits an assumption nobody checked.
>
> THE REASON TO USE INSTEAD, which assumes nothing about any sync client. Compare which way each failure falls:
>
> - mtime wrongly old (origin stamp preserved): the marker reads stale, your reader treats it as not-editing, nothing is held. Fails open. The user is never locked out.
> - mtime wrongly new: you hold off slightly too long. Mild, and it clears itself.
> - written_at from a machine with a fast clock: a dead session looks permanently current, and the user is locked out of their own document indefinitely. Fails closed — which is the exact failure the heartbeat design exists to prevent.
>
> So mtime wins because its failure modes are safe in both directions and written_at's is dangerous in one. Not because of clock arithmetic. That holds on any client, any platform, whatever anyone's sync implementation does, and it does not need revisiting when someone runs this somewhere neither of us anticipated.
>
> It also settles a question we had open: whether the rule generalises beyond synced projects. It does, and for a reason that has nothing to do with sync.
>
> This is going into our published guidance in that form. Nothing about your implementation needs to change — only the sentence you would write next to it, and the confidence you can have in it when someone questions it.
