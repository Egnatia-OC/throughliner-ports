# 9022700 — Eleven items processed and the queue's shelving model rewritten: below-the-line now means blocked by a named item, and a whole session was found running on a stale host

The session's largest outcome was not any single item but a change to what the cleared-to-run line means. The user's rule, in their own words: nothing is ever supposed to be below the line unless something in Unprocessed blocks it, and if the blocker is a thing in the world then it should be described in Unprocessed so that it actually gets asked about in /plan. Today's model records a blocker as a *sentence* in the shelved item's own prose, which /plan re-reads and classifies each session — so the blocker is never work anyone picks up. The queue supplied its own proof: [statusline-context-reader] sat below the line for weeks with a genuine user action buried in its lift-condition sentence, and nothing acted on it until that action was split out as a `[user]` line the day before, at which point it became visible immediately. One item's prose had been holding another item's job. This became [below-line-means-blocked-by-an-item], which restores a lint-checked `Blocked by: [slug]` field and retires prose lift-conditions along with the four-way classifier that read them. It is a reversal of `ee99142`, which had ruled out dependency headers as stale-header machinery; the reversal is argued rather than assumed, on the grounds that `ee99142` was itself reversed once at `f832385` and that a lint-checked slug cannot go stale the way a header can. It also supersedes finding 2 of the five-evidenced-rules item, which had flagged exactly this reversal as needing an argument it did not yet have. All eight below-line items were then migrated: four lifted because nothing in the queue blocked them, four kept below with a named blocker.

Separately, the session discovered mid-flight that it was itself running on the wrong plugin. The installed host was a snapshot predating `f9326dc`: it still contained the `docs/` folder and its four `SKILL.md` files still pointed at it, so every procedure followed for the first half of the session came from docset A, retired two commits earlier. The root cause is mechanical and worth stating plainly — `claude plugin update` matches on the version string, so re-running it against an unchanged version reports success and re-snapshots nothing however far the source has moved. A rezip had installed `-test1` while the source was still pre-`f9326dc`, and every build after that landed with no further bump. Bumping to `-test2` took immediately. Checking the pre-revert text then changed the item entirely: the fix already existed and the 2026-08-09 revert had deleted it. The old rezip ritual carried a cache prune, a stamp comparison run immediately after install and before the restart is even mentioned, a CLI-versus-app version check, and a post-restart hook-liveness proof. The stamp comparison catches this exact failure, and its own recorded history is that it caught a real shipped bug the day it was written down. So the capture became [rezip-verification-steps-restored], a restore rather than a design, and [hook-tests-not-in-rituals] was consolidated into it because the old step 4 *is* that item seen from the other side.

The pre-revert version was checked first, as the capture asked, and it says the same thing — same automatic trigger, same bar, same 2026-08-04 reasoning recorded in the user's name. So this is a genuine change of mind and not the revert restoring stale text, which is recorded in the item so a future session does not restore the trigger in good faith. Claude recommended removing the automatic trigger outright and the user chose it; the intuitive middle option of keeping the trigger but pausing once before publishing was rejected, because that pause is exactly the ask the document bars and the ask the user stopped. The user then added a second change in their own words: the rezip should run before the push so the test build is pushed too rather than generated after and left behind. Claude surfaced the precedent where committing a `-testN` suffix left the public repo advertising `1.16.0-test4` until the next release, and the resolution is that the push cleans the version on its way out.

The user then asked whether anything else lingering might be hiding the real face of the plugin and the model, which turned up something larger than the memory question. This project therefore tests the method's mechanics well and its communication rules barely at all — the half that has been rewritten most often.
