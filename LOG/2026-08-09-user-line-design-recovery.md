# 72f4fe9 — The four-part `[user]`-line design recovered: no completion asks anywhere, completion inferred and checked against the world, name-the-tool before tagging, and the downstream-action test

Four changes built across three commits over two days, recovered together because they are one design — any one alone leaves the behaviour incoherent. The 2026-08-09 emergency revert unwound all four, and brought back the completion-mode setting they had retired.

The asks are gone flat: not leading, not trailing, not as a light aside, not in a planning session, with no mode that turns them back on. The user's standing reaction is what settled it — the asks are jarring and upset her every time, and the instance that decided it was a close asking which `[user]` items she had completed, listing all three, immediately after a session that had walked one of them through from first step to result. The design had already tried twice to *minimise* this ask (a trailing note replacing a leading one; completion mode suppressing the planning sweep) — both mitigations of an ask nobody had questioned the existence of.

What replaces asking is inference from what a session can already see: a walk-through driven to its end this session is done, an item whose condition visibly hasn't cleared isn't, and the user mentioning one is the third way. The gap that leaves is real and deliberate — an item completed alone between sessions with nothing observable to show for it sits until the user mentions it — and it is written down in *both* the behaviour rules and the FAQ precisely so a future session doesn't notice the hole and propose an ask to fill it.

Two guards keep inference honest. Checking the **world** is not asking the **user**: where an item's completion has an observable result, the walkthrough records that check and the close runs it rather than accepting the report — earned by an item logged complete on the user's word when an OS lock had defeated the intent, with residue sitting unnoticed for months when one `git branch -r` would have caught it. And before a `[user]` tag stands, the tool that would do the work is named and confirmed absent or unauthenticated — a check that passes or fails rather than a judgment that can be talked into the wrong answer, earned by "create a private GitHub repo" being handed to the user when `gh` did it in seconds.

The fourth part is the downstream-action test, and it is the subtlest: a lift-condition awaiting an event that cannot happen until the user acts ("the collaborator replies", to a message never sent) manufactured user-work evaporation *from correctly-followed rules*. It is named as under-filing's second face, applies to the whole user-only branch rather than the case that motivated it, and fires again at the moment a lift-condition is written, which is the earliest point it can catch one.

The counterargument was weighed rather than ignored: some users would find a no-ask flow patronising, accepted because they are not the target market — being slightly over-helpful to an expert costs less than irritating the target user.

One decision made under uncertainty, and it should be read as provisional: docset A was left alone beyond removing a setup question that wrote to a template field that no longer exists. That kept a frozen doc unedited and left A's completion-ask text stale but inert (with the field gone, a docset-A session reads nothing and falls back to suppressed). It would have been a different call if A were known to be retired — see `[docset-a-retired-or-frozen-contradiction]`, filed at this close.
