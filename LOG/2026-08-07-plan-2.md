# dba6650 — Nineteen items processed, five of them folded into work that already existed, and three captures overturned by checks that each took under a minute

This session processed the whole of Unprocessed — seventeen items on the list at the start, plus two that arrived mid-session from another session running without the method. What it is mostly a record of is **consolidation**: five items were folded into existing work rather than kept as their own, because in every case the destination already carried the same file scope and the fold added nothing to it. Two more were deleted outright. So nineteen items in produced eleven pieces of standing work, not nineteen.

**Three captures said something confidently and were wrong, and each was caught by a check of a minute or less.** [skip-step-hardcodes-dev-repo-script-path] stated that the broken mover path was "exactly one" occurrence, "verified by grepping across both docsets" — docset A carried the identical bug at `docs/plan.md:99`, so there were two. [pre-merge-differential-audit] said its rhythm should be recorded "beside the merge/branch conventions" in CLAUDE.md — there are no merge or branch conventions in CLAUDE.md; the word appears twice in the file, both incidental, so the build creates a section rather than joining one. And [mover-move-repositions-readiness-marker] was filed as a defect with a fix direction to settle; reading the script and reproducing it on a scratch queue took two minutes and produced a complete diagnosis instead.

**That mover diagnosis is the session's most useful single output.** The readiness marker is not stored as a position — it is stored as an **anchor slug**, the item directly above it, and on reassembly it is re-inserted after that same item *wherever that item has moved to*. So the marker follows its anchor around the section. That accounts exactly for the reported failure, including the part nobody could explain: the moved item **was** the anchor, so the marker was dragged down with it, and an item deliberately shelved below the line ended up cleared to run unattended. It also explains every negative observation — the thirteen `--move-section` calls in the observing session, the nine deliberately watched ones recorded on a sibling capture, and the Unprocessed moves — none of them touched the anchor item, so none of them could have triggered it. And the correct behaviour is **already written in the same script**: `delete_item()` carries an explicit re-anchor branch that the reorder path never got. The sibling evidence item was folded in and deleted, its one real caution (none of those moves crossed the marker) carried into the regression test's design.

**The write-first contradiction turned out to be the session's organising thread.** [show-then-write-survives-at-step-level] was kept first and re-verified site by site: six step-level instructions genuinely contradict the doc-bound-text rule, two more are correctly show-first and a uniform sweep would break them (a commit message has no doc to be written to; an audit finding being reworded is not yet headed anywhere), and the migration case stays show-first as a decision rather than an omission, with its reasoning to be written into the doc so nobody re-opens it. Its sibling [claude-pointed-at-a-write-it-had-not-made] was merged in rather than kept, because the remedy is one clause in the same paragraph: **the pointer's summary is composed from what the re-read returned**, not written alongside it. That wording is deliberate and recurs twice more in this session's work — you cannot compose a summary from content you have not read, whereas you can forget to verify one. Removing the availability of the wrong move, rather than forbidding it harder, is the shape every remedy here takes.

**Two items were resolved by noticing that the method already contains the answer.** [dispatched-item-not-updated-when-answer-returns] asked how a work item learns that the thing it sent for has come back; its own honest counter — that the answering side is usually a different session in a different project — rules out any back-reference design, which puts the check on the requesting side, where the `[user]` lifecycle's *check the world, don't ask the user* rule already establishes the principle and `next.md`'s walk-through pre-flight already provides the firing site. [set-aside-silences-the-lift-condition] resolved the same way: the set-aside marker's own guards suppress *recommendations and offers*, never a silent mechanical check, so the marker and a lift-condition are not exclusive at all — they govern different things.

**And that item turned out to be worse than it was captured.** The set-aside marker is only safe because of the guarantee that nothing is quiet forever — set-aside items resurface when the queue has nothing else to offer. That condition is "no cleared work to run, and nothing unprocessed but set-aside items." **This queue holds fifty-five items.** The backstop does not reach, so on a working queue a set-aside is effectively permanent silence unless the user happens to remember. The fix therefore has to include disclosing the silence at the moment the marker is recorded — which is exactly what the user had to discover by asking.

**Claude's own behaviour produced three entries, one of them during this session.** At an item checkpoint the session asked "carry on, or stop here?" and then ran a grep anyway, without waiting — a plain `[PROMPT]` violation, harmless in content and surfaced unprompted, and the fifth instance in one day of a clearly-worded loaded rule slipping under local pressure. Filed as [action-taken-during-a-prompt-stop], and worth noting it is a different kind from the other four: those were failures of *method* (a wrong source for a string, a document used as scratch space, an announcement composed before its write), where this one is purely a failure of *timing* with nothing about the action wrong except when it happened — so the "compose it from the right source" remedy the others reach for has nothing to attach to.

**A second self-observation has real consequences for a mechanism the method depends on.** Comparing the target's content stamp against the installed host's meant importing `session_start` as a module, and Python wrote `__pycache__` **inside the directory the stamp is computed over**. The target's stamp changed; when the session restarted mid-run, the hook reported a different installed-host stamp with nothing shipped. That stamp is what replaced *asking the user what is installed*, and a false mismatch reads as "host-side changes are not live yet" — the confident-looking wrong answer. The bytecode was deleted before any commit. Filed as [reading-a-hook-changes-the-build-stamp]; the likely fix is excluding generated artifacts from the stamp, which both the rezip and release rituals already treat as non-plugin content, so the stamp currently contradicts the rituals either side of it.

**One item could not be processed, and saying why is the point.** [compaction-reinjection-has-no-usable-event] cannot pass the keep-step, because whether it has anything to build at all turns on an unchecked fact about which hook events can inject context and whether `transcript_path` reveals a compaction. Guessing that fact is precisely the error the item exists to record, so guessing it in order to process the item would have repeated the mistake one level up. **The user's instruction resolved it and became a standing rule for the rest of the session:** audit-shaped questions collect into the existing audit item rather than blocking the item that raised them. The two facts went to [audit-premise-claims-verification], the item was skipped with its candidate design banked, and it returns with an answer waiting instead of the same wall. That instruction was itself captured, with the honest counter recorded — it presumes a standing verification item exists, which is true here and may not be in a consumer project.
