# 33d5c87 — Decoupled push from release behind a mechanical trigger, reversed scrub-forward-only into a full-history rewrite, and greenlit a six-item batch

Releasing had stopped happening, and the reason was structural rather than practical. The Push ritual welded pushing to releasing, so every routine save carried the question *is this good enough to publish?* — a question with no answer when the honest one is that the project is unfinished and always will feel that way. The user named this directly as the cause, and it is recorded as theirs: making the release harder to avoid was not the goal, removing the judgment was.

So the ritual is now three actions instead of two. Push is `git push` and nothing else, after every /next and at any /done. Release fires **automatically** at any /done whose commits touched `plugin/si-plugin/`, decided by a file check with an explicit instruction that nothing may add a readiness condition back to it. Every release carries GitHub's pre-release flag, which states the project's testing status structurally so it is never re-decided or re-worded release by release.

Two alternatives were weighed and lost. Releasing on every rezip was rejected because rezip is a *local test* action — publishing something you are about to find broken is churn, not transparency. Releasing on every push was rejected because it re-couples the two at a lower ceremony level, letting the judgment creep back into "should I push yet". Frequency was never the lever; the mechanical trigger was.

Two premises the ritual rested on turned out to be stale, and both were checked rather than recalled. The `-testN` scheme was defended on the grounds that bumping the real version would nag the user's own projects to re-run /setup — `session_start.py` in fact emits a plain informational line with no prompt, so the main argument against releasing often had already evaporated. And the pre-release consistency sweep gathered its feed from `origin/main..HEAD`, meaning "unpushed" — which under routine pushing is usually empty, so the sweep would have read nothing and passed silently. It now reads the release span, and the tag lookup goes through `gh release list` rather than `git describe`, because this repo carries 135 unrelated local tags and `git describe` fails outright against them.

Those tags turned out to be the pre-rebuild history. They date 12–29 May 2026, the earliest being "Initial commit", none is an ancestor of HEAD, and 134 are on the public remote. A full-history clone on 2026-08-01 concluded that history was lost and would be on an old machine; that conclusion was wrong, because a clone follows branches and this is a disconnected graph. The capture recording the discovery was folded into [claude-md-old-history-claim-wrong] rather than kept beside it, since both edit one bullet, and its false replacement wording would otherwise have been built as written. Deleting those tags is the one action that would actually destroy that history, so the correction leads with that.

The session's largest reversal is on privacy. A prior session found a third party named in this public repo's committed entries, scrubbed the working tree, and cleared the red flag on recorded consent to **scrub forward only**. The user reversed that today: the working tree being clean is not enough while the name and the nature of the matter remain readable in the history. The scrub sweep was run over the entire orphan history first — 179 commits, 3,085 distinct prose files — and came back clean, so that history needs no rewrite and its red flag cleared on evidence rather than consent. The name survives in 12 commits of the main history, in no commit message and at no branch tip.

Scoping that rewrite surfaced a second exposure: the user's email address is the author on all 385 commits of this public repo. It appears in no file, so no edit or forward scrub reaches it. The rewrite was widened to the full history to remove both in one pass, on the reasoning that `git filter-repo` applies a text replacement and a mailmap together, and a second rewrite would have to re-rewrite the first one's own commits. The cost is real and recorded: the LOG index remap grows from 123 references to all 475. A step to set `git config user.email` to a `noreply` address **before** the rewrite is written into the item, because otherwise the next commit reintroduces exactly what the rewrite removed. What a rewrite cannot do was stated plainly to the user and is stated again here — every hash changes, GitHub retains unreferenced objects for a period, and existing forks or clones keep the old history. The honest claim is "removed from this repository going forward", never "removed from the internet".

It does not: /done routes by session shape silently and `done-plan.md` carries the whole of that work. The wrong first framing is recorded in the item so it is not inherited.
