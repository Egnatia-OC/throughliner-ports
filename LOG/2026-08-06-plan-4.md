# 410de83 — Seventeen items worked, and the session's own repeated slip turned out to be the method contradicting itself

A planning session on the blitz branch, run mostly from remote control. Seventeen dispositions: thirteen kept, three deleted, one filed-and-processed mid-session at the user's request. Two things came out of it that matter more than the item count — a product decision written into SPEC, and a diagnosis of a failure the session kept committing while it was processing the item about that very failure.

**The platform question got settled, and it is now product truth rather than a habit.** The user said plainly that this method is squarely based in the Claude Code desktop app and that they were tired of re-explaining it. That went into SPEC.md under Who it's for: the desktop app **is** the platform, as a product decision; the terminal is never a route, because it is not approachable for the non-coders this is for; and a workaround the audience cannot perform is not a workaround. Two open directions died on that decision — [move-to-vscode-extension] was deleted (created and deleted the same session), and the untested "run Claude Code from a terminal" escape was written off across every item carrying it.

**The Gradle item was re-scoped by the user's objection, and the objection was better than the item.** It had been processed earlier the same session as "warn the user about the sandbox and document it". That was wrong. The user never needed the sandbox explained — they needed Claude to say *"I can't build this, build it in Android Studio"* and move on. They already owned the tool, they use it routinely, and they were never asked. Their words: *"it spiralled around and around and around doing nothing"*. So the item is now the general **blocked-capability ladder**, written into SPEC and queued for `plugin-behaviour.md`: try it → **research whether a tool exists** (mandatory, before involving the user, because a non-coder cannot ask for a tool by name) → **ask for a named tool, once** (legitimate, not a hand-off) → only then hand back to something they already have. Plus: once a tool is available, Claude hands over only what it genuinely cannot do. Repeated hand-off is named as the failure mode. This is explicitly not a Gradle rule — the user's framing was *"it's all tools generally"*.

**The session's own repeated failure was diagnosed, and the diagnosis is the highest-value finding here.** Three times, Claude announced that text had been written to QUEUE.md before writing it — twice inside messages that were themselves capturing the previous instance. The user proposed the cause: the approval flow was reversed to write-first at some point, and there might be leftovers. A grep confirmed it. `plugin-behaviour.md`'s doc-bound-text rule says write-first-verify-then-point, while the step-level instructions still say the opposite at `plan.md:485` (the keep-step), `plan.md:685` and `done.md:471` (the wind-down re-scan), `plan.md:212`, `done.md:135`, `done.md:621` and `setup.md:112`. All three slips happened at steps in that list. A general rule read once at session start loses to a step-level instruction read at the moment of acting — so this is a half-migrated procedure producing the behaviour, not attention failing. Filed as [show-then-write-survives-at-step-level] with [claude-pointed-at-a-write-it-had-not-made] pointed at it as the probable cause; `migrate-checklist.md:36` is flagged as possibly deliberate rather than swept up.

**A mover bug was found at the last action of the session, and it touches the authorisation boundary.** A plain `--move` inside Processed, with no `--marker-after` given, silently repositioned the `--- Cleared to run above this line ---` marker — pulling [concurrent-session-support], deliberately shelved because it rewrites how every session begins, above the line and into unattended-run range. The script printed `marker placed`, which reads as reassurance and does not say the marker moved; the queue lint saw valid structure. It was caught only because line numbers were checked immediately afterwards for an unrelated reason, and corrected in-session with an explicit `--marker-after`.

**Two deletions were done by hand, at the cost the queue already predicted.** `reorder_queue.py` still has no delete operation, so removing an item takes a placeholder-and-collapse dance of four `Edit` calls. Both were completed without reaching for a shell write — recorded on [claude-reached-for-shell-write-against-rule] as evidence from the other side: the safe path is not merely unrewarded, it is measurably laborious every time.

**The queue was made remote-control-ready, deliberately.** The user is away from their desktop and wants to run /next from remote control, so every walk-through needing a computer was moved below the readiness line. The cleared region now holds 34 build items and no step that stops for a person at a desk; the one `[user]` item left above the line is a web form, doable from a phone. Nothing preserves that state automatically, so it is recorded on the forward advisory.

**One question from the user exposed a conflict between two correct rules.** Asked what would actually ask *"are you back at the desktop yet?"*, the answer is /plan's below-the-line revisit — but a `Set aside` marker's whole purpose is to remove an item from that question. An item carrying both has a condition nothing will ever ask about. Claude was about to create exactly that combination and the question caught it first. Filed as [set-aside-silences-the-lift-condition]; one live instance already exists.

**Also settled:** the user's "sanctioned tools list" idea turned out to be already queued as the "your tools" section in [prefer-the-generator-over-hand-building], so no duplicate was filed — it gained a clause instead, that every entry records how it was verified, since a tools list is precisely a list of capability claims and that is exactly how "Claude can run Gradle here" became settled fact on the strength of a command that could not detect the failure. The user also corrected the name: it records what is **available**, not what is **allowed**.
