# [HASH] — untracked core docs reframed against the sender's own reading: not a fault to detect but an offer whose consequences were never stated

Filed the day before from a consumer project's mail. A planning session there ran to completion — a red flag cleared, three SPEC edits, eight work items, nine captures — and staging at the close revealed `.gitignore` carried `SPEC.md`, `QUEUE.md` and `LOG/`. The adoption commit's own message says it wrote SPEC.md as product truth; that commit contains no SPEC.md.

The reframe came from reading the source rather than the report. `setup.md` line 426 already offers to add exactly those three paths to `.gitignore`, and [queue-privacy-default] widens that offer per document. So a check asserting the state is wrong would fire on a configuration the method itself creates on request, and would fire hardest right after the user chose it. What was actually missing is that nobody was ever told what follows. The sender read it as a defect; it is an offer with unstated consequences, and that changes the whole design.

Three always-loaded rules go quietly false, and one of them already knows how to handle it. Write-first's own test is whether the previous version is recoverable without the user's help — for an untracked file it is not, so those writes become show-first by the existing test rather than by a new rule. The rule had always had the right test and never had the fact. The other two are stated rather than repaired: a deleted queue item is not kept by git history, and `done-plan.md`'s `git diff HEAD -- QUEUE.md` returns nothing, so the close's mechanical record of its own work falls back to memory — the exact substitution that command was chosen to prevent.

Detection goes in `session_start` rather than in setup, because setup fires once and the reporting project was already adopted, so a setup-only check would have missed the very case that produced this. The hook already runs git in seven places and `git check-ignore` answers it in one call with no judgment.

That timing also dissolves the deadlock the sender hit, which is why their third suggestion was refused. Their close could not fix the state: the planning scope-lock refuses `.gitignore`, correctly, and the close marker's permitted list omits it, so it became a `[user]` line asking a non-coder to hand-edit `.gitignore` mid-close. They proposed adding `.gitignore` to the close marker's list. Detected at the session's opening instead, before any work, the same walkthrough costs nothing and interrupts nothing — so the fix is the timing, not the permission, and a deliberate refusal is not widened to solve a problem timing solves.

**Queue changes:** [gitignored-core-docs] rewritten from a capture into a designed item and cleared; [queue-privacy-default] stays held against it and lifts when it ships. `SPEC.md`'s privacy-posture paragraph rewritten to state the three consequences and the session-opening detection.
