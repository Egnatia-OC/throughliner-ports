# [HASH] — /setup's migration reads a project's own CLAUDE.md for retired vocabulary and reports what it finds

A consumer project reported that its `CLAUDE.md` described the queue as holding batches with Build/Test/Audit subheadings, a Deferred tests section, and items carrying `Parked:` headers. All four are retired. That file was written at setup and is read at the start of every session since, and nothing compares it against the current structure — so one of their sessions went looking for a section that no longer exists and had to establish from the shipped docs that it was gone.

**The scaffolding is already correct**, checked at processing: `CLAUDE-TEMPLATE.md` describes the two-section model, the readiness marker, the flavor tags and the red-flag marker. Nothing new is being scaffolded stale. So this is the harder case the report named — only projects adopted before those changes carry the retired paragraph, and no new ones are arriving.

**Detection, not reconciliation.** SPEC records that reconciling content whose template wording changed is deliberately out of scope, and that stays out: overwriting a paragraph the user may have written themselves is what ruled it out originally, and it is a wholesale conversion of a document they own. What came in is strictly smaller — the migration reads their file for retired terms and reports each alongside what replaced it, editing nothing. It runs in the migration rather than at every session start, because that is when the condition changes and when the user is already being told the project is behind.

**The build deviated from the item's chosen mechanism, and the deviation is the finding.** The item scoped three terms into `resources/retired-terms.md`, reusing the repo-wide check that already runs over the corpus. That was implemented, tested, and reverted within the hour: **every hit it produced was correct writing.** `migrate-checklist.md` and the migration recipe name the old sections because converting away from them is their entire job; `setup.md` names them to recognise the old shape; `session_start.py` names them to record what the first format epoch was. No string separates a stale use from a migration doc quoting the same heading, so the term could only ever fire against correct work — the same cry-wolf failure that file's own `ceiling of 200` entry records, and the same resolution. Detection therefore lives in `setup.md`'s own small table, scoped to **one file** where none of that prose exists. The attempt and its reversal are recorded in `resources/retired-terms.md` so it is not remade.

No format-epoch bump: the stale paragraph is prose the hooks never parse, which is exactly why all three existing checks pass it.

Depth: full — the item's chosen mechanism was implemented and then reverted on measurement.

Rule gate: run — admitted as an amendment to /setup's existing migration, which already tops up missing settings and halts on a stale format epoch; one detection added to a mechanism that exists, no slot spent. Nothing evicted; SPEC's out-of-scope sentence narrowed rather than removed. Failure evidence is one recorded consumer instance, admitted as thin on two stated grounds — the staleness was generated by our own scaffolding, so the affected population is every project adopted before the change; and the fix is a mechanical check rather than a prose rule.
