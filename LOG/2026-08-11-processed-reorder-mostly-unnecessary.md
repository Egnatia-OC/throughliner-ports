# 7c9922a — Four reorders retired: the close-out pass reduces to batching human stops, and captures append [processed-reorder-mostly-unnecessary]

Captured by the user, from noticing that Claude asked which of two cleared items should go first. Their words: it doesn't matter what order these are in, as they will be completed in the same session; there's no need to reorder stuff in Processed, and reordering is token expensive. The narrowing is Claude's, and it disagreed with the "no need" in one respect.

**The sharper half of the user's point, now stated in the docs.** Nothing said plainly that everything above the readiness line is built in one run, so a session treated intra-region order as though it carried weight — and spent a turn of the user's on a decision with no consequence.

**What went, and why each.** *Build-order re-derivation across Processed:* a genuine prerequisite is carried by `Blocked by:` and a blocked item sits below the line, so inside the cleared region there is usually no ordering meaning left to compute. *The Unprocessed reorder:* /plan's ladder already orders that section at the moment the order is consumed, with the user present — and the only thing that ever reads Unprocessed order is a /plan opening. The close was computing a durable order whose sole consumer immediately recomputes it. SPEC framed the two as complementary; that framing is what failed.

**What stays, and this is the disagreement recorded.** End-preferred placement of `[user]` and `[audit]` lines is kept: it batches the stops that need a human instead of letting one interrupt an unattended run, and it is one pass rather than an order re-derived. [lift-step-has-no-placement-rule], built in the same run, adds a cross-reference pointing at it — so dropping it would have left that reference pointing at nothing.

**Residue 1 was settled by a live instance rather than by argument.** Build-order was being kept for items that reshape what each other edit. That case arose for real this run: two items both rewrite the same guard. It was handled by writing *"this must land with [slug]"* into the item's prose; the adjacent placement came second and was convenience. **The prose carried the relationship and the position did not** — which is the argument the method already makes everywhere. So the one case build-order re-derivation was kept for is better served by a sentence in the item.

**Residue 2 accepted:** everything captured in that session was appended and the section read correctly as a chronological record. A human reading between sessions sees when things landed, which is more useful than a stale ranking.

**Third reorder, on the user's instruction: the skip-to-bottom move is retired.** Claude is capable of skipping an item within the session and leaving the file order alone, and the move was expensive. Their stronger reason is the one recorded: file order records *when things landed*, and the move overwrites that chronology with nothing more useful. **What the move was also doing, stated so the trade is deliberate:** it stopped a skipped item being presented first again next session, and the planning working file is session-scoped, so a skipped item now returns to the top and is offered first. A one-word skip to repeat — a real cost, not a free saving. A durable marker was already rejected once as a phantom queue state and is named so it is not re-proposed.

**Fourth: judgment placement of captures is retired; append always.** The user asked what the cheapest choice is, having supposed append was chosen for safety — it was not, it was the fallback. Append wins on cost, and on function: position no longer carries processing weight, so placement affects only how the file reads, and chronological is the better read. What is given up — related items no longer adjacent — is already carried better by slug cross-references, which survive reordering and say *what* the relationship is. Note this eliminates a rule rather than adding one, and removes a narration line the user never asked for.

**A tension recorded rather than resolved.** End-preferred is retained on the premise that a `[user]` stop interrupts an otherwise unattended run. [unattended-run-is-not-unattended] contests that premise directly. If it lands the way it reads, this decision should be revisited; keeping end-preferred now is the conservative call, not a rebuttal.
