# [UNFILLED] — Ten items processed and the isolation model taken out of our hands: worktrees are the harness's, the quiet-list gate is dead on Windows, and four reorders are queued for repeal

A long planning session that spent as much time on what the method should *stop* doing as on what it should build.

**The red flag cleared, and how.** [migration-skips-inbox-commit-question] was designed out rather than accepted: both the setup and migration paths will write `INBOX/` into `.gitignore` and say so in one line, with no question asked on either path. The user's reasoning decided it — anything read from the INBOX enters the project as a capture and emerges through processing as this project's own work, so the mailbox is leftover comms rather than user work; Claude confirmed the mechanic that reinforces it, namely that a read message is *archived* rather than deleted, so an un-ignored mailbox accumulates another project's raw text in a public repository forever. Claude's supporting argument was that the safe outcome should not depend on a question being asked, because a question is skippable and this one was skipped. A second instance of the same structural defect was found by reading the doc rather than inferring: Step 2C restores Step 2's missing *files* and never re-runs the *decisions* attached to them, so a migrated project can also keep a `.gitignore` that never gains its `.throughliner/` line.

**A live bug found from the user's own annoyance.** They reported constantly getting permission dialogs while in auto mode, with the hook naming QUEUE.md as outside a list that contains QUEUE.md. Traced and reproduced against the installed host: `_is_plan_quiet_path` builds its relative path from **normalised** paths, `os.path.normcase` lowercases on Windows, and the resulting `queue.md` is then tested against a case-sensitive tuple of capitalised names. It can never match. On macOS and Linux `normcase` is the identity function, so the gate works and the defect is invisible — which is why it shipped, one day earlier, with the restored planning-file gate. Rule 4's entire purpose is that a planning session's own working surface passes silently; inverted, it asks on every write, in the mode where the user has already said not to ask.

**The mechanism thread finally produced a mechanism.** [write-first-report-without-write] had reached the end of its remedies — the rule against reporting an unmade write is shipped, always-loaded, correctly worded, and still failed live. The insight that broke it open is that the claim is *mechanically checkable*: the report names a slug, and a slug either exists in QUEUE.md or it does not, so no semantic judgment is required. A `Stop` hook was verified as the right surface — it receives `last_assistant_message` verbatim, needing no transcript parsing, and can return a blocking decision that continues the conversation rather than ending it. The researched `PreToolUse` candidate was recorded as *not* transferable: a false report is text with no tool call attached, so a hook gated on tool calls never fires on it.

**The isolation question was reopened by the user refusing a plausible answer.** Claude proposed dropping branch-per-session; the user asked what the branching was *for*, and refused to design out an intentional design without knowing. The research that followed reversed Claude's position twice in one discussion — first promoting the worktree-override hook as the remote-control fix, then finding the documented refusal that most likely kills it. What settled is larger than either: session isolation belongs to the harness, and **the method cannot assume which model is running**. It must be safe when sessions share one tree (this machine's observed case) and correct when they do not, where each session edits its own copy of QUEUE.md and a capture filed in one never reaches the other. The shipped parallel-sessions advice knows only the first case. An empirical contradiction — a session opened with + New session sitting plainly in the main checkout with no `.claude/worktrees/` at all — was reported upstream as anthropics/claude-code#85560.

**Four reorders queued for repeal, on the user's arguments.** The close-out reorder of Processed, the close-out reorder of Unprocessed, the skip-to-bottom move, and judgment placement of captures. The through-line is theirs: reordering is expensive, and file order records *when things landed*, which is real information that every reorder overwrites. Claude's one disagreement is recorded rather than smoothed away — the end-preferred placement of `[user]` and `[audit]` lines earns its keep, because it batches the stops that need the user instead of letting one interrupt a build run. The Unprocessed close reorder fell to a sharper argument still: its only consumer is a /plan opening, which re-derives the order against the ladder anyway.

**The throughput floor turned out to be a bare number, and now has a derivation.** The user asked what the floor is and how it is determined; `plan.md` gives the sentence shape and never says where the number comes from, so this session's Claude picked six. Asked whether it could be traced off the dependency graph, it can: an unblocking term (Unprocessed items that held items name as blockers) plus a feeding term (the shortfall needed to keep the cleared region non-empty). Measured on this queue, both terms were zero — **the honest floor for this session was zero, not six**, since every blocker already sat in Processed. The graph itself is not a file; it is re-derived from `Blocked by:` lines each time anyone looks, which is why it cannot go stale and why it shows only declared dependencies.

**Three rule slips recorded, because this project's use of the plugin is its only real test.** Claude spawned a subagent without asking and without naming the cost; the throughput floor was written to the planning file and never said aloud, which is how the user noticed it was missing; and the wrong question was put at a mixed item — split-or-whole, a filing question — instead of the one the user owned, which was whether to design the remaining half now. That third one exposed a genuine gap: the keep-check and the skip recommendation both address a *whole* item, and neither covers an item half specified and half not.

**Two clean passes worth recording, since a pass is a finding.** The INBOX scan in `session_start.py` was suspected of failing and is correct — the messages simply arrived after that session had opened, which is the scan's real bound. And after a hand-written script wrongly reported the cleared region as empty, the shipped consumers were checked: `post_tool_use.py` matches the marker as a whole line and the mover uses a line-anchored regex, so neither can be confused by the header's backticked mention of it. The parse bug was Claude's own.
