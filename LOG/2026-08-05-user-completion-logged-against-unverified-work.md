# 0ad5fa9 — The completed-[user] close now verifies observable results against the world instead of accepting the report

A `[user]` item was once logged complete on the user's word and the work hadn't happened — an OS lock defeated their intent, and part of the residue (`origin/queue-redesign`) sat unnoticed for months when one `git branch -r` would have caught it. The design distinction that fixes it without reopening the removed completion ask: the never-ask rule forbids asking the USER; it never forbade checking the WORLD, and completion is already defined as inferred from what the session can see — a cheap mechanical check is literally the session seeing. So where an item's completion has an observable result (a file present or absent, a branch gone, a folder deleted, a URL responding), the walkthrough records that check and the close runs it — done.md's completed-`[user]` close gains a verify-don't-accept step, and /plan's async-mention path routes through the same check. A failed check produces a plain statement of what was found and leaves the item in place; it never becomes "are you sure you did this?". Where nothing observable exists, nothing changes — the item stays until the user mentions it, the lifecycle's deliberate gap.
