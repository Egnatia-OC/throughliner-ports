This session opened on a false alarm that turned out to be a real defect. A stale
`plugin/throughliner.zip` from 2026-08-09 — the last artifact of a rezip step that
no longer builds zips — sat beside the live source folder, and Windows Explorer
hides the `.zip` in its breadcrumb, so browsing into it looked exactly like
browsing the target. Inside, `docs-b/` held `plugin-behaviour.md`, a file split
into `skill-nonspecific-rules.md` on 2026-08-10, with every date frozen at the
9th. Read as live it said the project had been authoring the wrong docset for
days. Establishing that nothing was wrong took a session and several exchanges,
and the user twice, reasonably, disputed that it was a zip at all. The general
lesson became [retiring-a-step-leaves-its-artifacts]: a retired step's artifacts
are named and deleted in the same move, an amendment to the eviction rule rather
than a new rule.

The same item absorbed a second defect found while tracing whether a rule had
gone missing. None had — `47966bb` reworded the rule guarding the other
direction, and "/plan is for planning, /next is for building" is untouched and
older than both recent cuts. The defect is that plan.md states this session's
prohibition as "never build — code that needs writing is queued", and the
qualifier narrows it: deleting junk files and rewording a sentence is not code,
so it read as outside the prohibition, and this session proposed doing both
before catching it. The accurate statement already sits a few lines below, drawn
by destination rather than content type.

The queue's one uncleared red flag was cleared by designing it out rather than
by acceptance. [inbox-privacy-for-sensitive-correspondents] had three unsettled
questions; two decisions closed it. The address book becomes write-and-send only

A long detour into session isolation resolved one thread and opened another. The
premise that Claude Code documents a worktree per new desktop session was checked
and holds; the "Worktree location" setting was checked and is at its default with
no option to disable; and this machine still has no worktrees, so the
contradiction stands as already reported in `anthropics/claude-code#85560`. Two
things were learned along the way. Claude searched the web for this without first
reading `resources/research/worktree-isolation-and-desktop-sessions.md`, which
cites the same two URLs and had already established the same conclusion — filed
as [check-existing-research-before-offering]. And a cloud session's own
initialization steps revealed that it runs on a **clone** in a container, not a
worktree: in a clone both git dirs match, exactly as in a main checkout, so
`session_start` classifies it as a shared tree and hands it the one branch of the
parallel-session advice that actively misleads. The detection method was then
measured from a live cloud session rather than guessed —
`CLAUDE_CODE_REMOTE_ENVIRONMENT_TYPE` — and [clone-reads-as-shared-tree] records
that absence of the variable must mean "not cloud", so a rename by Anthropic
loses the improvement rather than producing a confident wrong answer.

been waiting on the external fact: a worktree inside the project's
`.claude/worktrees/` is session-allocated, one elsewhere is deliberate. It fails

The FAQ thread reversed twice and is worth reading in full. The user asked for
the criteria for an FAQ entry to be defined, and separately doubted the FAQ was
still needed. Claude argued the FAQ has a distinct reader and pushed back on
retiring it. Research then found no published criterion for what makes a question
an FAQ question — that absence being the finding — and a decade of consistent
technical-writing argument against the format itself, from the UK Government
Digital Service, A List Apart and passo.uno. Three of its four recurring failures
already describe this project, including the sync failure that is
[own-faq-diverged-from-shipped-template]. [faq-entry-criteria] was therefore
deleted, its content folded into [faq-cost-versus-value], because defining
criteria for a format that might be retired is work thrown away either way. The
user then settled it the other way: consumer-facing explanation lives in the FAQ,
because for a consumer the procedure docs are Claude's and there is no other
context for an answer to live in. That is a reasoned departure from the research
rather than an oversight, and the item says so, so anyone revisiting argues with
the reasoning rather than re-citing the sources. The consequence is stated
plainly: the FAQ's upkeep stays, so the saving comes from narrowing the sync
gate's trigger to changes that alter what a user actually does.

The session's sharpest finding came last. The user observed that research keeps
being packaged into build items, suddenly and across projects, and asked which
rule had broken. None had. `plan.md` still says /plan resolves research now, and
lists it first — but it is one word inside a fenced list, hedged immediately by
"A default, not an absolute", competing against a named blocking check. The
two-limb keep check requires stating which files change and what changes inside
them before an item may be kept, and when an item's answer is not yet known the
cheapest way to satisfy both limbs is to write "research X, then change Y", which
reads as a fully specified build. So the check that exists to keep undesigned
work out of Processed is the same check that rewards packaging research as build
work, and it fires hardest exactly where research is needed. Git dates the
hardening to `f8b03ea` on 2026-08-10, four days before the pattern became
visible. An earlier trace attributed it to `989c38b` — a false positive, because
that commit renamed the package folder and shows every string as newly added.
Filed as [research-packaged-as-build-work], with the explicit note that the keep
check must not be weakened: two correct rules were put in conflict and the
stronger won.
