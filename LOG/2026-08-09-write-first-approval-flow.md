# [HASH] — The approval flow inverted to write-first-then-report under one revert-undoes-it test, with commit messages and off-machine sends kept show-first, and the keep-step's move order reversed to match

The user asked for this on 2026-08-09, and it was adopted in practice from the moment they asked — so the method's text has been lagging the working practice until now. Their own stated want was simply to stop having drafts pasted into chat. The design below is Claude's, settled in the same session with the user's agreement; the distinction matters because the reasoning that follows is not theirs and should not be read as theirs.

What changed: Claude used to draft text in chat, wait for approval, then write. Now Claude writes and reports briefly what landed. plan.md's ground rule — never write to QUEUE.md without showing the exact text first — and plugin-behaviour.md's approval-time-outputs rule both **inverted** rather than relaxed; neither was weakened into a suggestion.

The load-bearing decision was to gate this on **one test rather than a list of carve-outs: does a revert fully undo it?** Yes for queue items and captures, LOG entries, SPEC edits and ordinary build edits — all tracked in git, so rejection costs a revert and nothing else, and the user reads the text in the doc where it lives anyway. No for two kinds: a commit message, because a commit is materially harder to unwind than a file edit and because it never becomes file content, so "write it first" has no meaning for it; and anything that leaves the machine — the feedback report, an outbound INBOX message — where no revert reaches the copy already delivered. The enumerated-list alternative was rejected on the gate's own wording rule, which asks for qualification expressed as structure: one test survives new approval moments being added later, whereas a list silently omits them. That is the rejected-intuitive-path worth recording, because a list is the obvious way to write this and would have decayed invisibly.

The trade is written into the rule rather than left to be discovered. Show-first guaranteed unapproved text never reached disk; write-first means a file briefly holds content the user has not agreed to. In a git repo that is cheap and recoverable, but rejection becomes a revert rather than a non-event, and the user has to be told so once. The risk this introduces is not rejection — it is the user *not noticing*, and a later commit sweeping unapproved text in. That is why the report after the write is specified as one line, specific enough to object to without opening the file, and explicitly never a re-paste of the text just written, which would spend the tokens the flip exists to save.

One thing it improves rather than costs: the write-then-verify-then-point rule exists because pointers were once emitted for writes that never happened. Write-first removes the gap that failure lived in, since the write is real before anything is reported. That was noted in the rule itself so a later reader does not mistake the flip for a loosening of that guarantee.

A dependent rule inverted with it, and this one was found by *using* the new flow rather than reasoned about in advance. The keep-step instructed: remove the item from Unprocessed first, then add it to Processed — explicitly because the drafted item was already approved and on screen, so nothing was lost if something interrupted between the two writes. Under write-first nothing is on screen, so that justification is gone and remove-first becomes the lossy order. The move reversed to destination-first: write into Processed, then remove from Unprocessed. The cost the original order avoided — a brief window where the item shows in both sections, reading as an uncleaned duplicate — is the lesser one, and it is bounded by closing both writes in the same turn.

This supersedes the ordering half of `[approval-flow-token-doubling-simplification]`, which reached the same flip from the token-cost direction and gated it on harness issue anthropics/claude-code#77134. The ordering is decided here and is not gated on the harness; if that issue lands it only makes the report cheaper to render. That item keeps its remaining scope.

Six approval moments across the procedure docs were flipped to match, and one — `setup.md`'s wholesale queue conversion during a migration — was deliberately left show-first: it was not named in the item's scope, and a bulk rewrite of an existing user queue is a defensible exception to leave for a session that decides it properly rather than one that sweeps it in.
