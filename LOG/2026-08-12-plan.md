**The worktree cluster resolved by checking the product rather than reasoning about it.** [concurrent-session-support] had been designed across three sessions as branch-per-session and held below the line with an instruction not to build it as written. A web check of Claude Code's worktree documentation settled it: the harness creates a session's isolated worktree and branch and **never merges it back**, prompting keep-or-remove at exit, where removing deletes the branch and all its work. So the surviving value is merge-at-close, which is what the user chose. A second finding reshaped the mechanics — git refuses to update a branch checked out in another working tree, so an isolated session cannot merge itself and the merge must run from the main checkout. That inverted the design: the isolated close warns and names the branch, and the main checkout's session start detects and offers. Two siblings were deleted into it — [worktree-override-hook], whose hook would hand back a path the harness documents as refusing, and [remote-session-start-has-no-owner], whose reconciliation half this now covers.

**The user challenged the premise and was right, which is recorded in the item.** Claude implied the design addressed their remote-start problem; they pointed out that if sessions branched automatically, git would have shown it at every close. `git worktree list` confirmed only the main checkout and the shelved Codex port — this project has never had a session worktree. The item is kept knowing its case is real in the product and unobserved here, and explicitly barred from being described as solving remote-start until an isolated session is actually seen. The likely reconciliation became [cleared-sessions-may-never-get-a-worktree]: the app gives a *new* session its own worktree, and the user works by pre-making sessions and clearing them.
