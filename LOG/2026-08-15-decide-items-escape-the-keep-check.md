# [HASH] — A skipped item names what would settle it, and where that is the user's decision, /plan asks before skipping

Reported by another project running Throughliner: three items in its queue each phrased "decide what happens to X", none naming a build. The two-limb keep check would have rejected all three and never ran on any, because it fires only when a session tries to move an item into Processed, and nobody tried. Skip-to-defer records nothing and moves nothing, so each returned unchanged next session and each /plan added another finding. Every individual step is the procedure working; the aggregate is an item that grows forever and never resolves.

Both checks the item asked for were run at processing and both changed the design. This project has one instance rather than three, and it is instructive rather than merely confirming: an item had been skipped and enriched twice, its two open questions named cleanly in its own prose, and when one was finally put to the user she answered it in a sentence. The naming had worked; nobody had asked. And the method *instructs* the enrichment — skip-to-defer says the sharpen-first is part of the move. So the growth the sender reports is procedure working, not procedure failing, which is why no individual step looks wrong.

The fix is therefore neither a filing-time test nor a limit on enrichment. Enrichment is not the defect; enrichment **substituting** for a decision that was available for the asking is. Two clauses on the existing recommendation: a skipped item names what would settle it and who owns that — a decision the user owns, a fact to look up, or a build that must ship first — and where the answer is a decision the user owns, the session asks before skipping. /plan is the one moment they are present and the cost of asking is a sentence.

The sender's own suggestion — flagging a capture whose description opens "decide" or "work out" — is recorded as rejected so it is not re-proposed. It keys on wording rather than on the condition, so it misses a design question phrased as a statement and fires on work genuinely named that way; the instance here opens "Setup should settle", which it would catch by luck rather than by design. And it fires at filing, where nothing can be done about it, rather than at the skip, where the user is present.

**A reply to the sending project is owed and could not be sent** — their finding was right and their mechanism was not adopted, and they should have both halves. That message names no sender, which is the condition [unattributed-mail-has-no-recovery-route] addresses going forward and which the user chose not to pursue backwards.
