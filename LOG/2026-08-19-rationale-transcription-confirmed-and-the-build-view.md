# [HASH] — a work item's rationale does reach the shipped docs, tested against git; the build gets a derived view carrying instructions and no history

The hypothesis had been filed the day before and pointed at by the forward advisory: /next transcribes what an item carries, and an item carrying three paragraphs of why offers no marker separating what to build from what was preserved for the record — so a build plausibly writes the reasoning into the doc it is editing. Two live efforts were treating that accumulation as an authoring-discipline problem, which made the test worth running before either of them ran again.

The test read commit `de2f5fc` from both ends: the item text removed from QUEUE.md as each of ten items was consumed, against the text added to `plan.md` in the same commit. It came back confirmed. [research-cited-not-restated]'s "a restatement reads as complete, so nobody goes upstream" arrives in the doc as "A restatement reads as complete, so a later session takes the item's account for the finding" — but that case proves little on its own, because the item instructed that its limit be written into shipped text. The settling case is [tool-build-implies-an-audit], which directed nothing: its clause order is preserved and its final sentence, "Nothing detects the absence of a step that never existed", is identical. In one hunk the build added roughly eight lines of operative rule and seventeen of explanation. The evidence is filed at `resources/research/rationale-flows-from-items-into-shipped-docs.md` rather than restated in the queue, and the item carrying the hypothesis was deleted — asked what changes inside which files, the answer was nothing, which makes it a finding rather than work.

The remedy is the user's and it beat the one Claude proposed. Claude's was a marker on the item telling a build which half to ignore; hers was to stop giving the build the history at all. That is structural rather than disciplinary, which matters here specifically: this corpus records four instances of a correctly-worded always-loaded rule failing to fire, and "state the rule harder" is already recorded as no longer a candidate direction. A build cannot transcribe what it was never given.

It also dissolves the collision Claude had raised against her own proposal. The always-loaded throughline rule says rationale rides the item inline and whole — keep the chain, not a summary; keep it inline, not in a field — so removing rationale from items would repeal it. But the full queue keeps everything; what the build reads is a projection. Nothing is deleted.

Two design points were settled in discussion rather than carried from the item. The separation is authored at the keep-step, not computed, because telling history from instruction is judgment and no script can do it — so each item gains a delimited build block carrying what changes in which files, the acceptance test, the red-flag state, and any recorded refusal. Refusals travel because stripping "X was refused because Y" makes the build re-propose X and stop to ask. And the view is read-only and regenerated, which removes the merge entirely: nothing rejoins because nothing left, and the only write-back is deleting the slugs that shipped, which `reorder_queue.py --delete` already does. Her proposed queue-merge skill was refused on that ground rather than on its merits — a sixth skill is the heaviest answer available, since every skill is loaded, documented and explained to consumers.

The one part of her design that did not survive is the build's close adding historical rationale back at log time: the build session does not have it, so it cannot. The fix is a targeted read — the view carries each item's slug, and the close resolves one slug against QUEUE.md, one entry rather than the file. It is a read, so it cannot collide with a planning session writing, and it happens after all editing is finished, so there is nothing left for the rationale to leak into.

The ripple was traced by grep rather than written from the discussion, which is what showed the true size: 22 files in the package name QUEUE.md, and the ones that must change are `plan.md`, `next.md`, `next-build.md`, `done-build.md`, a new generator script, `pre_tool_use.py`, `post_tool_use.py`, `session_start.py`, the migration recipe, the suites and the FAQ. It bumps the format epoch, so every existing project migrates.
