# [HASH] — The rule gate's site moved to /plan's keep-step, where refusing is still possible

The capture reported a run that built eight items, three authoring genuinely new standing rules, with the gate run once after all eight were built. The disposition was honest about its own timing and admitted nothing was refused — which is the failure `CLAUDE.md` documents in its own words: a gate that runs after the work exists cannot refuse, because refusing would mean undoing finished work.

**The capture asked /plan to weigh a partial fix and warned it might be over-claiming.** It proposed a `Rule gate:` field per item at the build's tick, alongside the depth field and the index candidate, and said plainly that this is still *after* that item's rules were authored, so it improves attribution without restoring the power to refuse.

**That warning is upheld, and the fix moved instead.** The planning session that processed this ran the gate about a dozen times, at the moment each rule was designed and before anything was built, and it refused repeatedly and substantively: a proposed freestanding rule turned into an amendment costing no slot; an exception refused outright on the restatement test, against the source audit's explicit recommendation; a freestanding rule admitted only after consolidate-in-place was weighed and lost on distribution; and three proposed evictions refused on recorded grounds. Every one of those is a refusal, which is the thing a close-time or build-time gate provably cannot do.

**So the split is compose-versus-transcribe, one stage earlier than `CLAUDE.md` already had it.** It said the close transcribes a disposition and does not compose one. The same relation now holds one stage back: /plan composes when the rule is designed, /next transcribes what the item already carries — and halts if it is about to author a rule with no disposition to transcribe.

**One documented location was wrong and is corrected.** `CLAUDE.md` said the disposition is written into the session's build working file. A planning session has no build working file, so the dispositions written during processing went into the queue items themselves — which is where they belong, since the item is what /next reads, so a disposition on the item travels to the build automatically.

**The honest limit is kept from the original capture and restated in the shipped text.** None of this lets anything tell an honest disposition from a dishonest one. A /plan-sited gate can refuse, which the alternatives cannot. That is a real gain and it is the whole gain.
