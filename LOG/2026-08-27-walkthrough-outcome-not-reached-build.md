# 32675a3 — Walk-through outcomes get a third value, and "deferred" needs the user's word

Two outcomes could not describe what actually happens to `[user]` work. An item
the run never presented was being recorded as deferred, which tells the next
session a decision was made when none was — and the item then sits unpresented
with a record explaining why nobody need present it.

Three values now: **done**, **deferred**, **not reached**. Done keeps its three
existing inference routes. Deferred is written only from the user's own word.
Not reached says the run never presented it, or presented it and got no answer,
and tells a later session to present it fresh — with no deferral to honour and
nothing to resume from.

**No completion ask was added for this**, and the vocabulary is what removes the
need: the no-completion-asks bar stands untouched, because the three values are
read off the session's own trail rather than obtained by asking.

Written at all three sites so they cannot disagree — the branch that produces the
outcome, and the two close docs that record it.

**Files touched:** `plugin/throughliner/docs/next.md` (the walk-through branch's
outcome block); `plugin/throughliner/docs/done.md` (the same block, read off the
session's trail); `plugin/throughliner/docs/done-build.md` (points at both rather
than restating them).

**Routed to Captures:** [spec-owes-warn-and-outcomes] — SPEC's `[user]`-work
paragraph has no vocabulary for an item a run did not reach. Filed rather than
written, since a build does not write product truth.

**Exercised the same session**, and all three values were used: one item done
from an observable check, one deferred on the user's actual word, and one left
incomplete because a standing commitment cannot be ticked by any session.

Rule gate: run — amendment to the walk-through branch's outcome recording and the close's record writing; parents named; nothing evicted.
