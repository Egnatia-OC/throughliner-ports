# [HASH] — /rescan tells the user a future planning session decides her captures, and the premise behind the complaint turned out to be false

Alex reported that running /rescan before the close of every planning session was not having the effect it was built for: once it ran she was no longer in /plan and had to run /plan again, which defeats the reason it was made a separate skill. Her second point is the sharper one and is hers: what a re-scan turns up is often needed to finish the planning work that just happened, so it should land in the session that still has those items in mind rather than waiting for a planning session that comes after a build.

**Her premise was tested rather than accepted, and it does not hold** — which is what made the item fixable rather than a platform limitation. Claude Code's documentation states that an invoked skill's rendered content "enters the conversation as a single message and stays there for the rest of the session". There is no running skill, nothing ends, and nothing has to be returned to; `plan.md` was present and governing for every turn after /rescan ran. The documentation also names this exact symptom — a skill appearing to stop influencing behaviour — and attributes it to the model choosing other approaches while the content sits there unread. The finding is filed at `resources/research/skill-content-lifecycle.md` with the quotes, the auto-compaction limit that is the one genuine exception, and the note that re-invoking an unchanged skill costs a one-line note rather than a second copy.

**Alex then found the second defect, and it is the stronger of the two.** /rescan's final step does not merely fail to hand back; it positively sends the work away. Its wording is *"a planning session decides what happens to each one"* — false read inside a planning session that is still running, since that one can decide them and /plan is entitled to. A missing instruction is an omission; a sentence pointing elsewhere is a misdirection, and it explains why the effect held so consistently when nothing had ended.

**Her second question settled a scope worry rather than opening one.** She asked whether the hooks and the enforcement are attached to /plan. Read in the code: `hooks.json` registers all four against Claude Code's own events and against tool names, and none is bound to a skill. The scope-lock is the one that looks skill-bound and is not — `pre_tool_use.py` decides a session is a planning one from the absence of this session's build working file, and says so in its own comment. So the planning standing list is in force in every chat with no build running, whether or not /plan was typed, and nothing was ever at risk. That narrowed the fix to two sentences in one document.

**The wider half was split out on her decision.** Claude first framed this as "the docs end when they shouldn't"; her correction was that they usually should — sometimes the session ends when planning or building is done, and that is correct, and sometimes the skills need to be alternately run depending on conditions, not normally but sometimes. That turns a rewrite into a design question with no answer yet: whether a procedure doc can tell finished from interrupted. It is [procedure-docs-cannot-tell-finished-from-interrupted], filed to Unprocessed, and this item claims nothing about the other four docs.

**The ripple was traced by grep rather than written from the discussion**, which found a third site the conversation had not: the shipped FAQ answer carries the same sentence, so every consumer is told the same thing. Two further hits were excluded by name — one about SPEC edits, a different subject, and one describing /done's lighter version of the same scan, where deferring to the next /plan is correct because /done really is closing.

**Files:** none this session — the item is cleared to run and carries a build block naming `rescan.md`, `faq-template.md` and the `FAQ/` copies.

Rule gate: run — admitted as an amendment to `rescan.md`'s existing final step, subordinate rather than freestanding, sited in a fetched procedure doc so no always-loaded slot is spent. The eviction is the "a planning session decides" wording, repealed at all three live sites. Failure evidence is the user's report of the same outcome at every planning session plus the documented mechanism showing the belief that wording created was false. A hook was considered and refused: nothing mechanical can read whether a conversation resumed a procedure.
