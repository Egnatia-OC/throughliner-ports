# [HASH] — the Taskflow integration assessed from this side before any message was sent, and reduced to three concrete asks

Alex opened a subject that had lived only in her head: pushing `[user]` work into Taskflow so a project executed mostly by hand has a to-do list rather than a conversation. She offered two routes — message Taskflowapp first, or assess from here and then message. Assessing first was chosen because it costs nothing and it is what turns a request to talk into a request for three specific things.

Four findings came out of reading Taskflowapp's own SPEC and queue. **Her mapping is Taskflow's model rather than an approximation:** subtasks inherit their parent's project, date and placement, and a parent has no checkmark of its own — it completes only when every subtask does. So `[user]` item as parent and walkthrough steps as subtasks yields one derived completion signal per item, and a half-done item cannot read as done. **The channel is already designed there and unbuilt:** the paid tier is cloud sync plus Claude reaching Taskflow through a remote MCP server, so Throughliner would be a client of a route Taskflow intends rather than an integration its local-first principle forbids — but the server and the setup flow are both unbuilt and sync is their precondition. **The sentence that looks like a wall is theirs to read:** Taskflow's SPEC says it does not import from, sync to, or export to any external task app, and the reading here is that Throughliner is not a task app being synced but Claude, the actor their paid tier sanctions. **And their own queue already holds the interim pattern**, in Alex's words there: *"We're just here, so we don't need the MCP."*

Two hazards were found by reading rather than assumed, and both sharpen the asks. Taskflow runs on the phone against a local database, so a file route means producing a file carried onto the device. And their existing whole-database export and import is a *restore* — pushing tasks through it would replace every other task in the app. What the bridge needs is an additive import, which Taskflow has neither built nor designed.

Alex chose the file-based route with MCP as the later transport, and a personal bridge rather than a shipped feature. The permission question that blocked the send was raised and settled in the same conversation: the parent-folder rule says Taskflow may be read and never written to, and her decision is that INBOX is the exception and the one sanctioned pathway, on the ground that a mailbox is a communication method rather than part of the product. Placed first in the cleared region — not because it is largest but because it is the only item whose payoff sits outside this project, so the sooner it goes the sooner Taskflow can answer.
