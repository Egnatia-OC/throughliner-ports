# 68ca27e — Found a real privacy leak in the public repo and scrubbed it, re-grounded the docset selection and the dependency model on checked facts, and cleared seventeen items to run

The session opened on the advisory to process the six session_start captures before the release, and stayed on that spine, but three things forced larger corrections than the advisory anticipated.

**The docset selection was rebuilt on a checked fact rather than an assumed one.** The live verification had already failed — no docset directive reaches a session — and the obvious next step was to work out why. Reading Claude Code's published hooks contract settled it in one fetch: the `model` field is documented as *not guaranteed to be present*, and there is no environment-variable equivalent. So this was never a bug to fix; phase 3 was built on a signal the vendor declines to guarantee, and the hook's own docstring cited the project's research saying exactly that. The decision is to select the docset from a recorded setting — asking which model the user runs, not which docset they want — with the payload field used when present and docset A as the final fallback. That change is also the release's gate: shipping while the headline feature is inert would announce a feature that does nothing. Two of the three candidate causes were eliminated at processing rather than left for the build (`docs-b` is present in the installed host; the classifier parses `claude-opus-5` correctly), so the build starts narrower.

**A red flag turned out to be realised, not hypothetical, and clearing it was the session's most consequential act.** [scrub-gate-before-approval] warned that private content could reach a public repo. Checking the repo's visibility — something nobody had done — showed it is public, and a sweep found committed LOG entries naming a real third party in an abuse and evidence-gathering context, readable for roughly six weeks, plus a consumer project name shipping inside `docs/` to every consumer. The user was shown the exposure, told plainly that deleting text does not remove it from git history, and given three options: rewrite history and force-push, scrub forward only, or make the repo private. **They chose to scrub forward only, accepting that history retains the original text and that the repo stays public.** Seven files were scrubbed to neutral descriptions with the method lessons intact; "scrolly-thing" was left in place by their explicit decision, being their own project rather than a third party's. The flag was then cleared on a second, separate informed consent: they were told that until the gate is built the same class of leak can recur, and chose to clear on that basis. What the incident actually taught is that the item's stated crux was not the failure — nobody scrubbed badly; the text was approved by both parties as unremarkable because neither was thinking about a third party. The failure sat upstream of any approval gate, which is why the build is now three parts (a write-time rule, an on-demand sweep, and a detected repo-visibility fact) rather than the single pre-approval gate originally proposed.

**The scrub itself broke a rule, and that is recorded rather than glossed.** Seven files were edited inside a /plan session with no work item, no scope and no /next. Checking `pre_tool_use.py` showed nothing was circumvented — the file scope-lock engages only while `_build.md` exists, so planning sessions have no file containment at all. The call to fix a live exposure immediately was right and would be made again; the method simply has no sanctioned shape for it. Both halves are captured together, because a scope-lock built without an emergency path would have blocked exactly this.

**The dependency model was corrected by the user, against Claude's framing.** The queued position was that queue position already expresses "this after that", so lift-conditions naming other items are redundant. The user pointed out that position carries *order*, not *dependency* — and since /plan reorders both sections at every close by unblock-potential, a dependency held only by position can be silently inverted by routine housekeeping. The old `Depends on:` / `Blocked by:` headers did this soundly and were removed deliberately in the 2026-07-03 redesign, which demoted the slug to "LOG traceability only". Reading that decision before reversing it mattered: what the redesign cut was a five-part apparatus, and restoring one lint-checked `Blocked by:` field is not the same as undoing it. The evidence that this is formalising existing behaviour rather than adding burden is that five lift-conditions were written *in this session* naming another queue slug — by a session that had just read the capture warning against it.

**A three-instance pattern was named.** In each case a clear prohibition was walked into because the procedure created pressure and offered no legitimate alternative: the below-line revisit gave no sanctioned way to stop asking, so a fifth queue state was invented; a "say nothing" rule leaked into narration because a neighbouring consolidate rule offered no carve-out; and "never build during /plan" was broken for the scrub because nothing sanctioned an urgent fix. The generalisation — where the method forbids something at a moment of real pressure, it must name the legitimate move in the same breath — is now written into the queue rather than rediscovered a fourth time.

**Link behaviour was settled empirically and closed a blocked item.** Live testing established that a plain `.md` link opens at the top, an `.md` link with a line suffix is dead, and code-file links land on the exact line. That unblocked write-first-link-don't-paste, which had been held below the line by an unresolved contradiction between two prior sessions, and it rescoped the Editor field: the field never controlled where links open, and its remaining job is editing, not reading. A later attempt to test whether other file formats could carry line anchors produced four failures that were then correctly discarded as unreliable — a `.py` file also failed under the same conditions, proving the test vehicle rather than the extensions was broken. That correction is recorded because the conclusion had almost been drawn.

**On run length, the user's evidence overrode Claude's caution.** Asked to clear as much work as possible, Claude proposed a marker-based pause scheme; the user pointed out that /next warns about run length every time, they always override it, and they have never once run out of context. Seventeen items were cleared on that basis, and the over-warning was captured as its own finding.

Two smaller corrections worth carrying: a provenance credit was found wrongly attributing an item to the user and was corrected after they challenged it, which produced a capture about credits being both ambiguous and mis-applied; and the queue mover failed twice more on the marker-above-all-items bug, needing a by-hand workaround both times, which now makes it the queue's most-firing defect and the first item cleared to run.
