# 115f851 — The Editor field retired and the line-anchored-link promise dropped, settling three contradictory observations on one verified fact: the app opens the file and ignores the anchor

This consolidates and repeals two captures the user raised from live observation, `[desktop-native-md-open-vs-editor-field]` and `[line-anchored-link-dead-in-desktop-app]`. Neither premise survived checking, so a single item replaced them rather than leaving two items carrying contradictory claims about the same mechanism.

Three observations were on record and only one holds. On 2026-08-01, that `.md` links open natively in the desktop app *at the correct line*. Later, on the same host, that clicking a line-anchored link did **nothing at all**. And at `5993a10`, from a deliberate `[user]` verification, that the link **opens the file at the top, silently ignoring the anchor**. The third is the one that came from a test run on purpose, and it falsifies the second outright. It also undercuts the first, which came from the session where two of its three app-behaviour claims were falsified the same way — so "at the correct line" does not stand either. Settled: the link opens, the anchor is ignored. The correction had already been applied pre-revert and was reverted with everything else; this re-applies it against the smaller single-docset surface.

The first consequence is that line-anchored links were a promise the app does not keep, stated in two places in the shipped docs. Both now link the file plainly and name the line in the prose instead ("around line 40"), so the number still helps a person reading even though the click will not use it. The count was verified this session as two sites rather than the seven the pre-revert correction spanned — that larger number covered both docsets, and the other one has since been deleted.

The second consequence is that the Editor field had no job left. It existed so the method knew which app to point a link at, and the desktop app opens `.md` in its own viewer regardless. With working mode retired by `[remote-control-opening-mention]` earlier in this run, the recorded editor was the *last remaining* gate on whether a pointer was emitted at all — so retiring it makes pointing the unconditional default, which is precisely what that item already decided. The two are halves of one change and were built together.

The cost was accepted rather than overlooked. A user *not* on the desktop app may genuinely depend on an external `.md` reader, and setup's editor question plus the FAQ's "keep a default reader open" advice existed for them. But that advice is now false for the desktop app, which is the method's stated environment, and the phone case is covered by the bundled inline-paste offer. So the field was retired outright rather than narrowed — a smaller, truer mechanism beats a conditional one kept alive for an audience the method does not target. That is the intuitive-but-rejected path here: narrowing reads as the safe move and would have left a gate nothing can evaluate.

One scope addition was approved mid-run, and it was a real half-wiring rather than an extra. `hooks/session_start.py` carried a missing-settings check keyed on a `## Editor` heading, which injects an instruction telling the session to open by asking which editor the user works in — the nag that in fact fired at the top of this very session. Retiring the field without removing that check would have left the hook demanding a setting nothing reads and `/setup` no longer writes, for every project lacking the section, forever. The check was removed and the settings-check mechanism left in place, empty, for the next setting that needs one. Verified by running the hook against this project: no editor nag emitted.

This resolves finding 2 of `[queue-items-on-falsified-premises]` — that item no longer needs to rewrite `[line-anchored-link-dead-in-desktop-app]`, because this repeals it.
