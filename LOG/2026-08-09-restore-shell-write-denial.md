# [HASH] — The structured-shell-write denial restored, and the sanctioned alternative restored alongside it so the guard has somewhere to send people

`pre_tool_use.py` regains `PY_INVOCATION` / `PY_OPEN_WRITE` / `PY_PATH_WRITE`, `structured_write_targets()`, `_is_inside()` and the Bash-branch denial, taken from `c4cf5af` rather than re-derived. Its test suite was already present and unchanged, which made verification immediate: eight cases, all passing, including the two that define the guard's shape.

The guard denies a scripted write to any file inside the project, and the word doing the work there is *any*. The original denial had two reasons and `c4cf5af` found they come apart. The scope-lock reason genuinely doesn't apply to a file the build already lists. The stale-view reason does, unconditionally: a shell's view of a file can be out of date, so a scripted write can silently overwrite work the editing tools would have refused to clobber, and that is true whatever the file is. So the check never consults the Files list — which is what makes it catch the real cases, since every recorded instance wrote to a file that was already in scope.

The item's one open question was answered by evidence rather than left to judgment, and the answer changed the build. It asked whether `scripts/reorder_queue.py` actually covers the shapes that keep tempting the script route, on the grounds that a guard with no usable alternative just gets worked around. It did not: the reverted mover had neither `--delete` nor `--move-section`, which are precisely the two operations all five recorded instances were reaching for. Hence the hard pairing with the mover restore in the same run. This session is the proof it was needed — it began by deferring a queue removal for want of a mechanical route, and finished by doing that removal with the restored `--delete`. Restoring the guard alone would have blocked the workaround and offered nothing in its place.

Two things are deliberately left permeable, and both are stated in the denial text the user actually sees rather than hidden in the source. The session scratchpad, the user's memory directory, and anything outside the project all pass, because they are sanctioned scratch space or somebody else's business. And a write whose target path is computed at runtime — a variable, an f-string, a concatenation — is not detected at all. That is a fail-open, and the denial names it as a gap rather than a permitted workaround, because general shell parsing was considered and rejected: it is fragile, and a false denial trains exactly the workaround behaviour the guard exists to stop. The queue mover itself passes for this reason, since its write target is computed.
