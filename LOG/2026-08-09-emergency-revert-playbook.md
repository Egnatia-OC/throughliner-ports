# 4f5e167 — The revert record split: eight general findings shipped as an on-demand recovery doc, the self-hosting gotchas kept host-only

The 2026-08-09 emergency revert wrote its own record. The /plan session that followed was the first real test of it, and the comparison was worth banking while both were fresh: the document is strong on *how to execute* a revert and near-silent on *what a revert does to the project afterwards*. That gap is what the shipped half now fills.

The legitimacy question had to be settled first, since a document holding steps nobody loads is the anti-pattern the executable-work-lives-in-the-queue rule names — /next never reads such a document, so its steps silently fall through. The discriminator used, which also governs `[work-plan-docs-stay-unrestored]` so the two cannot diverge: **a document is legitimate when something loads it.** `migrate-checklist.md` ships and is loaded on demand by /setup. This playbook's general half is reference consulted while recovering rather than a sequence to run, so it clears the bar — and to make that literally true rather than merely arguable, the behaviour rules gained the trigger that loads it.

The eight findings lead with the one that costs the most and announces itself least: **the queue keeps asking for work already done.** A rollback restores files but cannot restore the correspondence between the queue and reality, so sessions afterwards are handed finished work presented as ready, with nothing marking it. That happened seven times in the session after the revert, each caught by accident — and it happened again in this very session, where `[reorder-mover-marker-at-top-blind]` asked for a fix that had shipped at `f9326dc`. Two independent occurrences is what moved it from an observation to the document's lead claim.

The rest, in short: restore immediately everything that cannot possibly have caused the problem, because seventeen files sat needlessly missing for a day; check what depended on you, which is the one genuinely time-critical item, since a companion project built against a published format found out by breaking; remember that a rollback undoes *deletions* too, and nothing watches for changes inverting; say plainly when the target was merely the best available rather than actually good, or the project reads as fixed when it is only smaller; treat the LOG index as the recovery instrument, since one-line summaries are what make a 65-commit recovery tractable; know that shipped work survives only in its log entry while unbuilt work is the reverse; and don't trust the index's own dates, which were wrong once and repeated in good faith by a second project.

What stayed host-only is decided by one fact: a consumer reverting their own project never reinstalls this plugin. So the CLI-will-not-install-backwards gotcha, the PATH gotcha, and the word-count reasoning about this plugin's own docs all stay behind. The third gotcha — orphaned files after clearing the index and checking an old state back out, with rename-detected pairs escaping the deletion list — is general and did ship.

The verification section was kept as written; it is a good model, and it is the same shape `[rezip-verification-steps-restored]` separately restored for rezips in this run.
