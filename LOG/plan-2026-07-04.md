# [HASH] — /plan (resumed): decomposed [remaining-redesign-batches] into five ordered redesign-middle batches (red-flags-restore-defs → hooks/next/done/templates recut); decided red flags return as tagged work lines with open/resolved/accepted states (not a dedicated section), retired the test work-type while keeping build/audit/freeform flavors, and folded a canonical four-state work-line-states statement into plugin-behaviour.md; processed the earlier captures and filed [session-too-long-handoff-offer]

This resumed /plan session shaped the unshaped middle of the queue redesign and made two substantive design decisions along the way.

The middle of the redesign — /next, the /done family, the three hooks, and the templates/SPEC scaffolding — was captured as [remaining-redesign-batches] but never broken into buildable work. It was decomposed into five ordered batches: [red-flags-restore-defs] (the rulebook layer), [hooks-work-line-recut], [next-work-line-recut], [done-work-line-recut], [templates-spec-recut] — run in that order, before the dogfooding switch and [fresh-queue-clean-break].

Red flags. The redesign had removed the structured red-flags mechanism (the dedicated section and the open/resolved/accepted states), keeping only the plain-English screening. The user decided to restore the structure — but as tagged work lines, not a dedicated section. A red flag is a work line carrying a `Red flag · State: <open|resolved|accepted>` marker. The rationale, in the user's words: describe each risk in terms of what will be done about it, which is what the queue is for; and a dedicated section would be perceived as circumscribing any and all risks that exist, implying comprehensive data/security risk management the tool can't back up, when it only ever lists the risks Claude could identify. Tagged work lines let Claude surface and address a risk without that over-claim. The rejected alternative — a dedicated `## Red flags` section at the top, Claude's initial recommendation — lost on that over-claim risk and on "a section describes a state, not a next action." SPEC's risk principle survived the redesign intact and stays honest, so no SPEC edit was needed.

Work-type collapse. The /next and /done recuts settled how work-type survives the flat model: test is retired (a check Claude can run is part of building; a check needing the user is a `[user]` work line), while build, audit, and freeform stay as distinct execution flavors, now selected from a marker on the work line rather than a queue subheading (Option B). next-test.md and done-test.md are deleted. The [research-folder-always-in-scope] fold-in lands in the hooks batch (pre_tool_use adds `resources/research/` to the always-allowed set) with its scaffolding in the templates batch.

Four-state model clarification. The user corrected a recurring mischaracterisation: "decided but not ready" work is Processed below the cleared-to-run line, not left in Unprocessed. To stop it recurring, an explicit "Work-line states — the canonical four" statement (Unprocessed / Processed-above-line / Processed-below-line / Deleted; the cleared line replaces parking, order replaces dependencies) is folded into [red-flags-restore-defs]'s plugin-behaviour.md scope, since that doc loads every session start.
