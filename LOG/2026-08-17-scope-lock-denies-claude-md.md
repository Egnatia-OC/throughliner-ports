# dc52025 — the planning scope-lock is right about CLAUDE.md, and the reason gets written down

Raised three times from the same reading of the same code: a planning session cannot write CLAUDE.md, which is where this project's rules live. The item was honest that it might be intended behaviour and refused to assume.

It is intended. The item conflates deciding with writing. The rule gate runs at the keep-step and its output is a disposition on the queue item; the rule's text is typed later by a build. What the gate rejects is a build *deciding* whether a rule may exist — not a build writing out one that /plan already admitted. This session is the evidence: sixteen rule changes were dispositioned at the keep-step and every one queued its text as a build. Nothing was blocked and no decision moved downstream.

It is also genuinely unlike the three scope-lock gaps fixed the same day. Those were required writes with no permitted moment anywhere in the method. This write has a proper home.

Reading the hook's own account showed there is no CLAUDE.md-specific reason on record at all: the list is a whitelist of the planning surface, and rule text is denied for the same reason a template edit is — it is work, and a planning session queues work rather than doing it. So the clarification states the general sentence and names CLAUDE.md as the case that keeps being asked about.

The permission change was refused on the record so it is not proposed a fourth time.
