# 78fa417 — The INBOX address book becomes write-and-send only, and an outbound send now checks the recipient's ignore rules first

**This item carried a red flag, cleared at processing on 2026-08-14 by designing the risk out rather than accepting it.** The substantive clearing record was written at that /plan close; this entry carries it through and records what was built.

Some projects are private in a way that goes past "not published": the folder name alone can identify a real person and a sensitive matter. The INBOX design assumed correspondents are ordinary projects whose names are unremarkable, and had no notion of one that is not.

**The exposure was never publication, which is the part that took working out.** `INBOX/` is gitignored on every path already, so the address book is not published. The risk is that a session *reads* it and copies a name into QUEUE.md or a LOG entry, which are committed. Locating the file differently does not reach that. Restricting what may be done with its contents does — which is why the address book is now write-and-send only: a session may pass a recorded path to a send, and may never quote the path, name a correspondent in any document, or carry either into chat. That also answers what a session may read from it, so no separate decision was needed.

The second decision reaches the exposure this project cannot see. An outbound reply is written into the recipient's own folder, so a file from here appears inside a repository whose ignore rules this project does not control. Before writing, the sender now confirms that project's `INBOX/` is actually covered by its `.gitignore`, and refuses until the user says go where it is not. This is one more limb on a check that already runs — the sender already confirms the recipient has a mailbox — rather than a new mechanism.

**The alternative of sending with a warning was weighed and rejected.** A warning at the moment of sending is the kind that gets clicked past, and the cost of being wrong lands in a repository neither party can see. A refusal that waits for an explicit yes is the only version with teeth.

**Two of the four exposures are not closed, and the item is explicit that they must not be described as closed.** An inbound message may carry its sender's name, and nothing at the sending end requires anonymity — the one that prompted this identified itself only as "a project running throughliner 1.20.0-test2", which was the sender's discretion, not a rule. And anything an inbound message produces is processed into QUEUE.md, where the scrub checklist is the only thing standing between a sensitive sender's details and a public repository — and that checklist is Claude checking its own writing. Both are downstream of things this project does not control. What is closed is the route out of the address book, and the route into a repository this project cannot see.

Mixed authorship: the user raised the capture and gave the underlying instruction that surfaced it — that a particular correspondent's identity and path must not be recorded anywhere. She also proposed keeping the address book in the gitignored `INBOX/` folder and referencing it from CLAUDE.md, which turned out to be the design already in force and therefore to change nothing about the risk. The two decisions that close it were Claude's recommendations and her agreement.

Rule gate: run — admitted. Two amendments: the address-book section gains a use restriction, and the existing pre-send recipient check gains one limb. Both are subordinate to rules already there, so no slot is spent. Fetched rather than always-loaded, since `feedback-and-inbox.md` opens on a visible trigger. Not hookable: whether another project's `.gitignore` covers its mailbox is readable, but "a send is about to happen" is not a tool call. Nothing evicted.
