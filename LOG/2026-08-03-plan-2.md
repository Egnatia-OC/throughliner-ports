## Announcement published to Discord, 2026-08-03

Recorded in full per the artifact rule settled this session (CLAUDE.md, External communication). This is the text as approved and posted.

**Follow-up on the terse-docs experiment.**

Last time I made two claims: that newer models don't need the heavy "why" clauses, and that terser, more structured docs would hold adherence better. We ran it. The first held and paid off well. The second didn't, and chasing down *why* turned out to be the interesting part.

**What worked: cutting the why-clauses.** The old docset carries a reason attached to almost every rule, because Opus 4.8 genuinely needs it — strip them and adherence drops. The 5-series doesn't, so the light docset was authored by deleting them. Result: 255,885 → 156,964 bytes, a 39% cut.

The per-document breakdown is the part I'd point at, because it's nearly a controlled result. The reduction tracks how much rationale a document was carrying, not how long it was. The two rule-dense docs fell 56% and 41%. Two near-pure routing docs, already almost all mechanics, fell 4% and 11%. Where there was nothing to subtract, the light docset is the same size as the heavy one. So the saving is entirely subtraction — the notation contributed nothing.

**What didn't work: the pseudocode.** The case for it rests on two papers. Skill-as-Pseudocode (arXiv 2605.27955) measures agent task completion on ALFWorld; Mishra et al. (EMNLP 2023) measures NLP task accuracy across 132 Super-NaturalInstructions tasks. Both show real gains. Neither measures what I needed.

Task completion and rule adherence aren't the same thing. Completion asks whether the goal was achieved; adherence asks whether the constraints held on the way. Most of my behaviour doc doesn't tell Claude how to accomplish anything — it constrains how it behaves while accomplishing whatever it's doing. "One item per message, then stop and wait." There's no task that succeeds or fails at, and a model can complete the task *faster* by breaking it: dump all five steps at once, finish sooner, score better on any completion metric, having failed the rule completely. No completion benchmark would notice.

That matched what we saw. The code fences formalised the mechanics that get followed anyway; every rule that actually slips stayed prose, because those rules don't reduce to structure. So: hybrid by content type. A typed block has to be earned by real structure — a dispatch table, a set of conditions, a branch — and everything else stays prose.

Two things from going back to the literature this week.

The evidence *for* pseudocode is thinner than I'd assumed. Mishra's models are BLOOM and CodeGen — one of them a code model, so a code-shaped prompt flatters it for reasons that don't transfer to a frontier instruction-tuned model. And nobody appears to have tested prose vs pseudocode for standing behavioural rules at all. That's a gap in the field, not in my reading.

More useful: prose vs pseudocode is probably the wrong axis. The better-evidenced lever for a document of this shape — long, multi-section, always loaded, many independent rules — is explicit structural delimiting. XML-style section boundaries. The testing is consistent that it does nothing for short prompts and shows up on long multi-section ones, which is exactly my case.

**One honest caveat on the win above.** The 39% is measured. "The 5-series doesn't need the why-clauses" is Anthropic's guidance plus my own read of the result — it isn't measured either. Same weakness I'm criticising in the pseudocode case, so it gets the same treatment.

So the plan: stop judging this by reading. IFEval's design is the fix — express the rules that actually slip as script-verifiable constraints, run the same scenarios against each docset, count violations. Add structural delimiting as a third arm, since it's cheaper than a register change and doesn't touch the docs' voice.

Doing it now rather than later, while the old docset still stands as a fallback.

**Update from the same session.** I've scoped this as an actual build rather than an intention, because it turns out the tooling is already there. Claude Code's CLI runs non-interactively, loads a plugin from a directory for a single session, pins the model, emits structured output, and caps spend on a loop. So an A/B run against two docset builds is mostly wiring flags together, not a research project.

Which reframes what I'm building. The deliverable isn't a verdict on pseudocode — it's the ability to tell whether *any* change to these docs helps, which I've never had. Every register, wording and structure decision in this project so far was judged by reading the result. The register question just happens to be the first thing to point the harness at.

**Why I'm posting this at all.** Doc size is the most contested thing about this method. The standing objection is that nobody sane ships skill docs this large, and until now my entire defence was that it works anyway. That isn't a defence. It's an observation with no mechanism behind it, and I knew it.

That's what changes here. Doc size stops being something I defend and becomes something I control and measure. I'll be able to say which parts earn their tokens, cut the parts that don't, and put a number on what it costs when I get it wrong. And I'll publish what the harness says either way — including if it turns out the size critics were right.

I don't think they were.
