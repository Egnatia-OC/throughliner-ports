The session opened to reintroduce the old plugin's "Red flags" feature. The reintroduction is scoped to security, privacy, and breach risk specifically, and splits surfacing-now from gating-later: the surfacing half (the rule, the section, and three flag states — open, resolved, accepted) ships as a feature; the gate (an open flag blocks unattended autopilot) is designed into cruise control when it lands, reading the states the surfacing half defines. Accepted records informed consent in the LOG — the trail that protects the user if a breach surfaces later.

Two architecture decisions surfaced mid-promote and were captured, not built. First: SPEC's read-only-during-builds special case caused confusion — a direct /plan SPEC edit read as off-script even to the designer — so SPEC becomes a normal doc edited only through a planned build batch. Scope-lock already protects the property the lock guarded (a build can't edit the spec it builds against), so the dedicated lock is mostly redundant. Second: REGISTRY is write-only. Grep confirmed nothing reads its content, and the user — the non-coder it serves — never opens it, nor opened the richer old MANIFEST. It is retired (four docs down to three), replaced by asking Claude about the live code in-session.

The red-flags SPEC edit was made directly under the current model, since the spec-edit-batch model isn't built yet and blocking the feature behind it would be poor sequencing; the new model governs future spec edits.
