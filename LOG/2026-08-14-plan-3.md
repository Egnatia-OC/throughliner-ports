# [HASH] — An outside audit of the method's own repetition processed into fifteen items, five of its findings refused, and the `Runs alone` premise tested and refuted

Alex commissioned a redundancy audit from a Claude session with no context on this project, in her own words: find all the instances where the four skills unnecessarily repeat rules already in the always-loaded doc. It came back with seventeen findings, three inverse findings — rules repeated across skills but canonical nowhere — and an honest account of its own limits. She asked for the findings to be processed like captures. They were filed as twelve items and processed one at a time, with two adjacent items pulled in on her instruction and one blocker resolved outright.

**The audit was copied into the repository before anything was processed.** It arrived in Downloads, outside the project, where no later build could re-read it. It now sits at `resources/research/method-doc-redundancy-audit.md` with its index line, and every item cites it.

**Five of the audit's recommendations were refused, and the refusals are the substance of this session.** An outside reader can see that two passages say the same thing; it cannot see which copy is load-bearing. `done.md`'s provenance restatement was kept because it sits inside the LOG entry template at the exact moment rationale is re-authored — the named failure site of `[invented-rationale-compounds-past-the-shipped-rule]`, which records the rule being broken with the rule loaded. Deleting the one copy positioned at the failure would have been the worst move available. `next.md`'s flavor table was kept because its rows are the routing map, which exists nowhere else, and the audit's own stated exclusion covers it. `plan.md`'s "never build" clause was kept because it carries a qualifier the canonical rule lacks — that work outside the quiet list is queued *whether or not it is code*, which is what stops a planning session editing a doc on the grounds that prose is not building. `done.md`'s user-runnable table was kept because it is the routing half of a retirement notice, not a rule statement. And the audit's fix for `next.md`'s scope paragraph could not be applied as written: deleting the definition leaves the contrast two sentences later with only one of its two layers named.

**Two findings turned out to be understated and one overstated.** The capability check is not merely stated three times — two of the three tell the *same* anecdote about a diligent search for the wrong question, a hundred lines apart. Against that, the red-flag lifecycle's five copies reduce to two genuine cuts: `plan.md`'s keep-step and `next.md`'s halt are the sites where clearing happens and where the backstop fires, which is application rather than repetition.

**The three sub-docs the audit never saw were checked and came back clean**, which cuts against its own expectation that more duplication sat at those boundaries. `done-build.md`, `done-plan.md` and `done-audit.md` point at `done.md` rather than restating it.

**The two inverse findings went opposite ways under the rule gate, and that is the useful result.** The one-narration bundling rule ships as an *amendment* — a subordinate unit of the always-loaded message-shape rule, which already carries three such units — so it spends no slot, and the audit's whole argument for accepting an over-scoped rule evaporates: the parent already fires in all four skills. Its suggested inline `/setup` exception was refused, because restatement loses nothing and an exception is admissible only where restatement was attempted and lost content. The never-ask-whether-a-`[user]`-item-is-done rule ships *freestanding* and does spend a slot, since no parent shares its subject; consolidating in place lost on the distribution test, because /plan and /done never open the doc that currently owns it. Its six copies are all prohibitions — never ask, not leading, not trailing, not as a light aside — which is the gate's own signal that the action was never specified, and repeating a prohibition harder is what produced four copies in one file.

**The `Runs alone` premise was tested rather than queued, and it is false.** A throwaway repository, a folder rename half-landed, recovery attempted from both states: uncommitted, `git reset` then `git checkout -- .` restored the tracked tree exactly with one untracked directory left over that `git status` names; committed, `git revert` restored it exactly. The stated justification — that a half-landed rename leaves paths pointing at a folder that no longer exists, so finish it or do not start it — claims unrecoverability, and git recovers it in both states with one command. The marker is **not** repealed: it survives on the hazard the capture itself flagged, that a run in flight holds file paths in its working file and scope-lock list and a rename underneath it makes those stale. So the marker is right and its reason was wrong, which is the outcome the capture said to watch for, and the same shape as `[chip-replies-are-indistinguishable-from-user-authorship]` — a sentence quoted forward since `5234ec8` without anyone testing it. That resolution unblocked `[runs-alone-missing-from-line-format]`, which had been held for exactly this reason.

**The spec-sync gate then caught SPEC carrying the same refuted sentence** and it was corrected in this commit rather than deferred, because a false SPEC sentence is a defect fixed when noticed. SPEC and `plan.md` are briefly out of step, with SPEC holding the correct reason; the queued item says so, so the build does not redo it.

**This session's own conduct answered a queued item about the rule gate.** `[rule-gate-has-no-site-in-next]` asked /plan to weigh whether a per-item disposition at the build's tick is worth having, or whether claiming a fix that cannot refuse is over-claiming. Run about a dozen times here at design time, before anything was built, the gate refused repeatedly and substantively — one promotion turned into a free amendment, one exception rejected against the source audit's explicit recommendation, three proposed evictions refused on recorded grounds. So the gate does not need a stronger site inside the build; it needs its site at /plan's keep-step, where refusing costs a conversation instead of undoing finished work. /plan composes the disposition, /next transcribes it. One correction fell out: `CLAUDE.md` says the disposition goes into the build working file, and a planning session has none, so today's went into the queue items — which is the better home, since the item is what /next reads.

**`[no-field-for-ordering-preference]` demanded a fresh case or deletion, and the fresh case argued against its own remedy.** The audit item needed to run after a *set* of eight builds, and `Blocked by:` names one slug. Carrying that by placement plus one sentence of prose worked, survives a reorder, and costs almost nothing when violated. What the case exposes is that both instances share a cause that is not a missing field: `Blocked by:` gets reached for to express ordering, and it pushes an item below the line where the user cannot see it — which is what cost the Understudy project two designed items and their user's confidence that a feature was queued at all. Rescoped from a new field to a convention.

**Two failures of this session's own, both captured rather than narrated away.** The INBOX message went unopened through the entire /plan opening and was found only because the close lists the mailbox — in the project that authors the rule, with the rule loaded, and the message reported a defect in `plan.md`'s end-of-queue gate that this session then reproduced twice before reading it. And `plan.md`'s printed command for the queue mover omits the section argument the script requires, so it fails when run exactly as written, at a step every /plan opening runs.
