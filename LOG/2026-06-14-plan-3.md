# 34bf6b3 — Four top-of-queue fixes (deferred-test wall, parallel sessions, rezip/push split, visible drift) + scaffolding-resync reframed

A planning session that turned a confusing, overwhelming stretch of the queue into four concrete, plain-language fixes aimed at real friction, and corrected two mis-framings along the way.

**Deferred-test wall:** the /next pre-flight re-presents every pending deferred test (8 entries, none confirmable at that moment), which burns context and sits between the user and the batch she came to run. The deletion was already decided inside [deferred-test-lifecycle] but sat far down the queue. Carved it into a minimal top-of-queue batch [delete-preflight-deferred-tests] and trimmed [deferred-test-lifecycle] so the two don't both delete the step. Accepted trade-off: deferred tests stay recorded in QUEUE.md but aren't actively surfaced until [deferred-test-lifecycle]'s /plan-rolling ships — they aren't lost (/plan reads QUEUE.md), and nothing acted on them at pre-flight anyway.

**Parallel sessions:** the user had repeatedly been refused when trying to run a /plan chat and a /next build chat at once, and told it was off the table. It never was — "one build at a time" bans a second build (the _build.md collision), not a planning session alongside a build, and "don't cross plan and next" is about mixing modes within one session. The block was a misread. [allow-parallel-sessions] states plainly that parallel sessions are allowed, sharpens the rule wording, fixes the session-start active-build message, and records the one real precaution (don't let two chats write QUEUE.md or commit at the same instant).

**Rezip vs push:** the push-and-rezip ritual welds building the testable zip to publishing it, so the user had been deferring rezip because she wasn't ready to push — denying herself a private test build. [decouple-rezip-from-push] (this project's CLAUDE.md only, host-side workflow) splits them: rezip = light local build, no version bump, no push; push = the full release. The version bump stays at push, because bumping on every test build would make her own projects nag "re-run /setup" each time.

**Drift visibility:** investigation found the version-mismatch warning is only ~11 days old (added 2026-06-03) and is Claude-facing context, not a user-visible alert — so the user never saw it, and both this project and the Taskflowapp consumer project silently drifted, each missing .si-version. The old [scaffolding-resync] framing was wrong: the gap is general, not self-hosting. [make-drift-visible] fixes the real problem — detect drift by missing files/folders rather than version-number difference (killing the every-push false alarm), and surface it as a message the user actually reads, with an offer to catch up. [scaffolding-resync] was shrunk to just its leftover (content-level drift), with the wrong framing dropped and the reasoning recorded.
