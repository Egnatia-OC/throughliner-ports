# [HASH] — Walkthroughs name where each stored text lives, and verification steps list their claims

Two clauses on the existing walkthrough requirement, both from the same root: a
step that reads clearly to its author can be unfollowable to the person driving it.

**Where a walkthrough involves more than one stored text** — a pinned message, a
forum post, a register line — it names where each one lives. "Update the text" is
followable with one text and ambiguous with two, and the author never notices
because they know which they meant.

**Where a step verifies something, it lists the claims it checks**, so the user
knows what a pass actually covered rather than only that it passed. A verification
whose scope is unstated invites the reader to assume it covered everything.

Both are written as subordinate units of the parent requirement — each reads as a
continuation of its opening words, so neither spends a rule slot. `plan.md` needed
no change: it applies the requirement by reference rather than restating it, which
is what keeps the two sites from drifting.

**A separate verification-step rule was refused on the item**: it is the existing
name-the-thing-to-look-for requirement applied to one kind of step, so it amends
rather than stands free.

**Files touched:** `plugin/throughliner/docs/skill-nonspecific-rules.md`.

**Routed to Captures:** none.

**The first clause proved itself within the hour.** The test-rezips item walked
later in this run involves exactly two stored texts — a channel pin and every
future build entry — and naming which was which was the first thing that step
needed.
