# [HASH] — Three SPEC-maintenance rules ship, derived from the self-authoring gate, with its ceiling deliberately refused

The user's question, and she drew the host/target line herself: might SPEC benefit from some of the method's self-authoring rules — not for this project, but *shipped*, so that a real external project carries built-in SPEC-maintenance rules. The analysis was Claude's.

The structural analogy holds. `resources/self-authoring-rules.md` exists because the always-loaded rule corpus grew monotonically — every session could add, nothing ever removed, nobody counted until it was far too large. SPEC has the identical growth shape: every user-facing change adds a paragraph under the sync gate, nothing evicts, and no measure exists. It is read at every planning session and at every build run, so its cost is paid more often than the rule corpus's. A consumer is worse off than this project: their SPEC grows as their app grows, and nothing will ever tell them.

**Three of the gate's four parts transfer, and the fourth was refused — which is the decision worth recording.** Admission transfers: "does this sentence belong in SPEC, or downstream?" The rationale split transfers directly: SPEC carries a lot of why-we-chose-this prose that is session-record material. Staleness transfers: a SPEC sentence describing a retired mechanism is the same defect as a live rule naming a retired term.

**The ceiling does not, and shipping it would have been a mistake.** The instruction-count figure exists because a model follows only so many *instructions* reliably. SPEC is reference, read for content rather than followed as instruction, so the compliance argument behind the number is simply absent and only token cost carries over. More decisively, **SPEC has a floor the rule corpus does not have**: it must describe the product as it actually is, so it cannot be compressed past that without becoming false. A rule can always be evicted; a true sentence about a live feature cannot. So the derived rule set is deliberately smaller than its parent, which is the eviction-shaped half of this work.

**No growth measure ships either**, refused on this project's own evidence: the rule-lifecycle board's two report entries both lost their trigger when the ceiling was removed and now measure without ever firing — a number with no threshold is read once and skipped. There is also a practical wall, since the board runs off a script that is not in the plugin package. Staleness replaces it and is the better check anyway: a SPEC sentence describing a mechanism the app no longer has is actionable the moment it is pointed at, with no threshold needed.

**The correction the capture did not anticipate: SPEC is edited at two sites, not one.** Planning edits it when a decision changes it; a build that discovers it needs a SPEC change asks, adds SPEC.md to its file list, and edits inline. Authored only in plan.md, a build editing SPEC would never see these rules — the half-wired failure this project already records from the retired spec-edit batch type. So they are authored once in plan.md's existing SPEC ground rule, and next-build.md gains a pointer to them **by name, never a second copy**, so the two cannot drift.

**The admission rule cites existing research rather than asserting itself.** The user's point was that defining what belongs in SPEC requires knowing what a SPEC is *for*, which is also what this project's own gate demands: a declared limit states what it was derived from. An earlier version of this item queued that research into the build, which was wrong twice over — planning resolves research within its reach rather than capturing it, and the research already existed. `resources/research/spec-document-standards.md` is the derivation: spec-driven-development guidance is consistent that implementation detail belongs downstream of the spec, the constitution/spec split is already present here as CLAUDE.md versus SPEC.md, and it observes directly that large stretches of this project's own SPEC describe hook internals and version history rather than product truth.

Rule gate: run — admitted. Parent named: plan.md's existing SPEC ground rule, which all three are written as subordinate clauses of, so no slot is spent. Fetched rather than always-loaded, per the distribution test — the trigger is someone editing SPEC, which is visible. Not hookable: "does this sentence belong in SPEC" is judgment.
