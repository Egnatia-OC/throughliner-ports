The session opened with nothing above the readiness line and 48 unprocessed items, so `/next` had nothing it could build. It closes with five cleared items and a priority order the user approved.

The reprioritisation turned on one distinction the method already makes and nobody had applied to this queue: which risk is *actively spreading*. Only [history-rewrite-third-party-scrub] is — a third party's circumstances and the user's email are readable in a public repo now, and the exposure grows while it waits. Everything else is a risk sitting still in a design. It was deliberately **not** lifted above the line: it force-pushes a rewrite of the whole history and needs the user present, so clearing it would make it reachable by an unattended run. Its `Blocked by:` line was removed (that item shipped) and replaced with a lift-condition saying exactly that.

That item grew twice. The user asked where their pre-June logging had gone, and it was located in the disconnected tag history: 142 files under `_method/build-log/` at tag `v157`, the project's whole May 2026 record, in a folder nobody searching `LOG/` would find. That falsified the item's claim that the orphan history needed no rewrite — true of the third-party name, which was swept, but not of the email, which is on those commits like every other. Then the user asked about deleting the 135 tags cluttering the tag list. Refused, and the reasoning recorded: those tags are the only references keeping that history reachable, so deleting them is the one action that would destroy the logging just found. The alternative considered and rejected was renaming the range — it means creating 135 tags and deleting 135 tags on a public remote, which is 135 repetitions of the dangerous operation. Instead the user folded a **graft** of the two histories into the rewrite as a third strand, on the argument the item already makes for the email fix: the pass touches every commit and changes every hash anyway, so one force-push beats three.

Two documentation facts were corrected rather than assumed. `AGENTS.md` was traced to a 2026-07-24 copy of `CLAUDE.md`, edited twice since while CLAUDE.md was edited seventeen times — a Codex-side convention file whose tool was shelved four days after it was made. The FAQ work was restructured on the user's challenge — should a backfill have been preceded by an audit? It should. The audit now precedes it and must confirm that first, and also judge whether to patch or rebuild, and whether a flat 63-entry index is navigable at all. An FAQ can be accurate and still fail its reader.

The privacy thread produced the session's one consolidation. Three instances in one day — Claude writing an assessment of the user into a doc about to go public, Claude asking for account identifiers to put into a capture, and a capture draft naming the user and an email provider — all trace to one defect: `plugin-behaviour.md`'s protection is *titled* for third parties, and the title is doing the scoping. Two captures merged into [private-info-rule-scope-rewrite], which retitles the section and adds a solicitation clause and a self-disclosure clause. The solicitation half is the genuinely new mechanism: every existing protection governs writing, so by the time a write rule can fire the user has already been asked and answered.

**Red flag cleared this session** on that item — designed out by the solicitation clause, and the residual gap stated plainly rather than glossed: the fix does nothing until it ships and the host is reinstalled, so until then the user reviewing each draft is the only thing between a solicited identifier and a public commit. They were told this and chose to queue it rather than treat it as an emergency, on the grounds that no such data has actually been written.
