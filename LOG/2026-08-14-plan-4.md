## The INBOX report, and the reply that nearly could not be sent

A message from another project reported the QUEUE.md structure lint firing two false-positive flags on **every** PostToolUse invocation — every Bash call, every Edit — against the section preambles under `## Processed` and `## Unprocessed`. It was checked against the mechanism rather than taken on the report's word, and the report is right: `_check_orphaned_prose` in `post_tool_use.py` exempts any line beginning `>`, and its own docstring explains why — /setup scaffolds each preamble as a blockquote, positionally identical to a destroyed first item's stranded rationale, so form discriminates where position cannot. But `setup.md`'s scaffold writes both preambles as **plain paragraphs**. The exemption and the scaffold disagree, so every project set up by the shipped /setup trips the check forever.

It never surfaced here because this project's own QUEUE.md has no preambles at all — the section heading runs straight into the first item. The report was the only route it had.

The user chose the narrow fix (scaffold the preambles as blockquotes) over the wider one (exempt all prose above a section's first item), accepting the residual that already-adopted projects keep flagging until someone edits their file by hand. The wider fix would have repaired every project at once and stopped the check catching a genuinely destroyed first heading, which is the case it exists for.

**Answering the report exposed a second defect.** The message named its host version and build stamp but not the sending project. Identifying it took five separate checks and still did not settle: version files record the version at last /setup rather than the host actually running, so none matched; the quoted preamble text is the shipped scaffold and discriminates nothing; one project was eliminated only because it happened to have no preambles; and two then matched on every artifact readable from here. ## The strategy discussion, and the largest piece of the plan that had no queue item

The user set out her approach: dedupe and de-contradict first to cut the word count, then a final pass converting the rules to a law-prose style, after which the always-loaded self-authoring rules would make these audits unnecessary.

The sequencing is right, for a concrete reason — a restyle over a corpus holding four copies of one rule restyles it four times and gives each copy its own chance to diverge. The terminal claim does not hold, and the corpus is the evidence. **Admission and drift are different jobs.** Admission asks whether a rule should exist, worded this way, in this file, and fires when someone is writing a rule. Drift is what happens to a correctly-admitted rule afterwards, when something changes around it. No admission gate can prevent drift because the cause arrives after admission — and three items in the queue are pure drift that passed admission cleanly. Harder still, four recorded instances show correctly-worded always-loaded rules simply failing to fire, and the rule board is this experiment already run: it reported clean while five real rule defects shipped in the same session.

What the strategy genuinely buys is a change in **cost**, not necessity. So the goal was reframed: not eliminate the audits, but make them cheap enough to run routinely. The design test that follows is that **a mechanical check retires an audit class and a prose rule never does** — two of the five finish conditions turned out to be checkable by a script the project already owns.

Assembling the inventory of remaining work found that **the law-prose restyle — the terminal step of the entire plan — had no queue item anywhere.** Grepping QUEUE.md, SPEC.md, CLAUDE.md and `resources/` returned only the sentence recording the strategy, written an hour earlier in this same session. It existed solely in conversation, which is precisely the failure the method's own rule names.

The inventory item itself was deleted rather than kept: its only output would have been queue items, which is the shape `[research-packaged-as-build-work]` warns about, and planning work belongs in planning. It was resolved in-session instead. **Twenty-two items in five groups, plus the restyle**, with five stated finish conditions — recorded below so the deletion loses nothing.

## The output style: removed, after being asked whether it is even read

The user said she had never heard of the output style and did not know whether Claude reads it. She decided it goes.

The comparison was run at processing rather than deferred. Five rules are duplicated and die with the file. Three are unique and must migrate: the **speaking-cadence** rule (how often to speak, and the three occasions that warrant it — the always-loaded doc has only a weaker per-step clause), the **written-file-length** rule (nothing always-loaded reaches files at all), and the **counterweight** that length is free where it carries substance, without which the rest reads as an instruction to be terse.

**The user then caught a real defect in that design.** Her question — shouldn't these be conditions under other rules, per the self-authoring rules? — landed on the fact that the first draft said to *word* the migrated length rule carefully so it could not be misread against the two standing rules saying the opposite. That is the explanation remedy the admission rule explicitly rejects in favour of structure. Rewritten to require naming the parent and landing it as a subordinate unit, with the two scopes carried as structure: the record is written for completeness, a deliverable is written to the task's need. If no parent can be named, the rule does not migrate at all.

This is the first time in the session the gate refused a design on the user's initiative rather than Claude's, which bears directly on `[rule-admission-has-no-independent-approver]`, filed the same session — the gate's author and approver are otherwise the same party.
