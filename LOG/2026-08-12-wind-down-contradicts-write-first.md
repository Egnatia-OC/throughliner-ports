# [HASH] — The close now writes its captures before reporting them, and the two rules that seemed to conflict turned out to answer different questions

The always-loaded write-first rule lists captures under *write it, then report*, decided by whether the previous version is recoverable without the user's help — and a capture in a git-tracked QUEUE.md plainly is. The close said the opposite in as many words: present all candidates as one numbered set of fully-drafted captures for a single approval. Which one a session followed was decided by which it read last, and skill docs are read after the always-loaded rules, so the shipped procedure quietly won over the rule that governs above it.

The resolution is that the two were never in conflict. They answer different questions on different axes. Write-first answers *show-then-wait or write-then-report*, and its test is recoverability. The bulk-approval inversion answers *one item per message or all together*, and it is an exception to the one-at-a-time sequencing rule — its own examples, alternatives the user is choosing between and an audit's findings, are both about delivery shape. Separating the axes dissolves the contradiction: write all the captures, then report them together as one numbered set. They still arrive together, and nothing waits on approval before reaching disk. The close's error was reading "deliver together" as "show for approval first."

That distinction is now stated explicitly at the inversion block in the always-loaded rules, so the conflation cannot recur, and the three closes were flipped to write-then-report.

The grep found a **third** site the item had not named. It named done.md's wind-down and done-build.md's route-findings; `done-audit.md`'s route-stragglers step carried the identical sentence — "drafted, shown and approved before it's written, so this step waits on the user". Fixing only the two named files would have left the audit close telling sessions the opposite of the other two. The user approved adding it to scope. A final grep across the plugin, SPEC and CLAUDE.md confirms no draft-show-approve site remains.

This is expected to dispose of [stop-hook-fires-on-drafted-not-filed-captures], which sits below the line naming this as its blocker: under write-first the items genuinely exist when their slugs are named, so the hook passes on the truth rather than needing an exception taught to it. Confirming that and deleting the item is /plan's call at the revisit, not a run's.
