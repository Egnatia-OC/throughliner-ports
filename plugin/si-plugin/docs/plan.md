# /plan procedure

/plan is where unprocessed work becomes processed work through discussion. No building happens here.

Claude owns sequencing — the order work sits in, what gets built first — through discussion, not silently.

## Ground rules

- Never build during /plan. Want to write code? Queue it. Nothing mechanically *stops* a planning session writing files — there is no `_build.md`, so the build scope-lock isn't engaged — but a safety hook still watches: a write to anything outside the files a planning session touches by design (QUEUE.md, SPEC.md, LOG/, and the session's own working notes) surfaces a **permission prompt** to the user before it lands. The prompt asks; it never denies. The why: during a build there is an agreed file list to enforce, so a surprise write means drift and denial is right — but in planning there is no agreed list to drift from, the user is present, and a legitimate urgent write (fixing an active exposure, tidying at the user's request) is authorised in one word. Declining is a normal answer: the alternative is to capture the change as a work item and build it properly through /next. The prompt's job is visibility, not containment — a planning session should not be *stopped* from an urgent edit, it should be unable to make one unremarked; an approved out-of-shape write gets named in the session's LOG entry so the departure is on the record (done.md).
- One item at a time. Finish one before presenting the next.
- Read SPEC.md before proposing work. Don't queue contradictions.
- Process the accumulated unprocessed work before new planning work.
- Never write to QUEUE.md without showing the exact text first — and the rule keys to the write, not to where you are in the loop: the message immediately before any QUEUE.md write must contain the text verbatim. Approval attaches to shown text, never to a described shape, so a recommendation — however concrete — is not a draft, and "I'll add a line that does X" is not the entry. The reason: loop beats live in conversation memory and a compacted session loses them, but the write action is always visible, so keying the rule to the action holds even with no memory of which beat you're on.
- A recommendation is not a decision. A draft is not a written line. Both need the user's call.
- SPEC is a normal doc. When a planning decision changes what SPEC says — a new capability, a scope change, a reworded rule (the test is whether any SPEC sentence goes wrong) — edit SPEC in that same /plan session, with the user present and approving. Don't defer it. (A SPEC change a build discovers it needs is handled in the build, per next-build.md; a large SPEC rework is its own piece of work that names SPEC.md among its files.) The why: spec-driven development's contract is that any change altering behaviour updates the spec in the same commit (resources/research/spec-driven-development-edit-workflow.md). The /plan-close spec-sync gate (done-plan.md) enforces that atomicity — a session can't close with SPEC left behind the decision that changed it. When a change touches no SPEC sentence, none of this applies.
- /plan resolves what it can in-session; capture is only for what it can't. Research, queue-wide cleanup (line-ref drift, quoted-string staleness after a sweep), cross-item reconciliation, doc verification — anything within /plan's reach — gets done now, not filed for a later session. Reserve a capture for what /plan genuinely can't resolve this session: it needs data the session doesn't have, needs design discussion across sessions, needs user input not yet available, or surfaces a structural question whose answer would gate the work. This is a default, not an absolute — the test is "can /plan resolve this with what it has right now."

## Capture and processing discipline

The control rule for capturing and processing work, in one place. Pieces also appear in the steps and in plugin-behaviour.md; the canonical statement is here.

- **Two sections, one move between them.** QUEUE.md holds **Unprocessed** work (captured, not yet fully processed) and **Processed** work (discussed, agreed, ready to build). The only move is Unprocessed → Processed, made in /plan by discussing an item with the user and agreeing to keep it. There's no third state and no parking: an item is unprocessed, processed, or deleted. See plugin-behaviour.md Captures.
- **A work item carries a user-credit only when the user raised it.** Provenance is asymmetric and default-AI: an unmarked item is assumed to come from the AI (no AI-authorship label is ever written), and a `captured by you` credit is added only when the user personally raised, pushed through, or wrote the item — it stays on the item after processing. It's a convention, not a lint-enforced field. See plugin-behaviour.md Captures for the full line format (one-line description, prose rationale, slug, optional user-credit).
- **Who does the work, and how.** Work is Claude's to build by default. Mark an item `[user]` (a leading tag) only when it's work Claude genuinely *cannot* perform or witness — a check that needs the user's eyes, a decision only they can make, a physical action like tapping *send* or connecting a device. Work Claude can run itself — a terminal command, an install — stays Claude-work even when it's blocked on a push or restart; that's an ordering concern (shelve it below the cleared-to-run line with a lift-condition), not a `[user]` flavor. And a `[user]` item must carry a *described* walkthrough — the concrete steps the user will be walked through — settled at the keep-step below. /next builds the cleared Claude-work top-down, then walks the user through the `[user]` items. Claude-work also carries a flavor, settled here: an unmarked item is a build (the default), and `[audit]` is a review pass that reports findings instead of editing files. The flavor is a leading tag too; /next routes each item to its flavor's procedure. See plugin-behaviour.md Captures (Flavor marker) for the full tag set and the matched `[user]` rules (don't over-tag / don't under-file, plus the walkthrough rule).
- **Filing is any session; processing is /plan's.** Any session can append a capture to Unprocessed. Moving an item into Processed or deleting it — deciding its fate — happens only in /plan, because that decision is the user's (plugin-behaviour.md Routing and discipline, filing vs processing).
- **A surfaced risk is kept as a work item only once its flag is cleared.** When a kept item is a data-exposure, privacy, or breach risk Claude surfaced, its processed item carries a `Red flag · State:` marker (cleared / uncleared). Clearing that flag is part of processing it: **cleared** once the risk is designed out in-session or the user is told it plainly and chooses to proceed (the LOG records which). An item reaches Processed only with its flag cleared — a risk that can't be cleared stays a capture and returns to the bottom of Unprocessed, never a red-flagged item sitting **uncleared** in Processed. See plugin-behaviour.md Red flags.

## Step 1: Read state and entry question

Read QUEUE.md (both the Processed and Unprocessed sections) and SPEC.md. Check whether Unprocessed has items.

**Read the forward-recommendation advisory.** [SILENT when absent; BRIEF when present] If the top of Unprocessed holds a forward-recommendation advisory (a "Last session advises…" line filed by the previous /done — see plugin-behaviour.md Forward-recommendation advisory), read it and let it orient *where the session starts* — which item to look at first. It never narrows the session to only the advised item: Step 2 still processes the full Unprocessed queue regardless of what the advisory names. Surface it in one line — e.g. "Last session recommends starting with [slug]." The advisory is orientation, not a command: this session's own read may see things differently. Reading it here is the whole of Step 1's job with it — the **clear** happens at the /done close (done-plan.md), not at the end of this discussion, so it can't be skipped when a /plan ends via an off-ramp. This session's /done deletes the advisory once it has oriented the session, honouring any explicit persist-condition it carries.

**No completion sweep for `[user]` work** [SILENT]. /plan never asks whether Processed's `[user]` items are already done — that ask is gone from the method entirely, in every position it used to occupy, and so is the completion-mode setting that used to toggle it (a `Completion mode:` line in a project's CLAUDE.md is a leftover; ignore it silently — plugin-behaviour.md, "There is no completion ask"). The why: a recurring sweep reads as "why haven't you done these?" and nudges against the walk-it-through-in-/next workflow the method coaches, and any surviving ask-position becomes the place that pressure re-enters. Completion is inferred, never asked: if the user *mentions* having done one, close it at this session's /done through done.md's Completed `[user]`-item close (done-plan.md points there) — log under its slug, remove from Processed. Otherwise leave the items alone and say nothing about them. An item completed invisibly between sessions sits in Processed until the user mentions it; that gap is deliberate, and mentioning it is already a supported path.

**Below-the-line revisit** [SILENT when nothing lifts; BRIEF when proposing a lift; PROMPT only for the user-only batch]. Readiness is set once when an item is processed and, without this, never revisited — so an item correctly shelved *below* the `--- Cleared to run above this line ---` marker (because it waited on something outside the queue) depends on the user remembering to come back to it. Walk the below-line items in Processed; for each, read the **lift-condition** its prose records (what specific event or dependency must clear — Step 3 records this when placing an item below the marker) and classify:

- **Mechanically checkable** (a dependency slug built and verified per LOG, a push done, a file now present) → check it silently. If it has cleared, propose lifting the item above the marker (the lift itself is the /done close's marker placement — done-plan.md — narrated not asked).
- **User-only** (an external event only the user knows — a restart happened, a device was set up) → don't ask per item. Gather every user-only lift-condition across all below-line items into **one consolidated question**, asked once this session. Per-item asking is the nagging this revisit exists to avoid.
- **Provably still-waiting** (a dependency still unbuilt per LOG) → skip silently; nothing to propose.

Fold all of this — the mechanically-cleared proposals and the single user-only question — into the same Step-1 opening narration as the advisory-consume above, per plugin-behaviour.md "Consolidate the scans at a skill opening." An item with no recorded lift-condition can't be classified without nagging — treat that as a gap to note, and rely on the /done close recording the condition going forward (done-plan.md).

**Seed the queue from SPEC** [BRIEF, PROMPT — offer only in the trigger state; otherwise SILENT]. A rich SPEC describes buildable features that may have no path into the queue — the whole feature set "dies in SPEC" with nothing to build it (observed live in a Verso /plan: a full Gmail-client SPEC, an empty Processed, and only an ad-hoc save when Claude happened to notice). This step drains that gap, and it lives here in /plan — never in /setup, which stays scaffolding + interview and never auto-spawns work.

- **Narrow auto-trigger.** Offer to seed *only* in the thin-queue/rich-SPEC state: Processed is empty or near-empty **and** SPEC describes real features that aren't built yet (check LOG/index.md so already-built features don't count as unbuilt). This is the state that actually bit in Verso. Deliberately do **not** fire whenever SPEC merely outruns the queue — that would mean diffing the whole SPEC against the whole queue + LOG every session, the staleness-and-cost trap the method fights. Outside the trigger state, say nothing about seeding.
- **Manual invoke, any time.** The user can ask to "seed the queue from SPEC" whenever they want, independent of the auto-trigger. Same mechanism, user-initiated.
- **User owns granularity.** On either entry, ask whether to derive **coarse milestones** (a few big chunks) or **granular per-feature items** — the user's call, not Claude's.
- **Output goes to Unprocessed, never Processed.** Read SPEC, draft the derived items as ordinary captures (unmarked — AI is the default author, so no user-credit), show them for approval per plugin-behaviour.md Captures, and on approval append them to Unprocessed. Seeding fills the backlog for later processing — it never greenlights a build. The derived items then flow through the normal Step 2 processing loop like any other capture.

When Processed already holds real work, this step is silent — a well-fed queue needs no seeding.

Ask [PROMPT]: "Anything to discuss before we go through the unprocessed work?" (If Unprocessed is empty, ask what they'd like to work on.)

**If the user has something to discuss:** Handle it via the Step 2 loop — present, interview, recommend, wait, execute. Then ask [PROMPT]: "Anything else before we go through the queue?" Repeat until there's nothing more.

**Then process the unprocessed work:** Move to Step 2. Going through the unprocessed work is where every /plan session goes — a discussion item is just an optional first stop, never an alternative to it.

## Step 2: Process work [SEQUENCE]

**Planning state file: _plan.md.** When processing begins, create `_plan.md` to hold this session's planning state: the item list, the current item, and the beat reached. Update it at each beat transition, and append each item with its disposition — kept (moved to Processed), deleted, or skipped-this-session (moved to the bottom of Unprocessed, not to be re-presented this session), with slug. One line per item, so updates stay cheap. The skipped-slug record is what stops a skipped item re-surfacing later in the same session. The reason it exists: the file survives compaction, gives an interrupted /plan a resume path through session start, and hands /done a mechanical record of what was decided instead of a reconstruction from memory. /done reads it at close and deletes it — same lifecycle as _build.md.

**Process order.** Go through Unprocessed top to bottom, then any items raised in this session's own discussion. State the count upfront, counting both together ("5 items. First: ..."). Position in the file is the order — an item placed next to its relatives is processed there by design, not by strict age (plugin-behaviour.md Captures placement); oldest-first is only the append fallback at filing time.

Two passes run once, before the one-at-a-time loop: a subtractive triage drop, then a reorder with a throughput floor. Both fire at the same Step 2 opening, so combine whatever they surface into the fewest messages rather than narrating each on its own (plugin-behaviour.md, "Consolidate the scans at a skill opening").

**Triage bulk-drop pass** [SEQUENCE — bulk-approval inversion]. Skim Unprocessed for items obviously not worth doing and present them as ONE bulk-approval set the user contests by number (the bulk-approval inversion in plugin-behaviour.md's [SEQUENCE] rule). This pass only ever deletes — it never moves an item into Processed. An item is bulk-droppable only when there is a one-sentence, uncontestable reason it is not worth doing: its premise no longer holds, it duplicates another item, or LOG/index.md shows it already decided. If the drop-reason needs any argument to make, the item is not bulk-droppable — leave it for the deep loop below, where it gets the same one-at-a-time treatment as everything else. Draft each drop as its reason in one line, present the numbered set for a single approval, and on approval delete the items the user didn't name to keep back; the kept-back ones flow into the deep loop. If nothing is obviously droppable, say so in one line and move on.

   The pass never keeps in bulk, only drops — sliding undesigned work into Processed unread is the exact failure this ceiling exists to prevent, so bulk-approval runs in the delete direction alone. Exemplar: "Two look droppable — 1. **[old-slug]**: its premise is gone, the feature it targeted was cut. 2. **[dupe-slug]**: duplicates **[other-slug]**. Drop both, or name any to keep?"

**Start-of-processing reorder and throughput floor** [BRIEF]. Order the surviving Unprocessed items by unblock-potential — the item whose processing would let the most other work move forward goes first — then narrate the session's shape in one line: which items lead, and a floor for how many to process. **The reorder itself is conditional and change-scoped, not a full re-derivation:** consider only what changed since last session (items newly captured, dropped, or whose relationships shifted — read the slug-references items already carry rather than re-reasoning the whole queue from zero), and if the surviving order already puts the biggest unblockers first, leave it as-is — reorder only when an item genuinely sits in the wrong place. The throughput-floor narration still fires either way; the *move* is what's skipped when the order is already right. Word the floor as a recommendation, not a cap: "Ordered to process the biggest unblockers first — recommend processing at least N before your next /next," where N is the count of unblocker items now at the top. The floor is a planning-throughput target (vet enough that /next has ready work); it is not a context-budget count — session sizing stays out of /plan (that lives in [session-sizing-and-break-lines], left unprocessed). This start-of-session reorder mirrors the Step 3 close reorder, which still runs at close for the durable next-session pick-order state.

For each item:

1. **Present and interview** [DISCUSS, PROMPT] — The item's verbatim text lands ahead of analysis. For **every item after the first**, it was already sent at the end of the prior item's checkpoint, so this beat opens directly with analysis — no re-quote, and no "my read to follow"-style pre-framing of any kind. For the **first** item there's no prior checkpoint to have carried it, so quote it at the loop's opening — the raw item leads the message, and the analysis follows in that same message. There is **no separate "ready to dig into this one?" approval turn** before the analysis: presenting the item and beginning to work it is one beat, not two — a standalone go-ahead turn before analysis is the redundant gate this collapses. (The one wait that stays is the [PROMPT] at the end of the interview, where the user's actual decision is needed.) Why the verbatim still leads: the user takes the item in more easily reading the raw text before Claude's framing, rather than digesting the whole reaction bundled — but leading-then-analysing does that within one message, without spending a turn on a content-free "shall I continue?". When quoting the first item, re-read it from QUEUE.md first to confirm the quoted text matches the file, which also catches a context-drifted quote before it's discussed (if the file differs, correct it immediately). For later items that re-read already happened at the checkpoint that presented them. Engage with the item's substance: ask follow-ups to sharpen it or surface missing context, depth scaling with the item, until the picture is clear. Close the interview: when a delete lean is already clear, close on the combined recommend-and-ask in sub-step 3's merge guidance — not a bare "anything else to add?" trailed by a separate recommend turn; when the lean isn't clear yet, close with "anything else to add?" and let sub-step 3 carry the recommendation.

   **View-in-doc: pointer instead of paste when mode is local and an editor is recorded.** The verbatim item lives in QUEUE.md already, so re-pasting it into chat spends tokens on text the user can open in their own editor — but only if they're at the desktop. Check the render conditions per plugin-behaviour.md Working mode and view-in-doc rendering: the item is doc-resident (it already exists in QUEUE.md), so it's pointer-eligible when the `Working mode:` field is `local` AND an `Editor:` field carries a real value (any value other than `not recorded` or an absent field). When both hold, lead the message with a one-line pointer that names the item and links to the doc, instead of the pasted quote — for example: `First item — **[work-slug]** — is in [QUEUE.md](QUEUE.md) under Unprocessed.` — then the analysis follows in that same message, exactly as with the inline quote; there's no separate approval turn. The confirm-against-the-file re-read still runs, in its pointer form: re-read the item from QUEUE.md to confirm it's there and the pointer resolves (there's no quoted text to drift now, so this is a resolves-check, not a text-match — the read-back half of plugin-behaviour.md Working mode and view-in-doc rendering, since the item already exists in the doc). When mode is remote, or no editor is recorded, keep the verbatim inline quote exactly as above — the pointer is the token-saving path, the inline quote the safe default.

2. **Recommend** [PROMPT] — Recommend a route — **keep** (move the item into Processed) or **delete** — and say why:
   - **Keep** — the work is worth doing. The recommendation must describe what would actually get built, in terms the user can recognize as the work product (which files change, what gets added, removed, or rewritten — not just the topic or intent). Forcing function: if sub-step 1's interview hasn't yielded enough to describe the work concretely, the recommendation isn't ready — return to interviewing. Part of keeping is settling who does it and how: Claude-work by default, or `[user]` if it's the user's to run; and for Claude-work, its flavor — an unmarked build (the default), or `[audit]` for a review pass (mark the flavor as a leading tag on the item; see plugin-behaviour.md Captures, Flavor marker). Claude places the item in Processed by relationship judgment — beside a relative when it revises or builds on existing work, oldest-first otherwise — and reports where it went; a user-work item goes where the user agrees.
   - **Delete** — remove it. If it was already decided (check LOG/index.md), state the prior decision and commit.
   Stop and wait. The user decides.

   **Fold the recommend into the action when the user already agreed during the interview.** When present-and-interview already secured the user's explicit agreement to a specific route — Claude gave its lean and the user said to go with it — skip this standalone recommend-and-wait and go straight to the action in sub-step 3, naming the route in one line ("going with keep — drafting the item now"). This fold is scoped to **keep** only: keep is followed by the draft-approval step, which the user still owns, so folding loses no decision — the draft is the safety net. **Delete** can't fold to the action — it's terminal, with no later approval step to re-confirm it, so the user's explicit approval is still required before execution. But that approval doesn't need its own separate turn: when the lean is already clear it merges into the interview-closing turn (next paragraph).

   **Merge a clear delete recommend into the interview-closing turn.** When a delete lean is already clear by the end of the interview exposition, don't close with a bare "anything else to add?" and then re-state the recommendation in a separate turn — that names the route twice with a content-free exchange between. Instead, close the exposition on one combined, bold ask that carries the recommendation: "…my recommendation is to drop this; anything you'd change, or shall I delete it?" The user pushes back or approves in a single reply, and that reply is the terminal approval delete requires — so merging loses no decision, it only drops the empty middle turn. The standalone recommend-and-wait above stays the path when the lean genuinely isn't clear yet. Keep is unchanged: it folds to its draft, and the draft-approval remains its safety net.

3. **Execute keep or delete:**
   - **Keep** [DISCUSS, PROMPT] — Draft the processed item: its one-line description (with the slug at the end, and `[user]` if it's user-work), and the prose rationale under it carrying the discussion's reasoning as inline prose — see Why-pipeline in plugin-behaviour.md. **When the item is `[user]`, apply the `[user]` rules now** (plugin-behaviour.md Captures, Flavor marker): first, confirm it's genuinely user-only — work Claude *can* run but can't run *yet* (blocked on a push or restart) is Claude-work shelved below the line, not a `[user]` walk-through (the over-tag guard); and conversely, **don't under-file** — genuine user work must become a `[user]` work item, never left as a live chat question or a "you'd do that yourself" aside (the under-file guard, whose failure mode is user-work evaporation). Second, draft the walkthrough into the item's prose — the concrete steps the user will be walked through, so /next's walk-through can lead with them. **Not being able to script every step yet is not a reason to withhold the line:** file it with a *rough* walkthrough and sharpen it here at the keep-step, rather than deferring the whole line to prose or a question. The only thing that keeps work out of a `[user]` work item is genuine uncertainty it's user-work at all — which routes to Unprocessed as an ordinary capture to weigh, still tracked.

     **Decompose a mixed Claude-prep + user-step item.** When an item bundles work Claude can do with an irreducible user action — Claude prepares something, then the user has to run or witness the final step — don't keep it as one `[user]` item with Claude-work buried inside (which would either mis-tag runnable work as the user's, or hide a build inside a walk-through). Split it: file the Claude-doable parts as build item(s), and a single `[user]` work item reduced to only the irreducible user action, cross-referenced by slug. The `[user]` work item should name the one thing only the user can do, nothing Claude could have built. This is the same forcing function as splitting out a buried user-only prerequisite (below), applied to the whole item at the keep-step. Show the draft as a blockquote with a content-type lead-in (**Work item:**), per the approval-time outputs rule in plugin-behaviour.md. Don't write to QUEUE.md until approved. On approval, make the move so the item is never visible in both sections at once: **remove it from Unprocessed first, then add the drafted item to the Processed section** at the placement Claude reported — issue both writes in the same turn. The order matters: adding to Processed before removing from Unprocessed leaves a window where the item shows in *both* sections, and a glance during that window reads as a lingering duplicate that didn't get cleaned up. Removing from the source section first closes that window — the item is briefly in neither section rather than in both, which reads correctly as a move in progress, not a duplicate. It's safe to remove first because the drafted Processed item is already approved and on screen, so nothing is lost if something interrupts between the two writes; and the write-then-verify re-read below confirms the item actually landed in Processed. If the raw capture had no slug, give it one now. The item is written this turn, so if you confirm the move with a pointer (mode local and editor recorded), follow the write-then-verify-then-point ordering (plugin-behaviour.md Working mode and view-in-doc rendering): report "moved to Processed as [slug]" only after the Write returned success and a re-read confirms the item is in Processed and gone from Unprocessed.

     **Split out a buried user-only prerequisite before keeping.** As part of keeping an item, scan its rationale for a gating action that is (a) user-only — a step only the user can run — and (b) gates this item or other work. When one is found buried in the prose, don't leave it embedded: split it into its own `[user]` work item (its own slug) and reference that slug from the original item's prose, rather than the gate living only as a sentence inside a larger item. The why: a concrete gating action left embedded is invisible as next-work — its next-ness survives only in whoever's memory read the prose, the exact "next-ness lives in memory" failure the `[user]`-line mechanism fights (observed live in a consumer project, where an approval only a third party could give gated the whole tool but lived only as rationale prose). This fires at a different moment than the mid-session user-only-discovery rule (plugin-behaviour.md Routing and discipline): that files *new* discoveries as `[user]` work items; this reviews an item's *existing prose at the keep-step* and lifts a buried gate out into its own trackable line.
   - **Keep a surfaced risk with a red-flag marker** [DISCUSS, PROMPT] — When the item being kept is a security, privacy, or breach risk Claude surfaced (plugin-behaviour.md Red flags), the processed item gets one extra marker line under its description: `Red flag · State: <cleared | uncleared>`. Processing the risk *means* clearing it: set the state to **cleared** once this session designs it out (record how in the rationale) or the user is told the risk plainly and chooses to proceed (record the informed consent — what they were warned about and that they chose to go ahead — which /done writes into the LOG at close). An item only moves into Processed with its flag **cleared**; if the risk can't be cleared this session, don't keep it — leave it as a capture and return it to the bottom of Unprocessed (plugin-behaviour.md Flag states). Draft and approve the item exactly as a normal keep.
   - **Delete** — Remove the item from Unprocessed. **Relocate before removing when the content belongs elsewhere.** Delete means "not worth doing," so routing a fold through a plain delete risks dropping content the user wanted kept. When the item's content belongs in another home — a SPEC sentence, a LOG entry, or another work item's rationale — relocate that content first: edit the target with the user's approval, then remove the standalone item once the content is safely moved. This is a judgment call, not a new disposition — the item is still deleted, just after its worth-keeping content has been carried to where it belongs.

4. **Checkpoint** [PROMPT] — After every item, present the next item and then close on the off-ramps as the message's final, bold ask. Order within the message: when a next item is queued, lead with that item's verbatim text — the item only, no analysis — re-read from QUEUE.md first to confirm the quote matches the file (the confirm-against-the-file re-read lives here, not in the next item's present-and-interview beat); then, below the verbatim, put the off-ramps as the closing bold question — continue to the next item, skip this next one to the bottom for a later session, close out now (go to Step 4), or raise something else (loop back into Step 2 with the new item). All four must be genuinely on offer; deliver them conversationally rather than as a fixed form, but they land below the verbatim, not above it.

   **Skip-to-defer.** The skip off-ramp is folded into this one ask on purpose — a separate "dig into this one, or skip it?" gate before every item would re-create the over-asking the method just removed, so skipping is one option among the checkpoint's four, never its own turn. On skip: move that next item to the bottom of Unprocessed **through the mechanical mover, not by hand** — run `python plugin/si-plugin/scripts/reorder_queue.py QUEUE.md Unprocessed --move <slug> BOTTOM`, which relocates the item's whole prose block byte-for-byte (the item's text is unchanged by a skip, so hand-retyping it via Edit is pure corruption exposure — the same risk done-plan.md's close reorder routes through this script). Then record its slug in _plan.md as skipped-this-session, and don't re-present it this session — present the item after it instead. A skipped item is not deleted and not processed; it simply waits for a later /plan. **The skipped-this-session record is the _plan.md slug and nothing else** — there is no durable queue marker for a deferred item, no "parked" or "dedicated-pass" tag written to QUEUE.md; next session the item is ordinary Unprocessed again, picked up by whatever /plan reaches it. Skipping the last remaining item leaves Unprocessed non-empty, which is fine — the session can still close from the off-ramps. The verbatim is shown, then the ask hands the decision back — putting the ask last gives the message a proper landing instead of ending on a raw quote that reads as Claude stopping mid-thought. Why the verbatim still leads rather than the analysis: it lands the next item this turn so the user reads it before deciding, and when they continue, the next turn opens directly with analysis — the turn boundary is the separator. **Process-now offer after a user-filed capture** [PROMPT]. When the user files a fresh capture mid-/plan — a new idea or task they want recorded, raised through the checkpoint's "raise something else" or at any point in the session — don't close on a bare "anything else?" **Wind-down re-scan** [DISCUSS, PROMPT] — After every item is processed and before recommending /done (the Step 4 close-out), re-read this session's own discussion and surface candidate captures: things the user thought out loud but never explicitly flagged. The why: this is a best-effort safety net behind the capture-at-the-moment-of-noticing rule, memory-dependent so degraded after compaction. A non-coder who thinks out loud generates capturable material they never explicitly flag, so the re-scan catches what the moment-of-noticing rule outran. The find-then-file flow here is planning work, and /plan is the only skill that processes work and has the most free-form discussion — so /plan owns the full re-scan: it both files the surfaced captures and can carry them into processing. What stays /plan-only is *processing* the surfaced captures — keep / delete — which is the planning the no-planning-in-execution rule protects.
