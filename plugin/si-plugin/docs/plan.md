# /plan procedure

/plan is where unprocessed work becomes processed work through discussion. No building happens here.

Claude owns sequencing — the order work sits in, what gets built first — through discussion, not silently.

## Ground rules

- Never build during /plan. Want to write code? Queue it.
- One item at a time. Finish one before presenting the next.
- Read SPEC.md before proposing work. Don't queue contradictions.
- Process the accumulated unprocessed work before new planning work.
- Never write to QUEUE.md without showing the exact text first — and the rule keys to the write, not to where you are in the loop: the message immediately before any QUEUE.md write must contain the text verbatim. Approval attaches to shown text, never to a described shape, so a recommendation — however concrete — is not a draft, and "I'll add a line that does X" is not the entry. The reason: loop beats live in conversation memory and a compacted session loses them, but the write action is always visible, so keying the rule to the action holds even with no memory of which beat you're on.
- A recommendation is not a decision. A draft is not a written line. Both need the user's call.
- SPEC is a normal doc. When a planning decision changes what SPEC says — a new capability, a scope change, a reworded rule (the test is whether any SPEC sentence goes wrong) — edit SPEC in that same /plan session, with the user present and approving. Don't defer it. (A SPEC change a build discovers it needs is handled in the build, per next-build.md; a large SPEC rework is its own piece of work that names SPEC.md among its files.) The why: spec-driven development's contract is that any change altering behaviour updates the spec in the same commit (resources/research/spec-driven-development-edit-workflow.md). The /plan-close spec-sync gate (done-plan.md) enforces that atomicity — a session can't close with SPEC left behind the decision that changed it. When a change touches no SPEC sentence, none of this applies.
- /plan resolves what it can in-session; capture is only for what it can't. Research, queue-wide cleanup (line-ref drift, quoted-string staleness after a sweep), cross-item reconciliation, doc verification — anything within /plan's reach — gets done now, not filed for a later session. Reserve a capture for what /plan genuinely can't resolve this session: it needs data the session doesn't have, needs design discussion across sessions, needs user input not yet available, or surfaces a structural question whose answer would gate the work. This is a default, not an absolute — the test is "can /plan resolve this with what it has right now."

## Capture and processing discipline

The control rule for capturing and processing work, in one place. Pieces also appear in the steps and in plugin-behaviour.md; the canonical statement is here.

- **Two sections, one move between them.** QUEUE.md holds **Unprocessed** work (captured, not yet fully processed) and **Processed** work (discussed, agreed, ready to build). The only move is Unprocessed → Processed, made in /plan by discussing an item with the user and agreeing to keep it. There's no third state and no parking: an item is unprocessed, processed, or deleted. See plugin-behaviour.md Captures.
- **Every work item carries a provenance label.** Each item notes who raised it — "captured by you" or "by Claude" — and that label stays on the item after it's processed. See plugin-behaviour.md Captures for the full line format (one-line description, prose rationale, slug, provenance).
- **Who does the work, and how.** Work is Claude's to build by default. When an item is work only the user can do — a check that needs their eyes, a step in a tool Claude can't drive — mark it `[user]` on the item (a leading tag). /next builds Claude-work top-down and hands over at the first `[user]` item. Claude-work also carries a flavor, settled here: an unmarked item is a build (the default), and `[audit]` is a review pass that reports findings instead of editing files. The flavor is a leading tag too; /next routes each item to its flavor's procedure. See plugin-behaviour.md Captures (Flavor marker) for the full tag set.
- **Filing is any session; processing is /plan's.** Any session can append a capture to Unprocessed. Moving an item into Processed or deleting it — deciding its fate — happens only in /plan, because that decision is the user's (plugin-behaviour.md Routing and discipline, filing vs processing).
- **A surfaced risk is kept as a work item only once its flag is cleared.** When a kept item is a data-exposure, privacy, or breach risk Claude surfaced, its processed item carries a `Red flag · State:` marker (cleared / uncleared). Clearing that flag is part of processing it: **cleared** once the risk is designed out in-session or the user is told it plainly and chooses to proceed (the LOG records which). An item reaches Processed only with its flag cleared — a risk that can't be cleared stays a capture and returns to the bottom of Unprocessed, never a red-flagged item sitting **uncleared** in Processed. See plugin-behaviour.md Red flags.

## Step 1: Read state and entry question

Read QUEUE.md (both the Processed and Unprocessed sections) and SPEC.md. Check whether Unprocessed has items.

**Consume the forward-recommendation advisory.** [SILENT when absent; BRIEF when present] If the top of Unprocessed holds a forward-recommendation advisory (a "Last session advises…" line filed by the previous /done — see plugin-behaviour.md Forward-recommendation advisory), read it and let it orient *where the session starts* — which item to look at first. It never narrows the session to only the advised item: Step 2 still processes the full Unprocessed queue regardless of what the advisory names. Surface it in one line — e.g. "Last session recommends starting with [slug]." Delete the advisory from Unprocessed once the processing/build order is agreed (at the end of Step 2 or Step 3), whether the recommendation was followed or not — it has done its job. The advisory is orientation, not a command: this session's own read may see things differently.

**Completion-ask for handed-over `[user]` work** [SILENT when none in Processed; PROMPT when present]. If Processed holds any `[user]` item, it may already have been done — a past /next handed it over, the user ran it, but nothing removed it. Ask whether any such item is now complete, rather than leaving it to strand and get re-handed-over. Detection is by asking, not by scanning for a produced file (a handover can be a device check or a decision, not an artifact). For any the user confirms done, close it at this session's /done through done.md's Completed `[user]`-item close (done-plan.md points there) — log under its slug, remove from Processed. Fold this ask into the single Step-1 opening narration alongside the advisory-consume above, per plugin-behaviour.md "Consolidate the scans at a skill opening."

**Below-the-line revisit** [SILENT when nothing lifts; BRIEF when proposing a lift; PROMPT only for the user-only batch]. Readiness is set once when an item is processed and, without this, never revisited — so an item correctly shelved *below* the `--- Cleared to run above this line ---` marker (because it waited on something outside the queue) depends on the user remembering to come back to it. Walk the below-line items in Processed; for each, read the **lift-condition** its prose records (what specific event or dependency must clear — Step 3 records this when placing an item below the marker) and classify:

- **Mechanically checkable** (a dependency slug built and verified per LOG, a push done, a file now present) → check it silently. If it has cleared, propose lifting the item above the marker (the lift itself is Step 3's marker placement, narrated not asked).
- **User-only** (an external event only the user knows — a restart happened, a device was set up) → don't ask per item. Gather every user-only lift-condition across all below-line items into **one consolidated question**, asked once this session. Per-item asking is the nagging this revisit exists to avoid.
- **Provably still-waiting** (a dependency still unbuilt per LOG) → skip silently; nothing to propose.

Fold all of this — the mechanically-cleared proposals and the single user-only question — into the same Step-1 opening narration as the advisory-consume and the completion-ask above, per plugin-behaviour.md "Consolidate the scans at a skill opening." An item with no recorded lift-condition can't be classified without nagging — treat that as a gap to note, and rely on Step 3 recording the condition going forward.

Ask [PROMPT]: "Anything to discuss before we go through the unprocessed work?" (If Unprocessed is empty, ask what they'd like to work on.)

**If the user has something to discuss:** Handle it via the Step 2 loop — present, interview, recommend, wait, execute. Then ask [PROMPT]: "Anything else before we go through the queue?" Repeat until there's nothing more.

**Then process the unprocessed work:** Move to Step 2. Going through the unprocessed work is where every /plan session goes — a discussion item is just an optional first stop, never an alternative to it.

## Step 2: Process work [SEQUENCE]

**Planning state file: _plan.md.** When processing begins, create `_plan.md` to hold this session's planning state: the item list, the current item, and the beat reached. Update it at each beat transition, and append each item with its disposition — kept (moved to Processed), deleted, or skipped-this-session (moved to the bottom of Unprocessed, not to be re-presented this session), with slug. One line per item, so updates stay cheap. The skipped-slug record is what stops a skipped item re-surfacing later in the same session. The reason it exists: the file survives compaction, gives an interrupted /plan a resume path through session start, and hands /done a mechanical record of what was decided instead of a reconstruction from memory. /done reads it at close and deletes it — same lifecycle as _build.md.

**Process order.** Go through Unprocessed top to bottom, then any items raised in this session's own discussion. State the count upfront, counting both together ("5 items. First: ..."). Position in the file is the order — an item placed next to its relatives is processed there by design, not by strict age (plugin-behaviour.md Captures placement); oldest-first is only the append fallback at filing time.

Two passes run once, before the one-at-a-time loop: a subtractive triage drop, then a reorder with a throughput floor. Both fire at the same Step 2 opening, so combine whatever they surface into the fewest messages rather than narrating each on its own (plugin-behaviour.md, "Consolidate the scans at a skill opening").

**Triage bulk-drop pass** [SEQUENCE — bulk-approval inversion]. Skim Unprocessed for items obviously not worth doing and present them as ONE bulk-approval set the user contests by number (the bulk-approval inversion in plugin-behaviour.md's [SEQUENCE] rule). This pass only ever deletes — it never moves an item into Processed. An item is bulk-droppable only when there is a one-sentence, uncontestable reason it is not worth doing: its premise no longer holds, it duplicates another item, or LOG/index.md shows it already decided. If the drop-reason needs any argument to make, the item is not bulk-droppable — leave it for the deep loop below, where it gets the same one-at-a-time treatment as everything else. Draft each drop as its reason in one line, present the numbered set for a single approval, and on approval delete the items the user didn't name to keep back; the kept-back ones flow into the deep loop. If nothing is obviously droppable, say so in one line and move on.

   The pass never keeps in bulk, only drops — sliding undesigned work into Processed unread is the exact failure this ceiling exists to prevent, so bulk-approval runs in the delete direction alone. Exemplar: "Two look droppable — 1. **[old-slug]**: its premise is gone, the feature it targeted was cut. 2. **[dupe-slug]**: duplicates **[other-slug]**. Drop both, or name any to keep?"

**Start-of-processing reorder and throughput floor** [BRIEF]. Order the surviving Unprocessed items by unblock-potential — the item whose processing would let the most other work move forward goes first — then narrate the session's shape in one line: which items lead, and a floor for how many to process. Word the floor as a recommendation, not a cap: "Ordered to process the biggest unblockers first — recommend processing at least N before your next /next," where N is the count of unblocker items now at the top. The floor is a planning-throughput target (vet enough that /next has ready work); it is not a context-budget count — session sizing stays out of /plan (that lives in [session-sizing-and-break-lines], left unprocessed). This start-of-session reorder mirrors the Step 3 close reorder, which still runs at close for the durable next-session pick-order state.

For each item:

1. **Present and interview** [DISCUSS, PROMPT] — The item's verbatim text lands ahead of analysis. For **every item after the first**, it was already sent at the end of the prior item's checkpoint, so this beat opens directly with analysis — no re-quote, and no "my read to follow"-style pre-framing of any kind. For the **first** item there's no prior checkpoint to have carried it, so quote it at the loop's opening — the raw item leads the message, and the analysis follows in that same message. There is **no separate "ready to dig into this one?" approval turn** before the analysis: presenting the item and beginning to work it is one beat, not two — a standalone go-ahead turn before analysis is the redundant gate this collapses. (The one wait that stays is the [PROMPT] at the end of the interview, where the user's actual decision is needed.) Why the verbatim still leads: the user takes the item in more easily reading the raw text before Claude's framing, rather than digesting the whole reaction bundled — but leading-then-analysing does that within one message, without spending a turn on a content-free "shall I continue?". When quoting the first item, re-read it from QUEUE.md first to confirm the quoted text matches the file, which also catches a context-drifted quote before it's discussed (if the file differs, correct it immediately). For later items that re-read already happened at the checkpoint that presented them. Engage with the item's substance: ask follow-ups to sharpen it or surface missing context, depth scaling with the item, until the picture is clear. Close the interview: when a delete lean is already clear, close on the combined recommend-and-ask in sub-step 3's merge guidance — not a bare "anything else to add?" trailed by a separate recommend turn; when the lean isn't clear yet, close with "anything else to add?" and let sub-step 3 carry the recommendation.

   **View-in-doc: pointer instead of paste when mode is local and an editor is recorded.** The verbatim item lives in QUEUE.md already, so re-pasting it into chat spends tokens on text the user can open in their own editor — but only if they're at the desktop. Check the render conditions per plugin-behaviour.md Working mode and view-in-doc rendering: the item is doc-resident (it already exists in QUEUE.md), so it's pointer-eligible when the `Working mode:` field is `local` AND an `Editor:` field carries a real value (any value other than `not recorded` or an absent field). When both hold, lead the message with a one-line pointer that names the item and links to the doc, instead of the pasted quote — for example: `First item — **[work-slug]** — is in [QUEUE.md](QUEUE.md) under Unprocessed.` — then the analysis follows in that same message, exactly as with the inline quote; there's no separate approval turn. The confirm-against-the-file re-read still runs, in its pointer form: re-read the item from QUEUE.md to confirm it's there and the pointer resolves (there's no quoted text to drift now, so this is a resolves-check, not a text-match — the read-back half of plugin-behaviour.md Working mode and view-in-doc rendering, since the item already exists in the doc). When mode is remote, or no editor is recorded, keep the verbatim inline quote exactly as above — the pointer is the token-saving path, the inline quote the safe default.

2. **Recommend** [PROMPT] — Recommend a route — **keep** (move the item into Processed) or **delete** — and say why:
   - **Keep** — the work is worth doing. The recommendation must describe what would actually get built, in terms the user can recognize as the work product (which files change, what gets added, removed, or rewritten — not just the topic or intent). Forcing function: if sub-step 1's interview hasn't yielded enough to describe the work concretely, the recommendation isn't ready — return to interviewing. Part of keeping is settling who does it and how: Claude-work by default, or `[user]` if it's the user's to run; and for Claude-work, its flavor — an unmarked build (the default), or `[audit]` for a review pass (mark the flavor as a leading tag on the item; see plugin-behaviour.md Captures, Flavor marker). Claude places the item in Processed by relationship judgment — beside a relative when it revises or builds on existing work, oldest-first otherwise — and reports where it went; a user-work item goes where the user agrees.
   - **Delete** — remove it. If it was already decided (check LOG/index.md), state the prior decision and commit.
   Stop and wait. The user decides.

   **Fold the recommend into the action when the user already agreed during the interview.** When present-and-interview already secured the user's explicit agreement to a specific route — Claude gave its lean and the user said to go with it — skip this standalone recommend-and-wait and go straight to the action in sub-step 3, naming the route in one line ("going with keep — drafting the item now"). This fold is scoped to **keep** only: keep is followed by the draft-approval step, which the user still owns, so folding loses no decision — the draft is the safety net. **Delete** can't fold to the action — it's terminal, with no later approval step to re-confirm it, so the user's explicit approval is still required before execution. But that approval doesn't need its own separate turn: when the lean is already clear it merges into the interview-closing turn (next paragraph).

   **Merge a clear delete recommend into the interview-closing turn.** When a delete lean is already clear by the end of the interview exposition, don't close with a bare "anything else to add?" and then re-state the recommendation in a separate turn — that names the route twice with a content-free exchange between. Instead, close the exposition on one combined, bold ask that carries the recommendation: "…my recommendation is to drop this; anything you'd change, or shall I delete it?" The user pushes back or approves in a single reply, and that reply is the terminal approval delete requires — so merging loses no decision, it only drops the empty middle turn. The standalone recommend-and-wait above stays the path when the lean genuinely isn't clear yet. Keep is unchanged: it folds to its draft, and the draft-approval remains its safety net.

3. **Execute keep or delete:**
   - **Keep** [DISCUSS, PROMPT] — Draft the processed item: its one-line description (with the slug at the end, and `[user]` if it's user-work), and the prose rationale under it carrying the discussion's reasoning as inline prose — see Why-pipeline in plugin-behaviour.md. Show the draft as a blockquote with a content-type lead-in (**Work item:**), per the approval-time outputs rule in plugin-behaviour.md. Don't write to QUEUE.md until approved. On approval, move the item into the Processed section at the placement Claude reported, and remove it from Unprocessed. If the raw capture had no slug, give it one now. The item is written this turn, so if you confirm the move with a pointer (mode local and editor recorded), follow the write-then-verify-then-point ordering (plugin-behaviour.md Working mode and view-in-doc rendering): report "moved to Processed as [slug]" only after the Write returned success and a re-read confirms the item is in Processed and gone from Unprocessed.

     **Split out a buried user-only prerequisite before keeping.** As part of keeping an item, scan its rationale for a gating action that is (a) user-only — a step only the user can run — and (b) gates this item or other work. When one is found buried in the prose, don't leave it embedded: split it into its own `[user]` work line (its own slug) and reference that slug from the original item's prose, rather than the gate living only as a sentence inside a larger item. The why: a concrete gating action left embedded is invisible as next-work — its next-ness survives only in whoever's memory read the prose, the exact "next-ness lives in memory" failure the `[user]`-line mechanism fights (observed live in Metro-admin's leave-subproject, where a supervisor-only ask gated the whole tool but lived only as rationale prose). This fires at a different moment than the mid-session user-only-discovery rule (plugin-behaviour.md Routing and discipline): that files *new* discoveries as `[user]` lines; this reviews an item's *existing prose at the keep-step* and lifts a buried gate out into its own trackable line.
   - **Keep a surfaced risk with a red-flag marker** [DISCUSS, PROMPT] — When the item being kept is a security, privacy, or breach risk Claude surfaced (plugin-behaviour.md Red flags), the processed item gets one extra marker line under its description: `Red flag · State: <cleared | uncleared>`. Processing the risk *means* clearing it: set the state to **cleared** once this session designs it out (record how in the rationale) or the user is told the risk plainly and chooses to proceed (record the informed consent — what they were warned about and that they chose to go ahead — which /done writes into the LOG at close). An item only moves into Processed with its flag **cleared**; if the risk can't be cleared this session, don't keep it — leave it as a capture and return it to the bottom of Unprocessed (plugin-behaviour.md Flag states). Draft and approve the item exactly as a normal keep.
   - **Delete** — Remove the item from Unprocessed. **Relocate before removing when the content belongs elsewhere.** Delete means "not worth doing," so routing a fold through a plain delete risks dropping content the user wanted kept. When the item's content belongs in another home — a SPEC sentence, a LOG entry, or another work item's rationale — relocate that content first: edit the target with the user's approval, then remove the standalone item once the content is safely moved. This is a judgment call, not a new disposition — the item is still deleted, just after its worth-keeping content has been carried to where it belongs.

4. **Checkpoint** [PROMPT] — After every item, present the next item and then close on the off-ramps as the message's final, bold ask. Order within the message: when a next item is queued, lead with that item's verbatim text — the item only, no analysis — re-read from QUEUE.md first to confirm the quote matches the file (the confirm-against-the-file re-read lives here, not in the next item's present-and-interview beat); then, below the verbatim, put the off-ramps as the closing bold question — continue to the next item, skip this next one to the bottom for a later session, close out now (go to Step 4), or raise something else (loop back into Step 2 with the new item). All four must be genuinely on offer; deliver them conversationally rather than as a fixed form, but they land below the verbatim, not above it.

   **Skip-to-defer.** The skip off-ramp is folded into this one ask on purpose — a separate "dig into this one, or skip it?" gate before every item would re-create the over-asking the method just removed, so skipping is one option among the checkpoint's four, never its own turn. On skip: move that next item to the bottom of Unprocessed, record its slug in _plan.md as skipped-this-session, and don't re-present it this session — present the item after it instead. A skipped item is not deleted and not processed; it simply waits for a later /plan. Skipping the last remaining item leaves Unprocessed non-empty, which is fine — the session can still close from the off-ramps. The verbatim is shown, then the ask hands the decision back — putting the ask last gives the message a proper landing instead of ending on a raw quote that reads as Claude stopping mid-thought. Why the verbatim still leads rather than the analysis: it lands the next item this turn so the user reads it before deciding, and when they continue, the next turn opens directly with analysis — the turn boundary is the separator. The verbatim shown here is that next item's own presentation, not a forbidden look-ahead: the user acts on it immediately (it is the very next thing processed), so it is not a [SEQUENCE] violation. Wait for the user's call. On the last item there is no next verbatim to show, so the message is just the off-ramps as the bold ask, with "continue to the next" dropping out naturally — and it is worded **neutrally**, "anything else to capture or discuss, or close out?", never as a lean toward closing. An empty Unprocessed is not a signal the session is over; running the last item does not mean the session should wind down.

   **View-in-doc applies here too.** When mode is local and an editor is recorded (the render conditions from sub-step 1's check, per plugin-behaviour.md Working mode and view-in-doc rendering), lead the checkpoint with a one-line pointer to the next item in the doc — `Next item — **[work-slug]** — is in [QUEUE.md](QUEUE.md) under Unprocessed.` — in place of that item's pasted verbatim, then put the off-ramps below it as the closing bold ask, unchanged. The re-read still runs in its pointer form (confirm the item is there and the pointer resolves — the read-back half of plugin-behaviour.md Working mode and view-in-doc rendering). When mode is remote, or no editor is recorded, lead with the verbatim exactly as above.

**Process-now offer after a user-filed capture** [PROMPT]. When the user files a fresh capture mid-/plan — a new idea or task they want recorded, raised through the checkpoint's "raise something else" or at any point in the session — don't close on a bare "anything else?" (which can read as Claude parking their idea and moving on). File it first (draft, approve, write to Unprocessed as normal), then offer the branch: process it now, or carry on through the queue in order — and either way, anything else to add first? The choice is the user's: "now" loops it straight into the Step 2 present-and-interview loop; "carry on" leaves it in Unprocessed for its turn. This is scoped to a capture the *user* raised during /plan — processing is /plan's to do, so the offer is real here. A capture Claude raised mid-session doesn't get this offer; it confirms and resumes (plugin-behaviour.md, "close by who raised it").

After all items: Unprocessed should be empty of everything except items skipped this session (everything else kept or deleted), and Processed holds the kept work in order. Section headers intact.

**Neutral end-of-queue gate** [PROMPT]. When the queue empties, do **not** presume the session is over and do not slide straight into the wind-down re-scan or the Step 3 close. An empty Unprocessed is a resting state, not a stop signal. Ask one neutral question — "anything else to capture or discuss, or shall we close out?" — and wait. The wind-down re-scan and Step 3 close only proceed once the user actually chooses to close. If the user raises a further capture here, file it (draft, approve, write to Unprocessed) and then return to this same neutral gate — never re-lean to close after filing. This honours the "close by who raised it" rule (plugin-behaviour.md): a user-raised capture is followed by a neutral "anything else?", plus the process-now offer above, not a nudge toward the exit.

New items from conversation follow the same loop — check QUEUE.md for overlap first.

If Claude notices a gap: "I notice [X] — want to hear a suggestion?"

**Wind-down re-scan** [DISCUSS, PROMPT] — After every item is processed and before recommending /done (the Step 4 close-out), re-read this session's own discussion and surface candidate captures: things the user thought out loud but never explicitly flagged. Name the step's own best-effort nature in plain words when it runs — it re-reads whatever conversation is still in view, and a long session may have lost earlier discussion to compaction — so a surfaced-nothing result isn't read as "nothing was missed."

Present all surfaced candidates as ONE numbered set of fully-drafted captures for a single approval: the user contests by number, and only contested items are then taken one at a time. This is the bulk-approval inversion in plugin-behaviour.md's [SEQUENCE] rule — the re-scan is a result set produced under an understood criterion, so per-item approval would add round-trips without adding judgment the bulk view doesn't already give. Approved candidates are filed to Unprocessed; processing them (keep / delete) follows the normal flow, this session or a later /plan.

The why: this is a best-effort safety net behind the capture-at-the-moment-of-noticing rule, memory-dependent so degraded after compaction. A non-coder who thinks out loud generates capturable material they never explicitly flag, so the re-scan catches what the moment-of-noticing rule outran. The find-then-file flow here is planning work, and /plan is the only skill that processes work and has the most free-form discussion — so /plan owns the full re-scan: it both files the surfaced captures and can carry them into processing. But the *filing* half is not /plan-exclusive: /done runs a file-only version of this same re-scan at its close (see done.md's Wind-down re-scan section), because filing captures is allowed in any session. What stays /plan-only is *processing* the surfaced captures — keep / delete — which is the planning the no-planning-in-execution rule protects.

## Step 3: Close out [BRIEF, PROMPT]

**SPEC in sync before closing.** [SILENT when in sync; surface and fix when not] If a decision this session changed what SPEC says and SPEC wasn't updated in-session, catch it now: update SPEC with the user's approval before recommending /done. This is the obligation the /done-plan close enforces as a hard gate (done-plan.md) — surfacing it here means the close stays clean rather than stopping. The why: SDD atomicity — the spec moves in the same commit as the decision that changed it. Scope: every /plan close where a product-truth decision was made.

**Reorder both sections.** [SILENT when no reorder; BRIEF when reordering] Walk both sections and reorder by the principle that fits each:
- **Unprocessed → unlock-potential.** Process first what would unblock the most other work — an item whose resolution lets other items move forward sits above one that stands alone. Processing is meant to move work toward ready, so items that gate others come first.
- **Processed → build-order.** Build first what unblocks or reshapes the framing for later work — an item whose output is a prerequisite or input for a later item sits above the one that needs it.

Claude reorders and narrates; it does not ask. This is the existing ordering-ownership rule (plugin-behaviour.md Dependency ownership: "a judgment call Claude makes and narrates, not a question it asks") made specific to the close. The user owns keep/delete and scope, not order; order is low-stakes and reversible, so the narration is the catch-point where the user can redirect.

**Use the mechanical mover to apply the reorder — don't retype blocks.** Moving a work item by hand means retyping its whole prose block verbatim, which on a long queue silently degrades to a partial sort and risks corrupting an item with no error. Instead, once you've decided the order, apply it with the shipped `reorder_queue.py` script: it moves whole blocks byte-for-byte from a slug order you supply, and self-checks (same slug set and same block contents before and after, or it refuses to write and changes nothing). Only the *decision* — the desired order — passes through you; never the prose.

- **Locate the script** relative to the plugin, not by a hardcoded path: it lives at `scripts/reorder_queue.py` under the plugin root, and the plugin root is the grandparent of this skill's base directory (the base directory Claude is given at skill invocation is `.../<plugin-root>/skills/plan`). Derive it from there so it resolves wherever the plugin is installed.
- **Invoke it per section** you're reordering: `python <plugin-root>/scripts/reorder_queue.py <QUEUE.md path> <Processed|Unprocessed> <slug1> <slug2> …` giving the section's full desired top-to-bottom slug order. For Processed, place the cleared-to-run marker with `--marker-after <slug|TOP|BOTTOM>`; omit it to keep the marker where it currently sits. (Position the marker per "Position the cleared-to-run line" below — the mover just applies the placement you decided.)
- **Trust the self-check.** If the script exits non-zero (a slug-set mismatch usually means the queue changed under you — re-read it and rebuild the order), nothing was written; fix the input and re-run. A supplied order that matches the current queue is the only thing it needs.

Narration scales so it stays a real catch-point, not noise: a reorder that changes what /next would pick next is flagged clearly — e.g. "Moved [slug-a] above [slug-b] so it builds first — say if not." A trivial tidy (e.g. grouping related items with no pick-order change) gets one line. No reorder needed: say nothing. Scope: every /plan close, both sections.

**Position the cleared-to-run line.** [SILENT when its placement is unchanged; BRIEF when it moves] Before the close line, place or move the `--- Cleared to run above this line ---` marker in the Processed section so everything above it is greenlit to build and everything below it is processed but not yet greenlit. Walk Processed top-down and put the line just below the last item the user has agreed is ready to build; work the user is still settling — held for more thought, or waiting on something outside the queue — sits below it. If every processed item is greenlit, the line goes at the bottom of Processed; if none is, at the top. Narrate where it lands **only when it actually moves** this close — one plain line, e.g. "Everything processed this session is cleared to run; the line sits at the bottom." When your walk confirms the line is already correctly placed and nothing moved it, confirm silently and say nothing. This is the boundary the user would otherwise have to work out by hand each session, and the unattended build mode later inherits it as its run bound.

**Hold back an item that depends on unverified work.** When placing the marker, a processed item must not be cleared if it depends — by a slug reference in its prose — on another item that has been built but whose verification is still *pending*: a host-side item shipped but not yet confirmed live after reinstall (its liveness unresolved by the content stamp, or its observed check simply not run yet). Keep such an item below the marker until the dependency's verification clears. The why is autonomy: a cleared item can be built unattended by /next with no user in the loop, so clearing one that rests on built-but-unverified work would let the run stack committed work on a foundation that might later fail its check — the exact compounding an attended session would catch before it stacked. The distinction is the whole point: a dependency merely being *built* is not enough to clear its dependents; it must be built **and** verified. A dependency built and confirmed live places no such hold. Narrate it when it holds an item back — one plain line naming which item is waiting on which.

**Record the lift-condition when placing any item below the marker.** Whenever an item is placed (or kept) below the cleared-to-run marker — for a pending dependency, an external wait, or held-for-more-thought — record in the item's prose the specific event or dependency that would lift it: "cleared once [slug] is built and verified", "after a full computer restart", "once the manifest is pushed". Prose, not a new hook-parsed field — this keeps faith with rationale-is-prose and needs no hook change. This is the enabling half of the below-the-line revisit (Step 1): without a recorded condition, that revisit can't tell a still-waiting item from a now-ready one without nagging the user. An item held below with no recordable lift-condition is a sign it belongs in Unprocessed (still needs thought), not shelved below the line.

Scope: every /plan close; narrate on move, silent when unmoved.

**Place ready `[user]` handover work above the marker.** The cleared-to-run marker is the single gate for handover as well as for builds: /next hands over a `[user]` item only when it sits above the marker. So when positioning the marker, place a `[user]` item **above** it once its prerequisite work has shipped — the work it waits on is built and (where that work needed a live check) verified, re-derived from LOG the same way the hold-back rule above re-derives dependency state. A `[user]` item whose prerequisite is still pending stays **below** the marker, exactly like any other not-yet-ready item. This is why a `[user]` verification item for host-side work stays below until the reinstall lands and the shipped work is confirmed: its prerequisite isn't met yet. **Anti-pattern: don't hold a `[user]` item below the marker merely because it's the user's to run.** Being a handover is not a reason to shelve it — a ready `[user]` item with no pending prerequisite belongs above the marker so /next hands it over; only a pending prerequisite keeps it below. The why this lives in /plan and not in /next: the marker stays one positional gate rather than /next growing a second readiness check of its own — /next simply hands over what sits above the marker. Narrate it when a `[user]` item moves above the marker this close — one plain line naming which handover is now ready. Scope: every /plan close, walked alongside the marker placement above.
