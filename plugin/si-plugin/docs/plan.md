# /plan procedure

/plan is where unprocessed work becomes processed work through discussion. No building happens here.

Claude owns sequencing — the order work sits in, what gets built first — through discussion, not silently.

## Ground rules

- Never build during /plan. Want to write code? Queue it.
- One item at a time. Finish one before presenting the next.
- Read SPEC.md before proposing work. Don't queue contradictions.
- Process the accumulated unprocessed work before new planning work.
- Never write to QUEUE.md without showing the exact text first — and the rule keys to the write, not to where you are in the loop: the message immediately before any QUEUE.md write must contain the text verbatim. Approval attaches to shown text, never to a described shape, so a recommendation — however concrete — is not a draft, and "I'll add a line that does X" is not the entry. The reason: loop beats live in conversation memory and a compacted session loses them, but the write action is always visible, so keying the rule to the action holds even with no memory of which beat you're on.
- A recommendation is not a decision. A draft is not a written line. Both need the user's call.
- SPEC is a normal doc. When a planning decision changes what SPEC says — a new capability, a scope change, a reworded rule (the test is whether any SPEC sentence goes wrong) — edit SPEC in that same /plan session, with the user present and approving. Don't defer it. (A SPEC change a build discovers it needs is handled in the build, per next-build.md; a large SPEC rework is its own piece of work that names SPEC.md among its files.) The why: spec-driven development's contract is that any change altering behaviour updates the spec in the same commit (resources/research/spec-driven-development-edit-workflow.md). The /plan-close spec-sync gate (done-plan.md) enforces that atomicity — a session can't close with SPEC left behind the decision that changed it. When a change touches no SPEC sentence, none of this applies.
- /plan resolves what it can in-session; capture is only for what it can't. Research, queue-wide cleanup (line-ref drift, quoted-string staleness after a sweep), cross-item reconciliation, doc verification — anything within /plan's reach — gets done now, not filed for a later session. Reserve a capture for what /plan genuinely can't resolve this session: it needs data the session doesn't have, needs design discussion across sessions, needs user input not yet available, or surfaces a structural question whose answer would gate the work. This is a default, not an absolute — the test is "can /plan resolve this with what it has right now."

## Capture and processing discipline

The control rule for capturing and processing work, in one place. Pieces also appear in the steps and in plugin-behaviour.md; the canonical statement is here.

- **Two sections, one move between them.** QUEUE.md holds **Unprocessed** work (captured, not yet discussed) and **Processed** work (discussed, agreed, ready to build). The only move is Unprocessed → Processed, made in /plan by discussing an item with the user and agreeing to keep it. There's no third state and no parking: a line is unprocessed, processed, or deleted. See plugin-behaviour.md Captures.
- **Every work line carries a provenance label.** Each line notes who raised it — "captured by you" or "by Claude" — and that label stays on the line after it's processed. See plugin-behaviour.md Captures for the full line format (one-line description, prose rationale, slug, provenance).
- **Who does the work.** Work is Claude's to build by default. When a line is work only the user can do — a check that needs their eyes, a step in a tool Claude can't drive — mark it `[user]` on the line. /next builds Claude-work top-down and hands over at the first user-work line (the full handover mechanism lands with the /next rewrite).
- **Filing is any session; processing is /plan's.** Any session can append a capture to Unprocessed. Moving a line into Processed or deleting it — deciding its fate — happens only in /plan, because that decision is the user's (plugin-behaviour.md Routing and discipline, filing vs processing).
- **A surfaced risk is kept as a red-flag work line.** When a kept item is a data-exposure, privacy, or breach risk Claude surfaced, its processed line carries a `Red flag · State:` marker (open / resolved / accepted). Setting and changing that state is part of processing it — open if the risk carries into the build unaddressed, resolved if the design eliminated it in-session, accepted if the user is told the risk plainly and chooses to proceed. See plugin-behaviour.md Red flags.

## Step 1: Read state and entry question

Read QUEUE.md (both the Processed and Unprocessed sections) and SPEC.md. Check whether Unprocessed has items.

Ask [PROMPT]: "Anything to discuss before we go through the unprocessed work?" (If Unprocessed is empty, ask what they'd like to work on.)

**If the user has something to discuss:** Handle it via the Step 2 loop — present, interview, recommend, wait, execute. Then ask [PROMPT]: "Anything else before we go through the queue?" Repeat until there's nothing more.

**Then process the unprocessed work:** Move to Step 2. Going through the unprocessed work is where every /plan session goes — a discussion item is just an optional first stop, never an alternative to it.

## Step 2: Process work [SEQUENCE]

**Planning state file: _plan.md.** When processing begins, create `_plan.md` to hold this session's planning state: the item list, the current item, and the beat reached. Update it at each beat transition, and append each item with its disposition — kept (moved to Processed) or deleted, with slug. One line per item, so updates stay cheap. The reason it exists: the file survives compaction, gives an interrupted /plan a resume path through session start, and hands /done a mechanical record of what was decided instead of a reconstruction from memory. /done reads it at close and deletes it — same lifecycle as _build.md.

**Process order.** Go through Unprocessed top to bottom, then any items raised in this session's own discussion. State the count upfront, counting both together ("5 items. First: ..."). Position in the file is the order — a line placed next to its relatives is processed there by design, not by strict age (plugin-behaviour.md Captures placement); oldest-first is only the append fallback at filing time.

For each item:

1. **Present and interview** [DISCUSS, PROMPT] — The item's verbatim text lands on its own beat before analysis begins. For **every item after the first**, it was already sent at the end of the prior item's checkpoint, so this beat opens directly with analysis — no re-quote, and no "my read to follow"-style pre-framing of any kind. For the **first** item there's no prior checkpoint to have carried it, so quote it at the loop's opening as its own beat and end that message on a brief, bold closing prompt inviting the user to continue — don't let the message trail off on the raw quote with nothing handing the decision back. The analysis then opens the next turn, with the turn boundary as the separator, exactly as it works for later items. Why the verbatim lands on its own beat, ahead of analysis: the user takes the item in more easily when they can read the raw text before Claude's framing arrives, rather than digesting the whole reaction the moment it lands bundled. When quoting the first item, the separator that forces the quote out as its own beat is the re-read: after the quote goes out, re-read the item from QUEUE.md to confirm the quoted text matches the file, which also catches a context-drifted quote before it's discussed (if the file differs, correct it immediately). For later items that re-read already happened at the checkpoint that presented them. Engage with the item's substance: ask follow-ups to sharpen it or surface missing context, depth scaling with the item, until the picture is clear. Close the interview: when a delete lean is already clear, close on the combined recommend-and-ask in sub-step 3's merge guidance — not a bare "anything else to add?" trailed by a separate recommend turn; when the lean isn't clear yet, close with "anything else to add?" and let sub-step 3 carry the recommendation.

   **View-in-doc: pointer instead of paste when an editor is recorded.** The verbatim item lives in QUEUE.md already, so re-pasting it into chat spends tokens on text the user can open in their own editor. Check CLAUDE.md for an `Editor:` field with a real value (any value other than `not recorded` or an absent field). When one is recorded, render the first item's own beat as a one-line pointer that names the item and links to the doc, instead of the pasted quote — for example: `First item — **[work-slug]** — is in [QUEUE.md](QUEUE.md) under Unprocessed.` Still end that message on the same brief, bold closing prompt handing the decision back, so the beat lands rather than trailing off. The confirm-against-the-file re-read still runs, in its pointer form: re-read the item from QUEUE.md to confirm it's there and the pointer resolves (there's no quoted text to drift now, so this is a resolves-check, not a text-match). When no editor is recorded, keep the verbatim inline quote exactly as above — the pointer is the token-saving path, the inline quote the safe default.

2. **Recommend** [PROMPT] — Recommend a route — **keep** (move the line into Processed) or **delete** — and say why:
   - **Keep** — the work is worth doing. The recommendation must describe what would actually get built, in terms the user can recognize as the work product (which files change, what gets added, removed, or rewritten — not just the topic or intent). Forcing function: if sub-step 1's interview hasn't yielded enough to describe the work concretely, the recommendation isn't ready — return to interviewing. Part of keeping is settling who does it: Claude-work by default, or `[user]` if it's the user's to run (mark it on the line). Claude places the line in Processed by relationship judgment — beside a relative when it revises or builds on existing work, oldest-first otherwise — and reports where it went; a user-work line goes where the user agrees.
   - **Delete** — remove it. If it was already decided (check LOG/index.md), state the prior decision and commit.
   Stop and wait. The user decides.

   **Fold the recommend into the action when the user already agreed during the interview.** When present-and-interview already secured the user's explicit agreement to a specific route — Claude gave its lean and the user said to go with it — skip this standalone recommend-and-wait and go straight to the action in sub-step 3, naming the route in one line ("going with keep — drafting the line now"). This fold is scoped to **keep** only: keep is followed by the draft-approval step, which the user still owns, so folding loses no decision — the draft is the safety net. **Delete** can't fold to the action — it's terminal, with no later approval step to re-confirm it, so the user's explicit approval is still required before execution. But that approval doesn't need its own separate turn: when the lean is already clear it merges into the interview-closing turn (next paragraph).

   **Merge a clear delete recommend into the interview-closing turn.** When a delete lean is already clear by the end of the interview exposition, don't close with a bare "anything else to add?" and then re-state the recommendation in a separate turn — that names the route twice with a content-free exchange between. Instead, close the exposition on one combined, bold ask that carries the recommendation: "…my recommendation is to drop this; anything you'd change, or shall I delete it?" The user pushes back or approves in a single reply, and that reply is the terminal approval delete requires — so merging loses no decision, it only drops the empty middle turn. The standalone recommend-and-wait above stays the path when the lean genuinely isn't clear yet. Keep is unchanged: it folds to its draft, and the draft-approval remains its safety net.

3. **Execute keep or delete:**
   - **Keep** [DISCUSS, PROMPT] — Draft the processed line: its one-line description (with the slug at the end, and `[user]` if it's user-work), and the prose rationale under it carrying the discussion's reasoning as inline prose — see Why-pipeline in plugin-behaviour.md. Show the draft as a blockquote with a content-type lead-in (**Work line:**), per the approval-time outputs rule in plugin-behaviour.md. Don't write to QUEUE.md until approved. On approval, move the line into the Processed section at the placement Claude reported, and remove it from Unprocessed. If the raw capture had no slug, give it one now.
   - **Keep a surfaced risk as a red-flag work line** [DISCUSS, PROMPT] — When the item being kept is a security, privacy, or breach risk Claude surfaced (plugin-behaviour.md Red flags), the processed line gets one extra marker line under its description: `Red flag · State: <open | resolved | accepted>`. Set the state from the discussion — **open** if the risk carries into the build unaddressed, **resolved** if this session designed it out (record how in the rationale), **accepted** if the user is told the risk plainly and chooses to proceed (record the informed consent — what they were warned about and that they chose to go ahead — which /done writes into the LOG at close). The state can change as the discussion moves: open→resolved if it gets designed out here, open→accepted if the user hears the risk and proceeds. Draft and approve the line exactly as a normal keep.
   - **Delete** — Remove the line from Unprocessed.

4. **Checkpoint** [PROMPT] — After every item, present the next item and then close on the off-ramps as the message's final, bold ask. Order within the message: when a next item is queued, lead with that item's verbatim text — the item only, no analysis — re-read from QUEUE.md first to confirm the quote matches the file (the confirm-against-the-file re-read lives here, not in the next item's present-and-interview beat); then, below the verbatim, put the off-ramps as the closing bold question — continue to the next item, close out now (go to Step 4), or raise something else (loop back into Step 2 with the new item). All three must be genuinely on offer; deliver them conversationally rather than as a fixed form, but they land below the verbatim, not above it. The verbatim is shown, then the ask hands the decision back — putting the ask last gives the message a proper landing instead of ending on a raw quote that reads as Claude stopping mid-thought. Why the verbatim still leads rather than the analysis: it lands the next item this turn so the user reads it before deciding, and when they continue, the next turn opens directly with analysis — the turn boundary is the separator. The verbatim shown here is that next item's own presentation, not a forbidden look-ahead: the user acts on it immediately (it is the very next thing processed), so it is not a [SEQUENCE] violation. Wait for the user's call. On the last item there is no next verbatim to show, so the message is just the off-ramps as the bold ask, with "continue to the next" dropping out naturally.

   **View-in-doc applies here too.** When CLAUDE.md records an `Editor:` field with a real value (per sub-step 1's check), lead the checkpoint with a one-line pointer to the next item in the doc — `Next item — **[work-slug]** — is in [QUEUE.md](QUEUE.md) under Unprocessed.` — in place of that item's pasted verbatim, then put the off-ramps below it as the closing bold ask, unchanged. The re-read still runs in its pointer form (confirm the item is there and the pointer resolves). When no editor is recorded, lead with the verbatim exactly as above.

After all items: Unprocessed should be empty (everything kept or deleted), and Processed holds the kept work in order. Section headers intact.

New items from conversation follow the same loop — check QUEUE.md for overlap first.

If Claude notices a gap: "I notice [X] — want to hear a suggestion?"

**Wind-down re-scan** [DISCUSS, PROMPT] — After every item is processed and before recommending /done (the Step 4 close-out), re-read this session's own discussion and surface candidate captures: things the user thought out loud but never explicitly flagged. Name the step's own best-effort nature in plain words when it runs — it re-reads whatever conversation is still in view, and a long session may have lost earlier discussion to compaction — so a surfaced-nothing result isn't read as "nothing was missed."

Present all surfaced candidates as ONE numbered set of fully-drafted captures for a single approval: the user contests by number, and only contested items are then taken one at a time. This is the bulk-approval inversion in plugin-behaviour.md's [SEQUENCE] rule — the re-scan is a result set produced under an understood criterion, so per-item approval would add round-trips without adding judgment the bulk view doesn't already give. Approved candidates are filed to Unprocessed; processing them (keep / delete) follows the normal flow, this session or a later /plan.

The why: this is a best-effort safety net behind the capture-at-the-moment-of-noticing rule, memory-dependent so degraded after compaction. A non-coder who thinks out loud generates capturable material they never explicitly flag, so the re-scan catches what the moment-of-noticing rule outran. The find-then-file flow here is planning work, and /plan is the only skill that processes work and has the most free-form discussion — so /plan owns the full re-scan: it both files the surfaced captures and can carry them into processing. But the *filing* half is not /plan-exclusive: /done runs a file-only version of this same re-scan at its close (see done.md's Wind-down re-scan section), because filing captures is allowed in any session. What stays /plan-only is *processing* the surfaced captures — keep / delete — which is the planning the no-planning-in-execution rule protects.

## Step 3: Close out [BRIEF, PROMPT]

**SPEC in sync before closing.** [SILENT when in sync; surface and fix when not] If a decision this session changed what SPEC says and SPEC wasn't updated in-session, catch it now: update SPEC with the user's approval before recommending /done. This is the obligation the /done-plan close enforces as a hard gate (done-plan.md) — surfacing it here means the close stays clean rather than stopping. The why: SDD atomicity — the spec moves in the same commit as the decision that changed it. Scope: every /plan close where a product-truth decision was made.

**Position the cleared-to-run line.** [SILENT when its placement is unchanged; BRIEF when it moves] Before the close line, place or move the `--- Cleared to run above this line ---` marker in the Processed section so everything above it is greenlit to build and everything below it is processed but not yet greenlit. Walk Processed top-down and put the line just below the last item the user has agreed is ready to build; work the user is still settling — held for more thought, or waiting on something outside the queue — sits below it. If every processed item is greenlit, the line goes at the bottom of Processed; if none is, at the top. Narrate where it lands **only when it actually moves** this close — one plain line, e.g. "Everything processed this session is cleared to run; the line sits at the bottom." When your walk confirms the line is already correctly placed and nothing moved it, confirm silently and say nothing. This is the boundary the user would otherwise have to work out by hand each session, and the unattended build mode later inherits it as its run bound. Scope: every /plan close; narrate on move, silent when unmoved.

"Run /done to record this and commit, or keep planning." No chat summary — the LOG entry /done writes is the single session summary.
