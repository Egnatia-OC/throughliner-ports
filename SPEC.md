# SPEC — Sovereign Implementer

## What this is

A Claude Code plugin for non-coders. It gives users a structured workflow for building apps with Claude Code without needing to know how to code.

## Who it's for

Non-coders who know what their app should do but need a framework to keep Claude aligned.

**The Claude Code desktop app is the platform, and that is a product decision rather than a description of current habits.** The method is designed for, tested on, and targeted at the desktop app. It is not designed for the terminal, and a procedure must never route a user there — **the terminal is not approachable for the people this is for**, which is the whole premise above. This holds even where a terminal would be technically easier or would sidestep a limitation of the app: a workaround the audience cannot perform is not a workaround.

And where a limitation belongs to the app itself, it is reported to the app's makers and worked around within the app, never escaped by leaving it.

**This does not port to other models or other tools, and the reason is structural rather than a matter of effort.** The method *is* model-tuned prose. Its rules are worded for a particular model's way of following rules — which is why it once shipped its procedure docs twice, one wording per model family, before the older of the two was retired. A port to a different model or a different harness is that same problem one level up — the prose stops producing the behaviour it was written for, and correcting it means pulling threads and rewriting rules until what remains is a different method wearing the same name. This is a finding rather than a preference: it was tried, on a port that was built, did not respond right, and could not be corrected without ceasing to be the same thing.

**The precise claim, because a weaker one would be wrong.** It is not that rewording always changes the method — the two docsets that once shipped were reworded for different models and *did* carry the same method. They carried it because somebody made them: one author, a known target, deliberate authoring by subtraction, and a fidelity audit with recorded restores wherever they drifted. Fidelity there is a maintained property, paid for continuously. The claim is therefore: **rewording changes the method unless fidelity is actively maintained, and a port has neither a maintainer nor a neutral middle version to maintain toward.** Anything proposing a port should be read against that first.

**When Claude is blocked on a task it should be able to do, it follows a fixed order, and the order is the point.** This is general and applies to every tool, not to any one toolchain:

1. **Try it.**
2. **Blocked — research whether a tool exists that Claude can use.** This step is not optional and it comes before involving the user at all. A non-coder does not know which tools exist, so they cannot ask for one by name; if Claude does not look, nobody does.
3. **A suitable tool exists but is not installed or authenticated — ask for it, specifically and once.** Name the tool, say what it is for, and offer to walk the user through getting it. This is legitimate user work and not a hand-off: it is a single concrete request that ends with Claude doing the task.
4. **No tool exists — say so plainly, and hand the user back to something they already have.** Name the thing that does work, and stop.

**And once the tool is available, the same test governs its use: Claude hands over only the parts it genuinely cannot do.** Not the parts that look like the user's job, not the whole task because one step of it needs a person — installing something, clicking an approval, reading something only they can see. Everything either side of that step is Claude's. The test is *can Claude do this at all*, never *would it be easier to ask*.

**The failure this order exists to prevent is repeated hand-off, and it is worse than either doing nothing or asking once.** The observed case: Claude could not complete a build, did not research an alternative, and instead cycled — retrying, re-explaining, and handing the problem back — while the user already owned a tool that would have done it in one step and was never asked to use it. Spiralling reads as effort and produces nothing.

**The same order has a counterweight, and without it the rule above produces the opposite failure.** Reaching for a tool Claude can drive is right when the alternative is a vague hand-off; it is wrong when the user already owns a tool that does the job. So two checks pair with it. **At the start of something new:** where a standard generator exists for that kind of project — a new-project wizard, `cargo new`, `npm create vite` — it is used rather than the same thing being hand-assembled file by file, because build configuration is exactly where hand-assembly fails and exactly what a generator gets right. **At any point during the work:** if the item's goal is already met by a tool the user has, Claude stops and says so instead of building itself a second route to a result that already exists. Where the tool step is one only the user can run, it becomes a `[user]` step with a real walkthrough, not a suggestion left hanging — the guard decides whether to build at all, never who does it.

**And a fact the user states about their setup is written down, not held in the conversation.** When the user says which tools they have and which one they build with, that goes into the project's CLAUDE.md under "your tools", asked as one specific question at the moment it matters rather than as a standing interview question nobody can answer usefully. Each entry records how it was checked — a tool the user reports having is evidenced by their saying so; a tool Claude claims to drive is evidenced by having driven it — and an entry with no evidence recorded is read as unverified. The failure this fixes is a user repeating a true fact about their own machine every session while nothing changes, because the fact never left the chat.

**This does not conflict with not sending the user off to do things.** That rule exists to stop *vague* hand-offs that leave a non-coder holding a diagnosis they cannot make. A specific one-time request for a named tool is the opposite: it is bounded, it is answerable, and Claude carries the work afterwards.

## How it works

Splits changes into a build queue that helps the user harness Claude's skills in dependency management, not just coding. The secondary core functionality is basic context window management.

Four skills drive the workflow:
- `/setup` — scaffold project docs and run the onboarding interview. The workflow FAQ it copies in is treated as a **local copy of the plugin's own help rather than a document in the user's project**: it is gitignored so it never lands in their history as clutter, and restored from the shipped templates whenever it is missing — both halves, because the ignore rule alone would leave a fresh clone with no FAQ, which is what every session is pointed at. Where a project already has the FAQ committed from an earlier version, /setup offers to untrack it (leaving the files on disk) rather than doing it silently. This reaches the FAQ and nothing else: SPEC, the queue and the log are the user's own record and belong in their history.
- `/plan` — manage the queue, add ideas, resolve questions, check for drift.
- `/next` — pick the top piece of ready work and execute it, routed by its flavor: a **build** (Claude edits files) or an **`[audit]`** — a first-class review pass where Claude reads and reports findings for later review, without editing. (Audit is its own flavor with its own discipline; it never edits on the spot.) A `[user]` item is a walk-through rather than something Claude runs — reserved for work Claude genuinely can't do or witness (a check that needs your eyes, a decision only you can make, a physical action), never for work Claude could run itself but is only blocked from running yet. Claude leads by walking you through it live, one step at a time — running whatever parts it can and guiding the rest through the concrete steps the item carries — and names how to close it out only once you've finished: run /done, or mention it at the next /plan. /next works the cleared queue top-down — building each ready item and committing at the close — so a single invocation can clear several vetted items in a row without confirming each one, finishing at the readiness line.
- `/done` — close the build, record what happened, commit. Run on its own after changing files by hand (no /next first), it records and commits those edits too — reading them as the user's expected work, not a broken repo, and splitting them across separate log entries by judgment when they cover several distinct changes. It also records a completed `[user]` item — one it just walked you through, or one you've mentioned finishing — logging it and removing it from the queue, so a finished step doesn't sit there and get brought back to you next time; /plan does the same when you mention a `[user]` step you finished between sessions. Neither ever asks you which ones you've done.

Four project docs structure each project:
- `SPEC.md` — product truth. What the app is, who it's for, how it works.
- `QUEUE.md` — processed and unprocessed work. Processed work is vetted and ready to build; unprocessed work is captured ideas and tasks not yet fully processed — either not yet discussed, or discussed and worth doing but not yet designed enough to describe the build. One item per piece of work.
- `LOG/` — per-session records of what was built, tested, and decided, and of the session's other durable outputs. What belongs in an entry is settled by an artifact test — is this something the project might need to draw on again? — never by whether its subject was project-ish enough. So work produced alongside a build, such as an announcement written about the project, is recorded rather than lost. When outward-facing work recurs, Claude offers to record in the project's CLAUDE.md where it goes and whether its full text is kept.
- `GLOSSARY.md` — the words that have been explained to you, and the names this project has settled on. Claude reads it before using a technical term: a word that's in there has already been explained, so it gets used plainly; a word that isn't gets explained at the moment it's used and then recorded. That gives you a two-sided guarantee — **Claude never re-explains what you know, and never assumes you know what it hasn't told you.** Entries carry the explanation roughly as it was last given to you, so the glossary mirrors what you might actually remember rather than reading like a textbook, and it's updated each time a term is explained again, which is also what keeps it current. It holds two kinds of word: jargon from the wider world, and the names this project chose for its own things — including a word you picked yourself, which goes in with your reasoning and is then simply correct here. Where you've used the wrong word for a real technical thing, Claude names the standard one once and then just uses it, rather than either correcting you repeatedly or silently adopting a word that would leave you exposed elsewhere. Unlike the FAQ, it's committed with the project: it's your own record, not a copy of Claude's help.

Two hooks enforce discipline mechanically, and a third advises:
- `session_start` — detect project state and load the behaviour rules. It also detects the one project shape where its own consumer-facing checks misfire: a project containing the plugin's own package is being used to *develop the method* rather than to build an app, and there the "your plugin has been updated" report is meaningless and permanently wrong — the version recorded at setup and the version being produced can never agree again. On first seeing that shape Claude asks once whether it's right and records the answer; from then on it acts silently on what was recorded, and a recorded "no" is honoured permanently. Suppressed means silent, not announced as suppressed. Everything short and load-bearing — an uncleared red flag first of all — is placed ahead of the bulky rules text, so a context that gets trimmed keeps the part that matters. If the procedure-docs folder is missing from the installed plugin (a mispackaged or incomplete install), there is nothing to fall back to — the hook reports that state in a plain state line, naming that the folder is missing from the installed plugin rather than the project — never silently.
- `pre_tool_use` — enforces the scope-lock and git safety, and asks for your approval before Claude spawns a subagent (a cost guard that asks, never blocks). The scope-lock governs SPEC.md like any other file, and it applies **during a build**: it holds Claude to the file list the build agreed to, plus a small always-editable set that is **listed rather than named** — the queue, the log, the glossary, and the session's own working file. SPEC.md is deliberately not in that set, so a build changes what the project is only by having said it would. The set is enumerated because the collective name it used to carry ("method docs") had three plausible readings, one of which told a reader that a build may rewrite SPEC at will. That file list is an approximation of the real boundary, not the boundary itself — the work you agreed to is the contract, and a build could stay inside every listed file while doing more than was described; the hook cannot see that, so the build close compares each item's changes against its description and says plainly when they don't match (surfacing, never blocking). **Because the list approximates the boundary rather than being it, a build that finds the agreed work genuinely needs one more file adds it, says so in a line, and carries on** — the addition lands in the commit where it's as readable as any other change. The narration isn't optional: an expansion nobody announced is worse than one that stops, because the check is you reading what changed. What still stops the run is the different case — a piece of work so underspecified that Claude can't tell what it changes inside the files it names, where continuing would mean inventing scope you never agreed to. The distinction matters because a build run is unattended in practice, so halting on every legitimate discovery ends runs that could have finished. Outside a build there is no agreed list to hold to, so planning sessions get a lighter guard of a different kind — a write to anything beyond the files planning touches by design (the queue, SPEC, the log, the FAQ, the session's own notes) asks your permission first. The FAQ is on that list because keeping it current is a step the method requires at a close, and a required step that prompts every time teaches you to click through the ask that matters. That one asks and never refuses: its job is to make sure nothing gets changed without you seeing it, not to stop you fixing something. If a build is ever running without a file list at all, Claude is told so plainly rather than being left to assume the lock is on. **One limit is stated rather than papered over: the file check runs on Claude's editing tools, and a shell command can reach the disk outside the agreed list.** The hook catches the structured forms of that — a script whose target file is written out literally — and denies them wherever they point inside your project, naming the editing tools and the queue-item tool as what to use instead. This one is not a scope check and doesn't consult the file list: the shell can read a stale copy of a file and silently overwrite work, which is true whether or not the file was in scope and whether or not a build is open. (It was scope-conditional at first, and the two real slips it was built for both wrote in-scope files, so it caught neither.) Your session scratchpad sits outside the project and still passes, so scratch space stays available. A command whose target is computed at runtime is not detected. That residual gap is real and is described here rather than left implied by a claim of full containment; it is narrowed further from the other side, by giving the awkward edits that tempt a script route a proper tool of their own.
- `post_tool_use` — advisory QUEUE.md structure lint; flags format drift and a `Blocked by:` line that names a missing item or points the wrong way, never blocks.

**Editing-state signal — a published contract other apps can read.** While Claude is writing a file, the hooks publish a small marker saying so, so another application open on the same document — a Markdown reader or editor the user is reading and typing in — can hold off rather than the two landing on top of each other. It replaces a guess with a fact: a watcher can see *that* a file changed but not *who* changed it, and a wrong guess locks the user out of their own document mid-sentence.

It is a **heartbeat, not a lock**, and that is what makes it safe. Every marker carries a fresh timestamp, and a reader treats a stale marker as "not editing" whatever its flag says — so a session that crashes between starting a write and finishing one can never leave the user locked out. Staleness is the safety property, not a detail.

The contract, which another application is built against and which will not change without a version bump:

- **Location** — `.throughliner/` in the project root (the folder holding SPEC.md and QUEUE.md). A reader with a document open walks up the directory tree to find it, the way tools locate `.git/`.
- **One file per session**, named `editing-<session-id>.json`, holding `version` (leading, so a reader can recognise a format it doesn't understand and fall back safely; **currently 2**), `active`, `written_at` (ISO 8601 with an explicit UTC offset — for diagnosis, not freshness; see the reader policy below), `files` (**project-relative paths** — relative to the directory containing `.throughliner/`, forward slashes on every platform, no leading `./`, exactly one path per marker; a file outside the project falls back to its absolute path), and `producer` (a constant string naming what wrote the marker — this plugin writes `throughliner`, a format value that survives any product rename). Version 2 made `files` relative — a version-1 reader would resolve relative paths against the wrong root, which is exactly what the version field exists to prevent — renamed `updated` to `written_at` so the field is named for what it is safe to use for, and dropped `session` and `pid`, which nothing read: `pid` is unusable across machines and redundant on one, `session` restates the filename. One file per session rather than one shared file because two Claude sessions in one project is a supported shape: with a shared file, one session finishing a write would clear the flag while the other was still writing. The reader's rule is therefore trivially correct — **editing is happening if any file here is active and fresh.**
- **The signal fires per edit, not per build.** The opening hook writes `active: true` before each editing-tool call and the closing hook writes `active: false` after it, so a twenty-file build turns the signal on and off twenty times. A reader that maps the flag straight onto an indicator will flicker in every gap between edits, so it needs to hold briefly past `active: false`. No number is published for that hold, deliberately — nobody has measured real traffic yet, and publishing a guess would launder it into the interface. The trade-off that decides the length: a longer hold bridges longer thinking pauses; it also locks the user out for that long after every genuine finish.
- **Recommended reader policy, published as guidance rather than enforced** — treat `active: true` as editing; judge freshness by **the marker file's own local modification time**, treating a marker untouched for about 30 seconds as a dead session; treat a missing directory or an unreadable file as "not editing", never as an error. `written_at` is for diagnosis, never freshness — and the reason mtime wins is about failure direction, not clock arithmetic: an mtime that reads wrongly old fails open (nothing held, nobody locked out) and wrongly new fails mild and self-clearing, while a `written_at` from a fast or foreign clock fails closed — a dead session looks permanently current and the user is locked out of their own document indefinitely, precisely the failure the heartbeat design exists to prevent. That reasoning holds whatever any sync client does to timestamps, on any platform. Two more comparisons made explicit so no consumer guesses at them: **path comparison is case-insensitive on Windows** (the marker's path and the reader's open-document path can differ in case and be the same file — and matching them is the one comparison the signal exists for), and relative paths carry **no leading `./`**, so readers are not string-trimming. The hook reports facts and the reader decides policy, deliberately: the reader knows what its user is doing and the hook does not.
- **It fails open**, and must: most projects never have this plugin installed, so a reader that blocked on the directory's absence would be broken everywhere else. Writing the marker can never block or fail a tool call either — a companion-app convenience must not be able to stop the user's actual work.
- **What it cannot say** — that Claude has *finished* rather than paused to think. Nothing available can know that, and pretending otherwise would be the same false promise the timing guess was rejected for. What changes is that the reader is no longer guessing: it knows a write is in flight and exactly how long things have been quiet.
- **Two known limits** — writes made through a shell command aren't covered (the hook only sees the edit tools, and a shell command's target file isn't reliably knowable), and the signal only exists where the plugin is installed and the project adopted. Everywhere else the directory simply never appears, which the fail-open rule already handles.

The folder is transient session state, so /setup gitignores it and git never commits it. Gitignore is all that claim covers: it keeps the folder out of the repository and does nothing about file sync — a project inside a Drive/OneDrive/Dropbox folder replicates these markers as they are written, which is why version 2 stopped writing absolute paths (the identifying payload is gone rather than contained).

One behaviour doc steers everything the hooks can't enforce:
- `plugin-behaviour.md` — loaded at every session start in adopted projects. Carries the cross-skill rules (communication, capture routing, dependency ownership, file safety) and five response-shape tags ([SILENT], [BRIEF], [DISCUSS], [PROMPT], [SEQUENCE]) that procedure docs place on individual steps to control verbosity and interaction. Rule and tag definitions are compliance-hardened: each carries a why-clause, quantified constraints, and an explicit scope statement so it holds against the helpfulness pull of current models.

One output style sets the communication default at system-prompt priority:
- A concise output style — shipped in the plugin and applied automatically when SI is enabled. It lifts the plugin's communication structure (lead with the decision, one item at a time, gate detail) to system-prompt priority, the level that holds when lower-priority instructions are skipped. It steers structure and plain English, not terseness — the goal is to not overwhelm the non-coder who reads and approves everything, never to cap length.

**One set of instructions, tuned for the Claude 5 models.** The plugin ships a single set of procedure and behaviour docs, and every session loads it. There is nothing to configure and nothing to pick.

It used to ship two — a heavier, more prescriptive set and a lighter one — with the running model deciding which loaded. The heavier one existed for Opus 4.8, whose reliable rule-following depended on the fuller wording; the lighter one was written from it by subtraction for the 5-series, which follow a rule better with *less* prescription around it. The heavier set was retired in August 2026 once nobody was running 4.8, and with it went the model detection, the recorded-model setting it fell back on, and the redirect that pointed skills at the right folder.

**What that costs, stated rather than implied.** The heavier set was also the safety net: if the lighter one were ever missing from an installed copy, a session used to fall back to it and simply run more verbosely. Now there is nothing to fall back to, so a missing folder means a session with no procedure docs at all. `session_start` therefore says so plainly — and specifically that it's the *installed* copy that's incomplete, not anything in your project — rather than quietly carrying on. A clear report is weaker than a working fallback, and that trade was made deliberately.

**Doc-bound text — one rendering default, no stored mode.** Text destined for one of the method's docs (an existing queue item, a just-written capture or log entry, a readable edit) is **written to that doc first and approved in place**, so there is one rule rather than a split between written and not-yet-written text. Chat then carries a short summary of what was written, a link to the file plus the exact heading text to search for, and the ask — with the full text offered on request rather than front-loaded. This shape works the same at a desk and on a phone, which is why there is no location setting: the retired `Working mode:` field asked *where the user is* (local/remote) and its one measured user answered `local` regardless of location because it meant less text, so the field recorded reading appetite, not location. The short summary is what makes the pointer survivable — the link's own weaknesses (it lands at the top of the file, a `.md` line anchor is silently ignored — the file opens at the top rather than at the line — and the viewer can serve a stale snapshot) are mitigated, not fixed. A retired `Editor:` field once recorded the user's hand-editing app; nothing reads it — links open in the desktop app's own viewer regardless. Stale `Working mode:` and `Editor:` lines in existing projects are ignored silently, like the retired `Completion mode:` line. Content with no doc to live in, such as a commit message or a recommendation, is shown inline as before.

**The summary is the feature, not a saving.** This rendering is the decided default for every user — not a setting, not tier-dependent — and the reason is not cost. A queue item is written long *because Claude needs the detail*: the facts, the conditions, the options that were rejected and why. The user needs none of that text, only enough to decide what they are approving. So one rule serves both readers with different texts, and it is simultaneously the answer to how doc-bound text is shown and the answer to items growing into walls of text. There are no length caps on the summary — not by line, sentence, or any other number; the only test is whether the user understands enough to approve. A per-project summary-length setting was rejected as repeating the retired working-mode failure (a field answered strategically rather than truthfully), and length-by-size-of-text was rejected as an arbitrary cap under another name. The one thing that cannot be traded away is that the summary itself must be readable: a summary in unexplained jargon fails exactly as badly as the wall of text it replaced.

**`[user]` steps are never asked about.** A `[user]` item is walked through, and that is the whole of it — no session, at any point, asks whether one is already done. Claude works out completion from what it can see: a step walked to its end in the session is done, and a step the user mentions having done is done. Where neither applies — a step the user did on their own with nothing to show for it — the item simply stays in the queue until they mention it, which is a deliberate gap rather than an oversight. The earlier design tried to soften the question (moving it later in a message, adding a setting to switch it off in most projects); this removes it. The reasoning: the method is for people new to building this way, and being mildly over-helpful to an expert costs far less than repeatedly asking the target user to account for work they never agreed to do yet. The `Completion mode:` setting that governed the old question is retired; a project that still carries the line is unaffected — it is simply ignored.

**Set aside — the method's name for "not now".** When the user stops a walk-through partway, reroutes an offer ("capture it for plan"), or answers a waiting-item check with "no change", that signal lands as a `Set aside ·` line on the work item — the date, the user's words quoted, and whatever the session witnessed of progress, cause, and retry condition. The item doesn't move; like the red-flag marker, the line rides the work where it sits. Its effect is raise-suppression: recommendations, forward advisories, and revisit questions skip a set-aside item, so the same "not now" isn't re-asked through every channel — while warnings (an uncleared red flag, a security concern) are never suppressed. It is recorded only on the user's explicit signal — Claude never proposes setting something aside — and nothing is quiet forever: when the queue has nothing else to offer, set-aside items are raised again plainly, and the user naming an item lifts its marker at any time. For a part-walked `[user]` step, the recorded progress is what lets the next session resume at the right step without the completion ask the method removed. The marker is not lint-checked, deliberately: its substance — that the user really said not-now — is not mechanically verifiable, and a lint that checked only the line's shape would imply more than it can promise.

**Private information.** Project docs are committed, and a commit is permanent even where the text is later deleted — so the method's protection is upstream of any review, at the moments of writing and asking, in three rules. Third parties' names and private circumstances are not written into SPEC, the queue, or the log, because a method lesson never needs them. Claude does not solicit sensitive identifiers — email addresses, account numbers, keys, payment details — into a work item, because an item is almost always actionable without them: the user holds those details at the moment they do the work. And context about the user themselves is recorded as the decision plus its reason, never as a personal assessment. /setup detects whether the project's repository is public rather than asking (a typed answer goes stale silently) and records it, which is what makes the rules urgent rather than theoretical — and before the project's very first commit it also tells the user which email address their commits will carry, naming GitHub's noreply option, because commit metadata is the one exposure no later file edit can fix. There is one rule at the other end, when text leaves rather than arrives: **if the user says they are about to share something from their queue or log, Claude names what is actually in that particular text first** — third-party references, absolute paths, account or tool identifiers, anything about someone other than them. The text is already written and already approved by then; what the user cannot be expected to hold in their head is everything a document written weeks ago contains. It fires once per intended share, and says nothing at all when there is nothing worth naming, because a warning on every clean document is one the user learns to click past. A scrub sweep is available on demand for what is already written: it finds every occurrence of a name you know, and surfaces other capitalised candidates for a human to judge — names, not characterisations, which is why the self-disclosure rule is prevention-only. Where something has already been committed, Claude says plainly that deleting it does not remove it from the repository's history, and leaves the choice — rewrite the history, scrub forward only, or make the repository private — to the user.

**Working with someone who isn't using this method.** The record of *why* a project is the way it is assumes one person, working with Claude, recording their reasoning as they go. Where a second person contributes — a collaborator, a contractor, anyone sending changes from outside — their changes arrive with no reasoning in the record, and the method deliberately does not fill that in: reconstructing intent from a diff is exactly the thing it rules out, because a plausible invented reason is indistinguishable from a real one. So Claude names the gap rather than papering over it, and recommends one ask: that the contributor have their own AI tool write the reasoning into the pull request before opening it. That is the only route that scales, because the reasoning is produced by the same thing producing the changes — a hand-written paragraph over a machine-sized change collapses fifty decisions into one label. Where the contributor writes nothing, a structural fallback helps: give them an area of the codebase, so the thin history is contained at a boundary the log can describe honestly instead of being interleaved through everything. And the plain truth is stated rather than engineered away — **part of a shared project will have thinner history than the rest, and that is a cost of having the collaborator rather than a fault to fix.** A design pretending otherwise produces a mechanism nobody follows. The method cannot require anything of a person outside it: this ships as an ask to make, never as a step the method performs.

**Saying that one piece of work waits on another.** A queue item that cannot run until another one lands says so in a `Blocked by:` line naming that item, checked by the advisory lint: the named item must exist and must sit above the blocked one. Order alone can't carry this — position says what comes next, not why, so a reorder silently undoes a dependency held only by position. Everything else — a restart, an external event, a decision only the user can make, or work that has to be released and running first — records its condition in plain prose and sits below the readiness line. There are two routes, not three: a push marker between items used to be a third, and it is retired. /plan placed it and /next ignored it, so work needing a released, reinstalled version was built against the old one silently. The readiness line already does that job, and it is the gate the method actually maintains and surfaces at every close.

**Merging work, and grouping by shared scope.** Claude may merge one piece of agreed work into another without asking when the merge adds no files to the run's scope — it changes where the work lands, not what gets built — and it narrates the scope effect in the same line so the user can object; a merge that adds files is a widening and still asks. At processing, /plan **groups items that touch the same files, and the group is the unit work moves in**: a group is agreed together, moves into Processed together, and runs as one — one coherent pass over a file instead of three sequential ones, and one decision instead of three. Groups are derived from the items' file lists, so nothing has to be named or maintained by hand, and when /next presents a run it names the group and its shared scope in one line, which is the whole explanation of the order. Two things bound it. Grouping never displaces the ordering that comes first — dependencies, then unblock-potential — so a blocking item always runs on its dependency order whatever group it belongs to. And **grouping changes the packaging, never the standard**: every item in a group is still vetted on its own merits, so an undesigned item can't reach a build by touching the right file.

**Readiness line.** /plan maintains a line in the queue — rendered `--- Cleared to run above this line ---` — that marks which work is vetted and safe to build (above it) from work that still needs planning (below it). It is positioned at the close of a /plan session — the single close (run by /done) that always fires however the session ends, so the positioning is never silently skipped — and Claude narrates where it sits whenever the line moves, confirming silently when its placement is unchanged, so the user never has to work out by hand how much of the queue is safe to run next without being told the same boundary twice. /next inherits it as its run bound when it works several items in a row — a clean finish at the line rather than running into unvetted work.

**Lifting shelved work.** Work that /plan shelves below the readiness line is waiting on something outside the queue — a dependency still being verified, a step only the user can take, a restart. Each such item records, in plain prose, the specific **external** thing that would make it ready ("after a restart", "once the page is published") — a wait on other queued work is a `Blocked by:` line instead, which keeps this list short. At the start of every /plan, Claude revisits the shelved items and re-checks those conditions: anything it can confirm itself (a file now present, a step now taken) it proposes lifting above the line; anything only the user can confirm it gathers into a single question asked once, never one nag per item. And when the same item has come back across several sessions without moving, Claude stops asking and offers instead to return it to the bottom of the unprocessed list — so work the user has plainly deprioritised has a way to go quiet, rather than being raised forever. This means shelved work gets lifted when its wait actually clears, instead of resting on the user to remember it.

**Seeding the queue from SPEC.** A rich SPEC — especially one a deep /setup interview produced — describes buildable features that may have no path into the queue, so the whole feature set can "die in SPEC" with nothing to build it. /plan can seed the backlog from SPEC to close that gap: it offers this automatically only in the narrow thin-queue/rich-SPEC state (Processed empty or near-empty while SPEC describes real unbuilt features), and the user can invoke it manually any time. The user chooses the granularity — a few coarse milestones or granular per-feature items — and the derived items land in Unprocessed as ordinary captures for later processing, never straight into Processed. Seeding lives in /plan, not /setup: /setup stays scaffolding and interview, and never spawns work on its own.

**Processing flow.** When /plan works through the unprocessed queue, it runs two quick passes before the one-at-a-time discussion: a triage that skims for items obviously not worth doing and offers them as one batch to drop (the user contests by number; the pass can only drop, never advance work), and a reorder that puts the biggest unblockers first when the order needs it and recommends a floor for how many to process this session. The session opens by naming what's always available — skipping an item to the bottom for later, or raising something of your own — so each item's checkpoint can then close on a single two-sided question, *carry on or stop here*, rather than reciting a menu. That shape is deliberate: a trailing "shall we close out?" reads as a recommendation to stop, and a first-time user took it that way repeatedly. A capture the user raises mid-session comes with an offer to process it now or carry on — so the user is never made to feel their idea was parked.

**Closing advice.** However a session ends, the close names two things in order: start a new chat, then run the skill it recommends. Both halves, every time. A novice reads "run /next next" as an instruction to run it in the session that just ended, carrying a spent conversation into the next piece of work — and the wording says the action ("start a new chat"), not the method's own term for it.

**Asking for prioritisation doesn't rewrite the queue.** When the user says which work should get attention first, Claude adopts that as a **session-local focus order** — it states the order, works it, skips what doesn't match as it reaches it, and moves nothing. Rewriting the queue to express "do these first" pays a full mechanical rewrite for something a session can hold as an order of attention, and where the want is simply which work comes next, the cheap answer already satisfies it. Position in the file therefore sets the durable **default** order — what anyone resuming cold inherits — rather than an order every session is bound to, and Claude names the divergence in one line when it works its own order, so the real order is never undeclared. An explicit request to reorder the queue is still honoured, but it is treated as a decision rather than an instruction: Claude asks what outcome is wanted, names a route that reaches it without a rewrite, and offers the reorder anyway with its cost stated. The user's call either way.

**Close-out reorder.** At the close of a /plan session — the same always-run /done close that positions the readiness line — Claude walks both queue sections and reorders them when the session's changes have actually disturbed the order — leaving a still-correct order untouched: Unprocessed by unlock-potential (process first what would unblock the most other work), Processed by build-order (build first what unblocks or reshapes the framing for later work). Claude owns the reorder and narrates it — the narration is the user's catch-point to redirect. (The start-of-processing reorder above orders Unprocessed for the session about to run; this close reorder sets the durable order the next session inherits.)

**Forward-recommendation advisory.** When /done closes a session with a concrete recommendation for what to plan or build next, it files a "Last session advises…" note at the top of Unprocessed — advice, not a command. The next /plan reads it and lets it orient the session; that session's /done close then deletes it — the one close that always runs, so the clear isn't skipped when a /plan ends early — once it has oriented the session, unless the note carries a condition to persist longer. The note never moves into Processed and is never treated as real work; it's a transient handoff so the recommendation survives across sessions without depending on anyone's memory.

**Multi-item /next.** /next is the single queue-clearing runner. Invoked when the user wants ready work built, it works the cleared region of the queue top-down, building each item scope-locked; a single invocation can build several cleared items back-to-back without confirming each one. The close commits the run — one item's LOG entry verbatim when only one built, a summary commit when several did, each item still keeping its own LOG entry. It finishes cleanly at the readiness line. Because /next runs faster than the user can follow, it is unattended in practice — the autonomous build mode the Principles name — and it works because /plan feeds it a well-vetted cleared region: a no-progress stop (halting if the same error, empty diff, or failing check repeats on one item) keeps a stuck item from thrashing unwatched, and a red flag rides its work item into the build with its cleared state recorded in the LOG.

**Keeping projects current.** The plugin keeps improving while projects sit set up, so a project can fall behind what the current method scaffolds. This is caught in two places, and the split is deliberate. At the start of any session, `session_start` flags whole docs or folders the project is missing and offers /setup to add them — a presence check that gates nothing. The *setting*-level catch-up runs in **/plan's opening read** instead: it checks the project's CLAUDE.md against the settings the current templates add, and adds only what's missing, never rewriting anything the user wrote. Where a setting needs an answer, Claude asks in one line and says what reads it and what changes once it's answered. It sits in /plan because a start-of-session check fires before anything knows what the session is for, so its question can only attach itself to whichever command comes first — which is exactly what went wrong: it wedged an unrelated question into a close, and on another occasion held a queued build run behind an ask about a setting the method had since retired. /plan already reads project state and cannot hold a build run. The riskier case — reconciling content whose template wording changed — is deliberately out of scope for now.

**Reporting a problem — three destinations.** Because Sovereign Implementer is itself a plugin running inside Claude Code, a problem the user hits belongs to one of three things, and Claude routes by asking which is misbehaving. Work on *their app* is an ordinary capture in their QUEUE. A problem with *the method* — a skill misbehaving, a confusing step, a rule with a bad outcome — routes out to the plugin's author: Claude drafts a scrubbed, paste-ready report (what happened, which step, the version; never the user's app details or secrets) that the user reviews and pastes at flintcraft.tech/report; Claude never submits it automatically. A problem with *Claude Code itself* — the app, its viewer, its machinery — routes to a GitHub issue on the Claude Code repository: where the `gh` tool is available and signed in, Claude offers to file it directly, showing the exact text and posting only on an explicit yes, after first searching existing issues so a duplicate becomes a supporting comment instead of a new issue; where `gh` is absent, Claude drafts the text for the user to post themselves. All three are scrubbed by construction — a report describes a sensitivity without demonstrating it. When genuinely unsure which of the three, Claude asks rather than guessing. Either the user or Claude can raise a report; when Claude notices a problem itself it offers once, without nagging.

## Principles

- Never restrict ideation, just direct it. The user must be able to ideate at any point in the build cycle.
- Hooks enforce what must never happen; hardened rules and tags steer what should usually happen. Mechanical enforcement is cheap and unskippable; behavioural steering is written to survive priority conflicts on the models users actually run.
- Execution sessions trend toward pure execution. Ideas and discoveries can be captured anywhere, but deciding their fate is planning work and happens in planning sessions. This end state is realized as multi-item /next — an unattended-in-practice build mode that works the cleared queue, stopping only for what genuinely needs the user.
- Surface risk in plain language; never bury it. Claude screens for data-exposure and breach risks and flags them where the user can't miss them. It doesn't silently ship past a security concern, and it doesn't let a risk be accepted without a recorded, informed choice.
- Readable output is a control requirement, not a style preference. The user keeps Claude aligned by reading and approving what it does, so output too long to get through breaks that control — an error the user can't read past is one they can't catch. "Be thorough" means surfacing every important thing the user must see and act on, never emitting every word: lead with the decision, then stop; gate detail behind an explicit request. This is anti-overwhelm, not terseness — the levers are sequencing and leading with the decision, never a word-count cap, and plain English for the non-coder is the standard the concision serves, not a cost it trades away.
