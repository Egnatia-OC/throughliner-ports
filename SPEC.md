# SPEC — Throughliner

## What this is

A Claude Code plugin for non-coders. It gives users a structured workflow for building apps with Claude Code without needing to know how to code.

**Its distinctive value, and the thing it is named for: the user's intent keeps running the project after Claude has forgotten everything.** Claude's memory resets each session. The **throughline** is the thread of *why* that survives that reset — carried as prose from a captured idea, through the work item, into the session record — so a fresh, short, cheaper-model session still builds the project the way the user meant instead of re-deriving intent from the code and guessing wrong. That is the product, not a side feature; framing it as occasional why-lookup is what makes the approvals and the log-writing look like pure overhead.

**The throughline is the reasoning spine, and it is not any single file.** Intent lives in SPEC, rationale rides every QUEUE item, history lives in LOG. SPEC and QUEUE are read *during* planning and building, so the throughline shapes every plan and build silently rather than only on a "why?" query; LOG is the deep archive, pulled on demand. **LOG records the throughline and is not itself the throughline** — the tell is that a complete LOG can carry no throughline at all, every event recorded with the reasoning stripped out, which is exactly the failure the mechanism fights.

**What it is worth to Claude:** it is how Claude stays aligned to intent — not just to *what* the user wants but to *why they want it that way*. Rationale riding a rule is why the rule gets followed reliably, since bare rules slip. And recorded intent is what makes a contradiction visible at all, so drift can be caught.

**What it is worth to the user:** settled things stop being re-decided, because a rejected option's reason for losing is recorded and so is not re-proposed; silent regressions are prevented, since the reason a thing is the way it is can be read before changing it; institutional memory survives a break or a handover; a growing project stays coherent instead of rotting; and the project can be trusted to still reflect intent rather than depending on Claude remembering it.

**The perceived overhead is reframed rather than denied.** The approving is what makes the record genuinely the user's and therefore trustworthy — a reason they never vouched for is one they cannot trust on read-back. The log-writing pays a small cost now against the large "why did we do this?" cost later. And externalised intent is exactly what lets short, cheap sessions work at all.

**In user-facing help, the work-flow and the throughline are two separate beats.** How work moves — captured, processed, built — is the work pipeline. The throughline is the *why that travels alongside it* and survives Claude forgetting. Explaining them as one thing collapses the distinction.

## Who it's for

Non-coders who know what their app should do but need a framework to keep Claude aligned.

**It is built for someone willing to read and approve the record.** Someone who won't read is considered but is not the target, and the design is never lowered to them — a workflow built around its own expected non-compliance has nothing left in it. So the reading is assumed, and **length is the thing that has to be earned**: an artifact that outruns what a person will get through is the tool's failure, not the reader's.

**Every written artifact is therefore sized to be read.** Enough is written that the work can be done and the reasoning survives; short enough that reading it is worth a person's time. Both halves bind. An artifact too thin to rebuild intent from has failed, and so has one too long to get through — and the second failure is the one this method has actually produced, at scale, while the first was the only one it was watching for.

## How it works

Splits changes into a build queue that helps the user harness Claude's skills in dependency management, not just coding. The secondary core functionality is basic context window management.

Five skills drive the workflow:
- `/setup` — scaffold project docs and run the onboarding interview.
- `/plan` — manage the queue, add ideas, resolve questions, check for drift. It opens by running a mechanical digest of the queue rather than reading the whole file — one line per queue entry, carrying everything the session's queue-wide reasoning uses and none of the rationale prose, which is read per item as each is presented. Each line also carries **any other work item this one names whose work has already shipped**, and **the date the item first appeared in your queue** — both facts you can check, never a judgment about what to do with them. Work that shipped is recognised by its having a session record, which is what makes "has this been done?" answerable from the files rather than from memory; an item leaning on work already finished has a premise worth re-reading before it gets built. A separate block lists **every file named by two or more items**, which is where work that can be settled together shows up. The digest also reports **placement contradictions**: an item sitting in the ready region whose own text says it must not be built or was returned unbuilt, an item whose file list names nothing to change, and a loop of work waiting on itself — which can never be released, unlike an ordinary chain of waiting work, which resolves the moment its far end does and is already visible on each item's own line. It also flags **work resting on a superseded finding**: research you've filed under `resources/research/` gets a `Superseded by:` line at the top when it's overtaken, and any work item naming that file is flagged so the correction reaches the decisions built on it — otherwise a citation runs one way, and a finding that turns out to be wrong leaves every piece of work scoped against it silently wrong too. That flag reaches only items that *name* the file; work resting on a finding it never cites isn't caught, and the digest says so rather than letting you read it as complete coverage. These are surfaced for you and never acted on — moving work out of the ready region is your decision. The point is that work is otherwise checked on the way in and never looked at again, so an item can rot in place after it was placed correctly. **The method also carries rules for maintaining your own SPEC**, applied whenever a session edits it — from either site, planning or a build that discovers it needs a SPEC change. Three of them: what belongs in SPEC at all (product truth, not how a thing is implemented), that the reasoning behind a decision goes to the session record rather than into the SPEC sentence, and that a SPEC sentence describing something the project no longer does is a defect to correct rather than clutter to tolerate. **There is no size limit and no growth report**, because SPEC has a floor a rule list doesn't: it has to describe your product as it actually is, so a true sentence about a live feature can never be removed to save room.
- `/next` — pick the top piece of ready work and execute it, routed by its flavor: a **build** (Claude edits files) or an **`[audit]`** — a first-class review pass where Claude reads and reports findings for later review, without editing. (Audit is its own flavor with its own discipline; it never edits on the spot.) A `[user]` item is a walk-through rather than something Claude runs — reserved for work Claude genuinely can't do or witness (a check that needs your eyes, a decision only you can make, a physical action), never for work Claude could run itself but is only blocked from running yet. Claude leads by walking you through it live, one step at a time — running whatever parts it can and guiding the rest through the concrete steps the item carries — and names how to close it out only once you've finished: run /done, or mention it at the next /plan. A **`[freeform]`** item is one /next must not run at all — work you and Claude do by hand in a session of its own, because it is large or because it characteristically can't run inside a /next run. Repairs to the machinery /next itself depends on are one such case, where using a broken mechanism to fix itself is the risk, but they are an example rather than the definition. /next halts on one rather than skipping past it, and a close that finds one waiting says so. /next works the cleared queue top-down — building each ready item and committing at the close — so a single invocation can clear several vetted items in a row without confirming each one, finishing at the readiness line, and it never proposes doing fewer items than the line allows: the line is the run's bound and it is set during planning. A run has one other bound, and only one: an item marked **`Runs alone`** is work that is ready to build but must not share a run with other work, because a run in flight holds the file paths it is working from — a rename, a folder move, or a migration that moves paths underneath a run makes those stale mid-build. /next stops before it rather than sweeping it into a longer run, saying plainly why, and builds it on its own next time. The marker binds /next and nothing else; it never claims the work can't be done alongside other work by hand.
- `/rescan` — look back over the conversation for anything decided, noticed or asked for that was never written into a file, and file it as captures. **User-invoked, never positional**, and repeatable within one chat: it scans back only as far as the last /rescan, so running it twice does not re-surface the same things. It **files and never routes or builds** — the standing filing-vs-processing boundary, and the reason it does not build is that the installed plugin is a frozen copy, so a fix made mid-chat could not reach the chat that made it anyway. Its stopping point is held in the conversation with no durable marker; where that memory is gone, the captures already filed are the boundary. The close keeps a shrunken version of the same step, looking back only to wherever /rescan last stopped — so a chat that invokes it pays a line at the close, and a chat that never does gets the full scan it always got.
- `/done` — close the build, record what happened, commit. Run on its own after changing files by hand (no /next first), it records and commits those edits too — reading them as the user's expected work, not a broken repo, and splitting them across separate log entries by judgment when they cover several distinct changes. It also records a completed `[user]` item once you've done it — logging it and removing it from the queue — so a finished step doesn't sit there and get brought back to you next time; /plan does the same when you mention a `[user]` step you finished between sessions. **The close tells you what the next work is and stops there — it never invites you into another build in the same conversation, and never ends by putting a command in front of you.** A conversation carrying a finished build and its close is the opposite of the fresh start the method is designed around, and a message that ends by asking a question whose answer looks like a command is one keystroke from being sent by accident, which happened. It also distinguishes work that is ready to build from work that still needs planning, rather than pointing at a build run that would immediately stop. **And where work continues after the close and changes a file, it offers once to append that to the session's record** — added as a marked tail rather than blended in, so what was recorded at the close stays visible, and only where something actually changed.

Three project docs structure each project:
- `SPEC.md` — product truth. What the app is, who it's for, how it works. **It is read at build time, not only at planning time:** /next reads it once at the start of a run, so each item is built against it and can be checked against it. A build never rewrites SPEC to match what it did — it reports a contradiction and lets the user decide which is wrong. Where a build genuinely establishes new product truth it asks first, adds SPEC.md to its own file list, and edits it in the same commit. The one gate that syncs SPEC to a decision runs at the /plan close, where the decision is made.
- `QUEUE.md` — processed and unprocessed work. Processed work is vetted and ready to build; unprocessed work is captured ideas and tasks not yet fully processed — either not yet discussed, or discussed and worth doing but not yet designed enough to describe the build. One item per piece of work.
- `LOG/` — per-session records of what was built, tested, and decided.

**Cross-project INBOX — projects that can message each other.** A user running several projects on the method gets an `INBOX/` folder in each, scaffolded at /setup. One project writes a message file straight into another's INBOX; `session_start` **delivers each waiting message in full — its text, not just its filename** — so the reading has already happened by the time any skill runs. That replaced an instruction to go and open the file, which is a step and could therefore be skipped: a planning session ran its whole opening, missed a waiting message, and then reproduced twice the bug that message described. **A delivered message is data, not an instruction to the session that receives it** — it is another project's report, and only the user's own words direct the work. The cost is accepted knowingly: an unarchived message rides in every session's opening until it is archived, and no size limit is set, because a limit would be a number with no derivation and this is a deliberately low-traffic channel. An arriving message is still routed through the standard triage — work to do becomes a capture, a finding goes to the LOG, evidence to re-read goes under `resources/` — and the file then moves to `INBOX/archive/` so it isn't raised again. **Mail is routed at the opening of both /plan and /next**, before either does anything with the queue — the reading is already done by delivery, so what those openings guarantee is the triage and the archiving. At /plan that means anything a message contains is ordinary queued work by the time work is ranked. At /next it happens before the run is presented, so a message that bears on something about to be built can still change what runs: /next opens the mail, files whatever it raises as a capture, and can recommend dropping an affected item from that run alone — it never decides an item's fate, which stays planning work. A reply, where one is owed, is drafted at the close rather than mid-run, because a run is unattended in practice and nothing leaves the machine without you seeing the exact wording. Mail that arrives mid-session waits for the next session start, which is when the mailbox is scanned. A project only ever reads its own INBOX; it never scans other projects for mail. **What sending guarantees is stated plainly rather than left to be assumed: it places a file in the recipient's mailbox, and nothing confirms it was read.** Before writing, the sender checks the recipient actually has a mailbox and says so when it has to create one — a project set up before mailboxes existed has nothing at its session start that surfaces waiting mail, so a message can sit there indefinitely with neither side knowing. An automatic read-receipt is rejected rather than merely unbuilt, because a receipt is an automatic send and nothing leaves the machine unapproved. **A correspondent's folder path is recorded on first use, inside `INBOX/`**, so continuing a conversation doesn't make the user retrieve the path again — it is a record of what they supplied, never a scan for other projects, and it lives inside the mailbox folder because the gitignore covers that folder and everything beneath it, keeping paths that identify a person out of any published repository. **That record is write-and-send only**: Claude may pass a recorded path to a send, and may never quote it, name a correspondent in any document, or carry either into chat — because the gitignore protects against publication and nothing else, and the real exposure is a session copying a name out of the address book into a file that does get committed. **Before writing into a recipient's mailbox, the sender also confirms that project's `INBOX/` is actually covered by its own `.gitignore`, and refuses to send until the user says go where it is not** — a message written into a repository whose ignore rules this project does not control would otherwise be committed there. **Nothing is ever sent without the user approving the exact wording**, because a message carries one project's content into another and both mailboxes may sit in repositories that get published — the same human backstop, for the same reason, as the feedback report. **`INBOX/` is gitignored on every path — at /setup and at migration — and no question is asked. That protects against publication and nothing else**: the files still sit in plain text on disk, readable by any session in the project, which is why what may be done with their contents is restricted separately. A read message is archived rather than deleted, so a mailbox left in the repository accumulates another project's raw text forever, after its useful content has already been carried into the queue in this project's own words. The safe outcome must not depend on a question, because a question is skippable — and the migration path skipped it. Where a project already has INBOX files in its git history, /setup says so plainly rather than implying the ignore line undoes it.

Three hooks enforce discipline mechanically, and a fourth advises:
- `session_start` — detect project state, load behaviour rules, surface the queue's dependency facts in one line (how much work is ready, how much is held, and how many of the things it waits on are themselves unprocessed — emitted even when all three are zero, so a computed zero can't be mistaken for a check that never ran; it also **names** which held item waits on which blocker, and which held items name a blocker that is in neither section, which is the signal that something may be ready to lift), report **whether this session is isolated from any other session open on the project** (measured, never assumed — it decides which parallel-session advice applies). There are **three** isolation cases, not two: an ordinary shared working tree, a linked worktree, and a **clone inside a cloud container** — which is what a session started from the mobile or web app runs on. A clone is a main checkout, so the git comparison alone would call it a shared tree and give it the one piece of advice that actively misleads, that collisions are handled; the cloud case is therefore detected from the environment first, and told plainly that its work reaches the main machine only as a pushed branch. It also reports **any worktree carrying commits this checkout doesn't have**, so an isolated session's work can be offered a merge rather than stranded on a branch nobody is tracking (the offer happens in a main-checkout session, since git refuses to update a branch checked out elsewhere). **Those worktrees are classified rather than merely listed**: one inside the project's own `.claude/worktrees/` is where Claude Code allocates a session's worktree, so it is session work and the merge is offered; one anywhere else is a deliberate long-lived worktree and is never offered. The classification fails in one direction only — if the worktree location has been changed from its default, real session work is called deliberate and goes unoffered, which is a missed offer rather than a wrong one, name any **working file left behind by a session that never closed** (surfaced, never deleted, since it can hold the only record of what that session did), and halt the session when the project's documents are on an older format than the installed plugin expects (see Keeping projects current). The facts are inputs, not instructions: /plan turns them into its throughput recommendation, and other skills ignore them.
- `pre_tool_use` — enforces the scope-lock (which governs SPEC.md like any other file) and git safety. The lock reaches planning sessions too, against a **standing** list rather than a build's agreed one: a planning session may write your queue, your spec, your session records, your FAQ, your research notes and its own scratch files, and a write to anything else is refused rather than offered to you for approval. The refusal is the point — an approval request that gets waved through is not consent, and a planning session is where a change should become a piece of queued work instead of an edit. What it costs is stated rather than discovered: a genuinely needed change outside that list now stops the session and becomes an item, where it used to be one sentence. and asks for your approval before Claude spawns a subagent (a cost guard that asks, never blocks). It also blocks any attempt to write one of your files through a script rather than through the editing tools — whatever the file is, and whether or not it's in the current work's scope — pointing Claude at the editing tools instead, or at the purpose-built queue tool for large queue edits. A script whose target file is *worked out as it runs* rather than written down is blocked too, since a target nobody can read cannot be shown to be safe; the accepted cost is that a genuinely harmless scratch write has to name its file plainly.
- `stop` — checks Claude's finished response for a report that names a capture as filed, and confirms that entry is actually in your queue. If it isn't, the turn is fed back so the write can be made and you can be told plainly what happened, before you act on a report of work that doesn't exist. It catches reports that *name* the item; a vague "I've written that up" escapes it, which is accepted rather than hidden, since the rule already requires a report to name what landed. It blocks once per claim and then stops blocking, so a genuine mismatch can't trap the conversation.
- `post_tool_use` — advisory QUEUE.md structure lint; flags format drift, never blocks. It runs after an edit lands on the queue **and after any shell command**, since a write reaching the queue through a script bypasses the editing tools entirely. It also scans QUEUE.md, SPEC.md and LOG entries for things shaped like credentials — private keys, API tokens, email addresses.

**Privacy posture, settled at setup.** Scaffolding offers once to add `SPEC.md`, `QUEUE.md` and `LOG/` to `.gitignore` so they never enter the repository — the maximally-private posture, for anyone who doesn't want their plans, reasoning and session history tracked or published. The trade is stated when it's offered: those documents stop being version-controlled, so an unwanted change can't be undone by reverting. It is part of scaffolding rather than a sixth interview question, because it is answerable without knowing anything about the project. **A public repository is set up only when the user asks for one**, never volunteered, and the licence question travels with that offer rather than sitting in the interview — a licence only becomes a real question once the code is going somewhere public, and asked earlier it is one most non-coders cannot answer while still describing what their app is. The cost is named: someone who never asks for a public repository never considers licensing at all. **The offer may set up the repository and may never represent the contents as screened** — that would contradict the limit below, and the honest thing to say is that not publishing these documents is the only complete protection. The idea that open source implies open logging is deliberately not surfaced at setup: raising it at all nudges toward publishing planning documents, which is the direction that limit exists to avoid nudging.

**What the scrub gate does and does not promise.** The scan above catches credential *shapes* only: deterministic, no judgement, so it never produces false confidence. Alongside it, Claude reads what it is about to write against a checklist — personal names, case details, third-party data, identifying paths — at the three moments text enters a committed doc: filing a capture, keeping one as a work item, writing a LOG entry.

The limit is stated deliberately and must never be softened. The checklist is Claude checking its own writing, and no pattern can tell whether a sentence quietly identifies a real person — which is the thing that actually leaks from these files. So the method never tells a user their artifacts are scrubbed or safe to publish. A gate that over-claims is worse than no gate, because the user publishes more freely believing it worked. This is the same line the method holds on red flags: provide risk-*addressing*, never promise risk *management*. For a repository that will be public, the only real protection is not publishing these artifacts at all.

**Editing-state signal — a published contract other apps can read.** While Claude is writing a file, the hooks publish a small marker saying so, so another application open on the same document — a Markdown reader or editor the user is reading and typing in — can hold off rather than the two landing on top of each other. It replaces a guess with a fact: a watcher can see *that* a file changed but not *who* changed it, and a wrong guess locks the user out of their own document mid-sentence.

It is a **heartbeat, not a lock**, and that is what makes it safe: every marker carries a fresh timestamp, a reader treats a stale one as "not editing" whatever its flag says, and a missing marker means nothing is happening. So it fails open — a crashed session can never lock the user out of their own document, and the overwhelming majority of projects, which never have this plugin installed, are unaffected.

**The field-level contract lives in [EDITING-STATE-CONTRACT.md](EDITING-STATE-CONTRACT.md)**, at the repository root. It is a published interface another application is built against, so it needs a home a consumer can find and cite — which is not this document. What belongs here is what the product does; what the JSON fields are called belongs there.

One rules doc steers everything the hooks can't enforce:
- `skill-nonspecific-rules.md` — loaded at every session start in adopted projects. It carries only rules that fire whatever is running, which is what its name states and what admits a rule to it: communication, capture routing, dependency ownership, file safety, and five response-shape tags ([SILENT], [BRIEF], [DISCUSS], [PROMPT], [SEQUENCE]) that procedure docs place on individual steps to control verbosity and interaction. A rule that fires inside one skill lives in that skill's own doc instead, where it is paid only when that skill runs. Rules are stated bare, with the reasoning kept out of the operative statement; where a reason is genuinely needed to apply a rule correctly, it is reclassified as operative text and written into the rule itself rather than kept as an attached why-clause. Material whose trigger is unmissable is fetched on demand rather than always-loaded (the consumer feedback channel and the INBOX mechanics live in `feedback-and-inbox.md`), so the always-loaded set stays within the number of instructions a model follows reliably.

**The plugin no longer ships an output style.** One was shipped from 2026-06-15 to 2026-08-14, applied automatically at system-prompt priority. It was removed because its rules were stated three times over — in the always-loaded rules file, in the style, and (for this project's author) in a personal global instruction file — and triplication degrades the rules around it. The three rules the style alone carried moved into `skill-nonspecific-rules.md` and are described there: how often to speak while working, that a document written to disk is written to what the task needs, and the counterweight that length is free where it carries substance. What is lost with it is priority, not content: the migrated rules reach a session as ordinary always-loaded steering rather than at system-prompt level, and a consumer's own chosen output style is no longer overridden.

**Write-first approval.** Claude writes to the project's docs first and reports what landed, rather than pasting a draft into chat and waiting for approval before writing. Which moments work that way is settled by one test rather than a memorised list — **is the previous version recoverable without the user's help?** Queue items and captures, LOG entries, SPEC edits and ordinary build edits all answer yes: they are tracked in git, so an unwanted change costs a revert and nothing else, and the user reads the text in the doc where it lives anyway. Three kinds answer no and are still shown before they happen: a **commit message**, because a commit is materially harder to unwind and the message never becomes file content, so "write it first" has no meaning for it; anything that **leaves the machine** — the feedback report, an outbound INBOX message — where no revert reaches the copy already delivered; and a **wholesale conversion of a document the user already owns** where git does not yet hold it, which is what /setup's queue migration does to a project that may have been adopted moments ago. That third case is the test applied, not an exception bolted on: the wording used to ask whether a revert would undo it, which quietly assumed a safety net that a freshly adopted project may not have.

**And the user can ask for show-first at any time**, for the rest of that session — the switch moves only toward more showing, so the three cases above stay show-first regardless. It is held in the session and never stored, because it records where the user is right now rather than anything stable about them. Separately, a session can be asked to paste doc-bound text inline instead of linking to it; in a /next run that also displays each edit's new wording inline, with Claude naming any items large enough that inline display would bury the run. Showing an edit is visibility, not approval — the work was agreed at planning time — so it never makes a run wait. A single test rather than an enumerated carve-out survives new approval moments being added later, which a list would silently omit. The report after a write is one line naming what landed and where, specific enough to object to without opening the file, never a re-paste of the text just written. The trade is stated rather than discovered: show-first guaranteed unapproved text never reached disk, and write-first means a file briefly holds content the user has not agreed to — cheap and recoverable in a git repository, but rejection becomes a revert rather than a non-event, and the risk it introduces is not rejection but the user not noticing, which is why the one-line report carries the weight it does.

**View-in-doc rendering.** Text that already lives in a project doc (an existing queue item, a just-written capture or log entry, a readable edit) is surfaced as a one-line pointer plus a link to the file, rather than re-pasted into chat — the token-saving default, and unconditional: there is no stored setting gating it. Text that isn't written yet has nothing to point at, so it appears inline. Links are plain file links and never promise a line anchor: the desktop app opens `.md` in its own viewer and ignores the anchor, so where a line matters it is named in the surrounding prose instead. The one override is the user's: the session's first opening narration carries a one-line offer — bundled into a narration that already fires, never asked as its own question — to paste doc-bound text inline for that session, for anyone reading on a phone or away from their computer. Two settings that used to govern this, a stored working mode and a recorded editor, are retired: the app opens `.md` whatever editor is named, and the location field recorded how much text the user wanted pasted rather than where they were. A stale field in an existing project is ignored silently.

**No completion asks on `[user]` work.** A `[user]` step is walked through and nothing more: no session — building, planning or closing — ever asks whether one is already done, leading, trailing or in passing. Completion is *inferred* from what a session can see: a step walked to its end this session is done, a step whose prerequisite visibly hasn't cleared isn't, and the user mentioning one is the third way. Where a step leaves an observable result — a URL responding, a branch gone, a file present — the method checks the world rather than accepting the report, because a step was once logged complete when the work had in fact been blocked. The gap this leaves is deliberate and documented: a step completed privately, with nothing observable to show for it, sits in the queue until the user mentions it. The `Completion mode:` setting that once toggled a planning-time sweep is retired; a stale field in an existing project is ignored silently.

**Readiness line.** /plan maintains a line in the queue — rendered `--- Cleared to run above this line ---` — that marks which work is vetted and safe to build (above it) from work that still needs planning (below it). It is positioned at the close of a /plan session — the single close (run by /done) that always fires however the session ends, so the positioning is never silently skipped — and Claude narrates where it sits whenever the line moves, confirming silently when its placement is unchanged, so the user never has to work out by hand how much of the queue is safe to run next without being told the same boundary twice. /next inherits it as its run bound when it works several items in a row — a clean finish at the line rather than running into unvetted work.

**Lifting shelved work.** Work sits below the readiness line for exactly two reasons, and each is written on the item itself: **another named item in the queue blocks it** (`Blocked by: [slug]`), or **a date it must not be built before has not yet passed** (`Not before: YYYY-MM-DD`). The queue lint checks both — that a slug resolves to a real entry in the queue, and that a date is a real one. Work waiting on anything else *outside* the queue — a restart, a site going live, someone else's reply — is not shelved with a note about the wait; the awaited thing is filed as its own queue item, so it gets planned and done like any other work, and the held item names it. A date is the exception because it needs nobody: every other blocker takes a human or a build to resolve, while a date is read off the calendar by the hooks, so a queue item standing in for one costs a planning session to answer a question nobody has to think about. At the start of every /plan, Claude checks one thing per shelved item — has its blocker shipped, or has its date passed? — and proposes lifting the ones that are ready. Nothing is asked of the user, because the answer is in the record and the calendar rather than in their memory.

This replaced a model where the wait was recorded as a prose sentence inside the held item and re-interpreted each session. That failed in a specific way: a blocker written as a sentence inside another item is invisible as work, so nobody picks it up. One item sat shelved for weeks on a step buried in its wait-sentence, and became visible the moment it was filed as its own line. Relatedly, before any work is tagged `[user]` at all, the method names the tool that would do it and confirms that tool is absent or unavailable — a check rather than a judgment, because work that merely *sounds* manual has been handed to the user when a command-line tool could do it in seconds.

**Seeding the queue from SPEC.** A rich SPEC — especially one a deep /setup interview produced — describes buildable features that may have no path into the queue, so the whole feature set can "die in SPEC" with nothing to build it. /plan can seed the backlog from SPEC to close that gap: it offers this automatically only in the narrow thin-queue/rich-SPEC state (Processed empty or near-empty while SPEC describes real unbuilt features), and the user can invoke it manually any time. The user chooses the granularity — a few coarse milestones or granular per-feature items — and the derived items land in Unprocessed as ordinary captures for later processing, never straight into Processed. Seeding lives in /plan, not /setup: /setup stays scaffolding and interview, and never spawns work on its own.

**Processing flow.** A /plan session opens on two beats, in this order. First the triage: a skim for items obviously not worth doing, offered as one numbered batch to drop — the user contests by number, and the pass can only drop, never advance work. It fires only when something is obviously droppable, and it comes first because there is no point ordering items about to be deleted. Then one question, with its default named: anything the user wants to prioritise, or shall Claude work through them most-unblocking-first? That single question replaces what used to be a separate "anything to discuss?" opening, so the session asks two things where it once asked three. The reorder that follows applies whatever the user chose, and recommends a floor for how many items to process this session. Where nothing meaningfully unblocks anything else, the order falls through an internal ladder of four rungs — an uncleared red flag in the unprocessed queue first, then unblock-potential (how many other entries cite this one's slug, most-cited first), then longest first **by line count among entries at or above the section's median length**, and beneath that oldest first **by the date an entry was filed**. **Every rung either reads a field the queue digest already computes or subtracts two line numbers**, so ordering costs no judgment. Line count is deliberately the arithmetic and not an impression of length: an entry's last line minus its first, with nothing counting words and nothing reading the entry to place it. Longest-first rests on cost-of-reading rather than on length predicting anything about an item's readiness — long items are what make the queue expensive to reason across, so taking them first shortens it fastest. **It is partitioned at the median so that it terminates.** Unpartitioned it ranked every entry and so never yielded, which meant any rung beneath it could never fire at all — a rung that cannot be reached by construction. The median is a proportion of the section it orders, computed and printed by the digest at each session opening, so no figure is written into the method's text. The rung beneath it is decay, and it exists for the case of a long queue whose owner does not get through the full set for many sessions — for that person entries genuinely rot, and nothing in the shorter ladder ever reached them. It reads the **date filed** rather than file order, because the queue can be reordered on request and a file-order rung would then rank by something that had just been overwritten. **Staleness in the other sense is still not an ordering concern**: an item whose premise names work that has already shipped is flagged in the digest at the session opening, where the user sees it, rather than pulling the item forward — a different fact from how long the entry has been waiting. The ladder is applied and narrated, never offered as a choice: the user sees one line naming the order used. During the one-at-a-time pass, each item's checkpoint lets the user skip an item for a later session — skipping sets it aside for the rest of that session and does not move it in the file, so the queue keeps recording the order things landed. **An item skipped because it will not design out names what would settle it and who owns that** — a decision the user owns, a fact to look up, or a build that must ship first — **and where the answer is a decision the user owns, Claude asks before skipping rather than deferring again.** Planning is the one moment they are there, and an item that is enriched every session without the one available question ever being put is an item nobody is deciding — and a capture the user raises mid-session comes with an offer to process it now or carry on, so the user is never made to feel their idea was parked. New captures are added to the end of the queue rather than slotted in beside related work; a relationship between two items is written into the items themselves, where it survives any reordering.

**Close-out pass: batching the stops that need you.** At the close of a /plan session — the same always-run /done close that positions the readiness line — Claude makes one pass over the ready section, moving `[user]` steps and `[audit]` reviews to the end so the moments needing your attention sit together instead of interrupting a run partway through. Claude does it and says so; it isn't a question.

**That is the only reordering the close does, and the reduction is deliberate.** It used to re-derive the order of both sections. Neither re-derivation earned its cost. Everything above the readiness line is built by a single run, so its internal order rarely changes anything — and where two pieces of work genuinely affect each other, that is written into the work itself, which survives being moved where sitting next to each other does not. The unprocessed section is ordered at the start of the next planning session anyway, at the moment the order is actually used, so computing a lasting order at the close meant computing something its only reader immediately recomputed. Left alone, the queue reads in the order things landed, which tells you more than a ranking that was already stale.

**Forward-recommendation advisory.** When /done closes a session with a concrete recommendation for what to plan or build next, it files a "Last session advises…" note at the top of Unprocessed — advice, not a command. The next /plan reads it and deletes it in the same breath — surfacing it is what consumes it, unless the note carries a condition to persist longer. The clear sits at the read because the session reading the note is the one that can tell it is spent: it used to happen at that session's close, which meant a build session passing between two planning sessions left a consumed note behind, and the next /plan opened on advice about work that had already shipped. Clearing at the read means the note is gone even if the planning session then ends without acting on it, which is accepted — the advisory is orientation rather than work, and a session that read it has had the orientation it was for. The note never moves into Processed and is never treated as real work; it's a transient handoff so the recommendation survives across sessions without depending on anyone's memory.

**Multi-item /next.** /next is the single queue-clearing runner. Invoked when the user wants ready work built, it works the cleared region of the queue top-down, building each item scope-locked; a single invocation can build several cleared items back-to-back without confirming each one. The close commits the run — one item's LOG entry verbatim when only one built, a summary commit when several did, each item still keeping its own LOG entry. It finishes cleanly at the readiness line, or earlier at an item marked `Runs alone`. **Work raised mid-run that isn't part of what's being built is captured rather than done, and the run says why in one clause** — the run stays on agreed work, and the new thing gets weighed against everything still to come rather than being decided by whoever is in the room. **Asking a second time for the same thing carries a small change (a file or two) straight through**, since a repeated request is the user's decision; a large or half-designed one still gets a proposal to split, because a repeated request doesn't make a big change small.

Because /next runs faster than the user can follow, it is unattended in practice — the autonomous build mode the Principles name — and it works because /plan feeds it a well-vetted cleared region: a no-progress stop (halting if the same error, empty diff, or failing check repeats on one item) keeps a stuck item from thrashing unwatched, and a red flag rides its work item into the build with its cleared state recorded in the LOG.

**Keeping projects current.** The plugin keeps improving while projects sit set up, so a project can fall behind what the current method scaffolds. At the start of a working session, before /plan or /next, `session_start` catches this three ways: it flags whole docs or folders the project is missing (offering /setup to add them), it tops up an existing doc that's missing a newer *setting* the method has since added, and — the strongest of the three — it **halts the session outright** when the project's documents are on an older *format* than the plugin expects. **The update notice says that /setup wants a session of its own**, because the notice is what prompts someone to run /setup mid-session in the first place. /setup backs that up at the point of running: it **refuses outright while a build is in progress**, since it would otherwise fail file by file against the build's safety check rather than stopping cleanly at the door, and in a planning session it **describes what is about to happen and lets the user choose** — no refusal there, because nothing is blocked, but silence is the failure to avoid.

The halt exists because the other two only notice what's absent, and the damaging case is a file that is present but on a shape the method no longer reads correctly: nothing errors, so /plan and /next spend the whole session reasoning over stale scaffolding and report a confidently wrong picture. Each project records its format in a `.throughliner-format-epoch` marker and the plugin declares the current one; when the project is behind, the session opens by saying so and pointing at /setup, which migrates the documents rather than replacing them. The format number is deliberately **not** the plugin version — the version changes at every release, most of which change no format, so a version check would cry wolf and be learned-past. Detecting the format by inspecting the documents' structure was rejected for the same reason in reverse: it guesses, about files users legitimately hand-edit. The user can override the halt and carry on; they're told once that results may be unreliable until the migration runs. The top-up is add-only — it never rewrites or clobbers anything the user has written; where a setting needs an answer (like which editor they work in), Claude opens with a one-line question and writes the answer, and settings needing no answer are added silently with a note. The missing-setting check is a list, so new settings join it over time. The riskier case — reconciling content whose template wording changed — stays deliberately out of scope: overwriting a paragraph the user may have written themselves is the thing that must not happen. What is in scope is the strictly smaller half, **detecting retired terms**: the migration reads the project's own CLAUDE.md for names of method pieces that no longer exist — a queue of batches with Build/Test/Audit sub-headings, a Deferred tests section, `Parked:` headers — and reports each one alongside what replaced it. It reports and edits nothing, so it can never clobber their words, and the decision about their own file stays theirs. The gap it closes is real and was reported from a live project: that description was written at setup and is read at the start of every session since, so a session goes looking for a section the method removed months ago and has to work out from scratch that it is gone.

**Reporting a problem — three destinations, one question.** A user's problem is with one of three things, and each has its own home. Their **app** is ordinary work and stays as a capture in their QUEUE. The **method** — a skill misbehaving, a confusing step, a rule with a bad outcome — has nowhere useful to go in their own project, so it routes out to the plugin's author at flintcraft.tech/report. **Claude Code itself** — the app the method runs inside, its viewer, its links, its hooks machinery — belongs to Anthropic, and routes to a GitHub issue on `anthropics/claude-code`. Claude decides by asking which thing is misbehaving, and asks the user rather than guessing when it genuinely can't tell.

Both outward routes are scrubbed by construction — what happened, which step, the version; never the user's app details or secrets — and neither sends anything the user hasn't seen and approved. They differ only in mechanics, deliberately: a method report is a web form Claude can't submit, so Claude drafts it and the user pastes it; a Claude Code report can be filed with `gh`, so Claude posts it on an explicit yes rather than sending a non-coder to a GitHub form, falling back to a draft-and-paste when `gh` isn't available. The Claude Code route also searches existing issues first — which shapes the report rather than merely avoiding duplicates, since knowing the adjacent issues is what lets a report distinguish itself. Either the user or Claude can raise a report; when Claude notices something misbehaving it offers once, without nagging.

## Principles

- Never restrict ideation, just direct it. The user must be able to ideate at any point in the build cycle.
- Hooks enforce what must never happen; hardened rules and tags steer what should usually happen. Mechanical enforcement is cheap and unskippable; behavioural steering is written to survive priority conflicts on the models users actually run.
- Execution sessions trend toward pure execution. Ideas and discoveries can be captured anywhere, but deciding their fate is planning work and happens in planning sessions. This end state is realized as multi-item /next — an unattended-in-practice build mode that works the cleared queue, stopping only for what genuinely needs the user.
- Surface risk in plain language; never bury it. Claude screens for data-exposure and breach risks and flags them where the user can't miss them. It doesn't silently ship past a security concern, and it doesn't let a risk be accepted without a recorded, informed choice.
- Readable output is a control requirement, not a style preference. The user keeps Claude aligned by reading and approving what it does, so output too long to get through breaks that control — an error the user can't read past is one they can't catch. "Be thorough" means surfacing every important thing the user must see and act on, never emitting every word: lead with the decision, then stop; gate detail behind an explicit request. This is anti-overwhelm, not terseness — the levers are sequencing and leading with the decision, never a word-count cap, and plain English for the non-coder is the standard the concision serves, not a cost it trades away.
