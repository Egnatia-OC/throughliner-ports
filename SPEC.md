# SPEC — Sovereign Implementer

## What this is

A Claude Code plugin for non-coders. It gives users a structured workflow for building apps with Claude Code without needing to know how to code.

## Who it's for

Non-coders who know what their app should do but need a framework to keep Claude aligned.

## How it works

Splits changes into a build queue that helps the user harness Claude's skills in dependency management, not just coding. The secondary core functionality is basic context window management.

Four skills drive the workflow:
- `/setup` — scaffold project docs and run the onboarding interview.
- `/plan` — manage the queue, add ideas, resolve questions, check for drift.
- `/next` — pick the top piece of ready work and execute it, routed by its flavor: a **build** (Claude edits files) or an **`[audit]`** — a first-class review pass where Claude reads and reports findings for later review, without editing. (Audit is its own flavor with its own discipline; it never edits on the spot.) A `[user]` item is a walk-through rather than something Claude runs — reserved for work Claude genuinely can't do or witness (a check that needs your eyes, a decision only you can make, a physical action), never for work Claude could run itself but is only blocked from running yet. Claude leads by walking you through it live, one step at a time — running whatever parts it can and guiding the rest through the concrete steps the item carries — and names how to close it out only once you've finished: run /done, or mention it at the next /plan. /next works the cleared queue top-down — building each ready item and committing at the close — so a single invocation can clear several vetted items in a row without confirming each one, finishing at the readiness line.
- `/done` — close the build, record what happened, commit. Run on its own after changing files by hand (no /next first), it records and commits those edits too — reading them as the user's expected work, not a broken repo, and splitting them across separate log entries by judgment when they cover several distinct changes. It also records a completed `[user]` item once you've done it — logging it and removing it from the queue — so a finished step doesn't sit there and get brought back to you next time; /plan does the same when you mention a `[user]` step you finished between sessions.

Three project docs structure each project:
- `SPEC.md` — product truth. What the app is, who it's for, how it works.
- `QUEUE.md` — processed and unprocessed work. Processed work is vetted and ready to build; unprocessed work is captured ideas and tasks not yet fully processed — either not yet discussed, or discussed and worth doing but not yet designed enough to describe the build. One item per piece of work.
- `LOG/` — per-session records of what was built, tested, and decided.

Two hooks enforce discipline mechanically, and a third advises:
- `session_start` — detect project state and load behaviour rules.
- `pre_tool_use` — enforces the scope-lock (which governs SPEC.md like any other file) and git safety, and asks for your approval before Claude spawns a subagent (a cost guard that asks, never blocks).
- `post_tool_use` — advisory QUEUE.md structure lint; flags format drift, never blocks.

**Editing-state signal — a published contract other apps can read.** While Claude is writing a file, the hooks publish a small marker saying so, so another application open on the same document — a Markdown reader or editor the user is reading and typing in — can hold off rather than the two landing on top of each other. It replaces a guess with a fact: a watcher can see *that* a file changed but not *who* changed it, and a wrong guess locks the user out of their own document mid-sentence.

It is a **heartbeat, not a lock**, and that is what makes it safe. Every marker carries a fresh timestamp, and a reader treats a stale marker as "not editing" whatever its flag says — so a session that crashes between starting a write and finishing one can never leave the user locked out. Staleness is the safety property, not a detail.

The contract, which another application is built against and which will not change without a version bump:

- **Location** — `.throughliner/` in the project root (the folder holding SPEC.md and QUEUE.md). A reader with a document open walks up the directory tree to find it, the way tools locate `.git/`.
- **One file per session**, named `editing-<session-id>.json`, holding `version` (leading, so a reader can recognise a format it doesn't understand and fall back safely; **currently 2**), `active`, `written_at` (ISO 8601 with an explicit UTC offset — for diagnosis, not freshness; see the reader policy below), `files` (**project-relative paths** — relative to the directory containing `.throughliner/`, forward slashes on every platform, no leading `./`, exactly one path per marker; a file outside the project falls back to its absolute path), and `producer` (a constant string naming what wrote the marker — this plugin writes `throughliner`, a format value that survives any product rename). Version 2 made `files` relative — a version-1 reader would resolve relative paths against the wrong root, which is exactly what the version field exists to prevent — renamed `updated` to `written_at` so the field is named for what it is safe to use for, and dropped `session` and `pid`, which nothing read: `pid` is unusable across machines and redundant on one, `session` restates the filename. One file per session rather than one shared file because two Claude sessions in one project is a supported shape: with a shared file, one session finishing a write would clear the flag while the other was still writing. The reader's rule is therefore trivially correct — **editing is happening if any file here is active and fresh.**
- **The signal fires per edit, not per build.** The opening hook writes `active: true` before each editing-tool call and the closing hook writes `active: false` after it, so a twenty-file build turns the signal on and off twenty times. A reader that maps the flag straight onto an indicator will flicker in every gap between edits, so it needs to hold briefly past `active: false`. No number is published for that hold, deliberately — nobody has measured real traffic yet, and publishing a guess would launder it into the interface. The trade-off that decides the length: a longer hold bridges longer thinking pauses; it also locks the user out for that long after every genuine finish.
- **Recommended reader policy, published as guidance rather than enforced** — treat `active: true` as editing; judge freshness by **the marker file's own local modification time**, treating a marker untouched for about 30 seconds as a dead session; treat a missing directory or an unreadable file as "not editing", never as an error. `written_at` is for diagnosis, never freshness — and the reason mtime wins is about failure direction, not clock arithmetic: an mtime that reads wrongly old fails open (nothing held, nobody locked out) and wrongly new fails mild and self-clearing, while a `written_at` from a fast or foreign clock fails closed — a dead session looks permanently current and the user is locked out of their own document indefinitely, precisely the failure the heartbeat design exists to prevent. That reasoning holds whatever any sync client does to timestamps, on any platform. Two more comparisons made explicit so no consumer guesses at them: **path comparison is case-insensitive on Windows** (the marker's path and the reader's open-document path can differ in case and be the same file — and matching them is the one comparison the signal exists for), and relative paths carry **no leading `./`**, so readers are not string-trimming. The hook reports facts and the reader decides policy, deliberately: the reader knows what its user is doing and the hook does not.
- **It fails open**, and must: most projects never have this plugin installed, so a reader that blocked on the directory's absence would be broken everywhere else. Writing the marker can never block or fail a tool call either — a companion-app convenience must not be able to stop the user's actual work.
- **What it cannot say** — that Claude has *finished* rather than paused to think. Nothing available can know that, and pretending otherwise would be the same false promise the timing guess was rejected for. What changes is that the reader is no longer guessing: it knows a write is in flight and exactly how long things have been quiet.
- **Two known limits** — writes made through a shell command aren't covered (the hook only sees the edit tools, and a shell command's target file isn't reliably knowable), and the signal only exists where the plugin is installed and the project adopted. Everywhere else the directory simply never appears, which the fail-open rule already handles.

Marker files left by crashed sessions are swept at the next session start, after an hour — housekeeping only, since the staleness rule is what makes the signal safe. The folder is transient session state, so /setup gitignores it and git never commits it. Gitignore is all that claim covers: it keeps the folder out of the repository and does nothing about file sync — a project inside a Drive/OneDrive/Dropbox folder replicates these markers as they are written, which is why version 2 stopped writing absolute paths (the identifying payload is gone rather than contained).

One behaviour doc steers everything the hooks can't enforce:
- `plugin-behaviour.md` — loaded at every session start in adopted projects. Carries the cross-skill rules (communication, capture routing, dependency ownership, file safety) and five response-shape tags ([SILENT], [BRIEF], [DISCUSS], [PROMPT], [SEQUENCE]) that procedure docs place on individual steps to control verbosity and interaction. Rule and tag definitions are compliance-hardened: each carries a why-clause, quantified constraints, and an explicit scope statement so it holds against the helpfulness pull of current models.

One output style sets the communication default at system-prompt priority:
- A concise output style — shipped in the plugin and applied automatically when SI is enabled. It lifts the plugin's communication structure (lead with the decision, one item at a time, gate detail) to system-prompt priority, the level that holds when lower-priority instructions are skipped. It steers structure and plain English, not terseness — the goal is to not overwhelm the non-coder who reads and approves everything, never to cap length.

**Working mode.** The method carries a per-project **working mode** — a `Working mode:` field in CLAUDE.md, set once at /setup — that governs how doc-bound text (an existing queue item, a just-written capture or log entry, a readable edit) is surfaced to the user. In **local** mode, with an editor recorded, that text is surfaced as a one-line pointer or link to where it lives, saving the tokens of re-pasting it; in **remote** mode — the user driving Claude from a phone, where opening an edited file is impractical — the text is pasted inline instead. The field is a persistent default, so there is no per-session ask; the user overrides it for a single session with a word. The render decision keys on doc-residency first: text not yet written (an approval-time draft) is always inline, since there is nothing to point at.

**No completion asks on `[user]` work.** A `[user]` step is walked through and nothing more: no session — building, planning or closing — ever asks whether one is already done, leading, trailing or in passing. Completion is *inferred* from what a session can see: a step walked to its end this session is done, a step whose prerequisite visibly hasn't cleared isn't, and the user mentioning one is the third way. Where a step leaves an observable result — a URL responding, a branch gone, a file present — the method checks the world rather than accepting the report, because a step was once logged complete when the work had in fact been blocked. The gap this leaves is deliberate and documented: a step completed privately, with nothing observable to show for it, sits in the queue until the user mentions it. The `Completion mode:` setting that once toggled a planning-time sweep is retired; a stale field in an existing project is ignored silently.

**Readiness line.** /plan maintains a line in the queue — rendered `--- Cleared to run above this line ---` — that marks which work is vetted and safe to build (above it) from work that still needs planning (below it). It is positioned at the close of a /plan session — the single close (run by /done) that always fires however the session ends, so the positioning is never silently skipped — and Claude narrates where it sits whenever the line moves, confirming silently when its placement is unchanged, so the user never has to work out by hand how much of the queue is safe to run next without being told the same boundary twice. /next inherits it as its run bound when it works several items in a row — a clean finish at the line rather than running into unvetted work.

**Lifting shelved work.** Work that /plan shelves below the readiness line is waiting on something outside the queue — a dependency still being verified, a step only the user can take, a restart. Each such item records, in plain prose, the specific thing that would make it ready ("once X is pushed", "after a restart"). At the start of every /plan, Claude revisits the shelved items and re-checks those conditions: anything it can confirm itself (a dependency now built and verified, a file now present) it proposes lifting above the line; anything only the user can confirm it gathers into a single question asked once, never one nag per item. This means shelved work gets lifted when its wait actually clears, instead of resting on the user to remember it.

Before any such question is asked, the condition runs through a **downstream-action test**: is the awaited event downstream of an action the user has to take first? "Once the collaborator replies" reads as an external event, but if the message was never sent, the question can never be answered — user work existing only as a recurring prompt. Where the test finds one, the action is filed as its own `[user]` step and the condition waits on that instead. The same test runs at the moment a condition is written, which is the cheapest place to catch it. Relatedly, before any work is tagged `[user]` at all, the method names the tool that would do it and confirms that tool is absent or unavailable — a check rather than a judgment, because work that merely *sounds* manual has been handed to the user when a command-line tool could do it in seconds.

**Seeding the queue from SPEC.** A rich SPEC — especially one a deep /setup interview produced — describes buildable features that may have no path into the queue, so the whole feature set can "die in SPEC" with nothing to build it. /plan can seed the backlog from SPEC to close that gap: it offers this automatically only in the narrow thin-queue/rich-SPEC state (Processed empty or near-empty while SPEC describes real unbuilt features), and the user can invoke it manually any time. The user chooses the granularity — a few coarse milestones or granular per-feature items — and the derived items land in Unprocessed as ordinary captures for later processing, never straight into Processed. Seeding lives in /plan, not /setup: /setup stays scaffolding and interview, and never spawns work on its own.

**Processing flow.** When /plan works through the unprocessed queue, it runs two quick passes before the one-at-a-time discussion: a triage that skims for items obviously not worth doing and offers them as one batch to drop (the user contests by number; the pass can only drop, never advance work), and a reorder that puts the biggest unblockers first when the order needs it and recommends a floor for how many to process this session. During the one-at-a-time pass, each item's checkpoint lets the user skip an item to the bottom of the queue for a later session, and a capture the user raises mid-session comes with an offer to process it now or carry on — so the user is never made to feel their idea was parked.

**Close-out reorder.** At the close of a /plan session — the same always-run /done close that positions the readiness line — Claude walks both queue sections and reorders them when the session's changes have actually disturbed the order — leaving a still-correct order untouched: Unprocessed by unlock-potential (process first what would unblock the most other work), Processed by build-order (build first what unblocks or reshapes the framing for later work). Claude owns the reorder and narrates it — the narration is the user's catch-point to redirect. (The start-of-processing reorder above orders Unprocessed for the session about to run; this close reorder sets the durable order the next session inherits.)

**Forward-recommendation advisory.** When /done closes a session with a concrete recommendation for what to plan or build next, it files a "Last session advises…" note at the top of Unprocessed — advice, not a command. The next /plan reads it and lets it orient the session; that session's /done close then deletes it — the one close that always runs, so the clear isn't skipped when a /plan ends early — once it has oriented the session, unless the note carries a condition to persist longer. The note never moves into Processed and is never treated as real work; it's a transient handoff so the recommendation survives across sessions without depending on anyone's memory.

**Multi-item /next.** /next is the single queue-clearing runner. Invoked when the user wants ready work built, it works the cleared region of the queue top-down, building each item scope-locked; a single invocation can build several cleared items back-to-back without confirming each one. The close commits the run — one item's LOG entry verbatim when only one built, a summary commit when several did, each item still keeping its own LOG entry. It finishes cleanly at the readiness line. Because /next runs faster than the user can follow, it is unattended in practice — the autonomous build mode the Principles name — and it works because /plan feeds it a well-vetted cleared region: a no-progress stop (halting if the same error, empty diff, or failing check repeats on one item) keeps a stuck item from thrashing unwatched, and a red flag rides its work item into the build with its cleared state recorded in the LOG.

**Keeping projects current.** The plugin keeps improving while projects sit set up, so a project can fall behind what the current method scaffolds. At the start of a working session, before /plan or /next, `session_start` catches this two ways: it flags whole docs or folders the project is missing (offering /setup to add them), and it tops up an existing doc that's missing a newer *setting* the method has since added. The top-up is add-only — it never rewrites or clobbers anything the user has written; where a setting needs an answer (like which editor they work in), Claude opens with a one-line question and writes the answer, and settings needing no answer are added silently with a note. The missing-setting check is a list, so new settings join it over time. The riskier case — reconciling content whose template wording changed — is deliberately out of scope for now.

**Reporting a problem — three destinations, one question.** A user's problem is with one of three things, and each has its own home. Their **app** is ordinary work and stays as a capture in their QUEUE. The **method** — a skill misbehaving, a confusing step, a rule with a bad outcome — has nowhere useful to go in their own project, so it routes out to the plugin's author at flintcraft.tech/report. **Claude Code itself** — the app the method runs inside, its viewer, its links, its hooks machinery — belongs to Anthropic, and routes to a GitHub issue on `anthropics/claude-code`. Claude decides by asking which thing is misbehaving, and asks the user rather than guessing when it genuinely can't tell.

Both outward routes are scrubbed by construction — what happened, which step, the version; never the user's app details or secrets — and neither sends anything the user hasn't seen and approved. They differ only in mechanics, deliberately: a method report is a web form Claude can't submit, so Claude drafts it and the user pastes it; a Claude Code report can be filed with `gh`, so Claude posts it on an explicit yes rather than sending a non-coder to a GitHub form, falling back to a draft-and-paste when `gh` isn't available. The Claude Code route also searches existing issues first — which shapes the report rather than merely avoiding duplicates, since knowing the adjacent issues is what lets a report distinguish itself. Either the user or Claude can raise a report; when Claude notices something misbehaving it offers once, without nagging.

## Principles

- Never restrict ideation, just direct it. The user must be able to ideate at any point in the build cycle.
- Hooks enforce what must never happen; hardened rules and tags steer what should usually happen. Mechanical enforcement is cheap and unskippable; behavioural steering is written to survive priority conflicts on the models users actually run.
- Execution sessions trend toward pure execution. Ideas and discoveries can be captured anywhere, but deciding their fate is planning work and happens in planning sessions. This end state is realized as multi-item /next — an unattended-in-practice build mode that works the cleared queue, stopping only for what genuinely needs the user.
- Surface risk in plain language; never bury it. Claude screens for data-exposure and breach risks and flags them where the user can't miss them. It doesn't silently ship past a security concern, and it doesn't let a risk be accepted without a recorded, informed choice.
- Readable output is a control requirement, not a style preference. The user keeps Claude aligned by reading and approving what it does, so output too long to get through breaks that control — an error the user can't read past is one they can't catch. "Be thorough" means surfacing every important thing the user must see and act on, never emitting every word: lead with the decision, then stop; gate detail behind an explicit request. This is anti-overwhelm, not terseness — the levers are sequencing and leading with the decision, never a word-count cap, and plain English for the non-coder is the standard the concision serves, not a cost it trades away.
