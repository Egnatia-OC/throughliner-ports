Walkthrough — Taskflow Day 1

A worked example showing how a real project goes from empty folder to first build and beyond.

Starting from scratch

Taskflow begins as an empty folder. Running /setup walks through four prompts:

1. Project context

What the app does and what makes it distinct. For Taskflow: a task-planning app that treats today as the only screen that matters.

2. UX principles

High-level rules for how the app should feel. Taskflow's principles: Reduce planning pressure. Drag is the primary verb. No date pickers, no shame.

3. Core functionalities

Three to five features, each with a "user needs this because…" line. These seed UX.md.

4. First batch sketch

The smallest end-to-end buildable thing. For Taskflow: the one-day-at-a-time view.

Claude writes answers directly to UX.md (docs are open during setup). You seed the first build batch, and you're ready.

Risk accepted in action

Taskflow's One-day-at-a-time view entry in UX.md ends with a Risk accepted line explaining why there's deliberately no week view. This isn't a TODO or a compromise — it's a recorded decision that protects against re-litigation six months later.

If someone asks "why no week view?" the answer is on the page, with the reasoning that was current when the decision was made.

First build, first test note

The build ships. You test the result and write down what you notice:

"Couldn't find a due date — intentional? Screen hard to read at night — dark mode?"

Paste those notes into a new session. The planning route picks them up.

How a test note becomes a feature

The dark-mode item follows the full pipeline:

  1. Idea raised. Test note mentions "screen hard to read at night."
  2. Planning batch. The planning procedure creates a batch with design questions: justify a parallel theme? OS setting or manual toggle? Which UX entries need contrast review?
  3. Questions answered. You decide: yes, OS-based, two entries need a contrast pass.
  4. UX.md updated. You add a new Dark mode entry with rationale.
  5. Build batch. Created with Serves UX.md: Dark mode. Ready for /before-build.

If step 3 answers "no" — the idea doesn't justify the work — steps 4 and 5 don't happen. That's equally valid. The pipeline filters, not just queues.

UX principle conflicts get surfaced in chat immediately — they aren't quietly routed into a batch.

The method absorbs mid-stream ideation

Ideas arrive at unpredictable moments — during tests, conversations, feedback. The planning phase catches and routes them. But catching alone isn't enough; scoping matters.

A batch that says only "add dark mode" gives no testing anchor, no record of purpose, no surface for pushback. So every batch gets the same structure: Goal (why), Outputs (what changes), and Success criteria (how you'll know it worked). Written during planning — you speak the substance, Claude records it.
