The no-code method

A Claude Code plugin that keeps your app on track.

What is this?

A structured workflow for non-coders building apps with Claude Code. You describe what your app should do; Claude writes the code. The plugin makes sure Claude follows a rigid process: planning before building, testing before moving on, and keeping written records of every decision.

Without it, Claude drifts. It forgets decisions, builds things nobody asked for, and skips steps. The plugin prevents that with enforced guardrails — locked documents Claude can't edit, file-boundary enforcement it can't bypass, and phase gates it can't skip.

Who is it for?

People who already know what their app should be, but don't write code. You bring the product vision; the method structures how Claude turns it into working software.

Prior Claude Code experience helps but isn't required. Extensive plan-mode use before your first build is recommended.

What does it cost?

Two sessions minimum per feature. One to plan, one to build. Every shipped feature traces to a written rationale. Nothing gets built that nobody decided to build.

That's the trade-off: you move slower, but you never lose track of why something was built, whether it was tested, or what was decided along the way.

Quick start

  1. Install the plugin and run /setup in your project folder.
  2. Describe your app. The plugin walks you through four prompts.
  3. Run /before-build to lock your first batch, then /build to execute it.
  4. Test. Bring results to your next planning session.

The cycle

Every feature goes through two phases: planning and building. They alternate. A fresh Claude Code session (or /clear) separates them.

Planning sessions

Planning sessions decide what gets built. You open a session, the planning procedure does five things:

  1. Closes the previous test session — goes through each test row one by one, confirms pass or fail.
  2. Runs five drift checks — compares your docs against your codebase to catch anything out of sync.
  3. Scans open questions — picks up unresolved design questions from previous sessions.
  4. Sorts new ideas — classifies them as Suggestions (in scope) or Discoveries (out of scope, queued for later).
  5. Edits BACKLOG directly — records everything in the right place.

Source-of-truth doc edits (like UX.md changes) happen by hand — you apply proposed edits, remove resolved batches, reorganise priorities.

Build sessions

Build sessions ship engineering work. Three slash commands drive the process:

/before-build

Locks the batch. Validates the Serves UX.md: line, populates inputs and file lists, proposes splits if the batch is too large.

/build

Runs the build against the file list. A PreToolUse hook enforces file boundaries — Claude can only edit files listed in the batch.

After-build (automatic)

When the build finishes, the after-build procedure updates MANIFEST, checks docs for stale references, runs automatable tests, generates a recap, writes the build-log entry, sweeps for unrouted ideas, runs any project-specific close steps, verifies everything via a pre-commit checkpoint, and prompts you to commit and tag.

Between sessions

You /clear, refresh, run any user-verified tests, and bring outcomes to the next planning session. The cycle repeats.

Sessions are stateless; the docs are the memory. BACKLOG, MANIFEST, TEST-LOG, and build-log tell each session where things stand. Nothing carries over from in-memory state.

Your docs

After /setup, your project has six files and two folders. Together they act as guardrails — they hold your design decisions, queued work, and test outcomes so Claude knows where things stand at the start of every session.

The spine docs

CLAUDE.md

Entry point. Tells Claude where your docs live and how to behave. Read every session.

UX.md

Your app from the user's perspective. Every entry is something experienceable, with a rationale. You maintain this — Claude can only read it.

BACKLOG/

Deferred and queued work. INDEX.md lists everything; each batch gets its own file with scope and build details.

MANIFEST.md

Flat glossary of every named thing in your codebase. Name, file path, description. Claude maintains it during builds.

TEST-LOG.md

One row per test, 10 columns. Claude adds rows after builds; you confirm outcomes before the next build can start.

build-log/

Per-build narrative files: what shipped, decisions made, surprises, carried-forward items, and performance notes.

Also created by /setup

planning/drafts/

Holding area for ideas not yet ready for a specific doc. Zero maintenance burden.

research/

Findings from Claude's research. Persists across sessions for future reference.

Additional source-of-truth docs

Projects can declare extra locked docs — things like SYSTEM-PROMPT.md, COPY.md, or PATTERNS.md. Same locking rules as UX.md: Claude reads but can't edit.

Getting started

Install the plugin

The plugin installs via Claude Code's marketplace system. Once installed, it persists across sessions.

  1. Clone the repository: 
    git clone https://github.com/FlintCraftTech/sovereign-implementer.git
  2. In Claude Code, run: 
    /plugin marketplace add <path-to-clone>
  3. Then: 
    /plugin install no-code-method@sovereign-implementer
  4. Open a session in your project folder. Hooks fire at session start.

For one-off use without installing: claude --plugin-dir <path-to-clone>/plugin

Desktop app users

/plugin is CLI-only — it doesn't work in the desktop app. Run install commands in a CLI terminal first; the plugin then loads automatically in desktop sessions.

First install

  1. Open a terminal (PowerShell or Terminal).
  2. Run claude to start a CLI session.
  3. Run /plugin marketplace add <path-to-clone>
  4. Run /plugin install no-code-method@sovereign-implementer
  5. Close the CLI session. Open the desktop app. Verify under Customise (gear icon) → Plugins.

Checking your version

Desktop app → Customise → Plugins → gear icon on the plugin entry.

Updating

After pulling new changes, if the desktop app shows the old version:

  1. CLI: claude → /plugin uninstall no-code-method@sovereign-implementer
  2. /plugin marketplace add <path-to-clone> → /plugin install no-code-method@sovereign-implementer
  3. Close the CLI. Close the desktop app completely (on Windows: Task Manager to end the process). Reopen.
  4. Verify the version.

Your first session

Open Claude Code in your project folder and run /setup. The plugin detects your situation and runs the matching dialogue:

SituationWhat happens
Empty folderScaffolds all spine docs, walks you through four prompts.
Existing code, no docsScaffolds docs alongside your code.
Foreign docs presentOffers to migrate, overwrite, or leave them.
Already managedRefreshes footers and runs any migrations.

The four prompts (empty folder)

  1. Project context. What the app does and what makes it distinct.
  2. UX principles. High-level rules for how the app should feel.
  3. Core functionalities. Three to five features with rationale lines.
  4. First batch sketch. The smallest end-to-end buildable thing.

Answers land as [PROPOSED EDIT PENDING] blocks in the spine docs. You apply them to UX.md by hand, then seed the first build batch.

Managing the plugin

Once installed, the plugin fires in every folder. Here's how to control it.

Disable in a specific project

  • Desktop app: Customise → Plugins → gear icon → toggle off.
  • CLI: /plugin disable no-code-method@sovereign-implementer, then /reload-plugins.

Re-enable

  • Desktop app: Customise → Plugins → toggle on.
  • CLI: /plugin enable no-code-method@sovereign-implementer, then /reload-plugins.

Uninstall

CLI only (the UI uninstall has been reported as unreliable):

/plugin uninstall no-code-method@sovereign-implementer

Known issue: Disabled plugins may still run hooks. If you need a plugin fully off, uninstall rather than disabling.

Walkthrough — Taskflow Day 1

A worked example showing how a real project goes from empty folder to first build and beyond.

Starting from scratch

Taskflow begins as an empty folder. Running /setup walks through four prompts:

1. Project context

What the app does and what makes it distinct. For Taskflow: a task-planning app that treats today as the only screen that matters.

2. UX principles

High-level rules for how the app should feel. Taskflow's principles: Reduce planning pressure. Drag is the primary verb. No date pickers, no shame.

3. Core functionalities

Three to five features, each with a rationale line. These seed UX.md.

4. First batch sketch

The smallest end-to-end buildable thing. For Taskflow: the one-day-at-a-time view.

Answers land as [PROPOSED EDIT PENDING] blocks. You apply them to UX.md, seed the first build batch, and you're ready.

Risk accepted in action

Taskflow's One-day-at-a-time view entry in UX.md ends with a Risk accepted line explaining why there's deliberately no week view. This isn't a TODO or a compromise — it's a recorded decision that protects against re-litigation six months later.

If someone asks "why no week view?" the answer is on the page, with the reasoning that was current when the decision was made.

First build, first test note

The build ships. You test the result and write down what you notice:

"Couldn't find a due date — intentional? Screen hard to read at night — dark mode?"

Paste those notes into a new session. The planning route picks them up.

How a test note becomes a feature

The dark-mode item follows the full pipeline:

  1. Idea raised. Test note mentions "screen hard to read at night."
  2. Planning batch. The planning procedure creates a batch with design questions: justify a parallel theme? OS setting or manual toggle? Which UX entries need contrast review?
  3. Questions answered. You decide: yes, OS-based, two entries need a contrast pass.
  4. UX.md updated. You add a new Dark mode entry with rationale.
  5. Build batch. Created with Serves UX.md: Dark mode. Ready for /before-build.

If step 3 answers "no" — the idea doesn't justify the work — steps 4 and 5 don't happen. That's equally valid. The pipeline filters, not just queues.

UX principle conflicts get surfaced in chat immediately — they aren't quietly routed into a batch.

The method absorbs mid-stream ideation

Ideas arrive at unpredictable moments — during tests, conversations, feedback. The planning phase catches and routes them. But catching alone isn't enough; scoping matters.

A batch that says only "add dark mode" gives no testing anchor, no record of purpose, no surface for pushback. So every batch gets the same structure: Goal (why), Outputs (what changes), and Success criteria (how you'll know it worked). Written during planning — you speak the substance, Claude records it.

The disciplines

Four structural habits keep the method working. They're not suggestions — each one is enforced by hooks, procedure docs, or doc structure.

The four disciplines

1. "The user needs this because…"

Every UX.md entry ends with a rationale line. Forces you to articulate why before anything gets built. Protects against drift — six months later, the reason is still on the page.

2. The flag taxonomy

Every concern Claude raises has exactly one home:

  • Red flags → BACKLOG Red flags section. Persistent, visible.
  • Suggestions → chat. In-scope ideas for the current session.
  • Discoveries → planning batches. Out-of-scope ideas queued for later.

No concerns get lost. None get mixed up.

3. The feature pipeline

Rigid by design. Nothing skips a step:

Planning batch
→
Questions answered
→
UX.md entry
→
Build batch

4. The test-confirmation gate

You can't start a new build batch while previous test rows are unconfirmed. The planning procedure reads back each row one by one; bulk confirmations aren't accepted. A PreToolUse hook enforces this structurally.

Drift checks

Five automated checks run at the start of every planning session. Each catches a different kind of desynchronisation:

CheckWhat it catches
Direct-edit detectionUses git diff to find files changed outside a build. Asks per-file: "Was this you?"
UX.md ↔ what's builtFeature-to-feature comparison. Surfaces features described but not built, or built but not described.
MANIFEST ↔ codebaseName-to-name comparison. Catches renamed or deleted components still listed.
MANIFEST ↔ UX.mdLoose purpose check. Is each component serving something the user experiences? Plumbing is exempt.
TEST-LOG ↔ code-touchPer-row: has the tested component changed since the test passed? Flags stale results.

Anatomy of a batch

Every batch has two regions, written at different times during different phases.

Status tracking

An optional Status: line at the top of the batch tracks its lifecycle: queued (default), active (locked for build), parked (paused), or shipped (complete). Claude writes transitions automatically.

Scope context written during planning

  • Goal. Why this batch exists.
  • Outputs. What changes the user will experience.
  • Success criteria. Observable conditions that mean it worked.
  • Decisions. Unresolved scope questions (omitted once resolved).
  • Dependencies. What's needed from outside (omitted if none).
  • Red flags. Security or risk concerns (only when auto-detected).

Build operations written during before-build

  • Changes: Labeled [Requested] or [Suggested].
  • Inputs: Non-standard resources needed.
  • Files: Checkbox task list of files to create or edit.
  • Tests: Type and verifier per test.
  • Serves UX.md: Which UX entry the batch implements.

The Changes: delimiter separates the two regions. Everything above is strategic; everything below is tactical.

Why the rules

Every rule exists because something went wrong without it. Here's each one with the reasoning.

Push back rather than agree

Drift checks and red-flag surfacing assume Claude will push back when something looks wrong. If Claude defaults to agreement, those safety nets are disabled in practice even though the code still runs.

State regressions plainly

The after-build recap is your record of what happened. If Claude silently fixes a regression instead of reporting it, you lose visibility into what broke and whether the fix was actually right.

Lock batch scope once agreed

Scope creep during a build makes testing unpredictable, breaks the planning-gate filter, and undermines session predictability. If the scope needs to change, that's a new planning discussion — not a mid-build addition.

Five drift checks at different levels

Each check catches a different kind of desynchronisation: file-temporal, feature-to-feature, name-to-name, purpose-level, per-row code-touch. Bundling them into one check produces noise; separate passes catch what each is designed for.

Lock source-of-truth docs

Build sessions are the wrong environment for design changes. UX.md and other source-of-truth docs are read-only during builds so design decisions get proper deliberation in planning sessions.

No placeholders in source-of-truth docs

These docs are read by Claude at session start. Placeholders like [TODO] or [TBD] confuse the reader — is this an instruction or an unfinished thought? Every entry should be the actual instruction.

Project-specific UX principles

Generic principles ("be intuitive," "be fast") are too abstract to guard real decisions. Project-specific principles like "no date pickers, no shame" give Claude concrete criteria to push back against scope that violates them.

MANIFEST starts flat

Most projects never need sections in their MANIFEST. Pre-sectioning forces premature architecture decisions. Start flat; add structure only when navigability demands it.

BACKLOG is a folder, not four files

INDEX.md gives you one place to see what's outstanding. Per-batch files handle the content volume. The split is about content volume, not category.

"Risk accepted" as a labelled line

When you deliberately accept a trade-off (no week view, no offline mode), recording it as a labelled line keeps the reasoning on the page. Six months later, anyone asking "why not?" finds the answer without archaeology.

Per-row test read-back

Bulk confirmations ("all tests passed") silently flip rows the user didn't actually verify. Row-by-row read-back means every confirmation is deliberate.

Test types

Four test types, each with a default verifier. The verifier (Claude or user) is set per row, not per type.

TypeWhat it meansTypical verifier
Look and clickUI interaction — tap a button, check a screen.Structural checks → Claude. Judgement calls → user.
Run and readCommand execution — run something, read the output.Fully automatable.
Trigger and observeEvent-driven — cause an event, observe the response.Fully automatable.
Generate and inspectArtefact production — generate a file, inspect the result.Fully automatable.

All rows must reach Confirmed Explicitly: Yes before the next build can start.

Permission modes

Claude Code has its own permission system (Ask/Accept/Plan/Auto/Bypass). The plugin's PreToolUse hooks are a separate layer — they fire in every mode, including Bypass.

PhaseRecommended modeWhy
Pre-method ideationPlan modeNo edits needed yet.
PlanningAccept editsPlanning procedure edits BACKLOG.
Before-buildAccept editsWrites file lists into BACKLOG.
BuildAutoSource-file edits. Hooks enforce boundaries.
After-buildAutoWrites MANIFEST, TEST-LOG, build-log.

Permission prompts: Claude Code may prompt for permission on tool calls depending on your mode setting. Auto mode produces the fewest prompts.

The safety net

Three layers protect against working in the wrong state:

  1. SessionStart checks whether the folder is adopted (has method docs) or unadopted. Unadopted folders with substantial work get an advisory pointing at /setup.
  2. PreToolUse blocks Edit/Write/MultiEdit until /setup has run.
  3. /setup detects the case (empty, existing code, foreign docs, already managed) and runs the right dialogue. Nothing destructive without confirmation; every destructive option backs up first.

What's inside the plugin

Hooks (deterministic enforcement)

Python scripts that fire on Claude Code events. They enforce rules mechanically — no judgement involved.

  • SessionStart — detects folder state, injects behavioural rules.
  • PreToolUse — enforces edit boundaries: project boundary, locked docs, batch file list, test gate, adoption gate, read-before-edit, Serves-line check, destructive git guard.
  • PostToolUse — validates BACKLOG format after edits.
  • Stop — routes between batches or to after-build.
  • PreCompact — blocks mid-build compaction (recommends handoff instead).
  • UserPromptSubmit — classifies first prompt, injects routing hint.

Procedure docs

Five procedure docs, each specifying what Claude loads and does for that phase:

  • Planning — drift checks, idea routing, BACKLOG edits.
  • Before-build — batch locking, file list population.
  • Build — runs the build against the file list.
  • After-build — MANIFEST update, tests, recap, build-log.
  • Setup — four-case folder detection and scaffolding.

Slash commands

/setup, /before-build, /build — user-facing entry points that direct Claude to matching procedure docs.

Bundled docs

DOC-STRUCTURE.md and VOCABULARY.md — read by procedure docs at runtime for structural and terminology rules.

Where the method sits

Part of the spec-driven development family. Closest relative: Cline's Memory Bank (same shape — markdown as project memory, read at session start; different file structure, different audience). In the broader spec-driven literature, this maps onto the spec-anchored rigour level.

What's editable

Three layers of rigidity:

  • Method contract — edit at peril. Rules the machinery depends on. Each is annotated with what breaks without it.
  • Recommended habits — edit freely. /clear cadence, test-prep workflow, commit timing.
  • The build sequence — fixed. The four-phase cycle is the spine. Don't change the order.

Caveats

  • Iteratively developed. Not yet used to ship a complete app from start to finish.
  • Claude follows CLAUDE.md-style instructions reliably about 70% of the time. The method designs around this with read-only docs and reviewable decisions, but the headwind is real.
  • Claude Code's plan panel doesn't show the method's build sequence — it's internal to Claude Code with no plugin write surface. The actual queue is in BACKLOG.

When you need more

The full spec lives in universal-behaviour.md (behavioural rules) and DOC-STRUCTURE.md (structural rules) inside the plugin. Reach for them when a concept needs detail, a rule's edge case matters, or the method itself is being extended.
